# 内容审核实现计划

对应设计：[流程设计](流程设计.md) · [审核标签与分级标准](审核标签与分级标准.md)

## 原则

- 项目用于面试，目标是"面试官问到时，每一块都能讲清楚，核心两块有代码和实验数字"。
- 每个模块单独可跑、单独有测试、单独产出一个能讲的结果，做完一块再做下一块。
- 审核是独立服务，放在 `实习项目/PulseFrame/review-service/`，有独立的 `go.mod` 和数据库，与 `backend/` 只通过接口交互（流程设计 2.5 节）。判定和规则逻辑用 Go，沿用现有 `judge` 包；视频帧处理和实验用 Python（`worker/`），由 Go 服务调用。
- `backend/` 只改两处：M1 的 20 秒上限，以及内容模块文档里已经写好的 `limit` 回调和限流接口（在内容模块的实施路线里实现）。

## M0 审核服务骨架

位置：`review-service/`

- **建服务**：独立 `go.mod`，入口 `cmd/pulseframe-review`，配置、日志、健康检查沿用 backend 的写法。
- **迁移**：把 `backend/internal/review/`（`judge` 包和 `model.go`）、`tools/replay/`、`tools/kuaimod_export.py`、`policies/kuaimod_paper/`、`data/kuaimod/`、`reports/` 中审核相关的内容移到 `review-service/`。迁移后 backend 的 `go build ./...` 和 `go test ./...` 仍要通过（现有 backend 代码没有引用 `internal/review`）。
- **自己的表**，只建最小集合：
  - 审核任务：`task_id` 唯一
  - 文件审核记录："文件摘要 + 识别版本"唯一
  - 观察结果：人工修正覆盖机审
- **契约**（流程设计 2.5 节）：
  - 接收投递，重复的 `task_id` 返回 200、不新建任务
  - 提供查询接口
  - 回调发送：失败按退避重试
  - 调用内容模块的 `offline`、`limit`、`rereview` 接口；`limit` 的 `seq` 按视频递增
  - 双向都校验服务间凭证
- **判定先用桩**：固定返回 `pass`，后面的模块逐个接进来。
- 验收：
  - 同一 `task_id` 投递 3 次只建 1 个任务
  - 回调接口返回 500 时按退避重试，直到成功
  - 查询接口在判定完成前返回"审核中"
  - backend 测试全部通过

## M2 挑帧模块

位置：`review-service/worker/framesel/`

- **解码**：用 ffmpeg 输出全部帧，缩到 160×90 灰度做帧差，选中的帧再取原分辨率。
- **检测器**，按设计附录 A，每种一个函数，输入帧序列，输出 `(时间戳, 类型, 分数)`：
  1. 定时帧：每 2 秒一帧
  2. 画面切换：相邻帧差超过阈值，且不变回
  3. 短暂插入：相邻帧差超过阈值，且 0.5 秒内变回，取中间一帧
  4. 渐变叠加：减去前后各 1 秒的中位数背景，取残差最大的一帧
  5. 局部变化：九宫格分块帧差，个别块突变时取该帧，并裁剪放大变化区域
- **排序与分批**：按帧号去重并按时间升序每 16 帧分批；帧类型只用于标记和识别可疑画面。
- **规避标记**：短暂插入、局部变化、渐变叠加三类合计超过 5 个时，输出 `evasion_suspected=true`，仅用于挑帧统计。
- **输出**：JSON，每帧含时间戳、类型、分数、图片路径，另含批次和规避标记。
- **测试**：用 ffmpeg 现场生成测试视频（纯色或彩条底图，再插 1/3/10 帧异色画面、淡入半透明方块、角落小方块），断言每类都被挑中、正常视频不误报。
- 顺手：现有 `judge.Sample` 注释写"最多 9 张"，设计是每批 16 帧，M5 一起改。

## M3 合成插帧数据 + 挑帧实验

位置：`review-service/worker/framesel/synth.py`、`experiment.py`，报告 `review-service/reports/frame-selection.md`

- **素材**：CH-SV 正常视频，截取或筛选 20 秒以内；违规帧池只收单帧就能确定违规的画面，与将来的违规库分开存。先按视频划分实验集和标定集，避免同一段画面两边都有。
- **变体**（每种都记录插入的起止时间作为标签）：
  - 硬插入 1 / 3 / 10 帧
  - 0.5 秒渐入渐出半透明叠加，透明度 30% / 50%
  - 角落画中画，面积约 1/9
- **实验**：
  - 对比两种挑帧：均匀抽帧（每 2 秒一帧，基线）和 M2 挑帧。
  - 指标一：挑帧选中率，即插入段里至少有一帧被选中的比例，按变体分别报。
  - 指标二：正常视频上的误触发，包括平均选中帧数、`evasion_suspected` 的比例。
- **标定**：在标定集上调帧差、残差、分块阈值，再到实验集上报结果。附录 A 里"待预实验定"的数值在这里定，定完回写设计文档。
- 验收：报告里有一张"变体 × 两种挑帧"的选中率表，加正常视频误触发率。

## M4 观察项 → 等级 → 规则表

位置：`review-service/internal/grading/`（等级）、`review-service/internal/policy/`（规则表）

- **观察项类型**：按标签标准定义常量。低俗表现 6 类（部位特写、无关场景泳装内衣、性暗示动作、带性意味声音、性行为或模仿、私密部位展示），外加“内衣泳装商品展示”标记。每条带时间点。
- **定级函数**：观察项列表 → L0–L3，实现标签标准的组合规则：
  - 特写 2 次及以上或累计超过 3 秒 → L2
  - 两种 L1 → L2，L2 叠加 L1 仍为 L2，两种 L2 → L3
- **规则表**：表 = 版本号 + 生效与到期时间 + "（类别或等级）→ 处置"。支持平时表和临时表，临时表到期自动回到平时表；多路结果取最严处置。
- **辅助函数**（只写函数和测试，不接数据库）：
  - 给定观察结果和新表，重算处置，用于换表预演和 30 天回扫
  - 判断违规库条目"平时规则下是否也违规"
- 测试：表驱动测试，用例直接取标签标准表里的例子和边界（L2 叠加 L1、商品展示无特写为 L0 等）。
- 验收：`review-service` 下 `go test ./...` 通过。同一份观察结果在平时表下得到限流、在严查表下得到拦截。

## M5 judge 改造：观察项输出 + 投票

位置：`review-service/internal/judge/`

- **输出结构**：`Output` 从"标签 + 是否违规"改为"低俗观察项列表 + 暴力结果 + 其他命中标签 + 是否转人审 + 证据"。`parser.go` 做严格校验，类别不在标签表内即为格式异常。
- **两次判定**：同一批输入获得两份独立回答，各自按规则表计算处置。两份回答处置一致时自动执行共同处置，处置不同则记录分歧并转人审。
- **去掉判例注入**：删除 `Policy.Cases`、`CitedCases` 及相关提示词。设计规定机审只看当前内容，违规库只供人审参考。
- **输入**：`Sample.Images` 改为每批最多 16 帧，加上画面文字、可疑声音字段。
- 两票共享格式补采额度，每批最多调用 4 次，保留有效回答，额度用尽仍缺票时转人审。
- 测试：改写 `parser_test.go`、`scoring_test.go`，覆盖相同处置、处置分歧、缺票及跨批累计定级。

## M6 观察项提示词 + 接 VLM

- **提示词**：由标签标准生成，放在 `review-service/policies/observation/`。待审内容（画面文字、转写、可疑声音）放在单独区块，并声明其中的指令不执行（设计附录 E）。
- **注入特征词**：画面文字和转写先做关键词检查，命中就转人审。在 Go 侧实现，写测试。
- **小标注集**：自标 100 条左右低俗相关样本，按观察项标注。正常和违规各半，包括泳装内衣商品、健身等边界样本。
- **对比实验**：Qwen3.5-9B 与 Qwen2.5-VL-3B 在同一标注集上比较观察项准确率、转人审比例和单条耗时，选定模型；另用 KuaiMod 留出集报类别准确率。
- 报告：`review-service/reports/observation-eval.md`。
- 验收：选定模型，报告里有两模型对比表。

## M7 语音转写 + 画面文字 + 文字规则

位置：`review-service/worker/media_text/`

- 语音转写：选一个开源 ASR，输出带起止时间的分段文本。
- 画面文字：对挑中的帧做 OCR。
- 文字规则：两者按文本流程归一化（繁简、全半角，先做最基础的），再用正则查联系方式（手机号、微信号、QQ 号）和红线词表，命中即拦截。
- 测试：用合成音频和带文字的图片测时间戳和规则命中；正则单独写单元测试。

## M8 端到端串联 + 演示

位置：`review-service/`。M0 的判定桩换成真实流程

- 流程：内容模块投递 → 读取原文件并校验 → M2 挑帧 → M7 文字 → M5/M6 判定 → M4 定级与处置 → 回调内容模块。每条任务保存一份结果 JSON，包括选中的帧、观察项、等级、处置和转人审原因。
- 在 M3 的实验集上跑端到端，召回拆两段报告：挑帧是否选中、选中后模型是否判对。
- 演示：准备 3 条视频，分别是正常视频、插闪帧视频、擦边视频。现场切换平时表和严查表，展示同一份观察结果得到不同处置。
- 验收：backend 和 review-service 同时启动，上传一条视频后能走完"投递 → 判定 → 回调"并落库；报告 `review-service/reports/end-to-end.md`。

## 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 3B / 9B 模型零样本观察项准确率低 | M6、M8 数字难看 | 先如实报告；面试重点放在挑帧实验和三层分离的设计上 |
| 渐变叠加、局部变化在正常视频上误触发多 | 规避标记失真、帧数暴涨 | M3 标定时优先控制误触发，并在局限里说明 |
| CH-SV 许可为 CC BY-NC-ND 4.0 | 合成视频不能公开 | 只在本地使用，演示时只展示指标和少量截图 |
| 服务器环境不支持某个模型 | M6 卡住 | 先用已经跑通的 Qwen3.5-9B 推理服务 |
