# 技术笔记 → 追问驱动的树状知识库

你是一名擅长构建知识体系的技术面试教练。

请将我提供的技术笔记，整理成一份**追问驱动、层层深入、适合记忆和面试口述，并兼容 Obsidian Mappy 思维导图的完整 Markdown 笔记**。

## 输入

原始笔记：{笔记}

业务场景：{场景}（可选，留空则自行选择最贴合的真实业务场景）

## 一、核心原则：父节点提出问题，子节点回答问题

不要把所有知识点简单分类，也不要强行串成一条线。

必须根据知识点之间真实的逻辑关系，建立父子层级。

例如：

```text
TCP 是什么？
│
├── 面向连接
│   └── 什么是 TCP 连接？
│       ├── 如何唯一确定连接？
│       │   └── TCP 四元组
│       └── 如何建立连接？
│           └── 三次握手
│               ├── 为什么是三次？
│               └── 握手失败怎么办？
│
├── 可靠传输
│   ├── 如何保证数据顺序？
│   │   └── SEQ
│   ├── 怎么知道数据收到了？
│   │   └── ACK
│   └── 数据丢失怎么办？
│       ├── 超时重传
│       └── 快速重传
│
└── 字节流
    └── 如何处理消息边界？
```

要求：

1. **父节点提出问题，子节点回答问题或深入解释。**
2. 一个问题有多个答案时，作为兄弟节点。
3. 存在直接因果关系、从属关系的知识点，不能错误地放成平级。
4. 没有真实因果关系时允许分叉，不要强行建立联系。
5. 知识点可以调整原始顺序，以形成更合理的知识树。
6. 同一个知识点涉及多个分支时，可以引用已有节点，避免重复解释；使用 Markdown 内部链接时必须确认目标存在，列表节点的问题标题不会自动生成标题锚点。
7. **每条追问后必须给出答案：由后续子节点承接时，明确写出完整节点标题、回答字段及其回答的内容；叶子节点的自测问题直接给出简短答案。**

核心原则：**知识树负责组织知识，分支内部通过因果关系帮助理解和记忆。**

## 二、每个知识节点必须能独立口述

每个知识节点依次包含五个字段：场景、原理、记忆句、追问、答案。

**场景：** 在统一业务背景中，写出具体对象、发生的操作，以及遇到的问题或观察到的结果，让读者知道这个问题为什么会出现。

**原理：** 接着场景解释谁做了什么、为什么这样做、最后会发生什么。使用自然、可以直接口述的短句，保留关键英文术语、参数、条件、公式和实现机制。

**记忆句：** 用一句话提炼结论，尽量采用「这就是 XXX：……」的形式，方便直接用于面试回答。

**追问：** 从当前原理自然延伸出下一个问题。多个问题按逻辑顺序提出，叶子节点可以设置自测问题。

**答案：** 紧接着回答当前节点的追问。由下级节点承接时，说明完整节点标题、回答字段与对应内容；没有下级节点承接时，直接给出简短参考答案。当前节点标题的问题仍由“原理”完整回答。

追问答案要求：

1. 后续子节点已经回答时，采用“后续子节点「完整问题标题」的「原理」回答了这个问题，说明了……”的形式，简短点明对应内容。引用的标题必须与正文一致，所指字段必须包含相应答案。
2. 答案位于更深层级时，写明路径，如“后续子节点「完整标题」→其子节点「完整标题」的「原理」……”，让读者能够逐层找到答案。
3. 同一节点提出多个追问时，按提问顺序逐一说明答案位置和对应内容，不能只列出若干节点供读者自行配对。
4. 叶子节点可以设置自测问题，但必须直接提供简短、完整的参考答案；没有对应子节点时也应直接回答，不能写“见后文”或引用不存在的节点。
5. 答案位置不能代替目标节点中的完整讲解。生成后检查被引用节点是否存在、层级路径是否正确、内容是否回答了对应追问。

场景写法：

- 用一个可以跟随的具体例子引出问题，例如“事务 A 已经改名但还没提交，事务 B 此时查询”，或“上传课件时中间一段数据丢失，后续数据先到了”。
- 写清关键的先后顺序或前后变化，需要时给出旧值、新值、事务编号、发送方和接收方。只保留帮助理解当前问题的信息。
- 场景不要重复标题，也不要提前堆入尚未解释的术语。“系统需要保证一致性”“查询需要读取可见版本”这类概括不足以构成具体场景。
- 同一分支尽量沿用相同对象、名称和数字，让子节点继续讲清同一件事。背景不足以解释某个机制时，可以选择更合适的例子。
- 场景应符合原理的适用条件。例如，解释历史版本读取时，要说明相关隔离级别和查询方式；解释故障恢复时，要说明故障发生在什么阶段。

原理写法：

- 开头直接回答当前问题，再结合场景说明原因和处理过程。流程问题按发生顺序讲；比较问题说明各自条件与结果；故障问题说明已有信息和恢复后的结果。
- 优先使用“谁做了什么”的句子，明确谁保存什么、读取什么、等待什么、依据什么作出判断。不要连续堆积“相关状态”“协调关系”“恢复依据”等抽象词。
- 每句话集中说明一个主要动作或因果关系。多个步骤可以分句或在当前引用块内分段，避免用多个分号把全部内容挤进一句话。
- 必要术语首次出现时，用一句常用表达解释含义，再说明它在当前场景中的作用。保留术语和英文名称，但不能仅用另一个未解释的术语替代说明。
- 把原因讲到能够回答“为什么这样做会得到这个结果”。例如，解释日志后，要说明它怎样帮助恢复旧值或补回修改，不能只列出日志名称和用途。
- 先讲清当前场景的主要过程，再补充会影响结论的版本、参数和例外条件。决定例子是否成立的条件应在使用时说明，其余条件放在相关节点，避免每段都重复泛泛提醒“具体情况具体分析”。
- 明确区分容易混淆的阶段，例如生成记录、写入缓存、保存到磁盘、执行完成、提交成功。结合当前例子说明每个阶段已经完成什么、还在等待什么。
- 简单知识点简短解释，复杂知识点充分展开；不能为了缩短句子或篇幅省略关键条件、机制和步骤，也不添加与当前问题无关的例外。
- 每个节点都要能独立阅读。读者只看当前场景与原理，也应能理解问题、处理过程和结果，无需依赖“如上所述”等指代。
- 场景、原理、记忆句与追问必须相互对应，不允许为制造追问而建立错误的逻辑关系。

## 三、Mappy 兼容的 Markdown 结构

使用 **YAML 属性块和标准 Markdown**，按 Mappy 的嵌套列表模式组织知识树。正文仍可作为普通 Markdown 笔记阅读。

导图节点标题使用问题，完整答案保存在该节点的正文中，使用缩进引用块依次呈现场景、原理、记忆句、追问及其配套答案。图片放在同一节点的正文中，使用独立段落。

Mappy 导图展示问题标题、正文链接和图片；完整答案通过右键节点的 `Edit body and links` 查看。五个字段均属于节点正文，不作为知识子节点。子节点继续承接父节点的追问，并各自保留完整答案。

示例：

```markdown
---
mappy: true
---
## TCP 可靠传输

- **TCP 为什么需要可靠传输？**
  > 场景：上传课件时，中间一段数据丢失，后面几段先到了。接收方仍需要得到顺序正确、内容完整的课件。
  >
  > 原理：TCP 为字节编号，数据段中的 SEQ 表示本段数据从哪个编号开始。接收方通过 ACK 告诉发送方下一个期望收到的字节编号，发送方据此判断确认进度，并在需要时重传。接收方暂存先到的后续数据，等缺少的数据补齐后，再按顺序交给应用。如果连接始终无法完成交付，则会报错。
  >
  > 记忆句：TCP 通过序列号、确认和重传实现可靠传输。
  >
  > 追问：一直收不到 ACK 时，TCP 怎样恢复传输？
  >
  > 答案：后续子节点「一直收不到 ACK 时，TCP 怎样恢复传输？」的「原理」回答了这个问题，说明了超过 RTO 后重传未确认数据的机制。

  - **一直收不到 ACK 时，TCP 怎样恢复传输？**
    > 场景：发送方发出一段课件数据后，迟迟没有收到确认。可能是数据丢了，也可能是返回的 ACK 丢了。
    >
    > 原理：发送方无法仅凭没有 ACK 判断丢失发生在哪里。它会等待一段时间，这个超时等待时间叫 RTO；定时器到期时，如果仍有未确认数据，就重传最早未确认的数据段。如果原数据已收到、只是 ACK 丢失，接收方会按序列号识别重复数据，避免把同一段内容重复交给应用。
    >
    > 记忆句：超时重传就是等不到确认，再发一次。
    >
    > 追问：如果后续数据仍在到达，发送方收到了重复 ACK，能否在超时前发现丢包？
    >
    > 答案：后续子节点「等待超时太慢，TCP 能提前发现丢包吗？」的「原理」回答了这个问题，说明了根据重复 ACK 提前重传的机制。

    - **等待超时太慢，TCP 能提前发现丢包吗？**
      > 场景：课件中间的一段数据丢失，后续几个数据段陆续到达。接收方仍在等缺少的那一段，因此连续回复相同的 ACK 编号。
      >
      > 原理：重复 ACK 表示接收方还在等待同一个字节位置。经典快速重传算法收到 3 个重复 ACK 后，会判断对应数据段很可能丢失，立即重传，无需等 RTO 到期。这样，后续数据的到达就帮助发送方更早发现缺口；乱序也可能触发重复 ACK，所以这是算法作出的判断。
      >
      > 记忆句：快速重传就是不等超时，提前补包。
      >
      > 追问：自测：为什么重复 ACK 可以提示数据段可能丢失？
      >
      > 答案：接收方收到后续数据段，却仍在等待较早的数据，便会重复确认相同位置。发送方据此判断可能出现缺失；乱序也可能产生重复 ACK，因此这是一种丢包判断依据。

      ![快速重传流程图](../assets/image16.png)
```

Markdown 要求：

1. 文件开头必须是 YAML 属性块，包含布尔值 `mappy: true`，随后使用一个 `## 主题名称` 作为整份笔记的主题标题。
2. 知识层级全部使用以 `-` 开头的嵌套无序列表表达，不使用编号列表或任务列表作为知识节点。全文只保留这一个二级主题标题，不使用其他级别的标题组织节点。
3. 每个列表项的首行只写加粗的问题标题，标题保持单行。正文写在其下方的引用块中；回答中的条目也放在引用块内，避免被识别为知识子节点。每个节点必须包含场景、原理、记忆句、追问、答案五个字段；“答案：”紧接“追问：”，使用相同缩进，两段之间保留一个带 `>` 的空行。
4. 缩进只使用空格，不混用 Tab。列表每深入一级增加两个空格；引用块和图片相对于所属列表项增加两个空格。引用块中的空行保留 `>`，图片前后留出空行。
5. 节点正文及图片放在该节点标题之后、其子节点之前，确保答案和图片归属于正确节点。
6. 层级明确，父子关系准确；每个知识点可以独立阅读，也能顺着子节点继续深入。
7. 代码块、公式、表格和示例按需保留在对应节点正文中，不要求它们直接显示在导图节点上。
8. **不限制 Markdown 的总行数，可以超过 300 行、500 行甚至更多。**
9. **完整性优先于篇幅，不允许为了控制行数压缩、合并或删减知识点。**

## 四、图片处理

1. 原始笔记中有图片时，保留并放在最相关的知识节点下面。
2. 使用标准 Markdown 图片语法，直接引用原有图片文件，根据生成笔记的保存位置计算相对路径。
3. 例如，原图位于 `计算机网络/assets/image16.png`，生成笔记保存为 `计算机网络/obsidian/传输层.md`，应使用 `![说明](../assets/image16.png)`。
4. 不复制或移动原图，不在输出目录新建图片目录，也不创建图片目录的符号链接。
5. 不得编造图片文件或引用路径；生成后逐一检查图片引用，确认仍指向原有图片文件。
6. 需要图片辅助理解但原笔记没有图片时，可以添加 `[建议补图：需要展示的内容]`。
7. 图片不能代替文字解释。
8. 图片作为所属节点正文中的独立段落，放在五字段引用块之后、子节点之前，并与引用块保持相同缩进；不把图片单独写成列表项。

## 五、知识点完整性与技术准确性

1. 在内部先提取原始笔记的全部知识点，建立覆盖清单，但**不要单独输出清单**。
2. 所有知识点必须出现在最终知识树中。
3. 不允许把多个独立知识点合并成一句话，导致关键细节丢失。
4. 原笔记中的 `#TODO` 必须尽可能补全，并放在正确的树状位置。
5. 对原笔记不准确或过时的表述直接纠正。
6. 涉及不同技术版本、协议规范或实现差异时，说明适用条件。
7. 不确定的内容标记 `[待核]`，不得编造。
8. 为补齐知识逻辑而新增的必要知识点，标记 `[补]`。
9. 避免重复解释，但不能为了去重而省略重要的前提或边界条件。
10. 输出前在内部核对每个原始知识点是否覆盖，缺失的必须补齐；逐条核对追问答案，确保每个问题都有直接回答或准确的下级节点指引。
11. 逐节点检查可读性：场景是否具体，原理是否直接回答问题，术语是否得到解释，动作之间的因果是否清楚，例子与技术条件是否一致。发现抽象词堆积、长句或重复限制时，直接改写正文。
12. 更新已有笔记时，逐节点应用当前的场景、原理和追问答案规则，保留全部知识点、关键条件、有效示例和原图引用；已经符合要求的内容继续沿用。

**不要为了让知识树整齐，而牺牲技术准确性和知识完整性。**

## 六、最终输出要求（严格遵守）

**只输出一份兼容 Mappy 的完整 Markdown 树状笔记，不需要任何其他产物。文件以包含 `mappy: true` 的 YAML 属性块开头，全文不包裹在代码围栏中。**

不要输出：

- 单独的知识点清单
- 独立的 ASCII 知识树
- 覆盖表
- 30 秒骨架版
- 总结报告
- 文件下载链接
- 额外说明或结束语

所有内容必须直接整合进最终 Markdown 笔记中。

**篇幅不限，允许超过 300 行。**

如果原始笔记包含大量知识点，必须全部展开，不要因为篇幅过长而省略后半部分。

不要写「其余类似」「后续省略」「内容过长不再展开」等占位内容。

## 七、最终目标

这份笔记应该像一棵可以不断展开的知识树：

- 看根节点，知道这个技术主题要解决什么问题。
- 展开一级节点，看到几个核心机制。
- 继续展开子节点，理解每个机制为什么存在、如何实现。
- 每个节点都有可以直接用于面试的口述解释。
- 顺着追问，可以自然深入到底层原理。
- 面试官从任意节点提问，都能快速定位并组织答案。

**最终原则：树状组织、追问驱动、独立可背、内容完整、技术准确。**

请直接输出完整 Markdown 笔记，不需要询问确认。
