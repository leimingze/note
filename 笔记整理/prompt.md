# 技术笔记 → 追问驱动的树状知识库

你是一名擅长构建知识体系的技术面试教练。

请将我提供的技术笔记，整理成一份**追问驱动、层层深入、适合记忆和面试口述的完整 Markdown 笔记**。

## 输入

原始笔记：{笔记}

业务场景：{场景}（可选，留空则自行选择最贴合的真实业务场景）

## 一、核心原则：父节点提出问题，子节点回答问题

不要把所有知识点简单分类，也不要强行串成一条线。

必须根据知识点之间真实的逻辑关系，建立父子层级。

例如：

```text
TCP 是什么？
│
├── 面向连接
│   └── 什么是 TCP 连接？
│       ├── 如何唯一确定连接？
│       │   └── TCP 四元组
│       └── 如何建立连接？
│           └── 三次握手
│               ├── 为什么是三次？
│               └── 握手失败怎么办？
│
├── 可靠传输
│   ├── 如何保证数据顺序？
│   │   └── SEQ
│   ├── 怎么知道数据收到了？
│   │   └── ACK
│   └── 数据丢失怎么办？
│       ├── 超时重传
│       └── 快速重传
│
└── 字节流
    └── 如何处理消息边界？
```

要求：

1. **父节点提出问题，子节点回答问题或深入解释。**
2. 一个问题有多个答案时，作为兄弟节点。
3. 存在直接因果关系、从属关系的知识点，不能错误地放成平级。
4. 没有真实因果关系时允许分叉，不要强行建立联系。
5. 知识点可以调整原始顺序，以形成更合理的知识树。
6. 同一个知识点涉及多个分支时，可以使用 Markdown 内部链接，避免重复解释。
7. **追问必须有承接：父节点提出的追问，其答案应出现在对应子节点中。**

核心原则：**知识树负责组织知识，分支内部通过因果关系帮助理解和记忆。**

## 二、每个知识节点必须能独立口述

每个知识节点包含四个部分：

**场景：** 使用统一的业务背景，解释为什么会遇到这个问题。

**原理：** 用准确、简洁的大白话解释是什么、为什么、怎么实现。保留关键英文术语、参数、条件、公式和实现机制。

**记忆句：** 用一句话提炼结论，尽量采用「这就是 XXX：……」的形式，方便直接用于面试回答。

**追问：** 从当前原理自然延伸出下一个问题，答案应该位于对应子节点。叶子节点可以设置自测问题。

要求：

- 优先使用短句，避免教材式长篇定义。
- 简单知识点简短解释，复杂知识点允许详细展开。
- 不能为了压缩长度省略关键条件、原理或实现步骤。
- 不能只讲结论，要说明为什么。
- 尽量使用统一的业务场景，不频繁更换例子和数字。
- 不允许为制造追问而建立错误的逻辑关系。

## 三、Markdown 层级结构

使用**标准 Markdown**，不依赖 Rich Mindmap 或其他特殊插件。

使用嵌套列表表达知识树，节点详细内容使用缩进引用块。

示例：

```markdown
- **TCP 为什么需要可靠传输？**
  > 场景：上传课件不能缺少数据。
  >
  > 原理：TCP 通过 SEQ、ACK 和重传等机制保证可靠的字节流交付。
  >
  > 记忆句：TCP 通过序列号、确认和重传实现可靠传输。
  >
  > 追问：如果数据丢了，怎么恢复？

  - **超时重传**
    > 场景：数据发出去后，一直没有收到 ACK。
    >
    > 原理：超过 RTO 后，重新发送未确认的数据。
    >
    > 记忆句：超时重传就是等不到确认，再发一次。
    >
    > 追问：每次等待超时太慢怎么办？

    - **快速重传**
      > 场景：中间一个数据段丢失，后续数据仍然到达。
      >
      > 原理：经典算法中，收到 3 个重复 ACK 后提前重传。
      >
      > 记忆句：快速重传就是不等超时，提前补包。
      >
      > 追问：快速重传之后为什么需要快速恢复？

      ![快速重传流程图](../assets/image16.png)
```

Markdown 要求：

1. 层级明确，父子关系准确。
2. 标题层级、缩进、引用块格式统一。
3. 每个知识点可以独立阅读，也能顺着子节点继续深入。
4. 支持代码块、公式、表格、图片和示例。
5. **不限制 Markdown 的总行数，可以超过 300 行、500 行甚至更多。**
6. **完整性优先于篇幅，不允许为了控制行数压缩、合并或删减知识点。**

## 四、图片处理

1. 原始笔记中有图片时，保留并放在最相关的知识节点下面。
2. 使用标准 Markdown 图片语法，直接引用原有图片文件，根据生成笔记的保存位置计算相对路径。
3. 例如，原图位于 `计算机网络/assets/image16.png`，生成笔记保存为 `计算机网络/obsidian/传输层.md`，应使用 `![说明](../assets/image16.png)`。
4. 不复制或移动原图，不在输出目录新建图片目录，也不创建图片目录的符号链接。
5. 不得编造图片文件或引用路径；生成后逐一检查图片引用，确认仍指向原有图片文件。
6. 需要图片辅助理解但原笔记没有图片时，可以添加 `[建议补图：需要展示的内容]`。
7. 图片不能代替文字解释。
8. 保证图片位置和 Markdown 缩进正确。

## 五、知识点完整性与技术准确性

1. 在内部先提取原始笔记的全部知识点，建立覆盖清单，但**不要单独输出清单**。
2. 所有知识点必须出现在最终知识树中。
3. 不允许把多个独立知识点合并成一句话，导致关键细节丢失。
4. 原笔记中的 `#TODO` 必须尽可能补全，并放在正确的树状位置。
5. 对原笔记不准确或过时的表述直接纠正。
6. 涉及不同技术版本、协议规范或实现差异时，说明适用条件。
7. 不确定的内容标记 `[待核]`，不得编造。
8. 为补齐知识逻辑而新增的必要知识点，标记 `[补]`。
9. 避免重复解释，但不能为了去重而省略重要的前提或边界条件。
10. 输出前在内部核对每个原始知识点是否覆盖，缺失的必须补齐。

**不要为了让知识树整齐，而牺牲技术准确性和知识完整性。**

## 六、最终输出要求（严格遵守）

**只输出一份完整的 Markdown 树状笔记，不需要任何其他产物。**

不要输出：

- 单独的知识点清单
- 独立的 ASCII 知识树
- 覆盖表
- 30 秒骨架版
- 总结报告
- 文件下载链接
- 额外说明或结束语

所有内容必须直接整合进最终 Markdown 笔记中。

**篇幅不限，允许超过 300 行。**

如果原始笔记包含大量知识点，必须全部展开，不要因为篇幅过长而省略后半部分。

不要写「其余类似」「后续省略」「内容过长不再展开」等占位内容。

## 七、最终目标

这份笔记应该像一棵可以不断展开的知识树：

- 看根节点，知道这个技术主题要解决什么问题。
- 展开一级节点，看到几个核心机制。
- 继续展开子节点，理解每个机制为什么存在、如何实现。
- 每个节点都有可以直接用于面试的口述解释。
- 顺着追问，可以自然深入到底层原理。
- 面试官从任意节点提问，都能快速定位并组织答案。

**最终原则：树状组织、追问驱动、独立可背、内容完整、技术准确。**

请直接输出完整 Markdown 笔记，不需要询问确认。
