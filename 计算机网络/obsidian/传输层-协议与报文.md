# 传输层：协议与报文

[返回总览](传输层.md) · [连接建立](传输层-连接建立.md) · [可靠传输](传输层-可靠传输.md)

统一场景：在线课堂中，学生上传课件、观看直播，浏览器访问课堂服务。`[补]` 表示原文之外的必要知识。

- **A01｜课堂服务为什么需要传输层协议？**
  > 场景：同一台设备既上传课件，也播放课堂音视频。
  >
  > 原理：传输层通过端口把数据交给对应应用；TCP 与 UDP 提供不同的连接、交付和消息边界能力。
  >
  > 记忆句：这就是传输层：把主机间通信交给对应应用，并提供所需的传输能力。
  >
  > 追问：TCP 和 UDP 各自提供什么，业务如何选择？

  - **A02｜TCP 提供什么服务？**
    > 场景：课件上传需要收到完整、有序的文件内容。
    >
    > 原理：TCP 是面向连接、提供可靠交付、基于字节流的传输层协议；两端维护连接状态，完成编号、确认和重传。
    >
    > 记忆句：这就是 TCP：用连接状态管理一条可靠、有序的字节流。
    >
    > 追问：连接、可靠性和字节流分别意味着什么？报文如何表达，适合哪些业务，又有哪些代价？

    - **A03｜面向连接为什么强调两个端点？**
      > 场景：每个学生分别与课堂服务器上传课件。
      >
      > 原理：一条 TCP 连接只关联两个端点，不能直接提供广播或组播；服务器可以同时维护许多条连接，分别服务不同学生。
      >
      > 记忆句：这就是面向连接：每条连接管理两个端点之间的通信状态。
      >
      > 追问：自测：一条连接只有两个端点，为什么服务器仍能服务多人？连接标识见[连接建立](传输层-连接建立.md)。

    - **A04｜TCP 的可靠性由什么保证？**
      > 场景：课件数据在途中丢失、重复或乱序到达。
      >
      > 原理：TCP 用序列号重组和去重，用校验和检测传输损坏，再结合确认与重传恢复缺失数据；持续失败时通过超时或错误结束连接。
      >
      > 记忆句：这就是可靠交付：恢复可恢复的传输问题，并让无法继续的连接报错。
      >
      > 追问：使用 TCP 是否就能保证课件已经保存？重传过程见[可靠传输](传输层-可靠传输.md)。

    - **A06｜如何理解 TCP 面向字节流？ #TODO（原问题，已补全）**
      > 场景：客户端连续发送课件名称和课件内容。
      >
      > 原理：TCP 只保留字节的连续顺序，不保留每次写入的边界；一次发送可由多次读取取得，多次发送也可由一次读取取得。
      >
      > 记忆句：这就是字节流：字节有顺序，应用消息没有天然边界。
      >
      > 追问：应用如何识别一条消息的结束位置？

      - **A07｜应用如何处理消息边界？ [补]**
        > 场景：服务器需要区分课件名称、大小和正文。
        >
        > 原理：应用协议可以使用固定长度、长度前缀或分隔符；接收方按协议累积和解析字节，长度与编码规则必须一致，使用分隔符时还要处理转义。
        >
        > 记忆句：这就是消息定界：应用协议自己定义每条消息占哪些字节。
        >
        > 追问：自测：一次 `recv()` 返回的数据为什么不能直接当作一条完整消息？

    - **A08｜TCP 首部怎样表达传输状态？**
      > 场景：服务器需要知道课件数据属于谁、排在哪里、确认到哪里。
      >
      > 原理：TCP 首部包含源与目的端口、序列号、确认号、首部长度、标志位、窗口和校验和等字段；它们共同表达连接与交付状态。
      >
      > 记忆句：这就是 TCP 首部：随数据携带连接、编号、确认和窗口信息。
      >
      > 追问：序列号、确认号、标志位和首部长度分别如何解释？

      - **A09｜SEQ 和 ACK number 怎样变化？ #TODO（原问题，已补全）**
        > 场景：从 `SEQ=101` 开始发送 100 字节课件。
        >
        > 原理：SEQ 是本段首个数据字节的编号；连续收到这 100 字节后，确认号为 `201`。SYN、FIN 各占一个序号，纯 ACK 不占。[补] 两个方向各自编号，序号按模 `2^32` 运算。
        >
        > 记忆句：这就是编号规则：数据按字节推进，SYN、FIN 各推进一位。
        >
        > 追问：自测：为什么 ACK 不能总按最近一个报文的 `SEQ+1` 计算？

      - **A10｜ACK、SYN、FIN、RST 标志分别表示什么？**
        > 场景：课堂连接经历建立、传输、正常关闭或异常终止。
        >
        > 原理：ACK 标志表示确认号有效；SYN 用于同步初始序号；FIN 表示本方向发送结束；RST 用于拒绝或重置连接。[补] 收到 RST 后仍需按状态和序号检查是否接受。
        >
        > 记忆句：这就是控制标志：确认、同步、结束发送、重置连接各有含义。
        >
        > 追问：自测：为什么 `ACK=1` 与确认号 `201` 不能混为一谈？

      - **A11｜为什么 TCP 有首部长度，UDP 没有？**
        > 场景：课堂连接需要协商 MSS、窗口扩大或时间戳等选项。
        >
        > 原理：TCP 首部含可变选项，通常为 20～60 字节，用 Data Offset 指示长度，单位为 4 字节；UDP 普通首部固定为 8 字节，不需要另设首部长度字段。
        >
        > 记忆句：这就是首部长度字段：告诉接收方可变首部在哪里结束。
        >
        > 追问：自测：TCP 不带选项时，Data Offset 应为多少？

    - **A12｜哪些课堂业务常使用 TCP？**
      > 场景：学生通过网页上传课件，也可能通过文件服务下载资料。
      >
      > 原理：FTP 和常见 HTTP/1.1、HTTP/2 通信使用 TCP；HTTPS 表示 HTTP 受到 TLS 保护。[补] HTTP/3 使用基于 UDP 的 QUIC，因此 HTTPS 不能一概等同于 TCP。
      >
      > 记忆句：这就是应用选择：文件和网页常用 TCP，但仍要看具体协议版本。
      >
      > 追问：自测：为什么看到 HTTPS 地址，还不能确定下层一定使用 TCP？

    - **A13｜TCP 有哪些局限？ #TODO（原问题，已补全）**
      > 场景：一次课件丢包可能延迟同一连接上后续数据的交付。
      >
      > 原理：有序字节流存在队头等待；建立连接有往返开销，连接状态消耗资源。[补] 连接通常由四元组标识，地址变化不直接支持透明迁移，TCP 本身也不提供加密。
      >
      > 记忆句：这就是 TCP 的代价：有序可靠交付需要等待、连接状态与额外机制。
      >
      > 追问：自测：同一 TCP 连接上的后续字节已经到达，为什么应用仍可能读不到？

  - **A14｜UDP 提供什么服务？**
    > 场景：课堂音视频希望逐个发送带有时间意义的数据报。
    >
    > 原理：UDP 基于 IP 提供无连接的数据报服务，保留消息边界，不内置确认、重传、按序交付、流量控制或拥塞控制。
    >
    > 记忆句：这就是 UDP：直接发送有边界的数据报，交付策略交给上层。
    >
    > 追问：UDP 首部包含什么，哪些课堂通信适合使用它？

    - **A15｜UDP 首部与校验和有什么作用？**
      > 场景：课堂音视频数据报需要送到正确端口并检查传输损坏。
      >
      > 原理：普通 UDP 首部四字段各 2 字节：源端口、目的端口、总长度、校验和。长度包含首部和数据；校验覆盖伪首部、UDP 首部和数据，发现损坏不代表能恢复丢失。
      >
      > 记忆句：这就是 UDP 首部：端口负责分发，长度描述边界，校验检查损坏。
      >
      > 追问：自测：为什么存在 UDP 校验和仍不能称为可靠交付？

    - **A16｜UDP 适合哪些课堂通信？**
      > 场景：进入课堂需要 DNS 查询，直播关心及时性，局域网还可能发送发现通知。
      >
      > 原理：传统 DNS 常用 UDP，音视频可按期限决定是否补包，IPv4 广播和 IP 组播也可使用 UDP；[补] DNS 在截断等情况下会改用 TCP，IPv6 没有广播。
      >
      > 记忆句：这就是 UDP 的常见用途：短交互、及时交付与组播通信。
      >
      > 追问：数据报丢失后，课堂应用应该如何处理？

      - **A17｜UDP 丢包了怎么办？**
        > 场景：一帧课堂音频晚到已无播放价值，课件内容却不能缺少。

        > 原理：应用按业务决定忽略、补偿或重传；及时性优先时可放弃过期数据，完整性优先时通常直接选择 TCP，或采用已有可靠 UDP 协议。
        >
        > 记忆句：这就是 UDP 丢包策略：由消息期限与完整性要求决定恢复方式。

  - **A19｜TCP 与 UDP 应按哪些维度比较？**
    > 场景：课堂平台需要同时设计课件上传与直播传输。
    >
    > 原理：比较连接、服务对象、可靠性、控制机制、首部、消息边界和大消息处理；选择依据是业务需求以及上层协议提供的能力。
    >
    > 记忆句：这就是协议比较：同时看交付能力、控制成本与消息组织方式。
    >
    > 追问：大消息怎样发送，长度怎样确定，同号端口能否共用？

    | 维度 | TCP | UDP |
    |---|---|---|
    | 连接 | 建立并维护连接状态 | 发送前不需要传输层握手 |
    | 服务对象 | 每条连接两个端点 | 可用于单播、广播、组播；可构成多对多通信 |
    | 可靠性 | 有序交付，传输失败时报告错误 | 不保证到达、顺序和不重复，上层可补充 |
    | 控制机制 | 包含流量控制与拥塞控制 | 本身不提供；应用仍应控制发送速率 |
    | 首部 | 通常 20～60 字节 | 普通 UDP 固定 8 字节 |
    | 传输方式 | 字节流，无应用消息边界 | 数据报，有消息边界 |
    | 大消息 | 按 MSS 等约束进行 TCP 分段 | 超过路径 MTU 可能需 IP 分片或发送失败 |

    - **A20｜MSS、MTU、TCP 分段与 IP 分片有什么关系？**
      > 场景：一份课件远大于网络一次可承载的数据量。
      >
      > 原理：MSS 限定 TCP 数据部分，MTU 限定链路承载的 IP 包大小；TCP 分段后按字节范围重传。UDP 大数据报若分片，任一片缺失就无法交付整份数据报。
      >
      > 记忆句：这就是两种划分：TCP 分段服务传输，IP 分片适应链路大小。
      >
      > 追问：自测：丢失一个 IP 分片，为什么 UDP 接收方拿不到其余片组成的部分消息？

      > 接收端由 TCP 重组各段；IP 分片则在目标主机的 IP 层重组后，才交给 TCP 或 UDP。[补] TCP 报文也可能发生 IP 分片。IPv4 允许分片还取决于 DF 等条件；IPv6 路由器不分片，由源端适应路径 MTU。重传时 TCP 分段边界不必与第一次完全一致。

    - **A21｜为什么 UDP 有总长度字段，TCP 没有？**
      > 场景：课堂服务器需要判断传输层数据占多少字节。
      >
      > 原理：UDP 用 Length 直接描述首部加数据；TCP 段长可由 IP 提供的承载长度确定。IPv4 中，TCP 数据长度等于 IP 总长度减 IP 首部长度，再减 TCP 首部长度。
      >
      > 记忆句：这就是长度获取：UDP 自带数据报长度，TCP 利用 IP 的承载长度。
      >
      > 追问：自测：IPv4 的计算公式为什么必须减去可变长的 IP 与 TCP 首部？

      > [补] IPv6 应从 Payload Length 扣除位于 TCP 前的扩展首部与 TCP 首部，不能直接套用 IPv4 总长度公式；普通 UDP 的 Length 已包含其固定 8 字节首部。

    - **A22｜TCP 和 UDP 可以使用同一个端口吗？ #TODO（原问题，已补全）**
      > 场景：课堂服务器希望同时监听 TCP 443 与 UDP 443。

      >
      > 记忆句：这就是端口作用域：同一个数值可以分别属于 TCP 和 UDP。
      >
      > 追问：自测：同为 443 端口，HTTP/2 与 HTTP/3 为什么可以同时提供服务？
