## 一、基础单机架构（Standalone）
### 架构说明
- 只有一个 Redis 实例，所有读写都打到这一台机器
- 数据全量存放在内存，支持 RDB / AOF 持久化
### 优点
- 架构最简单，延迟最低
- 运维成本低
### 缺点
- 单点故障（SPOF）
- 内存和吞吐受单机限制
### 适用场景
- 开发/测试环境
- 数据量小、可用性要求不高的缓存场景

## 二、主从复制架构（Replication / Master-Replica）
### 架构说明
- 一个 **Master** 负责写
- 多个 **Replica（Slave）** 从 Master 异步复制数据，负责读
- 默认是 **异步复制**
### 优点
- 读写分离，提升读吞吐
- 数据冗余，降低数据丢失风险
### 缺点
- Master 单点故障，故障需人工切换
- 异步复制存在数据不一致窗口
### 适用场景
- 读多写少
- 对高可用要求一般，但希望提升读能力

## 三、哨兵架构（Redis Sentinel）
### 架构说明
- 基于主从架构，增加 **Sentinel 集群**
- Sentinel 负责：
  - 监控 Master / Replica
  - 自动故障检测与切换（Failover）
  - 向客户端提供新的 Master 地址
### 优点
- 自动故障转移，提升高可用
- 对客户端透明（通过 Sentinel 发现 Master）
### 缺点
- 写仍然集中在单 Master
- 故障切换期间可能有短暂不可用
- 配置和运维复杂度上升
### 适用场景
- 需要高可用，但数据量仍在单机可承载范围内
- 中小型生产系统

## 四、Redis Cluster（官方分布式集群）
### 架构说明
- Redis 官方提供的 **分布式解决方案**
- 采用 **哈希槽（Hash Slot）** 机制：
  - 共 16384 个 slot
  - 每个 key 通过 `CRC16 % 16384` 映射到 slot
  - slot 分配到不同节点
- 每个分片通常是 **主从结构**
- 节点间通过 Gossip 协议通信
### 优点
- 数据分片，突破单机内存限制
- 高可用 + 自动故障转移
- 水平扩展能力强
### 缺点
- 不支持多 key 跨 slot 事务（除非使用 hash tag）
- 客户端需支持 Cluster 协议
- 运维复杂度较高
### 适用场景
- 大数据量、高并发
- 需要水平扩展的生产环境
