# 05 Redis 高可用

## 八股问答

### 1. 如果单个 Redis 服务器压力过大怎么办？

先定位瓶颈是内存、CPU、网络还是磁盘/持久化：

| 方向 | 做法 |
| --- | --- |
| 垂直扩容 | 提高内存、CPU、带宽 |
| 读写分离 | 主节点写，从节点读 |
| 水平扩容 | Redis Cluster 分片 |
| 缓存分层 | 本地缓存 + Redis + 数据库 |
| 热点治理 | 热点 Key 拆分、本地缓存、多副本 |
| 大 Key 治理 | 拆分、压缩、限流 |
| 连接与命令 | 连接池、Pipeline、控制慢命令 |
| 容量策略 | 设置 `maxmemory`、淘汰策略、监控淘汰次数 |

不要只把“加机器”当答案。先监控 `used_memory`、`maxmemory`、命中率、每秒命令数、慢查询、
过期删除和淘汰次数，再决定扩容或改造。

### 2. 如何保证集群的数据一致性？

首先要明确：Redis 主从复制是**异步复制**，Redis Cluster 也不是强一致系统。

- 主节点先执行写命令并返回，再异步发送给从节点。
- 从节点复制有延迟，主节点故障时可能丢失最近写入。
- Cluster 的多个 key 操作通常要求落在同一 slot，跨 slot 事务受限。
- 网络分区时，少数派节点无法完成故障转移，写服务可能停止。

可以提升一致性但不能变成强一致：

- 读写分离场景对一致性要求高时，读主节点或等待从节点追上。
- 使用 `WAIT numreplicas timeout` 等待指定数量的从节点确认。
- 配置 `min-replicas-to-write`，从节点数量不足时拒绝写入。
- 监控 `master_repl_offset` 和从节点 `slave_repl_offset`。
- 跨槽操作使用 hash tag，例如 `{user:1}` 让多个 key 映射到同一 slot。

如果业务真正需要跨节点强一致，应通过数据库、分布式事务或外部协调服务完成，而不是依赖 Redis。

### 3. 主从复制是如何实现的？

Redis 主从复制分为**全量复制**和**部分重同步**。

全量复制流程：

1. 从节点发送 `PSYNC`，带上 replication ID 和 offset。
2. 主节点判断无法部分重同步时，触发 `BGSAVE` 生成 RDB。
3. RDB 生成期间的写命令写入复制缓冲区。
4. 主节点把 RDB 发送给从节点，从节点清空旧数据并加载。
5. 主节点再发送缓冲区中的增量命令。

部分重同步：

- 如果 replication ID 未变化，且从节点 offset 落在 `repl_backlog` 范围内，主节点只发送缺失的增量命令。
- `repl-backlog-size` 太小、主从断开太久或复制 ID 变化时，会退化为全量复制。

核心字段：`replid`（复制 ID）、`repl_offset`（复制偏移量）、`repl_backlog`（复制积压缓冲区）。

主从复制默认异步，主节点写成功不代表从节点已经落盘；生产环境要监控复制延迟和从节点数量。

### 4. 如何应对主从数据不一致？

不一致主要来自复制延迟：

- 写入主节点后立即从从节点读，读到旧数据。
- 网络抖动导致从节点落库落后。
- 主节点故障后由落后的从节点接替，最近写入丢失。

应对方法：

- 对一致性要求高的读，直接读主节点或使用 `WAIT`。
- 读从节点时接受最终一致，并设置超时和降级。
- 监控从节点复制延迟和 offset，延迟过高时摘除流量。
- 配置 `min-replicas-to-write` 和 `min-replicas-max-lag`，避免从节点太少或太落后时继续写。
- 重要数据不要只存在 Redis，需要由数据库或消息系统兜底。

最后要接受一个事实：Redis 的主从复制不是强一致，做不到“任何时刻主从完全一样”。

### 5. 什么是哨兵？为什么要有哨兵机制？

哨兵（Sentinel）是独立运行的监控进程，用于监控 Redis 主从节点。

没有哨兵时，主节点宕机需要人工发现、切换和修改客户端连接，服务会中断较久。

哨兵解决：

- 自动检测主节点是否故障。
- 自动从从节点中选出新的主节点。
- 通知其他从节点和客户端更新主节点。
- 提供故障转移能力，降低人工介入。

生产上通常部署 3 个或更多哨兵，形成多数派，避免单点哨兵误判导致脑裂。

### 6. 讲一下哨兵机制？

哨兵通过心跳监控节点状态：

- 每个哨兵周期性发送 `PING`。
- 超过 `down-after-milliseconds` 没有响应，标记为**主观下线（S-DOWN）**。
- 其他哨兵确认后，达到 `quorum` 数量，标记为**客观下线（O-DOWN）**。
- 哨兵之间选举领导者，再由领导者发起故障转移。

故障转移选择新主节点的依据：

- 从节点优先级（`slave-priority`，现在是 `replica-priority`）。
- 复制偏移量更大，代表数据更新。
- runid 更小，作为最后的稳定排序。

新主节点确定后：

- 其他从节点改为复制新主节点。
- 旧主节点恢复后自动变成从节点。
- 哨兵把新的主节点信息写入配置并通知客户端。

哨兵保证的可用性依赖多数派。如果只有 2 个哨兵且 1 个宕机，无法形成多数派，可能不会发起故障转移。

### 7. Cluster 集群是什么？为了解决什么问题？

Redis Cluster 是 Redis 官方的分布式方案：

- 将数据按 **16384 个哈希槽**分片，每个主节点负责一部分 slot。
- 每个主节点可以带若干从节点，实现分片和故障转移。
- 节点之间通过 gossip 协议交换状态，客户端直接连接目标节点，无需中心代理。
- 解决单实例内存、CPU、写入吞吐和容量的横向扩展问题。

需要注意：

- 单个 key 的读写会被路由到固定 slot。
- 多个 key 必须落在同一 slot 才能保证部分原子性，跨 slot 的 `MULTI/EXEC` 受限。
- 集群内部复制仍是异步，存在数据丢失窗口。
- 客户端需要缓存 slot 映射并处理重定向。

### 8. 在 Cluster 集群的情况下客户端怎么知道该从哪个服务器上获取数据？

Redis Cluster 用 `CRC16(key) % 16384` 计算 key 对应的哈希槽。

客户端启动时通过 `CLUSTER SLOTS` 获取 slot 与节点的映射关系并缓存。

请求流程：

```text
key → CRC16 → hash slot → slot → node
```

如果节点发现 key 不在自己负责的 slot，会返回重定向：

- `MOVED`：该 slot 已经永久迁移到另一个节点，客户端应更新缓存并重试。
- `ASK`：该 slot 正在迁移中，客户端应访问目标节点执行一次 `ASKING` 后重试。

为了减少跨 slot 限制，可以让相关 key 使用相同 hash tag，例如：

```text
{user:1}:profile
{user:1}:orders
```

### 9. 集群内节点出现故障怎么办？

节点通过 gossip 交换状态：

- 连续收不到心跳时，节点先标记为 `PFAIL`（疑似故障）。
- 多个节点确认后，状态升级为 `FAIL`。
- 主节点故障时，其从节点参与选主，大多数节点同意后提升为新主节点。
- 原主节点恢复后通常会变成从节点，重新加入集群。

关键条件：

- 故障转移需要多数主节点和从节点确认，网络分区中的少数派不能完成选举。
- 如果某个 slot 没有可用主节点，且 `cluster-require-full-coverage yes`（默认），集群可能停止服务部分或全部写入。
- 数据一致性不是强一致：主节点故障时，最后未同步的写入可能丢失。
- 生产环境要监控节点状态、slot 覆盖、复制延迟和故障转移频率。

## 面试话术

“单实例压力大时我会先看瓶颈：内存、CPU 还是网络。内存和写入压力大可以分片到 Cluster，
读多写少可以做主从读写分离，热点 Key 可以本地缓存和拆分。
Redis 主从复制是异步的，默认是最终一致；哨兵负责自动故障转移，Cluster 负责横向分片和高可用。
客户端通过 `CRC16` 计算 slot，再用 `CLUSTER SLOTS` 缓存节点映射，`MOVED` 和 `ASK` 负责迁移时的重定向。
如果业务要求强一致，我不会只依赖 Redis，而是用数据库或外部协调机制做兜底。”
