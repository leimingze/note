# AOF 持久化机制

---

## 一、AOF 日志是什么

如果 Redis 每执行一条写操作命令，就把该命令以追加的方式写入到一个文件里，然后重启 Redis 的时候，先去读取这个文件里的命令并执行，就相当于恢复了缓存数据。

**注意：只会记录写操作命令，读操作命令不会被记录。**

---

## 二、AOF 写入全过程

Redis 写入 AOF 日志的完整链路：


1. 执行写操作命令
   例如：set name zhangsan

2. 追加到 aof_buf 缓冲区
   Redis 先把这条命令记到用户态内存里的 aof_buf（相当于"小纸条"）

3. I/O 系统调用 write()
   从 Redis 用户态跨入内核态，把数据递给操作系统

4. 内核缓冲区（page cache）
   内核接过来先放 page cache 里（速度快，但还没真正落盘）

5. 内核发起写操作 → 硬盘
   最终真正写入硬盘


---

## 三、AOF 的风险

### 风险 1：宕机丢数据

执行写操作命令和记录日志是两个过程。如果 Redis 还没来得及将命令写入硬盘时服务器宕机，这条数据就会丢失。

### 风险 2：阻塞后续命令

写操作命令执行成功后才记录到 AOF 日志，所以不会阻塞**当前**写命令的执行。但是将命令写入日志的操作也在主进程完成（执行命令也在主进程），如果写硬盘时 I/O 压力太大，写硬盘速度很慢，就会阻塞住，导致后续命令无法执行。

---

## 四、三种写回策略

Redis 提供了三种写回硬盘的策略，对应上述第 5 步（内核真正落盘时机的控制）：

在 `redis.conf` 中通过 `appendfsync` 配置项设置：

| 策略 | 行为 | 最多丢失数据 | 性能 |
|------|------|-------------|------|
| **always** | 每次写操作执行完后，同步将 AOF 日志写回硬盘 | 最多丢 1 条 | 最差 |
| **everysec** | 每次执行完写操作后，主线程先通过 `write()` 写入内核缓冲区，然后由 **bio 后台线程** 每隔 1 秒调用 `fsync()` 将内核缓冲区内容写回硬盘 | 最多丢 1 秒 | 中等 |
| **no** | 不由 Redis 控制写回时机，完全由操作系统决定 | 可能丢很多 | 最好 |

---

## 五、为什么需要 AOF 重写

AOF 文件不断追加写命令，时间越长文件越大。重启 Redis 时需要逐条执行 AOF 中的命令来恢复数据，文件过大会导致恢复过程非常慢。

AOF 重写的目的：**只记录最新状态，不记录历史过程。**

例如：


set name zhangsan
set name lisi
set name wangwu


重写后只保留：


set name wangwu


重写完成后，将新的 AOF 文件覆盖现有的 AOF 文件（不直接修改原有文件，避免出错）。

## 六、AOF 后台重写（BGREWRITEAOF）

### 为什么不在主进程做

AOF 重写很耗时（遍历整个数据库、生成命令、写文件），放在主进程会阻塞正常命令处理。

### 为什么用子进程而不是线程

| 方案 | 问题 |
|------|------|
| 线程 | 多线程共享内存，修改数据需要加锁，锁竞争降低性能 |
| 子进程 | 利用写时复制（COW），父子进程拥有独立数据副本，无需加锁 |

使用子进程的好处：

1. **不阻塞主进程**：重写期间主进程可以继续处理客户端请求
2. **无锁**：利用写时复制机制，父子进程各自拥有独立副本

---

## 七、子进程如何拥有主进程的数据副本

主进程通过 `fork()` 创建 `bgrewriteaof` 子进程时：

1. 内核将主进程的**页表**（虚拟地址 → 物理地址映射）复制一份给子进程
2. **不复制物理内存**，父子进程指向同一份物理内存
3. 共享内存标记为**只读**
4. 当父进程或子进程执行写操作时：
   - CPU 触发写保护中断
   - 内核在处理函数中**复制被修改的物理内存页**
   - 重新设置内存映射，将该页权限改为可读写
   - 然后才真正执行写操作

这就是 **写时复制（Copy-On-Write）**。

### 两个阶段会阻塞父进程

| 阶段 | 原因 |
|------|------|
| fork 创建子进程时 | 需要复制主进程的页表 |
| 写时复制发生时 | 复制被修改的物理内存页 |

## 八、重写期间主进程修改了已存在的 key 怎么办

### 问题本质

子进程开始重写后，它看到的是 `fork()` 那一刻的数据库快照。如果主进程后续修改了某个 key，子进程的内存数据就和主进程不一致了。

### Redis 的解决方案：双写机制

Redis 在创建子进程的同时，开启了一个 **AOF 重写缓冲区**（内存中的命令列表）。

从这一刻起，主进程每执行一条写命令，会同时写两个地方：

| 目的地 | 缓冲区 | 写入目标 | 作用 |
|--------|--------|----------|------|
| **aof_buf** | 始终存在 | 旧 AOF 文件 → 最终被新文件替换 | 保证数据安全，宕机可恢复 |
| **AOF 重写缓冲区** | 重写期间新增 | 新 AOF 文件（重写完成后追加） | 保证新 AOF 文件数据完整 |

**为什么需要两个缓冲区：**

- 缺 aof_buf → 重写期间宕机，数据丢失
- 缺重写缓冲区 → 新 AOF 文件数据过时，重放后不一致

## 九、AOF 后台重写的完整流程


1. 主进程收到 BGREWRITEAOF 命令
   ↓
2. fork() 创建子进程
   • 复制页表，不复制物理内存

   • 父子进程共享内存（只读）

   • 开启 AOF 重写缓冲区

   ↓
3. 子进程开始 AOF 重写
   • 遍历数据库快照（fork 时的状态）

   • 对每个 key 生成一条 SET 命令

   • 写入临时 AOF 文件

   ↓
4. 主进程继续处理客户端请求
   • 执行写命令

   • 写命令追加到 aof_buf → 旧 AOF 文件（正常追加流程）

   • 写命令同时追加到 AOF 重写缓冲区

   • 如果修改共享内存，触发 COW，产生独立副本

   ↓
5. 子进程完成重写，发送完成信号
   ↓
6. 主进程处理完成信号（短暂阻塞）
   • 将 AOF 重写缓冲区中的所有命令追加到新 AOF 文件末尾

   • 原子替换旧 AOF 文件

   • 关闭旧 AOF 文件

   ↓
7. 后续写命令正常写入新 AOF 文件


### 数据一致性保证

新 AOF 文件的内容 = **子进程的快照（fork 时刻的状态）** + **重写缓冲区（fork 之后的增量）**

重放新 AOF 文件后，数据状态与重写完成时主进程数据库状态完全一致。

---

## 十、一句话总结

**AOF 持久化 = 命令追加日志 + 三种写回策略权衡性能与安全；AOF 重写 = 子进程基于 fork 快照写基线 + 主进程通过重写缓冲区记录增量 + 重写完成后一次性追加合并，既保证不阻塞服务，又保证新文件数据完整。**
