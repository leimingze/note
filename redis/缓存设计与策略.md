# 什么是缓存雪崩、击穿、穿透
引入了redis缓存层，就会有缓存异常的三个问题，分别是：缓存雪崩、缓存击穿、缓存穿透
- 缓存雪崩：大量缓存数据同时过期、redis故障
- 缓存击穿：热点数据缓存过期
- 缓存穿透：数据既不在缓存、也不在数据库

# 缓存雪崩
当大量缓存在同一时间过期（失效）或者redis故障待机时，如果此时有大量用户请求，都无法在redis中处理，于是全部请求都直接访问数据库。
两个原因：
1. 大量数据同时过期
2. redis故障宕机

# 大量数据同时过期应对方法
1. 均匀设计过期时间
2. 互斥锁
3. 后台更新缓存

## 均匀设计过期时间（随机TTL）
给过期时间加上随机数

## 多级缓存
本地缓存+redis+db

## redis高可用
哨兵/集群

## 永不过期
不设TTL，后台异步更新


# 缓存击穿
问题描述：热点key（如秒杀系统）过期瞬间：瞬间几万个请求同时查询该key，全部落到数据库，db压力暴增

## 互斥锁方案
保证同他那个一时间只有一个业务线程更新线程，未能获取互斥锁的请求，要么等待锁释放后重新读取缓存，要么就返回空值或者默认值。

## 不给热点数据设置过期时间
由后台异步更新缓存，或者热点数据准备过期前，提前通知后台线程更新缓存以及重新设置过期时间。


# 缓存穿透
```text
请求 → 缓存（不存在）→ 数据库（不存在）
攻击者故意查 user:id=-1 这类不存在的 key
每次绕过缓存，直接打到 DB
```

## 缓存空值
查不到key的也缓存，优点是简单，缺点是浪费内存，数据不一致

## 布隆过滤器
判断key是否可能存在，优点是内存高效，缺点是有误判率，不支持删除

## 参数校验
拦截非法，优点是零成本，缺点是只能过滤明显非法请求

## 完整仿穿透代码
```python
def get_user(user_id):
    # 1. 布隆过滤器判断
    if not bloom.exists(f"user:{user_id}"):
        return None  # 一定不存在，直接返回

    # 2. 查缓存
    data = redis.get(f"user:{user_id}")
    if data is not None:
        return json.loads(data) if data != "NULL" else None

    # 3. 查数据库
    data = db.query("SELECT * FROM users WHERE id = ?", user_id)

    # 4. 写缓存
    if data is None:
        redis.setex(f"user:{user_id}", 300, "NULL")  # 空值缓存 5 分钟
    else:
        redis.setex(f"user:{user_id}", 3600, json.dumps(data))

    return data
```


# 布隆过滤器
- 不存元素本身（只存位）
- 允许误判（说存在，可能没有）
- 绝不漏判（说不存在，就一定不存在）

```text
布隆过滤器 = 一个 bit 数组 + K 个哈希函数

添加 key "hello"：
  1. hash1("hello") % M = 3  → bit[3] = 1
  2. hash2("hello") % M = 7  → bit[7] = 1
  3. hash3("hello") % M = 11 → bit[11] = 1

查询 key "world"：
  1. hash1("world") % M = 3  → bit[3]  = 1 ✅
  2. hash2("world") % M = 7  → bit[7]  = 1 ✅
  3. hash3("world") % M = 15 → bit[15] = 0 ❌
  → 全部为 1 才返回"可能存在"，有任意 0 返回"一定不存在"

误判原因：
  多个 key 的 hash 结果可能共同使某些 bit 为 1
  导致查询一个不存在的 key 时，所有位恰好都是 1
```
| 特性 | 说明 |
|------|------|
| 判断"不存在" | ✅ 100% 准确 |
| 判断"可能存在" | ⚠️ 存在误判率（可配置） |
| 空间复杂度 | O(M) bits（M = 位数组大小） |
| 时间复杂度 | O(K)（K = 哈希函数个数） |
| 是否支持删除 | ❌ 不支持（bit 被多个 key 共享） |

# 数据库和缓存如何保证一致性
| 模式 | 读流程 | 写流程 | 一致性 | 典型问题 | 适用场景 |
|------|--------|--------|--------|----------|----------|
| Cache Aside | 读缓存 → 未命中读 DB → 写缓存 | 先更新 DB → 再删缓存 | 最终一致 | 缓存击穿、脏读窗口、并发双写复杂 | 读多写少、业务可控 |
| Read / Write Through | 缓存层代理读 | 缓存层代理写（同步写 DB） | 逻辑强一致（内部同步最终一致） | 缓存层实现复杂、写性能依赖 DB | 对一致性要求较高的通用缓存 |
| Write Behind | 缓存层代理读 | 写缓存 → 异步写 DB | 弱一致（可能丢数据） | 宕机丢数据、异步队列复杂 | 写密集、可容忍少量丢失 |

## cache aside模式
```python
# 读操作
def read(key):
    data = cache.get(key)
    if data is not None:
        return data
    data = db.query(key)
    cache.set(key, data, ttl=3600)
    return data

# 写操作 — 先更新数据库，再删除缓存
def write(key, value):
    db.update(key, value)
    cache.delete(key)
    # 不要：cache.set(key, value)  ← 如果是 SET 可能读到旧缓存

# 经典错误：为什么先更新数据库再删缓存，而不是先删缓存再更新数据库
❌ 先删缓存再更新 DB 的问题：
时间线   线程A（写请求）          线程B（读请求）          数据库        缓存
─────────────────────────────────────────────────────────────────────────
t1      删除缓存 ✅
t2                              读缓存，未命中
t3                              读 DB（旧数据）          返回旧值
t4      更新 DB（新数据） ✅      
t5                              写缓存（旧数据） ✅

✅ 先更新 DB 再删缓存：
t1  线程A：更新 DB（新数据）
t2  线程B：读缓存（命中旧数据）→ 直接返回旧值
t3  线程A：删除缓存
✅ 线程B 在 t2 拿到了旧数据（脏读），但缓存最终是一致的。
```
## 延迟双删策略 
在「更新 DB」和「删缓存」的基础上，延迟一段时间后再删一次缓存，用来清除并发读请求可能回填的旧数据。
为什么"先更新 DB 再删缓存"还不够？
```text
时间线   线程A（写请求）          线程B（读请求）          DB          缓存
─────────────────────────────────────────────────────────────────────────
t1       更新 DB ✅（新值）
t2                                读缓存 → 未命中
t3                                读 DB → 拿到旧值 ❌
         （A 的事务已提交，
          但 B 的读可能在 A 提交前就发起了，
          或读的是从库，还没同步到新值）
t4       删除缓存 ✅(B 在 t4 之后才写缓存，A 删了个寂寞。)
t5                                把旧值写入缓存 ❌❌❌
```
所以需要再删一次缓存
延时N > 读请求从"查 DB"到"写完缓存"的端到端耗时

# 大key 问题
| 数据类型 | 大 Key 阈值（经验值） |
|---------|---------------------|
| String | value > 10 KB |
| Hash / Set / ZSet / List | 元素个数 > 5000 或 总大小 > 10 MB |
| 极端情况 | 单个 key 占用内存 > 100 MB |

## 大key危害
| 危害 | 说明 |
|------|------|
| 阻塞 | `DEL` 大 key 阻塞主线程（O(N) 遍历删除） |
| 带宽 | 网络传输耗时长 |
| 数据倾斜 | 集群中某节点内存远大于其他节点 |
| 过期删除 | 过期时一次性删除也阻塞 |

## 大key删除方案
```bash
# ❌ 不要直接用 DEL（会阻塞）
127.0.0.1:6379> DEL big_hash    # 可能卡几秒

# ✅ 方案 1：UNLINK（异步删除，Redis 4.0+）
127.0.0.1:6379> UNLINK big_hash  # 后台线程慢慢删

# ✅ 方案 2：分批删除（HSCAN + HDEL）
# 每次删 100 个字段
127.0.0.1:6379> HSCAN big_hash 0 COUNT 100
1) "cursor123"
2) 1) "field1"
   2) "val1"
   ...
127.0.0.1:6379> HDEL big_hash field1 field2 ... field100

# ✅ 方案 3：对于 List，用 LTRIM 分批删
127.0.0.1:6379> LTRIM big_list 0 -101  # 保留尾部，删前 100 个
```

# 热key问题
某个 key 被频繁访问（数万 QPS 甚至更高），导致单个 Redis 节点成为瓶颈。

## 热 Key 解决方案
| 方案 | 实现 | 优点 | 缺点 |
|------|------|------|------|
| 本地缓存 | 在应用侧用 Caffeine/Guava 缓存热 key | 零网络开销 | 内存占用大、一致性难保证 |
| 读写分离 | 主写从读，热 key 分散到从库 | 简单 | 可能有延迟 |
| key 拆分 | hot_key → hot_key:1, hot_key:2, ... | 分散到不同 slot/节点 | 代码改造大 |
| 使用 Redis 集群 | 分散到更多节点 | 原生命题 | 运维成本高 |
