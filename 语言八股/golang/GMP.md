# Go GMP 调度模型笔记（修正版）

## 一、基本概念

GMP 是 Go runtime 的调度模型，负责在用户态管理大量 goroutine 到少量 OS 线程的映射。

| 角色 | 全称 | 说明 |
|------|------|------|
| G | Goroutine | 协程的抽象，代表一个可执行任务。每次 `go func()` 创建一个 G 对象。G 必须绑定 P 才能被调度执行 |
| M | Machine | OS 线程的封装，上限 10000，是真正干活的"工人" |
| P | Processor | 逻辑处理器，承载本地运行队列，管理 G 与 M 的绑定关系。数量 = GOMAXPROCS，默认等于可用 CPU 核数 |

> **注意：** P 的本地运行队列长度为 **256**（环形数组），不是 P 的数量上限。P 的数量上限就是 GOMAXPROCS 的值。

---

## 二、GMP 整体执行流程

```
程序启动
→ runtime 创建 GOMAXPROCS 个 P，全部放入空闲 P 列表
→ 创建 M0（主线程），绑定 P0，跑 main goroutine
→ main 中遇到 go 调用 → 创建 G → 入队 → 调度循环开始

调度循环（每个 M 都在跑）：
  schedule()
  → findRunnable()    // 找一个能跑的 G
  → execute(G)        // 切换栈，执行 G
  → G 结束/让出/被抢占 → 回到 schedule()
```

---

## 三、findRunnable() 查找顺序

给当前 M 找一个能跑的 G，按优先级从高到低：

| 顺序 | 来源 | 方式 | 锁 |
|------|------|------|-----|
| 1 | runnext（P 上的优先槽） | 直接取 | 无锁 |
| 2 | 本地队列（LRQ） | `runqget` | 无锁 CAS |
| 3 | 全局队列（GRQ） | `globrunqget`，每 61 次调度批量取一次 | 加锁 |
| 4 | 全局队列兜底 | 同上 | 加锁 |
| 5 | 网络轮询器 | `netpoll`，捞就绪的网络 G | 非阻塞 |
| 6 | work-stealing | 随机选其他 P，从其本地队列后半段偷一半 | 无锁（原子重试） |
| 7 | 都没有 | `stopm()`：释放 P，M 进空闲池休眠 | — |

> **要点：** 全局队列优先级高于偷，但每 61 次才查一次（避免频繁抢全局锁）。日常大部分时候 M 从本地队列直接拿到 G，走不到偷那步。

---

## 四、G 创建与入队策略

```
go func() 创建 G
→ 优先放入当前 P 的本地队列
→ 本地队列满（256 个）→ 将当前 P 本地队列中一半的 G 移到全局队列
```

## 五、调度策略

### 5.1 协作式调度

G 在以下时机主动让出 CPU：

- channel 收发阻塞
- mutex 锁等待
- 网络 I/O 等待
- `runtime.Gosched()` 显式让出
- 主动调用 `time.Sleep`

让出后 M 不解绑 P，直接回 `schedule()` 找下一个 G。

### 5.2 抢占式调度（Go 1.14+ 异步抢占）

```
sysmon（runtime 启动的特殊 M，不绑 P，后台循环）：
1. 检测运行超过 10ms 的 G → 向所属 M 发送 SIGURG 信号
2. M 收到信号 → 进入 signal handler → 切换到 g0 栈 → 调用 schedule()
3. 被抢占的 G 状态重置为 runnable，放回 P 本地队列
4. M 重新走调度循环，选下一个 G 执行
```

**特点：**

- 不需要等函数调用，不需要检查标记，不需要栈里加标记
- 即使是死循环 + GOMAXPROCS=1 也能被抢占（1.14 之前不行）
- 信号是异步的，对 G 透明

### 5.3 一句话总结

> **本地优先、偷活、主动让、异步抢** —— 支撑 Go 高并发调度。

## 六、阻塞与唤醒（Hand Off）

### 6.1 用户态阻塞（channel / mutex / 网络 I/O）

```
G 阻塞 → gopark() → G 状态改为 waiting
→ M 不解绑 P，直接回 schedule() 找下一个 G
→ 条件满足后 goready() → G 回到 runnable，入队等待调度
```

**M 和 P 始终绑着，不浪费。**

### 6.2 内核态阻塞（syscall）

```
G 进入 syscall → M 随内核等待
→ sysmon 检测到 P 卡 syscall 超时 → retake() 回收 P
→ P 被分配给空闲 M 或新建 M 继续跑其他 G
→ syscall 返回 → exitsyscall()：
  拿到 P → 继续跑
  没拿到 → G 进全局队列，M 进空闲池休眠
```

### 6.3 对比

| | 用户态阻塞 | 内核态阻塞 |
|---|---|---|
| M 是否卡住 | 否 | 是 |
| P 是否解绑 | 否 | 是（延迟回收） |
| G 去哪 | waiting 状态等唤醒 | 返回后重新入队 |
| 其他 G 受影响 | 不受影响 | 不受影响（P 被别的 M 接管） |

## 七、去掉 P 会怎样

回到 Go 早期 GM 模型：

```
所有 G 放全局队列 → 所有 M 抢同一把锁（sched.lock）
→ 多核下锁竞争严重 → CPU 大部分时间花在等锁上
→ 缓存不友好（G 随机被不同 M 拿） → 性能暴跌
```

**P 的价值：**

| 有 P | 无 P |
|------|------|
| 本地队列无锁取 G | 全局锁竞争 |
| 缓存亲和（G 尽量在同一个 M 上跑） | 无亲和性 |
| 并行度可控（P 数 = GOMAXPROCS） | 无法控制 |
| work-stealing 兜底 | 无 |

## 八、P 和 M 的创建时机

### P

- **启动时一次性创建** GOMAXPROCS 个
- 数量固定，运行时不变（除非调用 `runtime.GOMAXPROCS()` 修改）
- 不销毁

### M

- **启动时：** 创建 M0，绑 P0
- **运行时动态创建：** 有活没人干 → `wakep()` → `newm()`
- **自旋 M 不足时：** sysmon 补充
- 上限 10000，实际远小于此
- 不销毁，闲了进空闲池休眠复用

---

## 九、GOMAXPROCS

| 项目 | 说明 |
|------|------|
| 是什么 | P 的数量 = 同时跑 Go 代码的最大并行度 |
| 默认值 | 可用 CPU 核数（Go 1.25+ 读 cgroup，容器里正确） |
| 怎么改 | `runtime.GOMAXPROCS(n)` |
| 设多少 | CPU bound = 核数；大量 syscall 可适当调大 |
| 上限 | 无硬编码上限（受系统资源限制） |
