# Demo 设计方案

本文档定义接口测试 demo 的整体设计：架构、端口分配、数据链路、故障注入与测试范围。

## 一、设计目标

- 用真实中间件完整复刻《软件测试基础》指南中的“取消订单”场景。
- 支持走完从业务规则、用例设计、手工验证、自动化、故障注入到测试报告的全流程。
- 可在本地 Mac 或远程服务器上运行，端口规划以服务器 `120.48.147.164` 为基准。

## 二、架构

```text
客户端（curl / Postman / pytest）
        │
        ▼
FastAPI 订单服务（:30051）
   │           │            │
   ▼           ▼            ▼
 MySQL       Redis       RabbitMQ
 (:30052)    (:30054)     (:30055)
 订单/事件     订单缓存    取消事件
 幂等记录
```

取消链路：

```text
发起取消 → 校验身份与订单状态 → MySQL 同一事务更新订单+写入 outbox 事件
→ 事务提交 → 当前请求删除 Redis 缓存并返回
                 └→ 后台任务独立轮询 outbox → RabbitMQ 发送取消事件
```

## 三、端口分配

服务器 `c` 上 30050 被 `mbti-server.js` 占用、30053 被既有
uvicorn 服务占用，因此 demo 使用以下空闲端口：

| 服务 | 端口 | 说明 |
| --- | --- | --- |
| 订单服务 API | 30051 | FastAPI，宿主 HTTP 端口 |
| MySQL | 30052 | 订单、outbox、幂等记录 |
| Redis | 30054 | 订单缓存与 MQ 故障开关 |
| RabbitMQ AMQP | 30055 | 取消事件消息 |
| RabbitMQ 管理台 | 30056 | RabbitMQ Web 管理界面，guest/guest |

## 四、数据模型

| 表 | 作用 | 关键字段 |
| --- | --- | --- |
| orders | 订单最终可信状态 | order_no、user_id、status、amount、cancelled_at |
| outbox_events | 待发送事件，与订单状态同事务写入 | event_id、order_id、status（PENDING/SENT）、attempt_count |
| idempotency_records | 幂等键与处理结果 | idempotency_key、order_id、result_status |

Redis 缓存键：`order:{order_id}`，TTL 5 秒；故障开关键：`fault:mq_publish`。

## 五、核心业务规则

1. 未登录返回 401；用户只能操作自己的订单，越权统一返回 404。
2. 待支付、待发货可取消；已发货、已完成拒绝；已取消返回已有结果。
3. 订单状态与 outbox 事件在同一事务提交，失败必须回滚。
4. 同一幂等键重复请求只产生一次副作用。
5. 并发取消只能有一次生效，最终状态必须合法。
6. 取消事件最终必须进入 RabbitMQ；Redis 旧缓存 5 秒内失效。

## 六、故障注入设计

| 故障 | 注入方式 | 预期现象 | 对应验证目标 |
| --- | --- | --- | --- |
| 数据库提交失败 | 请求头 `X-Fault-Injection: db` | 接口 500，事务回滚，订单与事件不变 | 事务一致性 |
| MQ 发送失败 | Redis 键 `fault:mq_publish=1` | 事件保持 PENDING；删除键后恢复 SENT | 消息可靠性 |
