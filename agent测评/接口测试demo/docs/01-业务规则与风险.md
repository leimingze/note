# 业务规则与风险

本文档对应学习指南第 2 章：把模糊需求变成可验证规则，并列出每条规则对应的风险与测试覆盖点。

## 业务背景

订单服务提供 `POST /api/orders/{order_id}/cancel` 取消接口。订单状态保存在 MySQL；
Redis 临时保存订单详情缓存；RabbitMQ 接收取消事件，供库存、退款等后续系统消费。
取消动作的完整链路：

```text
用户发起取消
→ 校验身份和订单状态
→ MySQL 在同一事务中更新订单并写入待发送事件
→ 事务提交
  ├→ 当前请求删除 Redis 旧缓存并返回真实结果
  └→ 后台任务把事件发送到 RabbitMQ → 消费者处理取消事件
```

## 已确认的业务规则

| 编号 | 规则 | 未遵守时的影响 |
| --- | --- | --- |
| R1 | 未登录用户不能取消或查询订单，缺少 X-User-Id 返回 401 | 匿名用户可操作他人订单 |
| R2 | 用户只能操作自己的订单；订单不存在或越权时统一返回 404，不泄露订单归属信息 | 越权读取他人订单信息 |
| R3 | 待支付、待发货允许取消；已发货、已完成拒绝取消（409）；已取消返回已有结果，不重复执行 | 已发货订单被取消导致资损 |
| R4 | 订单状态与待发送事件必须在同一事务提交，提交失败必须返回失败且订单不变 | 部分提交产生不一致数据 |
| R5 | 同一个幂等键的重复请求只产生一次取消副作用 | 重复取消产生多条事件、重复退款 |
| R6 | 并发取消或取消与状态变化竞争时，最终状态必须合法 | 状态竞争导致重复副作用或错误状态 |
| R7 | 取消成功后事件最终进入 RabbitMQ，Redis 旧缓存最迟 5 秒内失效 | 消息丢失或旧缓存误导下游 |

## 主要风险与验证方式

| 风险 | 影响 | 验证方式 |
| --- | --- | --- |
| 越权 | 用户可查看或取消他人订单 | 用例：他人订单返回 404；未登录返回 401 |
| 部分提交 | 订单已取消但事件未写入，消息永久丢失 | 用例：数据库故障注入后订单保持原状态、无事件 |
| 重复执行 | 同一次取消产生多条事件或多次退款 | 用例：幂等键重复请求、并发取消 |
| 状态竞争 | 取消与发货并发后状态矛盾 | 用例：并发取消只产生一次副作用 |
| 消息丢失 | 下游收不到取消事件，库存或退款不处理 | 用例：MQ 故障注入后事件保持待发送，恢复后最终发送 |
| 缓存旧值 | 用户看到已取消前的订单状态 | 用例：取消后缓存键被删除，查询返回新状态 |

## 未决问题（练习用）

真实项目中，评审阶段没有结论的问题要进入未决清单。本 demo 已做出以下简化假设，
学习时可以把它们当作评审问题重新提问：

- 取消待支付订单是否退款：demo 中待支付取消不触发退款语义，仅发送事件。
- 支付与取消并发时的处理：demo 以数据库条件更新保证最终状态合法，但不模拟支付流程。
- 登录态实现：demo 用 X-User-Id 请求头模拟，真实项目应使用完整鉴权体系。
