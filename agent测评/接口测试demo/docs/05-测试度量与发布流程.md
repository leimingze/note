# 测试度量与发布判断流程

本文档对照《软件测试度量与发布判断》指南，把“如何用指标证明可以发布”变成取消订单 Demo 的可执行流程。
配套工具：`scripts/metrics.py` 计算指标与门禁，`scripts/load_test.py` 采集初步性能数据。

## 流程总览

```text
定义指标口径 → 执行测试并记录状态 → 计算覆盖与执行指标
→ 补充缺陷、性能、可靠性证据 → 汇总发布看板 → 给出发布建议
→ 上线监控与复盘
```

## 第 1 步：定义指标口径

每个指标必须说清对象、分母、环境、版本、时间窗口和目标，否则数据不可比较、结论不可复核。

| 指标 | 对象 / 分母 | 环境与版本 | 时间窗口 | 目标 |
| --- | --- | --- | --- | --- |
| 需求覆盖率 | 已覆盖测试目标 ÷ G1-G7 全部测试目标 | 服务器 demo 版本 | 本版本 | G1-G7 全部有证据 |
| 测试条件覆盖率 | 已执行用例 ÷ C01-C12 | 服务器 demo 版本 | 本版本 | 核心用例全部执行 |
| 风险覆盖率 | 越权、并发、事务、消息、缓存等风险证据 | 服务器 demo 版本 | 本版本 | 高风险目标均有用例承接 |
| 执行率 | 已执行用例数 ÷ 计划执行用例数 | 服务器 demo 版本 | 本版本 | 全部执行 |
| 通过率 | 通过用例数 ÷ 已执行用例数 | 服务器 demo 版本 | 本版本 | 核心用例 100% 通过 |
| 阻塞率 | 阻塞用例数 ÷ 计划执行用例数 | 服务器 demo 版本 | 本版本 | 0 |
| 缺陷严重程度分布 | 各严重程度缺陷数量 | 服务器 demo 版本 | 本版本 | 无未关闭阻断/严重缺陷 |
| 性能（A2） | 200 RPS 下 P95 与错误率 | 压测环境需标注 | 压测窗口 | P95 ≤ 500 ms，错误率 < 0.1% |
| 线上质量 | 取消失败率、重复副作用、MQ 积压 | 灰度环境 | 灰度窗口 | 失败率连续 5 分钟 > 1% 回滚 |

## 第 2 步：执行测试并记录状态

一条用例在一个版本和环境中只能有四种状态之一：通过、失败、阻塞、未执行。
“已执行”只包含得到通过或失败结论的用例；阻塞和未执行不能混入通过率分母。

记录方式：把用例结果写入 JSON，格式见 `scripts/test_results.example.json`。
每条用例需要 id、名称、结果、是否核心、对应测试目标，并附证据：

- 接口响应：状态码与响应体
- 数据库证据：订单状态、outbox 事件、幂等记录
- Redis 证据：缓存键是否失效
- MQ 证据：事件是否进入队列

## 第 3 步：计算执行与覆盖指标

```bash
cd /data/leimingze/接口测试demo
.venv/bin/python scripts/metrics.py scripts/test_results.example.json
```

脚本输出：

```text
执行率 = 已执行用例数 ÷ 计划执行用例数
通过率 = 通过用例数 ÷ 已执行用例数
阻塞率 = 阻塞用例数 ÷ 计划执行用例数
需求覆盖率 = 已覆盖测试目标数 ÷ 计划测试目标数
```

结果必须分层查看：

- 核心与非核心分开，避免低风险通过掩盖核心失败。
- 按接口、集成、端到端分开，避免层级相互替代。
- 按版本和环境记录，代码变更后旧结果不能代表新版本。

## 第 4 步：补充缺陷、性能与可靠性证据

### 缺陷指标

| 指标 | Demo 中的记录方式 |
| --- | --- |
| 严重程度分布 | 阻断、严重、一般、轻微各多少 |
| 缺陷发现趋势 | 按天记录新增与关闭数量 |
| 重开率 | 已验证修复后又打开的缺陷 ÷ 已验证修复缺陷 |
| 缺陷逃逸率 | 上线后发现的有效缺陷 ÷ 测试期与上线后发现的有效缺陷 |

缺陷数量不是质量结论；复杂高风险测试发现更多缺陷是正常的。不能把“QA 发现多少缺陷”当绩效指标。

### 性能采样与 A2 缺口

```bash
# 只读压测：以 10 个并发线程持续请求 20 秒
.venv/bin/python scripts/load_test.py \
  --url http://127.0.0.1:30051/api/orders/90 \
  --header "X-User-Id: 10001" \
  --target-rps 200 --duration 20 --concurrency 10
```

当前脚本会在固定并发下尽可能多地发送请求，`--target-rps` 尚未参与限速。因此输出可以用于观察实际
吞吐、P95、P99 和错误率，不能单独作为“固定 200 RPS”达标证据。完善负载控制前，A2 必须保持未验证。

报告必须同时给出 RPS、P95、P99、错误率和资源情况，并标注预热方式、持续时间、并发模型、数据量与环境配置。
只说“P95 达标”而没有负载和错误率，结论不可复核。

### 可靠性证据

已有的 pytest 用例已经覆盖：事务回滚（C09）、MQ 故障恢复（C10）、事件进入队列（C12）。
这些证据直接进入发布看板的可靠性门禁。

## 第 5 步：发布看板与门禁

| 门禁 | 问题 | 通过条件（Demo） |
| --- | --- | --- |
| 覆盖 | 高风险目标是否都有证据 | G1-G7 均有证据，G7 由性能结果承接 |
| 执行 | 核心范围是否完成 | C01-C12 全部执行，核心用例全部通过 |
| 缺陷 | 剩余问题是否可接受 | 无未关闭的阻断或严重缺陷 |
| 性能 | 目标负载下是否达标 | 200 RPS 下 P95 ≤ 500 ms、错误率 < 0.1% |
| 可靠性 | 故障和恢复路径是否验证 | C09、C10、C12 全部通过 |
| 可运营性 | 上线后能否发现和止损 | 监控、灰度和回滚条件已准备好 |

`metrics.py` 会按这份门禁输出逐项通过与不通过，并给出不通过原因。
任一硬门禁不通过，发布建议不能写“通过”。

## 第 6 步：发布建议结构

QA 报告必须区分四件事：

- **已经证明**：在哪个版本、哪个环境、哪个范围内得到了什么结果。
- **尚未验证**：哪些条件因为环境、时间或范围没有测试。
- **已知风险**：遗留缺陷和限制影响谁、概率多大、损失多大。
- **发布建议**：通过、带风险通过或不通过，以及对应的灰度、监控和回滚动作。

示例结论：

```text
已经证明：服务器环境 12 条用例全部通过，事务、并发、MQ 故障恢复有证据。
尚未验证：性能 A2 未执行压测；G7 非功能目标暂无数据。
已知风险：性能未验证，高负载下可能出现长尾延迟。
发布建议：不通过；先完成 200 RPS 压测，再重新评估。
```

## 第 7 步：上线监控与复盘

上线后按业务结果、技术表现、数据一致性、恢复能力四层监控：

| 层次 | Demo 指标 | 触发动作 |
| --- | --- | --- |
| 业务结果 | 合法订单取消成功率、重复取消副作用数 | 下降时暂停灰度并检查业务状态 |
| 技术表现 | 接口 P95、错误码、事务失败、MQ 积压 | 超阈值时告警、扩容或回滚 |
| 数据一致性 | Redis 旧值、待发送事件、重复消费 | 触发补偿、重试和数据核对 |
| 恢复能力 | 告警发现时间、MTTR、回滚耗时 | 改进监控和预案 |

灰度期间取消失败率连续 5 分钟超过 1% 时回滚，不能等根因完全查清再止损。
线上问题复盘时只问一个问题：原有指标为什么没有提前暴露它？然后修正测试或监控设计。

## 常见误用对照

| 误用 | 正确做法 |
| --- | --- |
| 只看总通过率 | 分层看核心、接口、集成与专项结果 |
| 用缺陷数量评价 QA | 缺陷用于暴露风险，不用于个人绩效 |
| 把代码覆盖率当质量目标 | 代码覆盖率只说明“执行过”，不代表断言正确 |
| 只报告平均延迟 | 必须给 P95/P99 和错误率 |
| 改变分母或窗口后直接比较 | 指标必须注明对象、分母、环境、版本和时间窗口 |
| 达到数字门槛就机械发布 | 还要审查未测范围和业务风险 |
| 为了让看板变绿删失败用例 | 指标异常时定位原因，不修改口径制造成功 |

## 对照三遍法

- 第一遍：读懂本文档每个指标的口径和为什么单独使用会误导。
- 第二遍：用 `metrics.py` 对 12 条用例计算执行率、通过率、阻塞率和覆盖率。
- 第三遍：先完善 `load_test.py` 的目标 RPS 控制，再补充性能证据，形成完整发布看板并给出建议。
