# 取消订单 Demo：源码与测试学习指南

本文用于按真实执行顺序学习取消订单 Demo。第一部分先回答“请求进入系统后，代码如何协作”；
第二部分再回答“测试人员应验证什么、需要什么证据、怎样形成发布结论”。

## 1. 学习目标

完成本文后，应能独立说明：

- 一次取消请求经过哪些模块，以及 MySQL、Redis、RabbitMQ 分别负责什么。
- 订单状态、Outbox 事件和幂等记录为什么要这样设计。
- 为什么接口返回 `200` 仍不足以证明取消业务成功。
- 如何从业务规则和源码分支推导用例、断言、故障测试与发布门禁。

推荐先阅读源码部分，不要一开始就背测试用例；理解系统如何失败之后，用例才有意义。

# 第一部分：沿请求链路阅读源码

## 2. 先建立系统地图

被测接口是 `POST /api/orders/{order_id}/cancel`。API 是系统对外提供的调用入口，本项目使用
FastAPI 接收 HTTP 请求，并连接三个真实中间件：

```text
客户端（curl / pytest）
          |
          v
FastAPI 订单服务 :30051
   |          |            |
   v          v            v
MySQL       Redis       RabbitMQ
:30052      :30054       :30055
最终状态      临时缓存       取消事件
事务数据      故障开关       下游通知
```

关键原则：MySQL 是订单状态的最终可信来源；Redis 只是可失效的副本；RabbitMQ 用来异步通知下游。

## 3. 目录与职责

| 路径 | 阅读时要回答的问题 |
| --- | --- |
| `docker-compose.yml` | 系统依赖哪些外部服务，端口和数据卷如何配置 |
| `app/config.py` | 数据库、缓存和消息队列连接地址从哪里来 |
| `app/main.py` | 服务启动和关闭时初始化、释放哪些资源 |
| `app/api/orders.py` | HTTP 请求怎样校验、怎样转换成业务调用和响应 |
| `app/services/order_service.py` | 取消订单的核心规则和事务怎样实现 |
| `app/models.py` | 三张表保存什么，以及字段如何表达业务状态 |
| `app/cache.py` | 订单缓存怎样读取、写入和失效 |
| `app/mq.py` | 待发送事件怎样最终进入 RabbitMQ |
| `tests/` | 业务规则怎样变成可重复执行的证据 |
| `scripts/` | 怎样手工验证、压测和汇总发布指标 |

## 4. 服务怎样启动

入口命令是：

```bash
uvicorn app.main:app --reload --port 30051
```

`app.main:app` 表示加载 `app/main.py` 中名为 `app` 的 FastAPI 对象。应用生命周期依次执行：

1. `load_settings()` 读取环境变量或本地默认连接地址。
2. `init_db()` 创建 SQLAlchemy 引擎和数据库会话工厂。
3. `Base.metadata.create_all()` 创建尚不存在的数据表。
4. `init_cache()` 创建 Redis 客户端。
5. 创建并启动 `OutboxWorker` 后台线程。
6. 服务关闭时停止后台线程并关闭 Redis 连接。

数据库会话和 Redis 客户端通过 FastAPI 的依赖注入传给路由函数。依赖注入的意思是：路由声明自己
需要什么，框架负责在请求到来时提供，不由业务函数临时创建连接。

## 5. 查询订单链路

先读 `GET /api/orders/{order_id}`，因为它比取消链路简单：

1. `_get_current_user()` 读取 `X-User-Id`；缺失时立即返回 `401`。
2. `get_cached_order()` 尝试读取 `order:{order_id}`。
3. 缓存命中且 `user_id` 属于当前用户时，直接返回缓存内容。
4. 未命中时，`get_order_for_user()` 同时按订单 ID 和用户归属查 MySQL。
5. 找不到或不属于当前用户时统一返回 `404`，避免泄露他人订单是否存在。
6. 查询成功后，用 `OrderResponse` 约束响应字段，再写入 5 秒缓存。

这里能看到两个测试点：缓存命中也必须校验归属；Redis 出故障时，读取应回到 MySQL，而不是把缓存
当作最终数据源。

## 6. 取消请求怎样进入核心服务

`app/api/orders.py` 中的 `cancel_order()` 只负责 HTTP 层：

- 读取路径参数 `order_id`。
- 读取 `X-User-Id`、可选幂等键和测试专用故障注入头。
- 调用 `app/services/order_service.py` 中的同名业务函数。
- 把业务异常映射为 `404`、`409` 或 `500`，成功结果映射为 `CancelResponse`。

这种分层让业务逻辑不依赖 HTTP 状态码，也能被其他入口复用。

## 7. 核心取消事务

事务是一组必须整体成功或整体失败的数据库操作。核心服务按以下顺序执行：

1. 如果请求提供幂等键，先查询是否已有处理记录；有则返回已有结果。
2. 读取订单并校验归属；不存在或越权都抛出 `OrderNotFoundError`。
3. 已取消订单直接返回，不产生新副作用。
4. 只有 `PENDING_PAYMENT` 和 `PENDING_SHIPMENT` 可以继续取消。
5. `_try_apply_cancellation()` 使用带状态条件的 SQL 更新订单。
6. 更新成功后，新增一条 `PENDING` 状态的 Outbox 事件。
7. 提供幂等键时，同时新增一条幂等记录。
8. 数据库故障注入开启时执行回滚并返回 `500`；否则统一提交事务。
9. 提交成功后删除 Redis 订单缓存，再向客户端返回成功。

条件更新相当于：只有数据库中的状态仍然允许取消时才修改。多个请求并发到达时，只有一个请求能更新
一行数据，因此只应产生一次取消副作用。

## 8. 三张表为什么缺一不可

| 表 | 保存内容 | 解决的问题 |
| --- | --- | --- |
| `orders` | 订单归属、状态、金额、取消时间 | 当前订单究竟是什么状态 |
| `outbox_events` | 待发送事件、发送状态、尝试次数 | RabbitMQ 暂时不可用时不丢通知 |
| `idempotency_records` | 幂等键、订单、已有结果 | 客户端重试时不重复取消 |

幂等是“同一个业务请求执行多次，最终副作用仍只发生一次”。Outbox 是“先把待发通知与业务状态写入
同一个数据库事务，再由后台任务可靠发送”。

订单更新与 Outbox 事件在同一事务内提交，避免两种部分成功：

- 订单已取消，但没有事件，下游永远不知道。
- 事件已发出，但订单取消失败，下游拿到错误通知。

## 9. Outbox 后台发送链路

`OutboxWorker` 每秒轮询一次，每批最多读取 10 条 `PENDING` 事件：

1. 先检查 Redis 中的 `fault:mq_publish` 故障开关。
2. 对每条事件调用 `publish_event()`。
3. 发布时声明交换机、队列和路由关系，并发送持久化消息。
4. RabbitMQ 确认发布后，把数据库事件改为 `SENT`。
5. 发布失败时增加 `attempt_count`，保留 `PENDING`，下一轮继续尝试。

这保证的是“最终会重试”，不是“全世界只收到一次”。如果消息已经发出，但数据库更新 `SENT` 失败，
后台任务可能再次发送；真实下游消费者仍需按 `event_id` 做幂等处理。

## 10. 缓存一致性

查询成功会写入 Redis，取消事务提交后会立即删除缓存。删除失败时，代码记录错误，旧缓存最多保留到
5 秒 TTL 到期。TTL 是缓存的自动过期时间。

因此测试不能只断言 MySQL 已更新，还要确认：取消前能生成缓存、取消后缓存键被删除、再次查询返回
`CANCELLED`。

## 11. 一次正常取消的完整源码轨迹

```text
POST /api/orders/1/cancel
  -> app/api/orders.py：解析请求与用户
  -> app/services/order_service.py：校验规则
  -> 条件更新 orders
  -> 新增 outbox_events
  -> 可选新增 idempotency_records
  -> MySQL commit
     |-> app/cache.py：删除 order:1 -> 返回 200
     `-> app/mq.py：后台读取 PENDING 事件
         -> RabbitMQ 确认发布
         -> outbox_events.status = SENT
```

源码部分的检查标准：不看文档，能够沿上述轨迹指出每一步对应的文件、数据变化和失败结果。

# 第二部分：从测试角度重新理解系统

## 12. 从“返回值”扩展到“业务证据”

正常取消至少需要五层证据：

| 层次 | 要验证什么 | 示例证据 |
| --- | --- | --- |
| HTTP | 契约是否正确 | 状态码、错误码、响应字段 |
| 业务状态 | 订单是否真的改变 | `orders.status=CANCELLED` |
| 数据副作用 | 是否只写了应写的数据 | 一条 Outbox 事件、一条可选幂等记录 |
| 系统一致性 | 缓存和消息是否跟上 | Redis 键删除、RabbitMQ 收到消息 |
| 故障恢复 | 依赖失败后能否保持正确 | 事务回滚、事件保留并恢复发送 |

如果只断言 `200`，就无法发现“状态未改”“事件丢失”“重复事件”或“缓存仍是旧值”。

## 13. 用例怎样从规则产生

| 规则或风险 | 代表用例 | 核心断言 |
| --- | --- | --- |
| 待支付、待发货允许取消 | C01、C02 | `200`、状态改变、事件唯一 |
| 未登录和越权必须拒绝 | C03、C04 | `401/404`、订单与事件不变 |
| 已发货拒绝、已取消不重复 | C05、C06 | `409` 或已有结果、无新事件 |
| 客户端可能重试 | C07 | 同一幂等键只有一次副作用 |
| 多个请求可能同时到达 | C08 | 只有一个成功生效、事件唯一 |
| 数据库提交可能失败 | C09 | `500`、订单回滚、无事件 |
| RabbitMQ 可能暂时中断 | C10 | 订单已取消、事件先 `PENDING` 后 `SENT` |
| 缓存可能保存旧状态 | C11 | 取消后缓存删除，再查为新状态 |
| 下游必须收到通知 | C12 | 事件 `SENT`，队列消息内容正确 |

拒绝类用例不仅要验证错误响应，还要验证“什么都没有被错误修改”。

## 14. pytest 测试结构

`tests/conftest.py` 中的 fixture 是 pytest 提供给用例的可复用测试准备组件：

- `db_session`：每条用例前清空三张业务表，隔离测试数据。
- `redis_client`：清理订单缓存和 MQ 故障开关。
- `create_order`：按用例需要创建唯一订单。
- `api`：封装真实 HTTP 查询与取消请求。
- `fresh_db`：创建新数据库会话，读取 API 已提交的最新状态。
- `wait_until`：轮询等待后台异步结果，超时就明确失败。

每条测试遵循“准备数据 → 发起操作 → 检查响应 → 检查副作用”。例如正常取消同时检查响应、订单状态和
事件数量；数据库故障则检查 `500`、原状态和零事件。

`fresh_db` 很重要：复用旧数据库会话可能读到会话缓存或旧事务快照，造成测试看到过期数据。

## 15. 四类最值得精读的测试

1. `test_cancel_pending_payment_success`：学习一次成功不只断言响应。
2. `test_concurrent_cancel_single_effect`：学习用并发请求验证条件更新。
3. `test_cancel_db_fault_rolls_back`：学习通过故障注入验证事务原子性。
4. `test_mq_fault_keeps_event_pending_and_recovers`：学习验证异步系统的中间状态与最终状态。

异步测试不应固定写“睡 3 秒后应该成功”；这里使用 `wait_until` 持续观察条件，并在 15 秒内未满足时失败，
既允许正常调度波动，也不会把真实故障吞掉。

## 16. 从测试结果到发布判断

`scripts/metrics.py` 读取结果 JSON，并计算：

```text
执行率 = （通过数 + 失败数）/ 计划用例数
通过率 = 通过数 / 已执行用例数
阻塞率 = 阻塞数 / 计划用例数
覆盖率 = 已有执行证据的测试目标数 / 全部目标数
```

脚本进一步检查覆盖、执行、缺陷、性能、可靠性和可运营性六项门禁。发布报告必须区分已经证明、
尚未验证、已知风险和发布建议。

当前 `scripts/load_test.py` 是固定并发下尽可能多地发送请求；虽然接受 `--target-rps` 参数，但该参数尚未
参与限速。因此它可以观察吞吐、延迟和错误率，不能单独证明“严格在 200 RPS 负载模型下达标”。在把
性能 A2 判为通过前，需要先完善负载控制并记录环境与资源证据。

## 17. 读源码后应补充追问的风险

以下不是已经证实的缺陷，而是从实现中发现、尚需新增测试确认的边界：

- 幂等记录查询早于用户归属校验：他人拿到相同订单 ID 和幂等键时是否仍严格返回 `404`。
- 幂等键在表中全局唯一：两个订单复用同一键时，接口行为是否符合契约。
- Outbox 可能重复投递：下游是否按 `event_id` 去重。
- 多个服务实例同时轮询 Outbox 时，是否可能并发发送同一事件。
- Redis 删除失败时，5 秒内的旧值是否属于业务可接受风险。

测试设计的价值不是机械覆盖代码行，而是从实现和依赖关系中找出可能破坏业务结果的路径。

## 18. 建议实操顺序

1. 阅读 `app/main.py`、`app/api/orders.py` 和 `app/services/order_service.py`，手画一次请求链路。
2. 运行正常取消，分别查看 HTTP、三张 MySQL 表、Redis 键和 RabbitMQ 消息。
3. 精读 C01、C08、C09、C10 对应测试，再单独执行它们。
4. 运行全部 12 条用例，把结果填入 `scripts/test_results.example.json` 的副本。
5. 运行 `scripts/metrics.py`，对照六项门禁给出发布建议。
6. 从第 17 节选择一个未验证风险，先写预期，再补一条测试。
