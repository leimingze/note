# 软件测试基础：一个功能从需求到上线

软件测试不是“开发完成后执行一遍用例”，而是一套贯穿需求、开发、发布和线上运行的质量保障活动。本文面向没有测试经验的读者，用“取消订单”功能讲清一个版本的完整流程。

本文中的 **QA**（Quality Assurance，质量保障）既指测试岗位，也指该岗位承担的质量工作。阅读时始终沿着下面的顺序理解，不需要先背术语：

```text
理解业务背景
→ 需求评审
→ 分析风险与范围
→ 设计用例
→ 准备环境与自动化
→ 提测、执行、缺陷与回归
→ 发布、上线与复盘
```

先读懂案例中每一步为什么存在，再用小型练习项目复现，最后把同一套方法迁移到真实项目。

## 1. 需求来了：用户要取消订单

某电商平台的用户下单后，只能联系客服取消订单，处理慢且容易与仓库发货产生冲突。产品提出需求：

> 用户可以在订单详情页取消自己的待支付或待发货订单。

系统提供取消接口 `POST /api/orders/{order_id}/cancel`，其中 `order_id` 是订单编号。该功能涉及订单服务、MySQL 数据库、Redis 缓存和 RabbitMQ 消息队列。MySQL 保存最终可信的订单状态；Redis 临时保存订单详情以加快读取；RabbitMQ 把取消事件发送给库存、退款等后续系统。

项目中的初始链路是：

```text
用户点击取消
→ 订单服务校验身份和订单状态
→ MySQL 更新订单并写入待发送事件
→ 接口返回真实结果
→ 后台任务发送 RabbitMQ 消息
→ 库存或退款系统消费消息并完成处理
→ Redis 缓存失效，后续读取回到新状态
```

“待发送事件”是与订单状态一起写入 MySQL 的一条任务记录，后台任务稍后再把它发送到 RabbitMQ。这里的**事务**表示订单状态和事件记录要么一起成功，要么一起回滚，从而避免订单已经取消，但取消消息因发送失败而永久丢失。

原始需求还不能直接拿来写用例：谁可以取消、哪些状态允许取消、并发时以哪个操作为准、依赖失败后怎样处理，都没有讲清楚。QA 的第一项工作是推动这些问题形成明确结论，而不是自行猜测预期。

## 2. 需求评审：先把模糊需求变成可验证规则

### 2.1 QA 用什么框架检查需求

为方便检查，本文把常见评审问题整理为五个方面。这是一份实用检查清单，不是行业标准中的固定分类，也不要求每次机械地逐条提问。

| 评审层次 | 核心评审内容 |
| --- | --- |
| 业务与范围 | 为什么做？谁来用？这次做到哪里，哪些不做？ |
| 功能行为 | 什么情况下能做？正常怎么走？不能做或失败时怎么办？最后变成什么状态？ |
| 系统与数据 | 数据存在哪里？会调用谁？重复、并发或某个服务失败后，数据会不会乱？ |
| 质量属性 | 要多快、多稳定、多安全？出了问题能不能通过日志和指标找到？ |
| 验收与发布 | 满足什么条件才算通过？上线后看什么指标？什么情况必须回滚？ |

检查顺序是从“为什么做”逐步走到“怎样证明可以上线”，后面的问题依赖前面的答案。

### 2.2 评审问题从哪里来

需求表述来自原始需求、原型或技术材料，2.1 的五层框架提供检查角度。将两者逐项对照后，需求没有说清楚的地方就成为评审问题。

| 需求表述 | 对应评审层次 | 已明确内容 | 待明确内容 | 评审问题 |
| --- | --- | --- | --- | --- |
| 用户 | 业务与范围 | 操作者是用户 | 是否必须登录，哪些用户能操作 | 未登录能否取消？客服能否代取消？ |
| 自己的订单 | 功能行为、质量属性 | 不能随便取消别人的订单 | 怎样判断归属，越权时返回什么 | 根据哪个用户标识判断？会不会泄露他人订单信息？ |
| 待支付或待发货 | 功能行为 | 这两种状态可能允许取消 | 其他状态和状态同时变化怎么办 | 已发货、已取消怎么办？取消和发货同时发生时听谁的？ |
| 取消 | 功能行为、系统与数据 | 系统要执行取消动作 | 什么结果才算成功，会产生哪些后续动作 | 状态改成什么？何时提示成功？是否释放库存和退款？ |
| 原需求未说明失败处理 | 系统与数据 | 没有信息 | MySQL、Redis 或 MQ（消息队列）失败后的结果 | 数据库失败能否报成功？消息失败会不会丢？ |
| 原需求未说明质量指标 | 质量属性、验收与发布 | 没有信息 | 速度、一致时间、监控和发布标准 | 多快算合格？缓存多久一致？什么情况阻断发布？ |

已经明确的内容不必重复追问；如果原型、接口草案或技术方案引入新的依赖，再用同样的方法检查新增风险。

### 2.3 谁回答问题，怎样形成结论

QA 负责发现没说清楚的地方并推动结论形成，但不替其他角色拍板。每个评审层次都有主要决策者，也有不同的评审产出。

| 评审层次 | 主要决策者 | 需要形成的结论 | QA 的职责 |
| --- | --- | --- | --- |
| 业务与范围 | 产品、业务方 | 为什么做、谁能使用、本次做什么和不做什么 | 检查目标和范围是否明确，指出遗漏或冲突 |
| 功能行为 | 产品、开发、QA | 前置条件、主流程、分支、异常、输出和状态变化 | 补齐场景，确认每种条件下都有明确预期 |
| 系统与数据 | 开发、架构、DBA（数据库管理员） | 系统边界、接口契约、事实来源、事务、一致性和故障处理方案 | 检查过程和结果能否观察，失败后是否会产生错误数据 |
| 质量属性 | 产品、开发、运维、安全、QA | 性能、可靠性、安全、兼容性和可观测性目标 | 推动“快、稳定、安全”等描述变成可测量指标 |
| 验收与发布 | 产品、开发、QA、运维 | 验收条件、准入和退出标准、灰度指标及回滚条件 | 检查门禁是否有证据支撑，说明遗留风险 |

这里的**可观测性**是指系统能否通过响应、日志、指标和消息轨迹暴露内部状态，让问题可以被发现和定位。

例如 QA 问“什么时候算取消成功”，产品先确定用户应该看到什么结果，开发和架构再确定如何通过数据库事务和消息机制实现，QA 最后检查结果、过程和失败路径是否都能被验证。

没有结论的问题进入未决清单，记录责任人和截止时间；阻塞核心流程的问题未解决，不能开始用例设计。这种不运行程序、通过评审提前发现问题的活动属于**静态测试**。

需求评审的交付物不是一堆问题，而是一组经过相关角色确认、可以直接验证的规则。本项目最终确认：

- 登录用户只能取消自己的订单，越权时不能泄露订单信息。
- 待支付、待发货允许取消；已发货、已完成拒绝；已取消返回已有结果；已支付订单沿用现有退款流程。
- 重复或并发请求只能产生一次取消副作用；取消与发货并发后的最终状态必须合法。
- 订单状态真正提交后才能返回成功；提交失败必须明确失败；已经受理的库存和退款任务最终必须完成。
- Redis 旧缓存 5 秒内失效，取消事件 10 秒内进入 MQ；200 RPS 下 P95 不超过 500 ms、服务端错误率低于 0.1%。
- 响应、日志和消息可以关联同一次请求；核心用例必须全部通过，灰度取消失败率连续 5 分钟超过 1% 时回滚。

这里的**幂等**是指同一操作被重复执行时，只产生一次业务副作用；幂等键用于识别“这是同一次请求的重试”。`RPS` 表示系统每秒处理的请求数，`P95` 表示 95% 的请求响应时间不超过该值。

这些结论要写回产品需求文档（PRD）、验收标准或评审纪要并标明版本。需求变化时，先重新评审影响范围，再同步更新规则、用例和发布标准。

## 3. 测试设计：先写对一条，再补全一组

本章只解决一个问题：怎样把第 2 章确认的规则变成可以执行、可以判断结果的测试。学习顺序是先完成一条用例，再扩展为完整测试集。

### 3.1 从一条规则得到一条测试用例

先选择一条规则：

> 登录用户取消自己的待支付订单时，订单状态和待发送事件必须在同一个 MySQL 事务中提交；提交成功后接口才能返回成功。

这条规则还不能直接执行。QA 需要依次补齐测试目标、执行范围、具体数据、操作、预期结果和证据。

| 设计内容 | 本例答案 | 作用 |
| --- | --- | --- |
| 测试目标 | 证明正常取消不会出现部分提交或虚假成功 | 说明为什么要有这条用例 |
| 测试层级 | 组件集成测试 | 需要验证订单服务与真实 MySQL 的协作 |
| 前置条件 | 已登录的订单本人；一笔待支付订单 | 确定执行前的系统状态 |
| 输入与操作 | 使用唯一幂等键调用取消接口 | 说明怎样触发被测行为 |
| 预期结果 | 接口成功；订单变为已取消；只写入一条待发送事件 | 规定什么结果才算正确 |
| 检查证据 | 接口响应、订单记录、待发送事件记录和关联日志 | 让测试结论可以复核 |
| 清理方式 | 清理本次创建的测试订单和事件记录 | 保证用例可以重复执行且不影响其他数据 |

测试层级说明一次测试覆盖多大范围。ISTQB 基础级大纲定义了五个层级：

| 测试层级 | 测试对象 | 本项目中的位置 |
| --- | --- | --- |
| 组件测试 | 单个函数、类或组件 | 状态判断、条件更新和幂等逻辑 |
| 组件集成测试 | 同一系统内多个组件的交互 | 订单服务与 MySQL、Redis、RabbitMQ |
| 系统测试 | 部署完成的整个系统 | 从页面或公开 API 验证完整取消功能 |
| 系统集成测试 | 当前系统与其他系统的交互 | 订单系统与库存、退款系统 |
| 验收测试 | 完整产品与业务验收标准 | 产品、业务和 QA 确认是否满足交付条件 |

选择层级时，以“这条用例必须验证哪些组件”为准。只验证状态判断时放在组件测试；需要检查真实数据库事务时放在组件集成测试；需要确认退款系统收到并处理消息时放在系统集成测试。

接口测试不是固定层级，API 只是执行入口。只验证一个服务时，它可以属于组件测试；验证多个系统协作时，它也可以属于系统集成测试。契约测试用于检查请求、响应或消息格式。性能、安全和可靠性描述测试关注的问题，也不是测试层级。

### 3.2 从一条用例扩展为完整测试集

一条正常用例只能证明一种情况。QA 还要使用标准测试技术覆盖其他业务规则，再根据技术方案补充并发、故障和跨系统风险。

黑盒测试不依赖内部代码实现，而是根据输入、输出和业务规则设计用例。ISTQB 基础级大纲中的四种黑盒测试技术分别解决不同问题：

| 测试技术 | 解决的问题 | 在本需求中的用法 |
| --- | --- | --- |
| 等价类划分 | 输入很多，不可能全部测试 | 将订单编号分为本人订单、他人订单、不存在和格式错误等类别，每类选择代表数据 |
| 边界值分析 | 数值或时间边界附近容易出错 | 若付款不超过 30 分钟可以取消，就测试 29 分 59 秒、30 分钟和 30 分 01 秒 |
| 决策表测试 | 多个条件共同决定结果 | 组合登录状态、订单归属和订单状态 |
| 状态迁移测试 | 对象会在多个状态之间变化 | 检查允许、禁止和重复执行的状态变化 |

本需求先用决策表展开核心业务规则。表中的 `-` 表示该条件不会改变本行结果。

| 是否登录 | 是否本人订单 | 当前状态 | 预期结果 | 数据副作用 |
| --- | --- | --- | --- | --- |
| 否 | - | 任意状态 | 拒绝请求 | 无变化，不泄露订单信息 |
| 是 | 否 | 任意状态 | 拒绝请求 | 无变化，不泄露订单信息 |
| 是 | 是 | 待支付 | 取消成功 | 提交订单状态和事件，无退款 |
| 是 | 是 | 待发货 | 取消成功 | 提交订单状态和事件，触发退款 |
| 是 | 是 | 已发货、已完成 | 拒绝取消 | 无变化，无取消事件 |
| 是 | 是 | 已取消 | 返回已有结果 | 不重复更新，不重复产生事件 |

决策表和状态迁移覆盖业务规则，但不能自动发现事务、消息、并发和性能风险。这些用例要从技术方案和风险分析中补充。最终测试集按验证目标组织：

| 验证目标 | 代表性测试 | 主要层级或类型 | 关键证据 |
| --- | --- | --- | --- |
| 身份与状态规则 | 未登录、他人订单、各种订单状态、重复取消 | 组件测试、组件集成测试 | 响应、订单记录、事件数量 |
| 事务一致性 | 正常提交、MySQL 回滚、提交结果未知后重试 | 组件集成测试 | 响应、订单记录、待发送事件 |
| 消息与缓存 | MQ 中断恢复、重复投递、缓存按时失效 | 组件集成测试 | 待发送记录、MQ、消费记录、缓存值 |
| 并发正确性 | 两个取消并发、取消与发货并发 | 组件集成、系统集成测试 | 最终状态、成功次数、事件数量 |
| 跨系统流程 | 取消后释放库存或完成退款 | 系统集成测试 | 库存或退款状态、关联日志、消息轨迹 |
| 完整用户流程 | 从页面取消到最终结果可见 | 系统测试、验收测试 | 页面、接口、数据库和日志 |
| 非功能风险 | 200 RPS 性能、越权攻击、依赖故障恢复 | 性能、安全、可靠性测试 | 性能报告、安全结果和恢复记录 |

完成本章后，应能解释每项测试为什么存在、在哪个层级执行、需要什么数据、怎样操作、预期结果是什么，以及用什么证据证明结果。第 4 章再准备实际环境、数据和自动化代码。

## 4. 开发阶段：把设计变成可执行测试

开发编码时，QA 同步准备测试环境、账号、不同状态的订单、故障注入方式和数据清理方案，并确认响应、日志、数据库和消息都可以被检查。故障注入是主动制造一次可控失败，例如暂时停止消息队列，用来验证系统能否正确报错和恢复。

| 准备内容 | 工具或方式 | 用途与边界 |
| --- | --- | --- |
| 手工探索接口 | Postman | 发送请求并观察响应，适合快速确认接口行为 |
| 接口自动化 | `requests + pytest` 或 REST Assured + TestNG | 把稳定且需要反复执行的接口用例写成自动化测试 |
| 浏览器流程 | Selenium | 验证少量关键页面流程，业务组合主要放在更稳定的接口层 |
| 客户端请求排查 | Charles | 查看客户端实际发送的地址、请求头和请求体，不能替代服务端日志和内部数据检查 |
| 性能测试 | JMeter | 逐步增加负载，观察 P95、错误率、吞吐量（单位时间完成的请求数）和资源使用 |
| 集成环境 | 真实 MySQL、Redis 和 RabbitMQ | 验证真实数据流和故障路径；不可控外部服务可用可配置的替代服务，但不能模拟成功掩盖故障 |

自动化优先覆盖稳定、重复执行频繁、判断明确的场景。一次性探索、频繁变化的页面和主观体验问题不必强行自动化。

## 5. 提测准入：先确认版本值得测

开发提交测试版本后，QA 先检查：版本与变更清单明确；开发自测和必要单元测试通过；环境部署成功；测试数据、日志、MQ 和数据库可用；已知问题已说明。随后执行**冒烟测试**，也就是用最少的用例确认版本和环境具备继续测试的基本条件：

```text
本人待发货订单能取消
已发货订单不能取消
订单详情能读到取消后的状态
```

冒烟失败说明核心链路或环境不可用，应记录证据并退回，不进入全面测试。准入是节省无效执行成本，不是形式门槛。

## 6. 测试执行：从现象到缺陷闭环

执行顺序通常是冒烟 → 核心功能 → 异常和并发 → 跨系统一致性 → 探索式测试 → 专项测试。探索式测试是在理解系统的同时设计和执行测试，用于发现脚本化用例未覆盖的问题。每次执行都要记录版本、环境、数据、实际结果和证据。

发现“接口返回成功但订单仍是待发货”时，先确认需求和环境，再提交缺陷：标题、前置条件、步骤、预期与实际结果、复现率、版本、日志和数据证据、影响范围缺一不可。

开发定位并修改代码属于**调试**；QA 复现失败、报告缺陷、修复后确认和回归属于**测试**。严重程度描述缺陷影响有多大，优先级描述多快修复，两者不能混为一谈。

修复后先做**确认测试**，证明原缺陷消失；再按调用链和数据影响执行**回归测试**，确认修改没有破坏相邻功能。

## 7. 回归与专项：证明这次改动可以发布

回归范围从变更影响推导，包括直接修改的取消逻辑、调用它的页面和接口、共享订单状态、Redis 缓存、MQ 消费者以及历史同类缺陷。核心用例进入持续回归，不能只重跑曾经失败的那一条。

专项测试按风险进入，不是在发布前机械地全部执行：

- 安全测试验证对象级权限、身份失效、参数篡改和敏感信息泄露。
- 可靠性测试验证数据库失败、MQ 中断、重复消息和恢复后的最终状态。
- 性能测试验证目标负载下的 P95、错误率、吞吐和资源瓶颈，并检查是否产生数据错误。
- 兼容性测试根据实际支持的浏览器、客户端和接口版本选择范围。

## 8. 发布评估：QA 提供证据，不替团队拍板

测试完成时，QA 汇总版本、测试范围、通过情况、缺陷、性能结果、遗留风险和未测范围。**发布门禁**是发布前必须满足的条件；**灰度发布**是先向少量用户或流量发布，再根据线上指标决定是否扩大范围；**回滚**是在风险超出阈值时恢复到上一个稳定版本或关闭新功能。

本项目的门禁至少要求：核心流程通过，阻断和严重缺陷关闭，遗留风险有明确影响与责任人，监控、灰度和回滚条件已经准备。灰度期间取消失败率连续 5 分钟超过 1% 时回滚。

QA 的职责是说明“已经证明什么、还有什么未知、剩余风险多大”，并给出发布建议。最终决策由产品、开发、QA 和运维根据业务收益与风险共同承担，具体度量口径见[软件测试度量与发布判断](02-软件测试度量与发布判断.md)。

## 9. 上线与复盘：测试没有在发布时结束

灰度发布后，QA 使用受控账号验证核心链路，观察取消成功率、接口 P95、错误码分布、MySQL 事务失败、待发送事件积压、MQ 消费失败、Redis 旧值和告警。达到预先约定的回滚条件就执行预案，不能等根因完全查清才止损。

线上问题按需求、设计、代码、数据、环境或测试遗漏分析根因。有效的线上失败案例要补充为测试场景和回归用例，同时改进日志、监控或流程，让同类问题更早暴露。到这里，一个版本的 QA 流程才真正闭环。

## 10. 按“三遍法”完成学习

### 第一遍：理解流程

不用工具，独立讲清取消订单项目中每个阶段的输入、QA 动作、交付物和门禁。重点理解“业务规则 → 风险与范围 → 测试技术 → 测试用例 → 结果证据”，不要背孤立定义。

### 第二遍：在小型练习项目中执行

选择一个公开练习接口或本地订单项目，完成：

1. 写出 5 条明确的业务规则和对应风险。
2. 用决策表设计至少 8 条接口用例，并完整写出其中一条。
3. 用 Postman 手工验证，再用 `requests + pytest` 自动执行核心用例。
4. 同时检查接口响应和数据库状态，保留一份可复核的测试报告。
5. 注入一次数据库或消息故障，提交完整缺陷，并在修复后完成确认测试。

### 第三遍：在真实项目中强化

在真实网页或接口项目中，根据风险选择 Selenium、Charles、JMeter、MySQL、Redis 或 RabbitMQ 进行验证，并完整经历一次需求变更、提测退回、缺陷回归、发布评估以及将线上失败案例补入回归测试的过程。

最终应能用下面这段结构回答面试问题：

> 功能进入项目后，我先理解业务价值并评审需求，把模糊描述变成可验证规则；再根据失败影响确定优先级和范围，按测试层级、测试技术和结果证据设计可追溯用例；然后准备环境、数据和自动化，通过准入后执行测试、管理缺陷并完成影响回归；最后用测试结果和遗留风险支撑发布，上线后通过监控和失败案例回流继续闭环。
