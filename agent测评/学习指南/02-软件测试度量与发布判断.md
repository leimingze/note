# 软件测试度量与发布判断

测试流程回答“应该做什么”，测试度量回答“做到什么程度、证据是否足够、剩余风险有多大”。
指标不是为了证明 QA 做了很多工作，也不能替代业务判断；它们用于暴露进度、质量和风险，
支持团队决定继续测试、修复、发布、灰度或回滚。

本文延续[取消订单案例](01-软件测试基础.md)，只讲传统软件测试与交付中的度量。
Agent 的重复运行、评分器校准和版本差异判断属于后续指南，不在本文展开。

## 1. 先确定指标在回答什么问题

一个指标必须同时说明对象、分母、环境、版本、时间窗口和目标。只有“通过率 95%”没有意义：
它可能排除了阻塞用例，可能混入低风险重复用例，也可能来自与生产不同的环境。

| 质量问题 | 指标类别 | 主要使用者 |
| --- | --- | --- |
| 需求和风险是否被测试覆盖 | 覆盖指标 | QA、产品、开发 |
| 当前测试执行到哪里 | 执行指标 | QA、项目负责人 |
| 发现的问题是否影响发布 | 缺陷指标 | QA、开发、产品 |
| 系统在目标负载下是否可用 | 性能与可靠性指标 | QA、开发、运维 |
| 发布后是否产生用户影响 | 线上质量指标 | 产品、开发、QA、运维 |

指标必须服务于决策。不能改变测试范围、修复顺序、发布结论或改进动作的数据，不应进入核心看板。

## 2. 覆盖指标：证明重要内容没有漏测

覆盖率的关键不是百分比，而是分母是否代表真实风险。

| 指标 | 计算口径 | 适用判断 | 主要限制 |
| --- | --- | --- | --- |
| 需求覆盖率 | 已有测试条件的需求数 ÷ 应测需求数 | 是否存在完全未分析的需求 | 一条浅层用例也可能被算作覆盖 |
| 测试条件覆盖率 | 已有用例的测试条件数 ÷ 全部测试条件数 | 风险、状态和依赖是否落实到用例 | 测试条件必须先定义清楚 |
| 风险覆盖率 | 已覆盖风险权重 ÷ 全部应测风险权重 | 高风险是否优先得到证据 | 权重带有团队判断 |
| 代码覆盖率 | 被测试执行的代码 ÷ 统计范围内代码 | 自动化是否触达关键实现 | 执行过不等于断言正确 |

取消订单案例有 G1 至 G7 七个测试目标和 C01 至 C12 十二条核心用例。发布评估不只看
“十二条是否执行”，还要确认越权、并发、事务和消息一致性等高风险目标都有对应证据。

代码覆盖率适合发现“完全没有执行到”的代码，不适合单独作为质量目标。追求行覆盖率可能得到大量
没有有效断言的测试，却漏掉状态组合、数据副作用和外部依赖失败。

## 3. 执行指标：展示进度而不是包装结果

一条用例在一个明确版本和环境中只能有一种当前状态：通过、失败、阻塞或未执行。

```text
执行率 = 已执行用例数 ÷ 计划执行用例数
通过率 = 通过用例数 ÷ 已执行用例数
阻塞率 = 阻塞用例数 ÷ 计划执行用例数
```

“已执行”只包含已经得到通过或失败结论的用例。阻塞和未执行不能放进通过率分母冲淡失败，
也不能因为暂时无法执行就从计划中删除。

执行结果必须分层查看：

- 按核心与非核心用例区分，避免大量低风险通过掩盖核心失败。
- 按功能、接口、集成、端到端和专项测试区分，避免层级之间相互替代。
- 按环境、浏览器、数据类型或依赖状态区分，避免把不同条件的结果直接合并。
- 按版本记录，代码变更后旧结果不能自动代表新版本。

测试执行率衡量进度，不衡量产品质量；高通过率也只能说明已执行范围内的结果。

## 4. 缺陷指标：观察风险和过程问题

缺陷数量本身不是质量结论。复杂高风险测试通常会发现更多缺陷，简单测试反而可能得到漂亮数字。

| 指标 | 定义 | 能帮助判断什么 |
| --- | --- | --- |
| 缺陷严重程度分布 | 阻断、严重、一般和轻微缺陷数量 | 当前剩余风险集中在哪里 |
| 缺陷发现趋势 | 每个时间窗口新增和关闭数量 | 质量是否趋于稳定，修复是否跟得上发现 |
| 重开率 | 修复验证后重新打开的缺陷 ÷ 已验证修复缺陷 | 修复质量和影响分析是否充分 |
| 缺陷逃逸率 | 上线后发现的有效缺陷 ÷ 测试期与上线后发现的有效缺陷 | 测试和发布门禁遗漏了多少问题 |
| 平均修复时间 | 从确认缺陷到修复可验证的平均时间 | 团队处理缺陷的效率 |

缺陷逃逸率必须限定版本和观察窗口。上线一天与上线一个月的数据不能直接比较；生产流量、功能范围和
用户规模不同的版本也不能只比较缺陷个数。

不能把“QA 发现多少缺陷”设为个人绩效指标。它会激励拆分、重复提交或回避预防性工作，破坏真实质量信息。

## 5. 性能与可靠性指标：平均值通常不够

性能测试至少同时观察负载、吞吐、延迟、错误和资源，缺少任意一项都难以解释结果。

| 指标 | 含义 | 取消订单示例 |
| --- | --- | --- |
| RPS / TPS | 单位时间处理的请求或事务量 | 基准负载为 200 RPS |
| P50 | 一半请求不超过该延迟 | 描述典型体验 |
| P95 / P99 | 95% 或 99% 请求不超过该延迟 | 发现长尾慢请求 |
| 错误率 | 失败请求 ÷ 总请求 | 服务端错误率低于 0.1% |
| 饱和度 | CPU、内存、连接池、队列等接近上限的程度 | 定位容量瓶颈 |
| 可用性 | 成功提供约定服务的时间或请求占比 | 判断服务是否达到 SLO |
| MTTR | 故障发生后恢复服务所需的平均时间 | 衡量恢复能力 |

取消订单接口的 A2 要求“200 RPS 下 P95 不超过 500 ms，服务端错误率低于 0.1%”。
这三个条件必须一起报告。只说 P95 达标，却没有说明实际负载和错误率，结论不可复核。

性能数据必须标注预热方式、持续时间、并发模型、数据量、环境配置和监控证据。不同环境的数据可以分别
分析，但不能直接宣称为同一基线。

## 6. 线上质量指标：验证真实用户是否受影响

上线后的指标应从业务结果、技术表现和恢复能力三层建立。

| 层次 | 取消订单示例 | 触发动作 |
| --- | --- | --- |
| 业务结果 | 合法订单取消成功率、重复取消副作用数 | 下降时暂停灰度并检查业务状态 |
| 技术表现 | 接口 P95、错误码、事务失败、MQ 积压 | 超阈值时告警、扩容或回滚 |
| 数据一致性 | Redis 旧值、待发送事件、重复消费 | 触发补偿、重试和数据核对 |
| 恢复能力 | 告警发现时间、MTTR、回滚耗时 | 改进监控和预案 |

线上成功率不能只用 HTTP 200 计算。接口返回成功但数据库未更新、消息永久未投递，仍是业务失败。
成功定义必须与需求评审阶段的 Test Oracle 一致。

## 7. 用指标形成发布结论

发布看板应以门禁、证据和剩余风险为主，而不是堆积所有可采集数据。

| 维度 | 需要回答的问题 | 示例门禁 |
| --- | --- | --- |
| 覆盖 | 高风险目标是否都有证据 | G1 至 G7 均有测试承接 |
| 执行 | 核心范围是否完成 | 核心用例全部执行并通过 |
| 缺陷 | 剩余问题是否可接受 | 无未关闭的阻断或严重缺陷 |
| 性能 | 目标负载下是否达标 | 200 RPS 下 P95 与错误率达到 A2 |
| 可靠性 | 故障和恢复路径是否验证 | 事务、MQ 和重复消费测试通过 |
| 可运营性 | 上线后能否发现和止损 | 监控、灰度和回滚条件已验证 |

QA 最终报告需要明确区分：

- **已经证明**：在哪个版本、环境和范围中得到了什么结果。
- **尚未验证**：哪些条件因为环境、时间或范围没有测试。
- **已知风险**：遗留缺陷和限制会影响谁、出现概率和损失是什么。
- **发布建议**：通过、带风险通过或不通过，以及对应的灰度、监控和回滚动作。

## 8. 常见误用

- 只看总通过率，不看核心失败、阻塞和未执行范围。
- 用缺陷数量评价测试人员或直接比较不同复杂度的项目。
- 把代码覆盖率当成需求、状态和风险覆盖率。
- 只报告平均延迟，隐藏 P95、P99 长尾和错误请求。
- 改变指标分母、观察窗口或环境后，仍与旧版本直接比较。
- 达到数字门槛就机械发布，不审查未测范围和业务风险。
- 为了让看板变绿而删除失败、重试到成功或合并不兼容的数据。

指标的价值是让问题更可见。指标异常时应定位原因，不能修改口径来制造成功。

## 9. 按“三遍法”完成学习

### 第一遍：读懂口径

能够解释每个指标回答什么问题、分子和分母是什么，以及为什么单独使用会误导。

### 第二遍：小 Demo 计算

为一个有 20 条用例的小项目记录通过、失败、阻塞和未执行状态，计算执行率、通过率和阻塞率；
再加入缺陷严重程度、重开情况以及一份包含 RPS、P95 和错误率的性能结果。

### 第三遍：形成发布看板

在真实项目中建立覆盖、执行、缺陷、性能、可靠性和线上质量六类证据，输出一次发布建议。
随后选择一个线上问题，检查原有指标为什么没有提前暴露它，并修正测试或监控设计。

完成后应能回答：测试通过率很高是否代表版本可以发布；为什么平均响应时间达标仍可能有大量用户体验差；
以及如何用指标说明剩余风险，而不是只说“测试完成”。
