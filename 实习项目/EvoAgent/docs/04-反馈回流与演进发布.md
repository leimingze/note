# EvoAgent 反馈回流与演进发布

## 为什么这是一条独立的线

如果把 EvoAgent 只看成“一次请求 → 一份报告”，那它只是一个代码审查工具。真正让它具有产品闭环的是：

```text
审查 → 反馈 → 失败案例 → 候选版本 → 回放评测 → 门禁 → 激活/回滚 → 下一次审查
```

这条线不是“数据怎么保存”，而是“保存的数据如何影响未来行为”。

## 反馈从哪里来

用户可以在任务详情页或 API 提交：

- `false_positive`：误报；
- `missed_issue`：漏报；
- `bad_fix`：坏修复；
- `accepted`：接受。

调用链：

```text
POST /v1/tasks/{id}/feedback
  → ReviewService.record_feedback()
  → TaskStore.record_failure_case()
  → MemoryManager.remember_feedback()
```

反馈被写入 `failure_cases`，其中包含：

- task_id；
- category；
- finding（规则 ID、路径、行号、严重度等）；
- note；
- resolved 状态。

同时写入语义记忆，供后续相似仓库/任务查询。

## 两条进化路线

EvoAgent 同时支持两类版本化资产：

| 路线 | 候选对象 | 主要文件 | 评测方式 |
|---|---|---|---|
| 提示词进化 | `prompt` / `EVOAGENT_LLM_PROVIDER` 运行时配置 | `evolution.py`、`evolution_v2.py` | `RegressionEvaluator` 回放 |
| Agent Skill 进化 | `SKILL.md` 与资源文件 | `skill_evolution.py` | `AgentSkillReplayReviewer` 走真实产品运行时 |

### 提示词进化

入口：

```text
POST /v1/evolution/auto
POST /v1/evolution/propose
```

`EvolutionEngine.auto_propose()`：

1. 读取未解决 failure cases；
2. 调用 `RootCauseEvolutionGenerator`；
3. 生成候选 prompt additions、few-shot examples、Lead delegation rules、tool selection policy、budget parameters；
4. 只允许受限字段，禁止生成生产源码修改；
5. 保存候选版本；
6. 在 validation 和 holdout 上回放 baseline 与 candidate；
7. 计算 safety、completeness、improvement、non-regression；
8. 通过才激活，否则 rejected 或 deferred；
9. 激活后 `reload_skills()`。

核心指标：

- precision；
- recall；
- F1；
- severity accuracy；
- high severity recall；
- clean accuracy；
- success rate；
- 综合 score。

### Agent Skill 进化

入口：

```text
POST /v1/skill-evolution/auto
POST /v1/skill-evolution/propose
```

`SkillEvolutionEngine.auto_propose()` 会：

1. 读取未解决 failure cases；
2. 对 `false_positive` 删除 `<!-- evoagent:learned:* -->` 块；
3. 对 `missed_issue` 追加确认规则块；
4. 构造新的 `SKILL.md` 资源包；
5. 通过 `AgentSkillReplayReviewer` 运行完整的 Lead/Worker/Critic 产品运行时；
6. 比较 baseline 与 candidate 的指标；
7. 通过 validation improvement 和 holdout non-regression 才激活；
8. 激活后 resolve 被使用的 failure cases；
9. 版本与运行记录永久保留，可回滚。

## 发布与流量

`ReleaseManager` 按 `tenant + skill + task` 做 hash bucket，分配：

- `stable`：稳定版本；
- `canary`：金丝雀版本；
- `shadow`：影子流量（基础设施已存在，当前服务路径没有调用 `observe_shadow()` 接入完整 shadow 评测）。

`ReleaseManager.observe()` 在每次审查成功/失败后：

- 更新 `deployments.samples` 和 `errors`；
- 达到样本下限且错误率超过阈值时自动 rollback；
- 写入 alert。

`ReleaseManager.observe_shadow()` 与 `record_shadow_observation()` 已实现：

- 比较 primary/candidate finding keys；
- 计算 disagreement；
- 达到自动晋升策略时 promote。

但当前 `ReviewService` 的 `_process_queued` / `create_review` 只调用了 `observe()`，没有调用 `observe_shadow()`。因此“影子流量自动晋升”目前是已经准备好但尚未接入生产主链路的可复用能力。

## 版本数据为什么重要

每次候选评测都会保存：

- `evolution_runs`：candidate/baseline 分数、metrics、gates、原因、指纹；
- `skill_versions`：提示词版本、active、parent；
- `skill_artifact_versions`：SKILL.md 包、SHA-256、active、parent；
- `skill_evolution_runs`：Skill 候选评测记录。

这样即使候选人上线后表现不好，也可以：

1. 找到哪个版本引入了问题；
2. 查看当时的评测指标；
3. 回滚到上一个版本；
4. 保留失败版本作为证据，而不是直接丢弃。

## 推荐补进分类

你提出的四个视角本身是合理的：

1. **全貌与 Harness 分层**：回答“系统是什么、分几层”；
2. **产品组装**：回答“组件怎么拼成产品”；
3. **一次请求**：回答“一次输入经历什么”；
4. **数据留存与恢复**：回答“留下什么、怎么恢复”。

建议补上第五个视角：

5. **反馈回流与演进发布**：回答“留下的数据如何改变未来行为”。

理由：

- 前四个视角更多是“结构、组装、运行、存储”；
- 第五个视角是“学习与发布”，它连接 failure cases、evaluation cases、版本、激活和回滚；
- 不了解这条线，会把 EvoAgent 误读成“只调用 LLM 的审查器”，而忽略它真正的产品化价值。

## 演进边界与诚实声明

- 提示词演进是在固定评测集上做的，只能证明候选在评测分布上更好；
- `evolution_proof.py` 明确定位为“受控离线行为演化证明”，不声称外部 LLM 权重提升；
- Skill 演进通过同一套产品运行时回放，但真实 PR 仍需独立验证；
- 自动激活有门槛，不是“反馈后立即改线上”；
- 所有版本都保留 parent 与 SHA-256，避免不可追溯的静默替换。
