# EvoAgent 一次请求链路

## 请求入口

一次真实任务有两条入口：

1. **手动 API**：`POST /v1/reviews`，请求体里直接带有 `diff`；
2. **GitHub Webhook**：`POST /webhooks/github`，只携带事件元数据，Diff 由后台再去 GitHub 拉取。

两条入口最终都会调用同一个核心：

```text
ReviewHarness.run()
```

## 完整调用链

```text
HTTP 请求
  → ApiHandler.do_POST()
  → ReviewService.create_review() / enqueue_review()
      → TaskStore.create() + save_task_payload()
      → (异步) TaskQueue.submit() → _process_queued()
      → ReviewHarness.run()
          → AgentRuntime.execute()
              → planning → executing → reviewing
          → executing 内部：
              ModeRouter → Scanner/Lead/Worker/Critic/Gate
      → TaskStore.succeed()
  → (可选) GitHub 评论回写 → HTTP 响应
```

## 第一步：HTTP 与权限

`ApiHandler.do_POST` 先做认证，再做业务校验：

- 手动审查要求 JWT 和 `review` 权限；
- GitHub Webhook 改用 `X-Hub-Signature-256`；
- 管理接口要求 `manage` 或 `audit`。

`ReviewService` 随后检查 Diff 大小、仓库长度、`mode`、模型配置、仓库授权、启用角色和技能。失败会返回 400、401、403 或 500。

## 第二步：创建任务并保存输入

`_create_task` 生成 UUID、计算 Diff 的 SHA-256/字节数、调用 `ReleaseManager.assignment()` 决定 lane 和 shadow，然后写 `tasks` 并保存原始 Diff 到 `task_payloads`。任务初始状态是 `PENDING`。

如果是 GitHub Webhook，此时只创建 `diff_pending=True` 的 deferred task，后台 worker 再按 `diff_url` 拉取、校验并更新任务输入。

## 第三步：同步还是异步

### 同步

`create_review()` 在 `observability.span("review")` 中直接运行 Harness，返回 201 和完整报告。同步请求阻塞在 HTTP 请求里，适合调试或短任务。

### 异步

`enqueue_review()` 创建任务后 `queue.submit()`，返回 202 和 task_id。后台 worker 调用 `_process_queued()`。Redis Streams 提供消费组、ACK、lease、xautoclaim、重试和 DLQ；内存队列仅限进程内，重启后丢失。

## 第四步：ReviewHarness 启动

`ReviewHarness.run()` 先检查任务是否已经 `SUCCESS` 且有 `report`；是则直接返回已保存报告，不重复消耗模型。否则读取 trace 最大 step、加载 checkpoint、设置当前状态，并交给 `AgentRuntime.execute()`。

## 第五步：节点一 planning

`_planning()` 用 `parse_unified_diff()` 提取文件列表、新文件行号和新增行。若 Diff 没有文件或新增行则抛 `ValueError`，任务进入 `FAILED`；成功后状态进入 `PLANNING`，并保存 planning checkpoint。

## 第六步：节点二 executing

这一步调用：

```text
reviewer.review_with_context(task_id, diff, parsed, repository=..., tenant_id=...)
```

`ModeRouterReviewer` 会创建或恢复 context、创建 `ExecutionLedger` 和 `RepositoryToolSuite`、读取启用角色与技能、召回记忆，然后进入 `_agentic()`。

### 6.1 Scanner 阶段

先跑确定性能力：

```text
LocalRuleReviewer
  + SecurityRuleReviewer / ReliabilityRuleReviewer（注册 Scanner）
  + Diff AST evidence
```

产出不是最终结论，而是候选 finding 和证据。

### 6.2 Lead 委派

Lead 获得压缩后的 Diff、Scanner findings、可用 Agent Skills、期望证据，返回：

```json
{
  "action": "final",
  "delegations": [
    {
      "assignment_id": "security-1",
      "worker": "security",
      "objective": "...",
      "files": ["app.py"],
      "skills": ["api-compatibility"],
      "risk_domains": ["authorization"],
      "required_evidence": ["changed-line evidence"]
    }
  ],
  "risk_level": "...",
  "reasoning_summary": "..."
}
```

`_normalize_delegations()` 负责清理字段、去重、限制数量，并确保每个启用 Worker 至少有一个默认任务。

### 6.3 Worker 执行

`_run_pending_assignments()` 用 `ThreadPoolExecutor` 并行运行 Security 和 Correctness/Reliability Worker。

每个 Worker 由 `BoundedRole.run()` 驱动：

```text
最多 max_steps 步
  → 检查 Token/时间预算
  → ContextManager.build_managed_context()
  → JsonChatClient.complete_json()
  → 解析 action
      → tool：ToolRegistry.invoke() → observation → 继续
      → final：返回 findings
```

模型看不到完整 Diff，只能看到 `semantic-diff-v1` 压缩视图、当前工具目录和最近的观察。工具返回值会被记入 ledger，并按角色写入 working memory。

### 6.4 Lead 评估与返工

Worker 完成后，Lead 会评估：

- 是否缺少证据；
- 是否需要某个 Worker 返工；
- Critic 应该挑战哪些候选。

系统允许最多 2 轮返工。返工会带上 Lead 的 guidance 和 required_evidence，但不直接改变 Worker 的工具权限。

### 6.5 Critic 盲审

Critic 看到的是去除 source 身份的候选 finding：

- 不能新增 finding；
- 只能对每个 candidate 返回 accepted / rejected；
- 可以给出 objections 和 confidence adjustment；
- 可以独立调用工具验证反例。

最后 Lead 再根据 Critic 结果做最终选择。

### 6.6 FindingGate

通过 Agent 编排后，所有候选进入 `FindingGate.apply()`：

- 格式门禁；
- 证据门禁；
- 置信度门禁；
- 高危发布门禁。

被拒绝的 finding 会记录 rejected 列表，但不会进入最终报告。

### 6.7 记忆与检查点

通过门禁后：

- 每个 finding 写入 episodic memory（approved / rejected）；
- `consolidate_task()` 写入任务摘要并释放 working memory；
- 保存 `mode-router-summary`；
- 保存 `agentic-lead-session`。

## 第七步：节点三 reviewing

`_reviewing()` 做：

1. 从执行状态恢复 findings；
2. 计算整体 risk（存在 critical/high → high，medium → medium，否则 low）；
3. 从 `ModeRouterReviewer.collaboration_summary()` 读取协作摘要；
4. 组装 `ReviewReport`；
5. 状态进入 `REVIEWING`。

`ReviewReport` 包含仓库与 PR 元数据、summary/risk、findings、files_reviewed/reviewer、角色协作、run_mode/components，以及模型调用、工具调用、Token、成本、耗时和上下文压缩等执行事实。

## 第八步：成功、失败、取消

### 成功

```text
TaskState.REVIEWING → TaskState.SUCCESS
report_json 写入 tasks
trace_events 记录 SUCCESS
```

### 失败

```text
异常
  → RuntimeBudgetExceeded / RuntimeCancelled / provider error
  → TaskStore.fail()
  → record_failure_case(execution_error)
  → TraceEvent(FAILED)
```

普通异常会按 `node_retries` 重试；`ValueError`、取消、预算超限不重试。

### 取消

用户调用：

```text
POST /v1/tasks/{id}/cancel
```

`TaskStore.request_cancel()` 写入 `cancel_requested`。`AgentRuntime` 在每个节点尝试前检查 `store.is_cancelled()`，命中后抛 `RuntimeCancelled`，任务进入 `CANCELLED`。

## 队列失败与死信

异步任务失败时：

1. 未到 `max_attempts`：重试；
2. 达到上限：进入 DLQ；
3. `_on_dead_letter()` 把任务标记为 `FAILED`，创建告警；
4. 管理台可查看并通过 `POST /v1/queue/dead-letters/replay` 重放。

Redis 模式下，worker 只有在任务完成或安全入队后才会 ACK；长时间 pending 的消息由 `xautoclaim` 回收。
