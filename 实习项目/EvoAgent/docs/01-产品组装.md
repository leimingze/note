# EvoAgent 产品组装：组件怎么拼成一个可用产品

## 组装视角

看“全貌”时关注的是系统有哪些层；看“组装”时关注的是这些层之间的依赖、谁创建谁、谁注入谁，以及启动后到底发生了什么。

EvoAgent 的组装中心是 `ReviewService.__init__`，启动入口是 `api.run()`。

```text
python -m evoagent
  → Settings.from_env()
  → ReviewService(settings)
     → store / memory / context / observability
     → skills / llm / reviewer / harness
     → github / fixer / auth / release / alerts
     → evolution / skill_evolution / queue
  → ThreadingHTTPServer
     → ApiHandler(service, settings)
```

## 组装顺序

`ReviewService` 的构造顺序不是随意排列的，它体现了依赖关系。

| 步骤 | 组件 | 依赖与作用 |
|---|---|---|
| 1 | `Settings` | 从环境变量和 `.env` 读取配置，校验评测参数、认证密钥、价格参数 |
| 2 | `ReviewService` 构造开始 | 调用 `settings.validate_evolution()`，再调用 `resolved_llm()` |
| 3 | `store` | `create_store(settings.database_url, settings.db_path)` 选择 SQLite 或 PostgreSQL |
| 4 | `MemoryManager` | 依赖 store，负责租户/仓库隔离的记忆读写 |
| 5 | `ContextManager` | 独立纯 Python 组件，负责 Token 预算、Diff 压缩、观察窗口 |
| 6 | `Observability` | 可选 OpenTelemetry，无依赖时降级为无 Trace |
| 7 | `SkillRegistry` | 注册内置 `security-review`、`reliability-review`，再扫描 `skills/` 目录 |
| 8 | `JsonChatClient` | 如果配置了 LLM，则创建 OpenAI Chat Completions 兼容客户端 |
| 9 | `ModeRouterReviewer` | 注入 store、LLM、记忆、上下文、Skill 提供器，形成 Agent 编排器 |
| 10 | `ReviewHarness` | 注入 store 和 reviewer，形成一次审查的持久化执行壳 |
| 11 | `GitHubClient` | 读取 Diff、读写评论、拉取仓库内容 |
| 12 | `RepairVerifier` + `Fixer` | 生成修复、验证编译/测试、创建修复分支 |
| 13 | `AuthManager` | 创建默认管理员、签发短期 Token |
| 14 | `ReleaseManager` | 读取部署配置，分配稳定/金丝雀/影子通道 |
| 15 | `AlertManager` | 根据失败率生成告警 |
| 16 | `EvolutionEngine` | 提示词版本生成、回放、门禁、激活/回滚 |
| 17 | `SkillEvolutionEngine` | Agent Skill 版本生成、回放、门禁、激活/回滚 |
| 18 | `TaskQueue` | 注入 `_process_queued`，按 Redis 配置选择 Redis Streams 或内存队列 |
| 19 | `ThreadingHTTPServer` | 把 `ReviewService` 和 `Settings` 绑定进 `ApiHandler` 后启动 |

## 依赖注入关系

下面是最容易理解的依赖图：

```text
ReviewService
  ├── Settings
  ├── TaskStore / PostgresTaskStore
  │     ├── MemoryManager
  │     ├── EvolutionEngine
  │     ├── SkillEvolutionEngine
  │     ├── AuthManager
  │     └── ReleaseManager
  ├── JsonChatClient
  │     ├── ModeRouterReviewer
  │     └── EvolutionEngine / SkillEvolutionEngine
  ├── SkillRegistry
  │     └── AgentSkill / 内置 Scanner
  ├── ReviewHarness
  │     └── AgentRuntime
  ├── TaskQueue
  │     └── Redis Streams / memory-acked
  ├── GitHubClient
  ├── VerifiedPatchFixer / SuggestionOnlyFixer
  └── ApiHandler
```

`ReviewService` 本身不直接实现解题逻辑，而是把依赖注入给各组件。这样测试可以用假 store、假 client 或假 reviewer，不需要启动真实模型和数据库。

## 产品能力是怎么拼出来的

### 1. 提交审查

`web/index.html` 的“发起审查”表单提交到：

```text
POST /v1/reviews
```

ApiHandler 解析请求、调用 `ReviewService.create_review` 或 `enqueue_review`。如果是同步请求，直接运行 `ReviewHarness`；如果是异步请求，任务先入库，再由队列线程处理。

### 2. 异步生产模式

生产模式由三个环境变量决定：

- `EVOAGENT_DATABASE_URL`：空则 SQLite，`postgres://` 或 `postgresql://` 则 PostgreSQL；
- `EVOAGENT_REDIS_URL`：空则内存队列，配置后使用 Redis Streams；
- `EVOAGENT_ASYNC_WORKERS`：后台 worker 数量。

`docker-compose.yml` 使用 PostgreSQL + Redis，并设置：

```text
EVOAGENT_DATABASE_URL=postgresql://evoagent:...@postgres:5432/evoagent
EVOAGENT_REDIS_URL=redis://redis:6379/0
EVOAGENT_ASYNC_WORKERS=4
```

### 3. 代码审查能力

ReviewService 组装出的核心评审链路是：

```text
ReviewHarness
  → ModeRouterReviewer
      → LocalRuleReviewer / 注册 Scanner
      → Lead
          → Security Worker
          → Correctness/Reliability Worker
      → Lead 返工请求
      → Critic
      → Lead 最终综合
      → FindingGate
```

产品默认角色：

- `lead`：必须存在；
- `security`：安全、授权、敏感数据、危险调用链；
- `correctness-reliability`：状态、异常、并发、资源、兼容性；
- `critic`：盲审、反例、证据挑战。

可以通过 `EVOAGENT_ENABLED_AGENTS` 控制启用角色，也可以在单次请求里传 `enabled_agents`。

### 4. LLM 和模型配置

产品支持以下 Provider：

| Provider | 配置 |
|---|---|
| `deepseek` | `EVOAGENT_DEEPSEEK_API_KEY` |
| `openrouter-deepseek-free` / `openrouter-free` | `EVOAGENT_OPENROUTER_API_KEY` |
| `custom` | `EVOAGENT_LLM_BASE_URL` + `EVOAGENT_LLM_API_KEY` + `EVOAGENT_LLM_MODEL` |
| `local` | 未配置模型，只能启动服务，不能执行 agentic 审查 |

`Settings.resolved_llm()` 会把 Provider 转成统一的 `base_url`、`api_key`、`model`、`headers`，再由 `JsonChatClient` 统一调用。

### 5. 工具与能力包

工具不是直接写死给模型的，而是按角色分配：

- Lead：仓库列举、Diff 搜索、项目控制文件、测试定位；
- Security：读文件、符号、AST、Git、Scanner、仓库检查；
- Correctness/Reliability：同样的仓库事实工具；
- Critic：读文件、搜索、AST、Git、测试定位、Scanner、仓库检查。

Agent Skill 可以通过 `allowed-tools` 进一步收紧权限。Lead 只把一个 Skill 分配给某个 Worker 后，该 Worker 才能读取对应资源和工具。

### 6. 安全与隔离

产品组装时把安全能力放在多个边界：

- JWT 短期 Token 和 RBAC；
- 租户隔离查询；
- `repository_grants` 仓库授权；
- GitHub Webhook HMAC-SHA256；
- 任务、内存、失败案例、审计的 tenant 过滤；
- 路径穿越防护；
- 工具参数 Schema 校验；
- 仓库检查使用临时副本和环境白名单。

注意两个边界：

- Agent Skill 当前是“文本指令 + 受控资源读取”，代码中 `sandboxed=False`，没有独立进程沙箱或签名校验；
- 仓库检查的“隔离”是临时副本 + 受限环境，`network_disabled=False`，不能等同于完全离线沙箱。

### 7. 反馈与进化

产品把反馈作为一等公民：

- 用户在任务详情页提交误报、漏报、坏修复；
- `record_feedback` 写入 `failure_cases` 和语义记忆；
- `EvolutionEngine` / `SkillEvolutionEngine` 读取未解决反馈；
- 生成候选 Prompt 或 SKILL.md；
- 用固定评测集回放，通过门禁后激活；
- 激活后调用 `reload_skills()`，下次任务使用新版本。

### 8. 自动修复

修复不是简单拼接代码：

1. 从报告中挑出已通过门禁的 finding；
2. 拉取原文件内容；
3. 调用 `VerifiedPatchFixer` 生成统一 Diff；
4. 校验路径、hunk、行数；
5. 运行编译、tokenize、配置测试命令；
6. 在临时仓库副本里做修复前/后对比；
7. 创建独立分支和 Draft PR，不改源分支。

没有模型时退化为 `SuggestionOnlyFixer`，不会伪装成“自动修复成功”。

## 部署形态

### 本地零依赖

```shell
python -m pip install -r requirements.txt
python -m evoagent
```

默认监听 `127.0.0.1:8080`，使用本地 SQLite 和内存队列。

### Docker Compose

```text
postgres (PostgreSQL 16)
redis    (Redis 7)
evoagent (Python 3.11 + web + skills + evoagent)
```

服务对外暴露 `8080`，静态前端由同一个 HTTP handler 提供。

## 总结

产品组装回答的是“组件从哪来、依赖谁、怎么组合成完整产品”：

- `Settings` 提供外部配置；
- `ReviewService` 是组合根；
- `store`、`queue`、`llm` 是可替换实现；
- `ReviewHarness` 是执行壳；
- `ModeRouterReviewer` 是 Agent 编排器；
- `RepositoryToolSuite`、扫描器、Skill 是能力；
- `FindingGate` 和 `RepairVerifier` 是质量边界；
- API、Web、GitHub、自动修复是产品适配器；
- 反馈、评测、版本、发布是让产品持续演进的回路。
