# EvoAgent 数据留存与恢复

一次请求不只是产生一个报告，还会产生可复现、可审计、可恢复的状态。EvoAgent 把执行过程和执行结果都落到持久化层，这是它区别于“HTTP 调用 + 一段 LLM 输出”的关键。

## 数据分几类

建议把数据分成五组：

1. **请求与任务数据**：输入 Diff、任务元数据、状态、报告；
2. **执行与恢复数据**：trace、checkpoint、Agent 会话；
3. **记忆与反馈数据**：working memory、episodic memory、semantic memory、failure cases；
4. **评测与版本数据**：evaluation cases、evolution runs、skill versions；
5. **安全、审计与发布数据**：用户、成员、仓库授权、审计、部署、发布观察、告警、Webhook。

## 存储后端

### SQLite 默认

`EVOAGENT_DB_PATH` 默认是 `evoagent.db`，适合本地开发、单机低并发和快速验证。

### PostgreSQL 生产

配置：

```text
EVOAGENT_DATABASE_URL=postgresql://...@.../evoagent
```

`create_store()` 根据 URL 前缀选择 `PostgresTaskStore`。它和 `TaskStore` 提供同一套公共接口，上层代码不需要感知具体数据库。

### Redis 队列

配置：

```text
EVOAGENT_REDIS_URL=redis://.../0
```

用于：

- `evoagent:review:stream`：任务流；
- `evoagent:review:dlq`：死信；
- 消费组 ACK、lease、xautoclaim。

没有 Redis 时使用 `memory-acked`，进程内队列，重启丢失。

## 关键表与写入时机

### `tasks`

写入时机：

- `ReviewService._create_task()` 创建任务；
- `TaskStore.transition()`、`succeed()`、`fail()`、`cancel()` 更新状态与报告。

保存内容：

- `id`、`state`；
- `repository`、`pull_request`；
- `input_json`（source、diff 哈希、release lane、shadow、enabled agents/skills 等）；
- `report_json`；
- `error`；
- `tenant_id`；
- `cancel_requested`；
- `created_at`、`updated_at`。

### `task_payloads`

保存原始 Diff。它是任务恢复的第一前提：没有这个表，即使有 checkpoint 也无法重跑。

### `trace_events`

保存状态迁移：

```text
PENDING → PLANNING → EXECUTING → REVIEWING → SUCCESS
```

每条记录有 step、state、message、created_at。前端任务详情页的轨迹就是从这张表读出来的。

### `checkpoints`

节点级检查点：

```text
task_id + node
  → node: planning / executing / reviewing
  → status: completed / failed / in_progress
  → attempt
  → state_json
  → error
  → updated_at
```

Agent 会话级检查点：

- `agentic-lead-session`：保存 scanner findings、delegations、worker results、revision results、critic decisions、lead final、ledger、context；
- `mode-router-summary`：保存最终执行摘要、门禁、协作信息。

### `agent_memories`

四种 scope：

| scope | 用途 | 生命周期 |
|---|---|---|
| `working` | 本任务内工具观察 | 默认 86400 秒 TTL，任务结束后清理 |
| `episodic` | 已验证 finding、任务摘要 | 长期保存 |
| `semantic` | 反馈、规则知识 | 长期保存 |
| `procedural` | 流程类知识，当前代码中主要作为可扩展 scope | 长期保存 |

每条记忆都有：

- `tenant_id`、`repository`、`task_id`；
- `agent`；
- `scope`、`kind`；
- 关键词、metadata、importance；
- `created_at`、`expires_at`。

记忆查询按 tenant + repository 隔离，并支持过期清理。

### `failure_cases`

记录：

- 用户反馈：false_positive、missed_issue、bad_fix、accepted；
- 系统执行错误：execution_error；
- 关联 finding、note、task_id、created_at；
- `resolved` 标记，表示是否已经被演进流程使用。

### 评测与版本

进化流程会写：

- `evaluation_cases`：固定 Diff + 期望 finding + split；
- `evolution_runs`：baseline/candidate 指标、门禁、原因、指纹；
- `skill_versions`：提示词版本、active、parent_version；
- `skill_artifact_versions`：SKILL.md 包版本、artifact SHA-256、active、parent；
- `skill_evolution_runs`：Skill 候选评测记录。

### 安全、审计与发布

- `users`、`memberships`：登录用户和角色；
- `repository_grants`：租户仓库授权、自动修复权限；
- `audit_log`：review.create、repair.create、feedback.record、task.cancel、task.resume、deployment.configure 等；
- `webhook_deliveries`：Webhook delivery_id、payload SHA-256、task_id；
- `deployments`：stable/candidate 版本、canary/shadow 比例、错误率、状态；
- `release_observations`：release lane、primary/candidate 结果、分歧；
- `alerts`：失败率告警、DLQ、回滚/晋升告警。

## 恢复机制

### 1. 已完成任务

`ReviewHarness.run()` 开头检查：

```python
if task["state"] == "SUCCESS" and task.get("report"):
    return report
```

因此重复调用同一个 task_id 不会重复消耗 LLM。

### 2. 节点级恢复

`AgentRuntime.execute()` 加载 checkpoint 后，对每个节点：

```text
checkpoint status == completed
  → 跳过节点，直接恢复 state
checkpoint status == failed
  → 从该节点继续，并保留 failed 状态作为历史
```

例如：

- planning 已完成；
- executing 因 provider 临时失败而 failed；
- 重新运行时不会再次解析 Diff，而是直接重试 executing。

### 3. Agent 会话级恢复

`ModeRouterReviewer._load_lead_session()` 会读取：

```text
agentic-lead-session
  → protocol
  → session.phase
  → scanner_findings
  → delegations
  → worker_results
  → revision_results
  → critic_decisions
  → lead_final
  → execution ledger
  → context_management
```

`_agentic()` 的每个阶段都会判断是否已完成：

- scanner 已扫完就不重扫；
- delegations 已有就不重新委派；
- worker_result 已有就不重新运行该 assignment；
- critic 已做完就不重跑 Critic；
- lead_final 已有就不重新做最终综合。

测试里验证了“完成会话再次 resume 时不再调用任何模型”。

### 4. 队列恢复

Redis Streams：

- 成功后才 ACK；
- 失败时按尝试次数重投；
- 超过 `EVOAGENT_QUEUE_MAX_ATTEMPTS` 进入 DLQ；
- `xautoclaim` 回收超过 lease 的 pending 消息；
- DLQ 可通过 API 重放。

内存队列：

- 仅进程内，重启丢失；
- 不适合跨进程恢复，生产应使用 Redis。

### 5. 取消与终止

取消标志存在 `tasks.cancel_requested`。运行时在节点尝试前检查，取消后写 `CANCELLED` 和 trace。

### 6. 评测和版本恢复

- evolution run 与版本记录一体保存，即使候选未激活也能追溯；
- 激活版本可通过 `/v1/skills/{name}/versions/{version}/activate` 或 `/v1/skill-evolution/{name}/versions/{version}/activate` 回滚；
- evaluation case 固定指纹、数据集指纹和 Prompt SHA-256 都进入 metrics，用于复现。

## 能恢复什么、不能保证什么

| 恢复能力 | 状态 |
|---|---|
| 已完成任务直接返回报告 | 已实现 |
| 已完成节点跳过 | 已实现 |
| 失败节点重试 | 已实现，默认 `node_retries=2` |
| Lead 会话按阶段恢复 | 已实现 |
| Worker 已完成 assignment 恢复 | 已实现 |
| 队列 ACK / lease / DLQ / replay | Redis 模式已实现 |
| 取消任务 | 已实现 |
| 角色内部每一步模型响应都落盘 | 未实现，`BoundedRole` 只保存执行范围内观察 |
| `agent_messages` 消息日志 | 表存在，但当前代码没有主动写入调用 |
| Agent Skill 进程级沙箱 | 未实现，当前是文件读取约束 |
| 修复 PR 的执行结果持久化 | 修复结果通过 API 返回，未作为独立任务表保存 |

## 故障场景举例

### 场景一：模型调用超时

1. 任务执行到 `executing`；
2. provider 返回超时；
3. `AgentRuntime` 尝试重试；
4. 重试耗尽后写 `checkpoints["executing"] = failed`；
5. 任务进入 `FAILED`；
6. 调用 `resume` 后从 executing 重试，planning 不再重复。

### 场景二：进程在 Lead 委派后崩溃

1. `agentic-lead-session` 已保存 delegation；
2. 重启后调用 `resume`；
3. `ModeRouterReviewer` 加载 session；
4. 不重新委派，只运行未完成的 Worker；
5. 后续阶段继续按 session phase 推进。

### 场景三：异步 worker 在 Redis 消息处理中崩溃

1. 消息未 ACK；
2. lease 超时后由 `xautoclaim` 收回；
3. 任务重新投递；
4. 因任务 input/payload/checkpoint 都已在数据库，恢复后可以继续。

### 场景四：反馈导致 Skill 回滚

1. 新 SKILL.md 被激活；
2. 后续反馈证明其误报或漏报增加；
3. 版本记录仍保留；
4. 管理端可回滚到旧 active 版本；
5. reload 后新任务使用旧版本。

## 如何查看与操作

`GET /v1/tasks/{id}` 查看任务与轨迹；`/report` 看 Markdown；`/feedback` 看反馈；`/api/failures`、`/api/audit`、`/api/alerts`、`/api/queue/dead-letters` 查看失败案例、审计、告警和死信。`POST /v1/tasks/{id}/resume` 续跑，`POST /v1/queue/dead-letters/replay` 重放死信，版本回滚使用两个 `activate` 接口。

## 一句话总结

数据层负责让 EvoAgent 从“执行一次就忘记”变成“可审计、可恢复、可复现、可演进”。恢复的最小单元是 checkpoint，最大单元是完整任务；队列负责外部调度，数据库负责真实状态。
