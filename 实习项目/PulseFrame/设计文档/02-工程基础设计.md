# 工程基础设计

## 背景

PulseFrame 从零实现，当前阶段建立所有后续业务都能复用的运行基础。基座需要稳定启动、处理请求、公开运行状态并安全退出，同时保持各项职责清楚。

## 需求

- 配置错误时立即停止启动并说明原因。
- HTTP 请求由 Gin 接入。
- 每个请求具有请求标识，并能在响应与日志中关联。
- 系统异常使用统一错误结构，不向客户端公开内部细节。
- 服务提供存活和就绪状态。
- 服务设置请求读取、响应写入、空闲连接和退出期限。
- 进程收到终止信号后停止接收新请求，并等待现有请求完成。
- 工程具备自动化测试和静态检查入口。

## 当前非目标

- 不实现账号或其他业务接口。
- 不接入数据库、缓存和消息系统。
- 不创建 Worker、直播网关和内容安全 Agent 的空工程。
- 不建设完整监控平台和集群部署配置。

## 方案

| 能力 | 采用内容 | 原因 |
| --- | --- | --- |
| HTTP | Gin | 路由与中间件机制清晰，生态成熟 |
| 配置 | 标准库环境变量 | 当前配置少，读取和校验过程容易理解 |
| 日志 | log/slog | 标准库已满足 JSON 结构化日志需求 |
| 依赖装配 | 手工装配 | 当前依赖少，调用关系可以直接阅读 |
| HTTP 测试 | net/http/httptest | 可以验证完整 Gin 请求流程 |
| 生命周期测试 | 真实临时端口 | 可以验证监听、就绪与退出行为 |

## 目录

~~~text
backend/
├── cmd/pulseframe-api/
│   └── main.go               # 进程入口和基础依赖装配
├── internal/
│   ├── config/               # 配置读取与校验
│   ├── logging/              # JSON 日志器
│   ├── middleware/           # 请求标识、访问日志和异常恢复
│   ├── response/             # 统一错误结构
│   └── server/               # 健康状态、路由和 HTTP 生命周期
└── test/                     # 自动化测试
~~~

## 请求流程

~~~text
HTTP 请求
  -> 请求标识
  -> 访问日志
  -> 异常恢复
  -> Gin 路由
  -> Handler
  -> HTTP 响应
~~~

- 请求标识优先接收格式合法的上游值，否则使用安全随机源创建。
- 访问日志记录方法、路径、状态码、耗时和请求标识。
- 异常恢复记录请求标识和 panic 原因，对外只返回稳定错误。
- 404 和 405 也使用统一错误结构。

## 配置与健康

基座只读取运行环境、监听地址、日志级别和 HTTP 时长。所有值在服务监听端口前完成类型转换和边界检查。

- GET /livez：进程可以处理请求时成功。
- GET /readyz：服务完成监听并可以接收流量时成功。

## 验证

- 配置测试覆盖默认值、合法覆盖值、非法地址、非法时长和未知环境。
- 路由测试覆盖健康状态、请求标识、异常恢复、404 和 405。
- 生命周期测试使用真实临时端口验证监听和退出。
- 后端测试使用 60 秒超时，并执行 go vet ./...。

## 验收标准

- 核心 API 可以使用单条命令启动。
- 健康接口返回正确状态。
- 请求日志可以通过请求标识与错误响应关联。
- Handler panic 不会中止进程，也不会向客户端公开内部信息。
- 配置非法时拒绝启动。
- 服务可以在配置期限内优雅退出。
