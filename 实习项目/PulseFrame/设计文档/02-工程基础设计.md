# 工程基础设计

## 背景

PulseFrame 从零实现，第一个落地阶段需要建立所有业务模块共同依赖的运行基础。工程骨架必须让服务能够稳定启动、处理请求、暴露运行状态并安全退出，同时保持业务代码不依赖具体 HTTP 框架。

本阶段只建设核心 API 的最小工程能力，不接入数据库、缓存、消息系统，也不创建账号、视频等空业务模块。

## 需求

- 核心 API 能通过明确配置启动，配置错误时立即失败并说明原因。
- 对外 HTTP 请求由 Gin 接入，但 Gin 不能进入领域规则和应用用例。
- 每个请求具有唯一请求标识，并能在响应和日志中关联。
- 系统异常返回统一错误结构，不能向客户端暴露内部错误细节。
- 服务提供存活和就绪状态，供本地验证及后续部署探测。
- 服务设置合理的读取、写入和空闲超时，避免连接无限占用资源。
- 进程收到退出信号后停止接收新请求，并在限定时间内完成已有请求。
- 工程具备单元测试、HTTP 接口测试和静态检查入口。

## 非目标

- 不实现注册、登录或其他业务接口。
- 不选择数据库、缓存和消息系统。
- 不实现服务发现、服务网格和分布式事务。
- 不提前创建 Worker、直播网关和内容安全 Agent 的空工程。
- 不在本阶段建设完整监控平台和部署集群。

## 方案选型

| 能力 | 候选方案 | 选择 | 原因 |
| --- | --- | --- | --- |
| HTTP 框架 | 标准库、Gin、Echo、Fiber | Gin | 生态成熟、岗位常见，并且可以限制在 HTTP 适配层 |
| 配置 | 标准库环境变量、Viper、远程配置中心 | 标准库环境变量 | 当前配置简单，显式解析和校验更容易理解与测试 |
| 结构化日志 | `log/slog`、Zap、Logrus | `log/slog` | 标准库已满足当前结构化日志需求，避免过早增加依赖 |
| 依赖装配 | 手工装配、Wire、Fx | 手工装配 | 初期依赖较少，调用关系清晰，便于学习启动过程 |
| HTTP 测试 | `net/http/httptest`、外部接口测试工具 | `httptest` | 无需监听真实端口即可验证完整 Gin 请求链路 |

当配置来源、日志吞吐或依赖数量出现真实瓶颈时，再重新评估对应方案。

## 目录设计

```text
backend/
├── go.mod                              # Go 模块和依赖版本
├── cmd/
│   └── pulseframe-api/
│       └── main.go                     # 核心 API 的依赖装配和进程入口
└── internal/
    └── platform/
        ├── config/                     # 配置读取、类型转换和启动校验
        ├── logging/                    # 结构化日志创建和日志级别配置
        └── httpserver/                 # Gin 路由、HTTP 中间件和服务生命周期
            ├── middleware/             # 请求标识、访问日志和异常恢复
            └── response/               # 统一错误结构和响应写入
```

实际文件按实现需要创建，不为了匹配目录图拆出只有一个空壳的包。

## 请求处理链路

```text
HTTP 请求
  -> 请求标识
  -> 访问日志
  -> 异常恢复
  -> Gin 路由
  -> Handler
  -> 统一响应
```

- 请求标识优先接收格式合法的调用方标识，否则由服务生成，并写入响应头。
- 异常恢复记录请求标识和错误信息，对外只返回稳定的系统错误。
- 访问日志记录方法、路径、状态码、耗时和请求标识，不记录密码、凭据和完整请求体。
- Handler 只负责 HTTP 参数和响应转换；业务模块建立后，由 Handler 调用 Application 用例。

## 错误响应

成功响应直接返回对应资源或使用标准空响应，不强制增加统一成功外壳。失败响应采用统一结构：

```json
{
  "request_id": "请求标识",
  "error": {
    "code": "稳定的错误码",
    "message": "可对外展示的错误说明"
  }
}
```

- `code` 供客户端稳定判断错误类型，不能直接使用内部错误文本。
- `message` 不包含堆栈、文件路径、数据库信息或其他内部实现细节。
- 业务错误到 HTTP 状态码的映射由 HTTP 适配层负责。
- 请求标识生成成功后，所有错误响应都必须包含 `request_id`；如果安全随机源本身失败，则明确返回系统错误且不伪造请求标识。

## 配置范围

第一阶段只包含运行环境、监听地址、日志级别、HTTP 超时和优雅退出超时。配置需要解析为明确类型并完成边界校验；缺失或非法的关键配置必须让服务启动失败，不能静默改写为看似可用的值。

## 健康状态

- `GET /livez`：进程存活即可成功，用于判断是否需要重启。
- `GET /readyz`：服务完成初始化并能够接收请求时成功。
- 后续增加外部依赖时，就绪状态是否检查依赖可用性，需要根据故障传播风险单独设计。

## 启动与退出流程

```text
读取并校验配置
  -> 创建日志器
  -> 创建 Gin 路由和中间件
  -> 注册基础路由
  -> 启动 HTTP 服务
  -> 等待退出信号或服务错误
  -> 停止接收新请求
  -> 限时等待已有请求完成
  -> 退出进程
```

启动失败和退出超时必须明确返回错误，不能记录后继续伪装为正常运行。

## 测试与验证

- 配置测试覆盖默认值、合法覆盖值、非法地址、非法时长和边界值。
- HTTP 测试覆盖存活、就绪、请求标识透传与生成、异常恢复和统一错误结构。
- 生命周期测试使用真实临时端口启动服务，验证能够接收请求并在取消后退出。
- 所有后端测试使用 60 秒硬超时，完成后执行静态检查。

本阶段没有适用的业务公开数据集。验证应使用真实 HTTP 请求、真实进程生命周期和边界输入；不能为了满足“真实数据”要求而引入与问题无关的数据集。

## 验收标准

- 核心 API 能使用一条明确命令启动。
- `/livez` 和 `/readyz` 返回正确状态。
- 请求日志能够通过请求标识与错误响应关联。
- HTTP 请求处理中的未处理异常不会导致进程退出，也不会泄露内部信息。
- 配置非法时服务拒绝启动。
- 服务能够在退出期限内完成优雅关闭。
- `go test -timeout=60s ./...` 和 `go vet ./...` 执行通过。

## 面试表达

项目先建立最小工程基础，再实现业务模块。核心 API 使用 Gin，但框架只存在于 HTTP 接入层；配置、日志、错误处理和服务生命周期由独立平台代码管理。初期使用标准库完成配置和结构化日志，避免在需求简单时引入重型框架。所有基础能力都有可观察行为和自动化验证，后续业务模块可以复用同一套请求与运行规范。
