# 用户与认证模块设计

## 背景与目标

视频发布、互动和后续商家操作都需要稳定的用户身份。本模块建立账号密码登录闭环，避免把未来可能出现的手机端和小黄车业务提前耦合到一种 HTTP 传递方式或一张账号表。

第一版的目标是：用户可以注册、登录、查询本人信息和退出；服务端能识别登录身份，并对注册及登录滥用施加共享限流。

## 当前实施状态

- Go 后端已实现用户名密码注册、登录、当前用户查询、CSRF 令牌获取和当前会话退出；服务端会话与共享限流使用 Redis，用户数据使用 MySQL。
- 网页首版使用 Vue 3 与 TypeScript，覆盖注册、登录、会话恢复和当前设备退出；API 客户端使用浏览器 HttpOnly Cookie，不把会话令牌放进脚本。
- 本地开发由 Vite 将 /api 代理到 127.0.0.1:8081；后端 HTTP_ADDR 和 WEB_ORIGIN 必须分别与本地 API 地址、网页准确来源一致。部署时应让网页与 API 保持同站点。
- 已在真实 MySQL 8.4.11 专用数据库执行迁移，并使用专用 Redis ACL 用户完成网页到 API 的首轮真实联调；注册、重复注册、正确/错误登录、会话恢复、CSRF 获取、退出和退出后会话失效均得到预期状态码。专用 ACL 已验证不能读取其他键前缀。
- 前端已通过类型检查、7 项组件/API 测试、生产构建和 npm 依赖审计；后端已通过普通测试、竞态测试和 go vet。真实依赖故障、容量与负载验证仍未完成；远端端口访问策略也仍需收紧和复核。逐文件职责、实现链路与学习复盘见[实现与学习文档](03-用户与认证模块实现与学习.md)。

## 范围与边界

- 第一版只支持用户名和密码，不收集手机号或邮箱；不提供验证码、密码找回、第三方登录和多因素认证。未建立可信恢复渠道前，不宣称适合直接开放公众注册。
- 首个客户端为网页；原生手机 App 尚未实施。手机浏览器继续使用网页模式，原生 App 后续使用请求头传递凭据，共用账号与服务端会话用例。
- 注册用户都是普通用户。第一版没有后台封禁、角色授予、全设备退出或商家权限接口；这些操作不能通过客户端自报角色完成。
- 账号模块只拥有身份与凭据数据。商品、购物车、订单、支付和商家资格属于后续模块；账号 ID 是跨模块关联身份，不代表任何交易权限。

## 需求与约束

- 用户名唯一，并由数据库唯一约束处理并发注册；登录失败不能透露用户名是否存在。
- 密码不以明文、可逆密文或快速通用哈希保存；请求和日志不记录密码、Cookie、会话令牌或 CSRF 令牌。
- 登录态可过期，退出当前设备后立即失效；跨 API 实例共享，并在 Redis 故障时明确失败，不放行未经验证的请求。
- 网页 Cookie 不向脚本暴露会话令牌；修改类请求要防止跨站请求伪造。
- 第一版能在现有核心 API 内完成，不创建独立认证服务，不为了登录引入消息系统。
- 容量数字目前缺少真实流量依据。先建立正确性和基准负载，再按实际请求分布、延迟和故障数据调整。

## 方案选型

| 问题 | 候选 | 第一版选择与理由 | 代价及重评条件 |
| --- | --- | --- | --- |
| 身份数据 | MySQL、PostgreSQL | 使用已有的 MySQL 8.4；用户唯一约束和事务已能满足需求 | 不因未来可能的复杂查询预先换库；实际数据需求改变时重评 |
| 数据访问 | GORM、手写 SQL | GORM 限定在账号仓储适配层；结构迁移使用可审查的显式 SQL | 关键唯一冲突、事务和查询计划必须用真实 MySQL 验证 |
| 密码 | Argon2id、bcrypt | Argon2id；逐用户随机盐，保存算法版本与参数 | 登录时消耗 CPU/内存；当前使用 19 MiB、2 次迭代、并发默认 4 且最多 8，部署前仍需容量校准 |
| 会话 | 短时 JWT、MySQL 会话、Redis 会话 | Redis 中保存不透明会话；过期与当前设备退出可直接执行 | 每次鉴权依赖 Redis；故障和数据丢失会使用户重新登录 |
| 网页传递 | Bearer 请求头、Cookie | 网页用 HttpOnly Cookie；不要求页面脚本保管会话令牌 | 浏览器自动携带 Cookie，必须处理 CSRF |
| 防滥用 | 单实例计数、MySQL 计数、Redis 限流 | Redis 共享原子计数；避免多实例各自放宽限制 | Redis 不可用时相关接口明确失败；阈值需测试校准 |

JWT 能减少服务端会话查询，但单纯签发后无法即时撤销，角色和账号状态也可能滞后；不作为第一版唯一登录态。MySQL 会话便于持久化，但会给每次鉴权增加数据库查询；Redis 已承担限流，第一版选它管理短期会话。该选择不等于 Redis 内的角色或账号状态可以代替 MySQL 权威数据。

## 数据与模块边界

### MySQL 用户数据

账号模块管理 `users` 表：不可变的用户 ID、用户名、密码哈希、账号状态、创建及更新时间。第一版只创建普通且有效的账号；用户名采用 3 至 32 位 ASCII 小写字母、数字与下划线规则，数据库使用与规则一致的大小写敏感唯一索引。非法格式直接拒绝，不静默改写密码或用户名；用户名碰撞以唯一约束结果为准，不以预查询作为并发保证。

密码哈希采用自描述格式保存 Argon2id 参数、盐和结果；使用安全随机源生成盐。密码至少 8 个 Unicode 字符，UTF-8 字节数不超过 1024；认证 JSON 请求体不超过 4096 字节。哈希与验证共享非排队并发闸门，默认 4、允许 1 至 8；容量满时快速返回服务不可用，不静默排队。当前只接受本版本生成的参数，参数升级时必须同步更新解析上限和容量验证。容量仍需在目标机器测量单次验证耗时、并发内存和登录峰值。密码原文仅用于当次验证，不进入数据库、日志或响应。

结构变更通过版本化 SQL 迁移执行，应用启动不自动修改生产表结构。启动配置拒绝 MySQL `root`，要求使用指定业务库的专用账号；Redis 地址、ACL 用户名和密码均为必填，专用 ACL 的具体命令与键前缀权限须在接入前核查。注册成功后返回不含密码哈希的用户信息，不自动登录。

### Redis 会话与限流

登录成功后使用密码学安全随机源生成至少 256 位的不透明令牌。网页 Cookie 保存原始令牌；Redis 键只使用该令牌的 SHA-256 摘要，值最小化保存用户 ID、绝对过期时间及会话关联的 CSRF 令牌。会话初期采用固定七天有效期，不在每个请求刷新 TTL，以免高频浏览引发额外写入；该期限属于产品策略，实施时结合体验和安全测试复核。

每次受保护请求依据令牌摘要查询 Redis 并检查过期时间；缺少、非法或过期会话返回 401。当前设备退出删除对应会话，Cookie 同时失效。不同设备可以有独立会话；第一版不提供设备列表和全设备退出。会话数据丢失时要求重新登录，不用未验证的 Cookie 重建会话。

注册与登录按来源 IP 和登录标识设置组合限流。当前只信任实际 TCP 对端地址，Gin 的可信代理列表为空；接入反向代理前必须显式配置可信代理范围，不能信任任意 `X-Forwarded-For`。Redis Lua 脚本先原子检查所有桶，获准后才递增并设置过期；拒绝请求不会继续创建随机身份键。限流默认值为登录 IP 30 次/15 分钟、IP＋用户名 10 次/15 分钟、注册 IP 8 次/小时，均可配置，公网开放前需通过误拦截与负载数据复核。限流命中返回 429；Redis 不可用时注册、登录和会话校验明确返回服务不可用，不静默跳过限制或身份校验。

Redis 使用独立键前缀和专用权限，不对共享实例执行清库操作。投入使用前核查其 ACL、网络隔离、内存上限、淘汰策略、持久化和故障恢复；会话允许丢失并要求重登，但不能让其他缓存写入无界挤占会话空间。

## HTTP 契约与流程

第一版接口使用 `/api/v1/auth` 前缀：

| 接口 | 输入及成功结果 | 主要失败 |
| --- | --- | --- |
| `POST /register` | 用户名、密码；创建用户，201 返回公开的本人基本信息 | 400 参数非法，409 用户名已存在，429 限流，503 依赖不可用 |
| `POST /login` | 用户名、密码；200 设置会话 Cookie，不在 JSON 返回令牌 | 400 参数非法，401 凭据无效，429 限流，503 依赖或哈希容量不可用 |
| `GET /me` | Cookie；200 返回本人基本信息 | 401 会话无效 |
| `GET /csrf` | Cookie；200 返回当前会话的 CSRF 令牌，`Cache-Control: no-store` | 401 会话无效 |
| `POST /logout` | Cookie 与 CSRF 令牌；撤销当前会话，204 | 401 会话无效，403 CSRF 校验失败 |

表中公共路径均接在该前缀之后；其他系统故障使用现有统一错误结构并携带请求标识。登录时先检查限流，再按用户名读取用户，校验密码及 MySQL 中的账号状态，成功后写入 Redis 会话并设置 Cookie；用户名不存在和密码错误对外使用同一种 401 说明。Redis 会话创建失败时不能先返回登录成功。`/me` 从 MySQL 读取当前用户基本信息，受保护请求不能仅相信 Cookie 中自报的用户 ID。

第一版只采用 Cookie 作为网页会话凭据，不同时接受 URL 参数中的令牌。将来原生 App 可在 HTTP 适配层使用 Bearer 凭据和平台安全存储，但必须明确 Cookie 与 Bearer 同时出现时的处理规则，不能因请求头存在而跳过 Cookie 路径的 CSRF 校验。业务用例只接收经过验证的主体身份，不依赖 `gin.Context`。

## 网页安全边界

前端只保存当前公开用户资料和界面状态，不读取或保存会话 Cookie。页面加载时通过 GET /me 恢复身份；登录成功后由浏览器接收 HttpOnly Cookie；退出时先请求 GET /csrf，再把会话绑定令牌放入 X-CSRF-Token 请求头。注册成功不自动登录，与后端用例契约保持一致。用户名和密码仍由服务端执行权威校验，浏览器校验只用于即时反馈。

当前前端及运行命令见 ../frontend/README.md；图片来源和许可见 ../frontend/ASSETS.md。

- 生产环境全程 HTTPS；Cookie 使用 `HttpOnly`、`Secure`、`SameSite=Lax`、`Path=/` 和仅当前主机有效的作用域，不写入密码、角色或用户资料。开发环境如使用 HTTP，要显式区分 Cookie 配置，不把不安全设置带入生产。
- 优先让网页和 API 位于同一站点。当前 API 只允许精确 `WEB_ORIGIN`，凭据型 CORS 仅开放 `GET`、`POST`、`OPTIONS` 及 `Content-Type`、`X-CSRF-Token`；不能使用通配来源加凭据。`SameSite=Lax` 要求网页与 API 保持同站点。
- 注册、登录、退出及后续所有改变状态的 Cookie 请求先检查 `Origin` 与允许的准确来源；来源不可验证时拒绝，不把 GET 设计成状态修改操作。已登录的修改请求还必须通过与当前会话绑定的 CSRF 令牌校验，由网页放入自定义请求头；页面重新加载后通过 `GET /csrf` 获取令牌。登录创建新会话时轮换会话令牌和 CSRF 令牌。
- `HttpOnly` 防止脚本直接读取 Cookie，但不能防止同源恶意脚本代用户发请求；仍需对网页输入进行输出编码和脚本注入防护。CSRF 令牌也不能取代权限检查。
- 密码验证前执行限流，并对不存在用户名使用等价的验证路径以降低账号枚举风险；密码校验受并发闸门约束，容量耗尽会明确失败，避免 Argon2id 成为无界资源入口。

## 账号状态与后续高风险业务

第一版只有新建有效账号，没有改变状态或授予权限的公开用例；因此当前设计不声称已实现封禁后全设备即时下线。未来加入封禁、修改密码、商家权限等操作时，需要先定义 MySQL 状态变更与 Redis 会话撤销的顺序、失败补偿和可接受的生效延迟，并用并发与故障测试证明。Redis 会话中的用户 ID 仅表示认证身份，不能作为永久有效的角色快照。

在上述状态变更用例实现前，不通过手工修改 `users` 表来替代封禁流程：这样无法可靠撤销已存在的 Redis 会话。

涉及订单地址、退款、支付资料或结算等高风险操作时，业务侧必须从权威数据核对最新账号状态与操作权限，并按风险要求重新验证用户身份，保留审计记录。实现这些功能之前，还必须建立可信联系方式、账号恢复和必要的商家验证流程；这些不是第一版用户名密码模块已具备的能力。

## 现有环境与接入条件

已在 `120.48.147.164` 上的 MySQL 8.4.11 实例创建 PulseFrame 专用数据库和受限账号，并使用版本化 SQL 创建 `users` 表；应用连接使用 SSH 隧道，不使用 MySQL `root`。Redis 使用专用 ACL 用户与 `pulseframe:auth:*` 键前缀，权限已验证不能访问其他前缀。

## 面试表达

第一版用户模块选择 MySQL 保存长期账号事实，Argon2id 保护密码，Redis 保存短期可撤销会话并做共享限流。网页通过 HttpOnly Cookie 携带不透明令牌，服务端用摘要查会话，修改请求另做来源和 CSRF 校验。这样避免 JWT 在封禁和退出上的撤销难题，也不让浏览器脚本保管登录令牌；代价是依赖 Redis 的可用性和账号状态变更时的跨存储一致性。当前只承诺注册、登录和当前设备退出，封禁与交易操作在加入对应业务时以权威状态校验、撤销协议和故障测试补齐。
