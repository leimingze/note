# MySQL 是真相源，Redis 是加速层
先改 MySQL，再处理 Redis

# DEL：数据变了，缓存直接作废
UPDATE MySQL
→ DEL Redis
→ 下次请求查 MySQL 并重建缓存
适合 role、昵称、权限列表这类普通数据更新。优点是逻辑简单，不容易双写错。

# SET：某个状态必须马上生效
UPDATE MySQL
→ SET Redis
适合 banned、强制下线、紧急开关这类需要立即阻断的状态。

# 相比 SET，DEL 的核心优势是降低缓存和数据库双写不一致的风险
```bash
如果采用 UPDATE MySQL + SET Redis，可能出现
A 更新 MySQL = admin
B 更新 MySQL = vip      // 数据库最终是 vip

B SET Redis = vip
A SET Redis = admin      // A 晚了一步
真正危险的点其实是 “数据库更新顺序”和“缓存 SET 顺序可能不一致”
如果采用 UPDATE MySQL + DEL Redis
A 更新 MySQL
B 更新 MySQL
A DEL Redis
B DEL Redis
Redis miss
→ 查 MySQL
→ 得到最终值 vip
→ 回填 Redis
```

# 那为什么不用分布式锁？不能解决吗？
不是分布式锁不能解决，而是缓存一致性场景下，通常可以通过删除缓存降低并发写错的风险，因此没必要付出分布式锁带来的性能损耗和系统复杂度。
