# 总体架构与目录设计

## 背景

项目需要从零实现短视频、直播互动和内容安全能力。这些功能的运行特征不同：普通业务接口以短请求为主，后台任务需要异步执行，直播弹幕需要维护大量长连接，内容安全 Agent 又有独立的调用和评测流程。

因此需要提前设计模块边界和部署边界，让目录能够清楚表达职责，并为后续独立扩缩容和故障隔离留出空间。但目录整齐本身不是拆分服务的理由，只有运行方式、容量或故障边界不同的工作负载才考虑独立部署。

## 需求

- 业务代码按账号、视频、审核、Feed、互动、推荐、弹幕和直播等领域组织。
- 模块之间通过明确接口协作，不能直接修改其他模块的数据。
- 初期能够以较少进程运行，降低本地开发和测试成本。
- 特殊工作负载能够在需要时独立构建、部署和扩容。
- 所有部署单元遵守统一的配置、错误、日志、监控、安全和故障处理规范。
- 目录结构应服务于职责边界，不提前创建没有实现内容的空服务。

## 方案选型

| 方案 | 优点 | 问题 | 结论 |
| --- | --- | --- | --- |
| 单体按技术层组织 | 起步简单，文件数量少 | 业务增多后模块边界容易混乱 | 不采用 |
| 每个业务模块独立微服务 | 隔离和独立部署能力强 | 早期开发、测试和数据一致性成本过高 | 暂不采用 |
| 单仓库模块化单体，特殊工作负载独立部署 | 同时保留开发效率、模块边界和演进空间 | 需要严格维护模块依赖 | 采用 |

最终选择一个代码仓库管理项目。普通业务模块先由核心 API 统一承载，后台任务、直播长连接和内容安全 Agent 根据实际需求成为独立部署单元。独立部署不等于每个模块必须拥有独立仓库或立即拆分数据库。

### 核心 API 的 HTTP 框架

核心 API 使用 Gin 处理对外 HTTP 请求，包括路由、中间件、参数解析和响应输出。Gin 只允许出现在业务模块的 HTTP 适配层以及服务启动层，领域规则和应用用例不能依赖 `gin.Context`。

事件 Worker 不使用 Gin。直播网关、跨进程通信和内容安全 Agent 的接入方式在对应模块设计时，根据连接模型、性能和部署需求单独选型。

## 部署单元

### 核心 API

承载用户认证、视频业务、审核流程、Feed、互动、关系、搜索和运营接口。第一阶段只需要运行这个部署单元。

### 事件 Worker

承载不需要在用户请求内同步完成的任务，例如媒体基础处理、消息通知、数据聚合和审核任务调度。只有出现真实异步需求后才创建并运行。

### 直播网关

承载直播房连接、实时弹幕、在线状态和连接治理。它与普通短请求的运行特征不同，在直播阶段独立实现和部署。

### 内容安全 Agent

承载内容分析、上下文查询、风险判断和受限工具调用。它通过稳定接口与审核流程协作，不直接修改核心业务数据。

## 目录设计

```text
PulseFrame/
├── PulseFrame项目总纲.md             # 项目目标、功能范围和实施约束
├── 设计文档/                          # 总体架构及各业务模块设计
├── backend/                           # Go 后端工程
│   ├── cmd/                           # 可执行程序入口，只负责依赖装配和启动
│   │   ├── pulseframe-api/             # 核心业务 API
│   │   ├── event-worker/              # 异步事件和后台任务
│   │   └── live-gateway/              # 直播连接与实时消息网关
│   ├── internal/                      # 不对仓库外部暴露的后端代码
│   │   ├── modules/                   # 按业务领域组织的功能模块
│   │   │   ├── account/               # 用户、认证、账号状态和权限
│   │   │   ├── video/                 # 视频上传、发布和内容状态
│   │   │   ├── review/                # 审核任务、决定和复核记录
│   │   │   ├── feed/                  # 内容流查询与分发
│   │   │   ├── interaction/           # 点赞、收藏和评论
│   │   │   ├── relation/              # 关注及用户关系
│   │   │   ├── notification/          # 站内通知和未读状态
│   │   │   ├── recommendation/        # 行为利用、候选内容和排序
│   │   │   ├── danmaku/               # 短视频时间轴弹幕
│   │   │   └── live/                  # 直播房、直播状态和实时互动
│   │   ├── platform/                  # 配置、服务启动、日志和可靠性能力
│   │   └── contracts/                 # 跨部署单元的接口与事件契约
│   ├── migrations/                    # 数据结构变更及其模块归属记录
│   └── tests/                         # 跨模块集成、契约和系统测试
├── moderation-agent/                  # 内容安全 Agent 独立工程
└── deployments/                       # 本地和集群部署配置
```

目录只表示目标结构。实际开发时按模块实施顺序逐步创建，不提前生成空目录。

## 分布式治理基线

- **身份传递**：跨进程请求必须携带可验证的调用身份和用户上下文，不能信任调用方随意传入的用户编号。
- **请求追踪**：请求、事件和后台任务使用统一关联标识，支持定位一条业务链路。
- **超时与取消**：所有跨进程调用必须设置超时，并向下游传递取消信号。
- **重试与幂等**：只有满足幂等条件的操作才能自动重试；写操作必须定义重复请求的处理方式。
- **错误契约**：区分业务错误、权限错误、资源不存在和系统错误，禁止把内部错误细节直接返回给客户端。
- **事件契约**：事件包含唯一标识、类型、版本、发生时间和生产者；契约变更必须考虑兼容性。
- **数据归属**：每个业务模块拥有自己的数据写入权；跨模块读取和修改必须经过公开接口或事件。
- **健康与退出**：每个部署单元提供存活和就绪状态，并支持停止接收新请求后完成必要清理。
- **可观测性**：统一记录结构化日志、关键指标和调用链路，错误不能被静默吞掉。
- **安全边界**：配置与凭据分离，内部接口进行服务身份校验，高影响操作保留审计记录。

治理基线先定义规则，再随模块逐步实现。第一阶段不为了展示分布式能力而部署全部单元，也不预先引入服务发现、服务网格或分布式事务组件。

## 演进顺序

1. 用户与认证阶段只实现核心 API，同时建立统一配置、日志、错误和测试规范。
2. 出现媒体处理或可靠异步任务后，再增加事件 Worker。
3. 实现直播时增加直播网关，并验证多实例连接和消息恢复能力。
4. 实现内容安全时增加 Agent 工程，通过审核模块接入核心业务。
5. 只有容量测试或故障证据表明现有边界不足时，才继续拆分业务服务。

## 数据验证

总体架构不能只靠架构图证明合理。每增加一个部署单元，都需要通过真实业务数据或公开数据集回放、容量测试和故障演练，验证独立部署是否改善吞吐、延迟、资源隔离或故障恢复；没有验证收益的拆分不作为项目成果。

## 面试表达

本项目没有一开始把所有业务拆成微服务，而是选择单仓库的模块化架构。账号、视频和 Feed 等普通业务先由核心 API 承载，以降低早期开发和一致性成本；异步任务、直播长连接和内容安全 Agent 因运行模型和扩缩容方式不同，预留独立部署边界。后续是否继续拆分，由容量测试和故障证据决定，而不是由目录数量决定。
