# 思考
1. 用户 id 用于标识用户，不承担鉴权功能。自增主键可以用于数据库内部；当前对外用户 id 采用 UUIDv4。时间戳型分布式 id 也可能暴露创建时间，不能认为使用它就隐藏了业务信息。
2. 账号、密码、Cookie 和令牌都通过 HTTPS 传输；服务端日志不记录密码或完整令牌。
3. 数据库不保存明文密码。使用 Argon2id 保存带随机盐的密码哈希及算法参数，登录时使用对应库验证密码。哈希参数按部署环境测试后配置。
4. HTTPS 保护传输过程，密码哈希降低数据库泄露后的风险。额外使用非对称加密不能解决客户端或服务端已经被控制时的密码泄露。
5. 多种登录方式应关联同一个用户。users 保存用户及账号状态，password_credentials 保存用户名与密码哈希，external_identities 保存第三方身份与用户的关联；新增手机号、邮箱登录时再增加对应身份记录。
6. 每次业务请求不查询 users 表判断登录态。当前使用短期 JWT 验签；登录与刷新时查询账号状态，Redis 保存可撤销的刷新会话。
7. 登录态用于验证请求携带的凭据及其所属用户。Bearer Token 的持有者可以使用它，令牌本身不能证明请求一定由用户本人发送。
8. 当前操作者的 userId 从已验证的凭据中取得。请求参数中的用户 id、订单 id 等可以作为目标资源标识，但服务端仍需检查访问权限。
9. Session 方案：每次登录创建独立会话，客户端携带随机 SessionID，服务端查询会话识别用户。它便于撤销，但业务请求需要访问会话存储。
10. 令牌方案：JWT 包含用户标识、到期时间等声明并附带签名。签名用于验证来源与内容完整性，载荷通常可直接读取，不能放入密码等秘密。
11. 长短令牌方案：业务请求携带短期 Access Token；Refresh Token 仅用于刷新和退出。撤销刷新会话后，已经签发的 Access Token 在到期前仍可使用，最长约15分钟。

# 暂定方案
数据结构见 [登录与注册-数据结构](登录与注册-数据结构.md)，包含 MySQL 表、字段约束和 Redis key-value。

1. 当前采用用户名密码注册与登录 + QQ 登录，前端与 API 同源部署。业务请求只验签 JWT，接受退出、封禁后已有 Access Token 最长约15分钟的有效期；已经进入处理中的请求不撤回。
2. 长短令牌方案：Access Token + 强制轮换的 Refresh Token。Access Token 最长15分钟，会话从首次登录起最多7天，刷新不延长这7天。以下 userId、sessionId 均为示例标识。

2.1 登录
客户端：
```text
POST /api/login
Content-Type: application/json
Body: {username, password}
```
服务端：
```text
1. 校验请求来源、输入格式与长度，按账号和来源限制登录尝试
   错误账号或密码统一返回 401 {reason: "INVALID_CREDENTIALS"}
   触发频率限制返回 429；具体额度通过配置管理

2. 查询账号并验证密码
   用户名按注册时相同规则处理，使用 Argon2id 库验证密码哈希
   密码正确但 users.status = disabled → 403 {reason: "ACCOUNT_DISABLED"}
   读取 users.authVersion；该版本在封禁或撤销全部登录时递增
   数据库或 Redis 不可用 → 503，不作为密码错误处理

3. 生成独立会话及 Refresh Token
   sessionId = 安全随机生成的128位标识
   refreshToken = 安全随机生成48字节，使用无填充 base64url 编码
   tokenDigest = SHA-256(refreshToken)
   absoluteExpiresAt = 本次登录时间 + 7天
   每次登录创建独立的新 sessionId

4. 生成 Access Token（JWT）
   {
     "sub": "用户UUID",
     "sid": "sessionId",
     "iss": "pulseframe-auth",
     "aud": "pulseframe-api",
     "iat": 当前时间的 Unix 秒数,
     "exp": min(当前时间 + 15分钟, absoluteExpiresAt) 的 Unix 秒数
   }
   使用成熟 JWT 库，签名算法固定为 RS256
   私钥由服务端密钥配置提供，验证端只接受配置中的可信公钥
   kid 只能选择已配置的公钥，不能用于加载任意文件或网络地址

5. 原子写入 Redis 会话、令牌映射和用户会话索引
   key = session:{sessionId}
   value = {
     userId, authVersion, currentTokenDigest: tokenDigest, absoluteExpiresAt
   }
   key = refresh:{tokenDigest}
   value = sessionId（Redis String）
   两个 key 都在 absoluteExpiresAt 到期，不保存原始 Refresh Token

   SADD user:{userId}:sessions {sessionId}
   索引用于按用户查询会话；有效期覆盖所有成员的最晚到期时间
   创建或刷新会话时清理已到期成员，不能缩短其他会话所需的索引有效期
   原子操作采用 Redis Lua；相关 key 必须位于同一主节点
   当前采用单主 Redis；转为 Cluster 时需调整 key，使相关操作位于同一槽位

6. Redis 写入成功后返回
   {
     "accessToken": "eyJ...",
     "expiresIn": 900
   }
   expiresIn 按本次 JWT 的到期时间计算
   Access Token 只保存在客户端内存，不写入 localStorage
   Set-Cookie: refreshToken=xxx; Path=/api; HttpOnly; Secure; SameSite=Strict; Max-Age=604800
   Cookie 不设置 Domain；令牌响应使用 Cache-Control: no-store

7. 所有携带 Cookie 的变更请求均校验 Origin 与配置的前端源完全一致
   Origin 缺失或不匹配时拒绝，并要求 Content-Type: application/json
   QQ 跳转回调单独使用一次性 state 校验
```

2.2 日常请求
客户端：
```text
GET /api/user/profile
Authorization: Bearer eyJ...
```
服务端：
```text
1. 提取 Bearer Token，使用成熟 JWT 库验证
   只允许 RS256，必须验签成功
   必须存在有效 exp，且当前时间未达到 exp
   iss 必须为 pulseframe-auth，aud 必须包含 pulseframe-api
   sub、sid 必须存在且格式有效；iat 与 exp 必须符合服务端签发规则
   只有签名、来源、受众及其他声明有效而 exp 到期时，返回 TOKEN_EXPIRED
   其他令牌错误 → 401 {reason: "INVALID_TOKEN"}
   过期 → 401 {reason: "TOKEN_EXPIRED"}

2. 从 sub 取得当前用户，并检查目标资源权限
   身份有效但没有资源权限 → 403
   JWT 验证不查询 Redis 或 MySQL
   退出或封禁无法立即撤销已签发的 JWT，服务端仍需检查目标资源权限
```
客户端：
```text
页面重新加载、内存中没有 Access Token 时，尝试刷新一次
收到 TOKEN_EXPIRED 时，同一会话只发起一个刷新请求，其他请求等待结果
同源多个标签页通过 Web Locks 协调刷新，通过 BroadcastChannel 同步结果

POST /api/refresh
Content-Type: application/json
Cookie: refreshToken=xxx（浏览器自动携带）
Body: {}

刷新成功后，用新 Access Token 重试因 TOKEN_EXPIRED 被拒绝的请求一次
鉴权必须发生在业务副作用之前，其他业务错误不触发自动刷新
401 表示需重新登录，403 表示账号禁用，503 表示服务暂时不可用
刷新响应丢失、轮换结果无法确认时，不自动重复使用旧 Refresh Token，要求重新登录
```
服务端：
```text
1. 校验 Origin，读取 Cookie，计算 tokenDigest
   查询 refresh:{tokenDigest} 与对应 session:{sessionId}
   映射或会话不存在、已到绝对期限 → 401 {reason: "LOGIN_EXPIRED"}
   Redis 故障 → 503，不清除客户端凭据，也不签发新令牌

2. 查询 users.status 与 users.authVersion
   已禁用 → 撤销该会话，返回 403 {reason: "ACCOUNT_DISABLED"}
   版本与会话记录不一致 → 撤销该会话，返回 401 {reason: "LOGIN_EXPIRED"}
   查询失败 → 503
   登录和刷新均检查账号状态，数据库中的封禁不能只依赖 Redis 清理

3. 为本次轮换生成新的随机 Refresh Token、摘要和候选 Access Token
   JWT 的 exp = min(当前时间 + 15分钟, absoluteExpiresAt)

4. 用 Lua 原子重新校验并更新 Redis
   会话必须仍存在、未到期，映射仍指向该 sessionId，摘要必须等于 currentTokenDigest
   校验失败返回 LOGIN_EXPIRED，不修改当前会话
   删除旧 refresh:{tokenDigest}，创建新摘要到 sessionId 的映射
   更新会话中的 currentTokenDigest
   会话及新映射沿用原 absoluteExpiresAt，用户索引保持同一 sessionId
   刷新不得重新创建已撤销的会话
   刷新与退出操作串行生效，失败时不返回候选令牌
   同一旧令牌并发刷新只能有一个成功，其他请求返回 LOGIN_EXPIRED
   客户端协调刷新，避免正常并发请求因使用已删除的旧映射而失败

5. 原子轮换成功后返回
   {
     "accessToken": "eyJ...",
     "expiresIn": 本次 JWT 剩余秒数
   }
   Set-Cookie: refreshToken=新令牌; Path=/api; HttpOnly; Secure; SameSite=Strict; Max-Age=会话剩余秒数
   Cache-Control: no-store
   Cookie 与 Redis 都不能超过 absoluteExpiresAt
```

2.3 退出登录
客户端：
```text
与刷新共用会话操作锁，等待进行中的刷新结束后退出
通过 BroadcastChannel 通知其他标签页清除 Access Token

POST /api/logout
Content-Type: application/json
Cookie: refreshToken=xxx
Body: {}
```
服务端：
```text
1. 校验 Origin，计算当前 Refresh Token 的摘要

2. 使用 Lua 原子查询当前映射并核对会话的 currentTokenDigest
   匹配后删除映射和 session，并从用户会话索引移除 sessionId
   映射或会话不存在时按重复退出返回 204；已轮换的旧令牌不能定位当前会话
   映射存在但摘要不匹配时返回 401，不删除其他令牌对应的会话
   Redis 故障返回 503，不能声称服务端会话已经撤销

3. 成功后清除 Cookie，属性与设置时一致
   Set-Cookie: refreshToken=; Path=/api; HttpOnly; Secure; SameSite=Strict; Max-Age=0
   客户端清除内存中的 Access Token
   已被复制的 Access Token 仍可使用至到期，最长约15分钟
```

2.4 封号踢人
客户端：
```text
管理员提交封禁目标 userId 的操作
```
服务端：
```text
1. 验证管理员身份和管理权限
2. 在 MySQL 事务中设置 users.status = disabled，并递增 authVersion
   数据库提交成功后，后续登录与刷新必须拒绝该账号
3. 数据库提交成功即完成封禁，无需批量删除 Redis 会话
   旧会话及令牌映射按原 absoluteExpiresAt 自动到期，最长保留至登录后7天
   旧会话尝试刷新时，按2.2检查账号状态与版本，拒绝续期并撤销该会话
4. 即使并发登录或刷新留下旧会话，其 authVersion 也不能用于后续刷新
   已签发 Access Token 到期前仍有效；不承诺立即终止已开始的请求
5. 恢复账号时只恢复 status，不恢复旧 authVersion 或旧会话
   用户必须重新登录
   若仅要求全部设备退出，则只递增 authVersion，不禁用账号
```

2.5 用户名密码注册
客户端：
```text
POST /api/register
Content-Type: application/json
Body: {username, password}
```
服务端：
```text
1. 校验 Origin 与输入，并按来源限制注册频率
   username：3至24个 ASCII 字母、数字或下划线，统一小写后保存和查询
   password：12至128个 Unicode 字符，UTF-8 编码最多512字节
   密码不去空格、不改大小写、不截断
2. 使用 Argon2id 与独立随机盐生成密码哈希，保存算法参数
3. 在同一个 MySQL 事务中创建 users 与 password_credentials
   users 使用 UUIDv4 标识，初始 status = active、authVersion = 1
   password_credentials.username 有唯一索引，由数据库判断并发重复注册
   所有数据库请求使用参数化查询
4. 提交成功返回 201，不自动登录
   用户名冲突返回 409，输入错误返回 400，依赖故障返回 503
   注册成功后客户端进入登录流程
```

2.6 QQ 登录
客户端：
```text
点击 QQ 登录 → 访问服务端登录入口 → 跳转 QQ 授权页
QQ 将浏览器跳转到预先登记的 HTTPS 回调地址
```
服务端：
```text
1. 创建随机 state 与浏览器绑定凭据，有效期5分钟
   Redis 保存 state 摘要、绑定凭据摘要、固定回跳目标和到期时间
   绑定凭据通过单独的 HttpOnly、Secure、SameSite=Lax Cookie 下发
   该 Cookie 只用于授权回调；refreshToken 仍保持 SameSite=Strict
2. 回调必须携带匹配 state 与绑定凭据，原子消费一次，拒绝过期或重复使用
   不接受客户端指定任意回跳地址
3. 服务端使用授权码向 QQ 换取凭据，并通过 QQ 接口取得当前应用的 openid
   校验凭据属于预期 appId；客户端提交的 openid 不能直接作为登录依据
   appSecret 由服务端密钥配置提供，不下发到浏览器
4. 按 provider = qq、appId、openid 查询 external_identities
   三个字段组成唯一约束；身份关联的 userId 必须指向已有用户
   已有关联：读取对应用户
   没有关联：在一个事务中创建用户和身份关联；并发唯一约束冲突时回滚事务，再查询已有的关联
   不按昵称或未经独立验证的邮箱自动合并账号
5. 要绑定已有本地账号，必须先通过该账号的近期认证，再完成 QQ 授权
   已绑定其他用户的 QQ 身份拒绝重新绑定
6. 检查账号状态，并复用2.1的会话创建流程
   回调仅设置 Refresh Token Cookie，再跳转固定的同源前端页面
   不把 Access Token 或 Refresh Token 放进跳转 URL
   前端通过 /api/refresh 取得内存中的 Access Token
```
