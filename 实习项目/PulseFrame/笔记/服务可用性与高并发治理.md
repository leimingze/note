# 服务可用性与高并发治理

适用范围：PulseFrame 的用户名密码注册、登录、刷新、退出、QQ 登录与绑定。

关联文档：[登录与注册](登录与注册.md)、[登录与注册数据结构](登录与注册-数据结构.md)。

本文记录设计要求和引入条件。当前业务接口尚未编写，文中的治理能力不代表已经部署或通过运行验证。

## 1. 当前设计原则

1. 开发环境采用单实例 MySQL、Redis，代码从开始就明确依赖故障、超时和请求结果。
2. 正式服务根据可用性目标选择主备与故障切换，并在上线前验证恢复行为。
3. 身份、账号状态或刷新会话无法验证时，返回明确错误。
4. 已有 Access Token 可继续完成 JWT 验证；业务数据访问是否可用，由对应依赖决定。
5. 扩容依据吞吐量、延迟、资源使用及失败数据，按已确认的瓶颈选择措施。

## 2. 当前需要具备的治理能力

| 主题 | 当前设计要求 | 对应问题 |
| --- | --- | --- |
| 网络调用与超时 | MySQL、Redis、QQ 分别设置连接与操作超时，并受请求总期限约束 | 依赖变慢导致请求长期等待 |
| 连接池 | 限制连接数量、等待时间，复用连接并监测池状态 | 连接耗尽及依赖过载 |
| 重试 | 明确可重试操作、错误类型、次数上限及总时间预算 | 重复写入、负载放大 |
| 幂等 | 逐接口规定重复请求的结果 | 客户端无法判断上次操作是否成功 |
| 频率限制 | 登录按账号和 IP，注册按 IP 计数 | 密码猜测、批量注册 |
| 并发限制 | 限制同时执行的密码哈希及外部调用数量 | CPU、内存或连接被占满 |
| 资源隔离 | MySQL、Redis、QQ 使用各自的连接资源和并发预算 | 一个慢依赖影响整个服务 |
| 等待队列 | 限制排队容量与等待期限，请求取消后释放资源 | 请求积压引发级联故障 |
| 故障响应 | 区分认证失败、流量限制和依赖异常 | 错误重试、误清除凭据 |
| 监测 | 记录依赖错误、延迟、连接池等待、排队及限流事件 | 无法判断瓶颈和故障范围 |

这些要求同样适用于单体服务访问数据库、Redis 和第三方平台。

### 2.1 依赖故障时的行为

| 故障 | 受影响的功能 | 处理方式 |
| --- | --- | --- |
| Redis 不可用 | 登录与注册限流、刷新会话、当前会话退出、QQ 授权上下文 | 对需要访问 Redis 的操作返回503 |
| MySQL 不可用 | 注册、登录、刷新、QQ 身份关联、账号封禁 | 对需要访问 MySQL 的操作返回503 |
| QQ 不可用 | QQ 登录与绑定 | 返回明确的授权服务异常，保留已有本地登录状态 |
| 密码哈希并发达到上限 | 新的密码验证与密码哈希计算 | 在有限等待后拒绝超出容量的请求 |
| 业务依赖不可用 | 需要该依赖的业务操作 | JWT 验证可通过，但业务操作仍需返回对应依赖错误 |

```text
401：凭据无效、登录会话失效，客户端进入相应的认证流程。
403：身份有效但权限不足，或账号被禁用。
429：超过规定的请求频率，客户端停止连续重试。
503：依赖暂时不可用或服务容量不足，客户端保留凭据并提示稍后操作。
```

进程存活检查与依赖状态监测分开，避免依赖故障触发应用反复重启。就绪检查应按实例承接的流量设计，不能因为 Redis 故障就无条件阻断原本可以继续验签的请求。

### 2.2 重试、幂等与结果不确定

| 操作 | 当前处理原则 |
| --- | --- |
| MySQL 只读查询 | 仅对明确的瞬时故障，在总时间预算内有限重试 |
| 参数、密码或权限校验失败 | 不自动重试相同请求 |
| 用户注册 | 不自动重复提交；唯一索引防止重复账号，但不能据此认定第一次请求未成功 |
| Refresh Token 轮换 | 不自动重复提交旧令牌；轮换结果无法确认时重新登录 |
| 当前会话退出 | 重复退出返回204，可在请求期限内重试；当前令牌及会话关系仍需校验 |
| 同一 QQ 身份绑定同一账号 | 已有相同关联时返回成功；绑定其他账号时拒绝 |
| QQ 授权码兑换 | 按第三方接口语义处理；已消费的授权上下文不能重复使用，必要时重新发起授权 |
| 封禁或版本递增 | 不盲目重试更新；重复执行可能继续增加版本并影响后续会话 |

连接中断或超时，只能说明调用方没有得到确定结果，操作可能已经提交。唯一索引解决重复数据问题；完整的接口幂等还需要定义同一业务请求的识别方式、结果保存与重复返回规则。

重试控制：

1. 一个调用链只选择一个负责重试的层级，避免客户端、服务端和依赖组件同时重试。
2. 设置次数上限与总时间预算，每次重试都使用剩余期限。
3. 使用退避和随机间隔，避免大量请求同时再次访问故障依赖。
4. 限制重试流量相对初始请求的比例；预算耗尽时返回错误。
5. 请求取消、频率限制、持续故障或结果不确定的写操作不进入自动重试。
6. 恢复后逐步增加允许的调用量，避免积压请求同时释放。

### 2.3 频率限制与并发限制

频率限制控制一段时间内允许进入处理的请求数。当前使用 Redis ZSET 滑动窗口：

| 维度 | key |
| --- | --- |
| 同一登录名 | rate:login:account:{username} |
| 同一 IP 登录 | rate:login:ip:{normalizedIp} |
| 同一 IP 注册 | rate:register:ip:{normalizedIp} |

用户名保留原始大小写。IP 从可信来源取得，使用 Go net/netip 解析、Unmap、String 规范化。多个应用实例访问同一个 Redis 计数，形成共享的全局限制。

窗口和额度通过配置管理。Lua 原子检查相关维度，全部通过后才增加计数；密码错误或注册冲突不退还额度。Redis 不可用时返回503。

并发限制控制当前正在处理的请求数：

- Argon2id 同时消耗 CPU 和内存，需要独立的并发上限。
- MySQL 和 Redis 需要连接数量及连接等待上限。
- QQ 调用需要独立的并发预算、超时及连接资源。
- 请求频率不高也可能因依赖响应缓慢而累积大量并发，因此两种限制需要共同考虑。

### 2.4 隔离、队列与资源释放

按依赖设置独立资源预算，使 QQ 长时间等待不会占满全部请求处理能力。这对应舱壁隔离的思路，Go 服务可以使用独立客户端、连接池和信号量控制并发。

排队需要同时约束容量与等待时间：

1. 请求只在剩余期限内等待资源。
2. 队列已满或等待超时后，明确返回容量不足。
3. 请求取消后停止无效工作并释放已经取得的资源。
4. 不通过不断增大连接池或队列掩盖依赖处理能力不足。

## 3. 按条件引入的可用性措施

| 措施 | 引入条件 | 设计要点 |
| --- | --- | --- |
| 熔断 | 某依赖持续失败或超时，调用仍在大量占用资源 | 打开时快速失败，经过等待后允许少量探测，确认恢复再正常调用 |
| 自动故障切换 | 单实例故障已不能满足可用性目标 | 验证旧连接失效、重新连接、未完成事务和数据一致性 |
| 自适应限流 | 固定额度不能适应明显变化的服务容量 | 依据延迟、排队、并发和资源指标调整允许量，验证稳定性 |
| 本地限流降级 | Redis 故障时仍需接受部分请求，且业务明确接受额度放宽 | 多实例本地计数会改变全局额度，必须作为独立方案评估 |
| 读请求降级 | 数据允许短时间陈旧，且已有明确的新鲜度要求 | 明确缓存数据来源、有效期与恢复规则 |
| 写请求降级 | 业务允许延后处理，且能可靠保存待处理请求 | 返回已接受与最终成功应有不同语义 |
| 服务依赖度降级 | 可选依赖异常，主流程仍可正确完成 | 例如已定义为可选的展示信息，失败时不能伪装成完整成功 |

当前认证设计遇到 Redis 故障返回503，尚未采用本地限流替代。密码校验、账号状态和刷新会话校验属于认证所需条件。

Hystrix、Resilience4j、Sentinel 属于具体组件或生态选型。当前后端使用 Go，应根据需要选择适配 Go 的客户端与治理组件；熔断器本身不能代替连接超时、并发限制或数据高可用。

## 4. 高并发读写方案的选择

| 方案 | 适用条件 | 当前模块需要注意的事项 |
| --- | --- | --- |
| MySQL 读写分离 | 读取负载成为瓶颈，且部分查询允许复制延迟 | 账号状态和 auth_version 必须满足及时生效要求，认证查询不能随意路由到滞后的副本 |
| 本地缓存 | 存在高频重复读取的数据，且允许实例间短暂不一致 | 明确容量、过期、更新与淘汰规则，谨慎缓存账号状态 |
| W-TinyLFU 等淘汰策略 | 本地缓存的访问分布和命中率已经有测量依据 | 使用成熟缓存组件，根据命中率与资源占用选择策略 |
| SingleFlight | 同一个缓存缺失项触发大量并发加载 | 合并重复读取，不合并不同用户的写操作或令牌轮换 |
| Redis 分布式缓存 | 多实例共享热点数据，且缓存一致性方案明确 | 设计缓存穿透、集中失效、热点加载和更新顺序 |
| CQRS | 读写访问模型差异明显，共用模型已影响维护或性能 | 明确查询模型更新方式及延迟，不因使用 Redis 就认定已经采用 CQRS |
| 数据分片 | 数据规模、单库容量或写入吞吐量已成为限制 | 先明确分片键、跨分片操作、全局唯一约束和扩容方式 |

当前 Redis 中的刷新会话属于认证状态，无法只靠 users 表恢复原有授权。会话丢失后需要重新登录，不能直接套用“缓存未命中就查询 MySQL 并重建”的流程。

缓存治理按所缓存的数据选择：

- 缓存穿透：校验无效输入；对确有必要的不存在结果设置短期缓存，并考虑新建数据后的更新。
- 缓存击穿：同一热点失效时合并加载，约束回源并发。
- 缓存雪崩：分散到期时间、限制回源负载，并明确缓存整体故障时的行为。
- 缓存更新：明确数据库与缓存的更新顺序、失败处理及允许的不一致时间。

## 5. 指标与验证

| 维度 | 应观察或验证的内容 |
| --- | --- |
| 请求表现 | 到达速率、吞吐量、成功率、P95/P99 延迟 |
| 错误分类 | 区分预期的401、403、429与依赖异常、超时和服务端错误 |
| 资源占用 | CPU、内存、密码哈希并发、数据库与 Redis 连接数量 |
| 等待情况 | 连接池等待、排队长度、排队时间及取消请求数量 |
| 重试与熔断 | 初始请求数、重试比例、重试成功率、熔断状态和恢复探测结果 |
| 身份状态 | 封禁后刷新被拒绝、版本不一致、会话到期及轮换冲突 |

验证场景：

1. Redis 和 MySQL 分别不可用或响应变慢，确认请求在期限内结束，连接与队列不会持续增长。
2. 已有 JWT 在认证存储故障期间仍能完成验签；依赖业务数据库的操作按对应错误处理。
3. 注册、刷新和绑定在“提交成功但响应丢失”时，客户端不会盲目重复写入。
4. QQ 响应缓慢时，本地密码登录的资源预算仍可使用。
5. 并发登录、密码猜测和批量注册达到限制后，后端资源仍受控。
6. 多实例共享限流额度，IPv6 不同写法使用同一个 IP 计数。
7. 故障恢复后验证连接恢复、请求结果及会话状态，而非只检查端口恢复监听。

具体阈值根据目标流量、部署资源和压测结果确定，不将未经验证的数值作为生产承诺。

## 6. 后续部署调整

数据库和 Redis 的连接地址、凭据、模式及超时通过配置提供，由统一组件创建客户端。service 通过 DAO、会话组件访问存储。

从单实例切换到 MySQL 主备、Redis Sentinel 或托管高可用时，通常可以集中调整部署、连接组件和配置，但需要验证：

- 故障检测与切换时间是否满足可用性目标。
- 原有连接失效后是否能连接到新的可用节点。
- 未完成请求、事务及令牌轮换的结果如何确认。
- 复制延迟或切换期间的数据丢失会怎样影响账号状态和会话。
- Redis 会话丢失时的重新登录行为，以及异步复制丢失最近轮换写入时的影响。

设计模式帮助控制代码依赖与修改范围；服务是否能在节点故障后继续提供能力，仍取决于部署架构、数据一致性和故障恢复验证。
