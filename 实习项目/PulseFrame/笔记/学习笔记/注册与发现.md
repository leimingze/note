# 服务发现
当服务 A 需要调用服务 B 时，它怎么知道服务 B 现在在哪里、有哪些实例可用

| 问题 | 解决方式 |
|------|----------|
| **服务在哪** | 自动维护「服务名 → 实例地址」的映射关系 |
| **实例变化** | 实时感知实例的上线、下线及故障状态 |
| **负载均衡** | 配合客户端或代理侧实现请求分发 |
| **解耦依赖** | 调用方只依赖服务名，不依赖具体 IP |

# 可用地址管理
- 正常来说：服务启动时就会向服务注册中心注册自己的地址，并在退出时注销地址。
- 异常：如果某服务突然挂掉，还没来得及向服务注册中心注销。
所以服务注册中心应该有对已注册的服务地址的探活能力。

1. 主动探活：服务注册中心周期性的向每个已注册测测的服务地址发起探测请求。适用于服务较少的后台。
2. 心跳探活：服务实例按固定周期给注册中心 / 协调器 / 监控组件发一个“我还活着”的信号，就叫心跳

心跳探活有风险：误判、雪崩
- 若意外删除正常的服务，导致相关业务用不了；方案：避免过于敏感，加上重试次数
- 当某实例真实宕机时，若该服务承载流量较大，其全部请求会瞬间转移至剩余节点。若剩余节点容量评估不足，可能因突发流量过载而连锁宕机，最终演变为服务雪崩。熔断限流、负载均衡、容量冗余、降级隔离
