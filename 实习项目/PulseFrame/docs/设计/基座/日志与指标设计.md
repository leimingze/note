# 日志与指标模块 · 阅读与应用说明

本文按“从低层到高层、从被调用到调用方”的顺序，说明当前日志与指标模块的实现。先给出阅读顺序表，再解释每个文件是什么、新增/修改的方法做什么，最后总结模块整体是什么、为什么这样设计，以及每一步改动分别解决了什么问题。

## 一、阅读顺序表

| --- | --- | --- | --- | --- |

## 二、各文件是什么、方法做什么

### 1. `config/env.go` —— 配置读取工具
新增 `parseBool`：把环境变量文本解析成布尔值，缺失或为空时用默认值，无法解析时报错。是 `loadMetrics` 读取开关的基础。

### 2. `config/metrics.go` —— 指标配置
- `Metrics` 结构：开关（`Enabled`）、暴露路径（`Path`）、采集周期（`CollectInterval`）。
- `loadMetrics`：读取环境变量 `METRICS_ENABLED`、`METRICS_PATH`、`METRICS_COLLECT_INTERVAL`，并调用 `validate` 校验。
- `Metrics.validate`：路径必须以 `/` 开头，采集周期必须大于零。

### 3. `config/config.go` —— 总配置装配
`Config` 新增 `Metrics` 字段，`Load` 在读取完 MySQL/Redis 后加载指标配置。这样入口一次 `config.Load` 就拿到完整配置。

### 4. `metrics/error_types.go` —— 错误分类枚举
定义服务端使用的 `error_type` 固定集合（如 `config_invalid`、`dependency_timeout`、`internal_error`、`panic`）。设计上，对外 `error_code` 由 `response` 维护，内部 `error_type` 由本模块维护，两者分开、不混用。当前仅定义枚举，供后续依赖错误分类引用。

### 5. `metrics/registry.go` —— 指标注册表
- `Registry`：持有进程内 `prometheus.Registry`，集中定义四类指标：
  - HTTP：`http_requests_total`、`http_request_duration_seconds`、`http_requests_in_flight`、`http_response_errors_total`；
  - 依赖：`dependency_operations_total`、`dependency_operation_duration_seconds`、`dependency_errors_total`、`dependency_ready`；
  - 连接池：MySQL 连接数/使用中/空闲/等待次数/等待时长，Redis 池总数/空闲/超时；
  - 生命周期：`process_ready`、`startup_failures_total`、`shutdown_total`。
- `New`：创建独立注册表并注册全部指标，避免使用全局默认注册表。
- `Prometheus`：返回内部 `prometheus.Registry`，供 `/metrics` 端点读取。

### 6. `metrics/collector.go` —— 连接池指标采集器
- `PoolStatsProvider` 接口：定义 `MySQLStats()` 与 `RedisPoolStats()`，让依赖对象作为数据源。
- `NewCollector`：绑定注册表、数据源和采集周期。
- `Run`：用 ticker 周期采集，随上下文取消而停止，启动后立即采集一次。
- `collect`：读取 `sql.DB.Stats()` 与 `redis.PoolStats()`，把数值写入对应指标，不写日志。

### 7. `middleware/metrics.go` —— HTTP 指标中间件
- `NewMetrics`：保存指标注册表。
- `Handle`：请求进入时 `RequestsInFlight` 加一；完成后记录方法/路由/状态码，更新数量、耗时、进行中请求，并根据 context 中的错误码累加错误计数。

### 8. `response/error.go` —— 统一错误响应
- `ErrorCodeContextKey`：Gin context 中保存错误码的键。
- `WriteError`：除写出 JSON 错误响应外，还把错误码写入 context，便于指标中间件统计错误。

### 9. `server/router.go` —— 路由与中间件装配
`RouterDependencies` 新增 `Metrics`；`NewRouter` 在指标开启时注册指标中间件，并在 `registerPlatformRoutes` 中注册 `GET /metrics`（通过 `promhttp.HandlerFor` 读取进程内注册表）。

### 10. `internal/app/dependencies.go` —— 共享依赖与指标
- `Dependencies` 新增 `Metrics` 与采集器字段。
- `NewDependencies`：创建 MySQL/Redis 后创建指标注册表；若指标启用，则创建采集器并启动 goroutine。
- `MySQLStats` / `RedisPoolStats`：实现 `PoolStatsProvider`，向采集器提供真实连接池统计。

### 11. `internal/app/run.go` —— 服务入口编排
`Run` 用 `logger.With("service", "pulseframe-api", "environment", cfg.Environment)` 生成带公共字段的日志器；按 `cfg.Metrics.Enabled` 决定是否把注册表传给路由。启动/退出日志共用该日志器。

## 三、模块整体是什么、为什么设计

日志与指标模块是服务“可观测性”的基座：

- 日志回答“某个请求发生了什么”，当前基座已有 `slog` JSON 日志、请求 ID、访问日志、异常恢复；本次主要补齐公共字段与应用绑定。
- 指标回答“服务整体是否正常”。本次用 Prometheus 进程内注册表，暴露 HTTP、依赖、连接池和生命周期四类指标，并在 `/metrics` 端点输出。

设计动机：业务模块只补充业务名称、操作名称和错误分类，不直接创建输出器或修改采集规则，从而保证可观测性出口统一、口径一致、不与业务串联。

## 四、基于改动的分别解决方案

| 问题 | 方案 | 对应改动 |
| --- | --- | --- |
| 指标无统一数据源 | 集中 `Registry` 注册所有指标，避免散落全局变量 | `metrics/registry.go` |
| 指标开关/路径/周期无法配置 | 新增配置项并校验 | `config/metrics.go`、`config/env.go` |
| 连接池状态不可观测 | 周期读取 `DB.Stats` / `PoolStats` 并发布 | `metrics/collector.go`、`dependencies.go` |
| 请求量、耗时、并行度不可观测 | 中间件记录请求指标 | `middleware/metrics.go` |
| 错误无法按类别统计 | 统一错误码写入 context，中间件据此累加错误指标 | `response/error.go`、`middleware/metrics.go` |
| 对外错误码与内部错误分类混淆 | 分开维护 `error_code` 与 `error_type` | `response/error.go`、`metrics/error_types.go` |
| 指标无处暴露 | 注册 `/metrics` 端点 | `server/router.go` |
| 日志缺乏公共字段（service/environment） | 用 `logger.With` 生成带公共字段日志器 | `internal/app/run.go` |
| 指标生命周期与依赖绑定 | 依赖对象持有注册表与采集器，随上下文启停 | `internal/app/dependencies.go` |

整体效果：服务启动后即可通过 `/metrics` 观察请求与连接池状态，日志带公共字段便于关联检索，错误分类可支撑后续告警。
