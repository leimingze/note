# 内容审核：设计与实施

## 先看这一页

**这是什么**：一个独立部署的审核服务。内容与发布模块把待审视频交给它，它判断"能不能发"，再把结论回调回去。

**链路一句话**：先用便宜、确定的规则筛一遍，再用大模型看一遍，拿不准的交给会查规则条文的 Agent，最后由一段确定性代码决定怎么处理；任何环节出问题或拿不准，都交给人。

```
内容与发布模块 ──投递任务──→ 审核服务 ──回调结论──→ 内容与发布模块
                              │
           ┌──────────────────┼────────────────────────────┐
           │  ① 规则层  →  ② 模型层  →  ③ Agent 层  →  ④ 判罚引擎 │
           │   便宜确定      看图看字      查条文判灰区     定处置     │
           │      └──────── 任何一层出错或拿不准 ────────→ 人审队列 │
           └───────────────────────────────────────────────┘
```

**只做什么**：只审视频发布（标题、简介、封面、关键帧）。覆盖风险标签体系的全部 13 个一级类加兜底类，其中 8 类自动判定并评测，涉政、未成年一律送人审。评论、直播、账号资料、申诉都不做。具体分"必做 / 加分 / 只写设计"三档，见第一节。

**怎么证明它没问题**：三套 benchmark。判得准不准（效果评测）、出故障时会不会乱放行（链路评测）、新热点和新绕过手法出现后还有没有效（适应性评测）。

**从哪开始**：第一步写判罚引擎和判罚配置，见第八节。

与内容与发布模块的接口（投递、回调、对账查询）见 [内容与发布](../内容与发布/内容与发布.md) 的"审核对接"，本文只讲审核服务内部。

## 一、范围

### 1. 审什么

**审核对象**：标题、简介、封面、关键帧。画面里的文字由多模态模型直接读，不单独接 OCR。

**风险类别**：覆盖 [风险标签体系](风险标签体系.md) 的全部 13 个一级类，外加兜底类 OTHER。类别、二级标签、依据条款和 S0–S4 等级以该文件为唯一来源，本文不重复列举。

"覆盖"和"评测"是两件事：系统对每一类都有明确的处理方式，不存在默默放过的类别；评测只抽能自动判定、又能合法造出数据的类别。

| 处理方式 | 一级类 | 说明 | 怎么验证 |
|---|---|---|---|
| 机器自动判 | SEX 色情低俗、VIO 暴力血腥、ILL 违法违禁品、FRD 诈骗黑产、ADV 广告导流、DNG 危险行为、VAL 不良价值观、MIS 虚假信息 | 从文本和画面能判断，走完整四层链路 | 主评测集 |
| 一律送人审 | POL 政治安全、MIN 未成年人 | 风险最高，出现相关信号就送人审，宁可多审。MIN 判断需要看图，而评测数据不能收集涉及未成年人的图像 | 覆盖测试 |
| 规则检测 | GEN AIGC 标识、QLT 低质 | GEN：读取文件元数据里的生成合成标识，按【标识办法】打标签；QLT：黑屏、无声、纯静态图在预处理阶段检测 | 单元测试 |
| 部分处理 | IPR 侵权 | 判断是否获得授权需要版权库，本期没有。识别到影视画面、他平台水印时送人审 | 覆盖测试 |
| 兜底 | OTHER | 可疑但不属于任何已知类别，送人审。标签体系不可能写全，这一类保证新型风险不被默默放过 | 覆盖测试 |

模型层和 Agent 层输出到二级标签（如 `SEX-软色情`、`MIS-伪科学`），判罚引擎按二级标签定等级。同一个一级类下不同二级标签的等级可以差很多，例如 `SEX-轻度性暗示` 是 S3，`SEX-色情` 是 S1。

GEN 的标识结果（"该内容为生成合成内容"等提示）和 S3/S4 一样，当前回调契约里没有对应字段，先记录在审核服务内部。

**不审**：语音、视频动作、评论、直播、账号资料。

### 2. 做到什么程度

| 档位 | 内容 | 说明 |
|---|---|---|
| 必做 | 四层链路、判罚引擎、兜底与人审队列、决策日志、效果评测与消融实验、链路评测 | 证明链路设计对、出故障不乱放行。第八节第 1～5 步 |
| 加分 | 知识库与 Agent 层、检索评测、新热点集评测、红队攻防 | 证明 agent 能力和上线后仍有效。第八节第 6～7 步 |
| 只写设计，不实现 | 漂移监测告警、规则更新后回扫、申诉、临时策略的管理界面、人审工作台界面、视频指纹库 | 文档里讲清楚怎么做，面试能答，但不写代码 |

### 3. 两个前提

**独立开发，不依赖内容与发布模块**：内容与发布模块的业务代码还没写。审核服务用测试脚本扮演投递方和回调接收方，独立开发和评测，按 [内容与发布](../内容与发布/内容与发布.md) 的接口契约实现。和那边联调放到那边做完以后，不作为本模块的验收条件。

**评测时人审是模拟的**：没有真实审核员。评测时用标注答案充当人审结论，也可以注入一定错误率；"送人审"在指标里只算成本，体现为人审率。红队攻防里"人工确认后回流"同样用标注答案模拟。

## 二、链路：一条视频怎么走完

### 1. 三个例子

**例 1：标题"刷单兼职日赚500，加V：abc123"**（第①层就结束）

```
→ ① 规则层：
     正则命中微信号 → ADV-站外导流（S3）
     关键词命中"刷单兼职" → FRD-兼职与情感诈骗（S1）
→ ④ 判罚引擎：两个标签取最严 → S1 → 驳回，并标记作者账号风险
→ 回调"驳回"，理由"含兼职刷单诈骗信息"
全程不调用模型，成本几乎为零
```

如果标题只有微信号、没有诈骗词，就只命中 ADV-站外导流，等级 S3：视频可以发，但不进推荐。

**例 2：普通美食视频**（第②层就结束）

```
→ ① 规则层：无命中
→ ② 模型层：各类别分数都低于"通过线"（例如都 < 0.3）
→ ④ 判罚引擎：无标签 → 通过
→ 回调"通过"
```

**例 3：标题"这个茶喝一个月不用吃降糖药"**（走到第③层）

```
→ ① 规则层：无命中
→ ② 模型层：MIS-伪科学 0.55，落在通过线 0.3 和驳回线 0.85 之间，属于灰区
→ ③ Agent 层：
     查医疗类条款 → 找到"抖音医疗 X：不得宣称替代药物治疗"（条款编号为示意）
     查类似判例 → 找到同类"保健品替代药物"的处置公告
     结论：MIS-伪科学，依据 [抖音医疗X]
     服务端校验：引用的条款确实是这次查出来的 ✓
→ ④ 判罚引擎：MIS-伪科学 → 等级 S2 → 驳回
→ 回调"驳回"，理由按模板生成"宣称产品可替代药物治疗"
```

### 2. 四层各做什么

| 层 | 做什么 | 输入 | 输出 | 什么时候直接结束 |
|---|---|---|---|---|
| ① 规则层 | 哈希黑名单、关键词、导流正则 | 标题、简介、封面哈希 | 命中的标签 | 命中高置信规则 |
| ② 模型层 | 一次多模态模型调用 | 标题、简介、封面、关键帧 | 每个类别的分数和证据 | 分数高于驳回线或低于通过线 |
| ③ Agent 层 | 查条文、查判例，判断灰区 | 灰区样本 + 模型层结果 | 标签 + 依据条款 | 总是交给④ |
| ④ 判罚引擎 | 标签 → 等级 → 动作 | 前面各层的标签 | 通过 / 驳回 / 送人审 | — |

前一层能定的，后一层就不跑。越往后越贵、越慢，处理的样本越少。

### 3. 各层细节

**① 规则层**

- 封面和视频的 sha256 黑名单
- 关键词用 AC 自动机匹配。匹配前先归一化：全角转半角、繁体转简体、转拼音、去掉插入的符号、emoji 映射为文字。这一步专门对付"加 V""薇❤"这类变体
- 导流正则：手机号、微信号变体、URL
- 词表和正则带版本号

**② 模型层**

一次多模态模型调用，要求按 JSON schema 输出：

```json
{
  "labels": [
    { "code": "VIO-强烈感官刺激", "score": 0.82, "position": "画面", "evidence": "第 3 帧大面积出血" }
  ]
}
```

每个类别有两条线：高于驳回线直接判违规，低于通过线直接判安全，中间是灰区，交给③。两条线在开发集上调出来（见第五节）。

**③ Agent 层**

只处理灰区。可以调用的工具：

| 工具 | 作用 |
|---|---|
| `search_policy(query, category)` | 查条款库，先按类别过滤（知识库见第七节） |
| `search_cases(query, category)` | 查判例 |
| `get_frames(start, end, fps)` | 对可疑时间段加密抽帧 |
| `get_author_history(author_id)` | 查作者违规历史 |

它和普通 RAG 的区别：不是检索一次就回答，而是 Agent 自己决定查什么、查几次。例 3 里先查条款，拿不准再查判例，这就是 Agentic RAG。

Agent 的约束见第四节"兜底"。

**④ 判罚引擎**：见第三节。

### 4. 模型选型：开源模型 + vLLM 自部署

全部使用开源模型，用 vLLM 部署。vLLM 对外提供 OpenAI 兼容接口，审核服务只依赖这个接口，换模型只改配置。

| 用途 | 模型 | 说明 |
|---|---|---|
| ② 模型层 | Qwen3.8-27B，关闭思考模式 | 原生支持图片输入，中文能力强；FP8 约 38 GB，单卡可部署。关闭思考模式保证速度 |
| ③ Agent 层 | 同一个 Qwen3.8-27B，开启思考模式 | 支持工具调用。与②共用一个 vLLM 实例，按请求切换思考模式，只部署一份 |
| 红队 Agent | 同上 | 离线评测使用 |
| 检索向量 | Qwen3-Embedding（vLLM 以 embedding 模式部署） | 条款与判例加起来不到一千条，向量直接放内存暴力计算相似度，不需要向量数据库 |
| 对照基线 | LlavaGuard-v1.2-7B-OV | 开源的图像审核专用模型，只在消融实验里作对照组 |

型号依据 2026-11 的 vLLM Recipes。下载前核对模型卡、vLLM 最低版本和许可证。显存不够时可以换 INT4 量化（约 24 GB）或更小的 Qwen3.5 型号。

**用到的 vLLM 能力**

| 能力 | 用在哪 | 作用 |
|---|---|---|
| 结构化输出（按 JSON schema 约束解码） | ② 模型层 | 从解码阶段保证输出符合 schema，"输出格式不对"这类兜底基本不会触发 |
| 工具调用（`--enable-auto-tool-choice`，按模型卡配置 tool parser） | ③ Agent 层 | Agent 调用检索等工具 |
| 前缀缓存（prefix caching） | ②③ | 系统提示词和类别条款在每次请求里都相同，复用缓存降低首 token 延迟 |
| 固定温度与随机种子 | ②③ | 提高同一样本多次运行的一致性，对应一致性指标 |

自部署还有一个好处：链路评测可以直接对 vLLM 做故障注入，比如限流、停掉实例，测出来的是真实部署下的表现。

## 三、判罚怎么做

### 1. 核心原则：模型只"判"，代码来"罚"

- **判**（是什么问题）：由①②③输出标签，例如 `MIS-伪科学`
- **罚**（怎么处理）：由判罚引擎按配置表查出来，是一段确定性代码，不调用模型

这样分开的原因：模型输出有随机性，同一条视频跑两次可能说法不同；但处置必须稳定、可解释、可回放。

### 2. 判罚三步

**第一步：标签 → 等级**。每个标签在配置表里对应一个等级，同时命中多个时取最严的。

| 等级 | 含义 | 例子 |
|---|---|---|
| S0 | 违法且涉嫌犯罪 | 毒品交易、金融诈骗、恐怖主义 |
| S1 | 违法 | 色情、兼职刷单诈骗、赌博 |
| S2 | 平台不允许发布 | 软色情擦边、强烈感官刺激画面、伪科学 |
| S3 | 可以发，但不进推荐 | 站外导流、轻度性暗示、一般血腥 |
| S4 | 低质 | 搬运、黑屏花屏 |

每个二级标签的等级见 [风险标签体系](风险标签体系.md)。

**第二步：调整等级**

- 新号、有违规历史的账号提高一级
- 临时策略：突发热点期间可以临时调严某个类别，到期自动失效（见第六节）

**第三步：等级 → 动作**

| 等级 | 回调给内容与发布模块 | 审核服务内部另外记录 |
|---|---|---|
| S0 / S1 | 驳回 | 标记作者账号风险 |
| S2 | 驳回 | — |
| S3 | 通过 | 标记"不进推荐"，供以后的推荐模块读取 |
| S4 | 通过 | 标记"降权" |
| 无标签 | 通过 | — |

当前对接契约只有"通过 / 驳回"两种结论，所以 S3、S4 对内容与发布模块来说都是"通过"，差别只记录在审核服务里。

### 3. 给作者的理由

理由按"标签 + 条款"模板生成，例如"宣称产品可替代药物治疗"，不直接转发模型原话。这样同一类违规每次说法一致，也不泄露模型的推理过程。

### 4. 判罚配置

配置表就是"标签 → 等级"的映射，加上每个类别的通过线和驳回线、账号提级规则、临时策略。配置带版本号，每条结论都记录用的是哪个版本，以后可以用新配置回放旧样本，看结论会怎么变。

配置的内容从哪来：原始文档里讲"违规后怎么处置"的部分（例如【规定】第十、三十四条）和"某段时间要从严"的部分（例如节日期间的提醒），不进知识库，由人读完翻译成这里的配置。Agent 不检索它们，因为怎么罚由代码决定，不由模型决定。原始文档怎么拆见第七节。

标签、等级与条款的对应关系直接取自 [风险标签体系](风险标签体系.md)。

## 四、兜底怎么做

### 1. 唯一原则：拿不准或出故障，一律交给人，绝不默认通过

审核服务所有的兜底最后都汇到同一个出口：**人审队列**。

| 出问题的地方 | 现象 | 兜底 |
|---|---|---|
| ② 模型层 | 调用超时、报错、输出不符合 JSON schema | 重试，仍失败则送人审 |
| ② 模型层 | 模型服务持续不可用 | 熔断，新任务跳过模型直接送人审 |
| ③ Agent 层 | 超过步数、token 或时间上限 | 送人审 |
| ③ Agent 层 | 引用的条款不在本次检索结果里（编造条款） | 结论作废，送人审 |
| ③ Agent 层 | 一条相关条款都查不到（知识库缺这类规则） | 不自动驳回也不自动通过，送人审，并记录"依据缺口" |
| ④ 判罚引擎 | 出现涉政或未成年相关信号 | 送人审 |
| 服务进程 | worker 处理到一半崩溃 | 从上一个检查点继续，已完成的模型调用不重做 |
| 投递 | 同一任务重复投递 | 按 `task_id` 去重，只处理一次 |
| 回调 | 回调内容与发布模块失败 | 按退避重试，对方按任务状态去重，只落一次结论 |
| 回调 | 审核服务一直没回调 | 内容与发布模块定时调查询接口对账（对方已实现） |

### 2. 人审队列（最小实现）

- 一张队列表加一个管理接口：列出待审任务、提交结论
- 人审结论就是最终结论，走同一个回调通道
- 人审的样本不受 5 分钟时效要求约束，视频在此期间保持"待审核"。人审率控制在 5% 以内，不影响整体 P95
- 待审任务超过设定时长就告警
- 不做工作台界面，用接口或简单脚本即可

### 3. 为什么能放心兜底

- 从来不会出现"模型挂了所以默认放行"
- 链路评测专门注入故障来验证这一点（见第五节 B）

## 五、怎么证明链路没问题：Benchmark

| 评测 | 回答的问题 | 怎么做 |
|---|---|---|
| A. 效果评测 | 判得准不准？每一层有没有用？ | 标注好的评测集 + 消融实验 |
| B. 链路评测 | 出故障时会不会丢任务、乱放行？ | mock 模型 + 故障注入 + 自动断言 |
| C. 适应性评测 | 新热点、新绕过手法出现后还有效吗？ | 新热点集 + 红队攻防多轮 |

### A. 效果评测

**评测集**：约 800 条，分成开发集和测试集。通过线和驳回线只在开发集上调，最终结果只报测试集。

- 正常样本占一半以上，否则误杀率没有意义
- 只覆盖"机器自动判"的 8 个一级类，每类至少 50 条违规样本。少于这个数，召回率差一两条就是好几个百分点，结论不稳
- 违规样本标注到二级标签，尽量覆盖每类下等级不同的二级标签（例如 SEX 下既有 S1 的色情，也有 S3 的轻度性暗示），这样才能测出判罚等级对不对
- 样本形式以"标题 + 简介 + 封面图"为主
- 违规样本：文本类用治理公告和医疗公约的案例改写，再自动生成谐音、拆字、emoji 变体；图像类用公开研究数据集
- 语境样本：同样的内容放在新闻、科普、批判警示的语境里，专门测会不会误杀
- 每条标注：期望标签、期望等级、期望动作、依据条款、理论上该由哪一层拦住

**合成视频集**：上面的样本只有封面图，验证不了抽帧。用 ffmpeg 拼几十条视频：在正常片段的开头、中段、末尾分别插入违规画面，验证抽帧覆盖全程，能拦住"前几秒正常、后面才违规"的规避手法。

**指标**

| 指标 | 说明 |
|---|---|
| 严重漏放率 | S0/S1 被判通过的比例。目标为 0，第一指标 |
| 分类别召回率与精确率 | |
| 正常内容误杀率 | |
| 动作准确率 | 最终动作与期望动作一致的比例 |
| 人审率 | 越低说明自动化程度越高 |
| 引用有效率 | Agent 引用的条款真实存在且与结论相关的比例 |
| 一致性 | 同一样本跑 N 次，结论相同的比例 |
| 成本与耗时 | 每千条成本，P50/P95 耗时 |

**消融实验**（最核心的结果）：依次跑下面四组，把召回、误杀、人审率、成本、耗时放在同一张表里，证明每一层都有用。

1. 只有规则层
2. 规则层 + 模型层
3. 再加 Agent 层
4. 完整链路（再加判罚引擎）

另外加两组模型对照：模型层换成更小的 Qwen 型号，看效果下降多少、成本和耗时省多少；模型层换成 LlavaGuard，和专用审核模型比较图像类别的效果。

**Agent 层的检索评测**

- 每条违规样本标注了正确条款，统计正确条款有没有被检索出来（Recall@k）
- 三种给 Agent 条款的方式对比效果和成本：全部条款塞进上下文 / 先按类别过滤 / 类别过滤 + 判例检索
- 缺口测试：删掉某类的全部条款再跑，系统应该把这类样本送人审，而不是瞎判或编条款

**覆盖测试**：13 个一级类加 OTHER，每类准备几条触发样本，只验证每一类都走到正确的处理路径（自动判定、送人审或规则检测），不统计准确率。POL、MIN 只用不含违法内容的触发样本。GEN 和 QLT 是确定性规则，用单元测试验证。

### B. 链路评测

用 mock 模型（可以配置延迟、错误率、超时）做压测和故障注入：

| 场景 | 要证明的事 |
|---|---|
| 持续压测 | 吞吐量；端到端 P95 满足内容与发布模块要求的 ≤ 5 分钟 |
| 突发积压 | 积压任务多快能消化完 |
| 处理到一半杀掉 worker | 不丢任务，已完成的模型调用不重复 |
| 同一任务重复投递 | 只处理一次 |
| 模型 50% 超时 | 所有任务最终都有结论，没有一条未经人审就放行 |
| 回调失败 | 重试后内容与发布模块只落一次结论 |
| 抽样回放决策日志 | 用日志里的模型输出和配置版本重跑判罚引擎，结论 100% 一致 |
| 尝试修改或删除决策日志 | 执行失败 |

每个场景写成自动断言，不靠人工看日志。

### C. 适应性评测

**新热点集**：从治理公告里取时间较晚的案例组成一个集合，不放进开发集。

1. 知识库里没有对应规则时测一次召回，作为基线
2. 只按公告补充词表、条款或判例，不改代码和提示词，再测一次召回和误杀
3. 报告召回提升、误杀变化，以及从补充到生效花了多久

注意：补充的判例不能就是测试样本本身，否则等于泄题。

**红队攻防**：用一个红队 Agent 改写已知违规样本，攻击自己的链路。

1. 每轮记录攻击成功率（改写后被判通过的比例）和正常样本误杀率
2. 绕过成功的样本经过人工确认后回流成新规则（见第六节）
3. 再攻击下一轮

预期攻击成功率逐轮下降、误杀率基本不变。最后再用 ToxiCloakCN 这类外部对抗集测一次，避免只对自己生成的改写有效。

### D. 数据合规

评测数据不收集真实违法内容，不收集任何涉及未成年人的图像。MIN 类因此不进评测集（见第一节）。

## 六、上线后怎么保持有效

静态的规则只能证明上线那天有效。热点会变（概念漂移），想绕过审核的人也会换手法（对抗性适应）。

本节哪些要实现：补知识、人审回流、决策日志和 `decided_by` 要实现；漂移监测告警、规则更新后回扫、申诉只写设计（见第一节"做到什么程度"）。

**热点变化：补知识，不重新训练**

- 新热点只要往词表、条款库或判例库里加内容就能生效，分钟级，不用重新训练模型。这是"大模型 + 检索"方案相比传统分类模型的优势
- 紧急情况用临时策略：临时加词、临时调严某个类别，有生效时间和过期时间，到期自动失效
- 每天看两个信号，异常就告警：各类别命中率的日环比；人审推翻机审的比例（突然升高说明出现了没覆盖的新情况）
- Agent 记录的"依据缺口"按类别汇总，就是下一批要补的文档清单
- 规则更新后回扫：用新规则重跑近期已发布视频，可能违规的调用内容与发布模块的复审入口（`POST /internal/videos/{videoId}/rereview`，`trigger=manual`），走正式复审流程，回扫本身不直接下架

**绕过手法变化：人审结论回流**

1. 人审确认违规、但机审放过或判成灰区的样本，抽取其中的变体写法，生成候选规则和候选判例
2. 候选规则必须先在评测集上跑：召回提升、误杀不升，才允许合入
3. 不允许系统自动上线规则，否则攻击者可以故意投喂特定内容，诱导系统学进会误杀正常内容的规则

**可追溯**

| 要求 | 怎么做 |
|---|---|
| 查得到（可审计） | 决策日志只增不改，应用账号只有 INSERT 权限，改判也是追加一条新记录。保存输入哈希、各层原始输出、Agent 每一步的工具调用与返回、命中的规则与临时策略、配置版本、提示词版本、模型名。留存至少 6 个月 |
| 知道是谁定的（可问责） | 每条结论记录 `decided_by`：机器或某个审核员。审核员改判必须填理由。临时策略和回流规则记录创建人与审批人 |
| 作者能申诉（可申诉） | 最小版本：申诉进人审队列，不能分给原审核员。内容与发布模块目前没有申诉入口，也不允许"已驳回"改成"已通过"，需要先在那边补契约 |

## 七、Agent 层的知识库

### 1. 知识库只有两类：条款库和判例库

| | 条款库 | 判例库 |
|---|---|---|
| 回答什么问题 | 什么不允许 | 类似情况以前怎么判 |
| 入库单位 | 一条条款 | 一个案例 |
| Agent 怎么用 | `search_policy` | `search_cases` |
| 能否作为驳回依据 | 能，依据只能引用条款 | 不能，只作参考，帮助判断边界和语境 |
| 规模（2026-11-16） | 约 6 万字 | 106 篇公告，约 15 万字，整理后条数待定 |
| 检索方式 | 先按类别过滤，通常只剩十几条，直接全部给 Agent | 关键词检索加向量检索 |

本地文档不全，以后还会持续补充。所以要定的不是"现有文件怎么分"，而是"任何一份新文档进来怎么拆"。

### 2. 原始文档怎么拆

一份原始文档进来后，按内容拆到三个去处，剩下的不用：

| 文档里的内容 | 去处 |
|---|---|
| 规定什么不允许 | 条款库 |
| 具体案例：什么内容、怎么判的 | 判例库 |
| 违规后平台要怎么处置、怎么处罚；某段时间要从严 | 不进知识库，由人翻译成判罚配置（见第三节"判罚配置"） |
| 处罚统计、谣言澄清、宣传类内容 | 不用 |

用现有文件举例：

| 原始文档 | 条款库 | 判例库 | 判罚配置 | 不用 |
|---|---|---|---|---|
| 【规定】 | 第六、七条（违法和不良信息） | — | 第十、三十四条（平台的处置义务） | — |
| 【细则】 | 100 条"不得出现" | — | — | — |
| 【抖音医疗】 | 正文 | 附带的 6 个案例 | — | — |
| 抖音治理公告 | 规则更新类，如《营销行为》规则更新 | 专项治理、防骗提醒 | 节日提醒，如清明期间提醒，作为临时策略 | 处罚通告、谣言澄清 |

抖音治理公告这个目录最能说明问题：同一个来源里，四个去处都有，所以不能按来源整个归类，必须逐篇判断。

### 3. 每条内容的标注

**条款**

| 字段 | 取值 | 用途 |
|---|---|---|
| 条款 ID | 沿用[风险标签体系](风险标签体系.md)的写法，如 `规定6(9)`、`细则64` | 引用依据；保持稳定，文档更新只升版本，不改编号 |
| 效力层级 | 法律 > 行政法规 > 部门规章 > 行业标准 > 本平台规范 > 他平台规则（仅参考） | 冲突时高层级定下限、取最严 |
| 风险类别 | 风险标签体系的一级类，可多选 | 检索前按类别过滤 |
| 适用载体 | 视频 / 封面 / 标题 / 直播 / 评论 / 账号资料 | 审视频时排除直播、评论类条款 |
| 垂类 | 医疗 / 金融 / 新闻 / 通用 | 医疗内容优先查医疗条款 |
| 时效 | 生效日期、失效日期、被哪条替代 | 只查当前有效的 |
| 来源 | 发布机构、原文链接、抓取日期、完整度 | 可追溯；只有标题没有正文的不能作为唯一依据 |

**判例**

| 字段 | 取值 | 用途 |
|---|---|---|
| 判例 ID | 如 `抖音公告-2024-03-27-AI虚拟人` | 记录 Agent 参考了哪个判例 |
| 违规手法 | 一两句话概括内容是什么、怎么违规 | 检索的主要文本 |
| 处置结果 | 删除、限流、封号等 | 让 Agent 知道以前判得多重 |
| 关联条款 | 条款 ID 列表 | 从判例找回可以引用的条款 |
| 风险类别、适用载体 | 同条款 | 检索前过滤 |
| 日期与来源 | 发布日期、原文链接 | 可追溯；新热点集按日期划分 |

判例里的"关联条款"很重要：Agent 通过判例找到相似情况后，顺着关联条款回到条款库，最终引用的仍然是条款。

PulseFrame 是独立平台，抖音、快手的规则对它没有约束力。MVP 阶段可以引用，但效力标为"参考"，给作者的理由里不出现他平台名称；长期应整理出本平台社区规范。

## 八、实施：从哪一步开始

代码位置：独立进程 `backend/cmd/pulseframe-review`，业务代码放 `backend/internal/review`，文件组织沿用 auth 模块的约定（model → errors → repository → service → handler → routes），使用自己的数据库。

### 第 1 步：判罚配置与判罚引擎（从这里开始）

**为什么先做它**：所有层的输出最后都汇到这里。先定下"有哪些标签、对应什么等级、产生什么动作"，后面每一层就知道该输出什么，评测集也知道该标什么。它是纯函数，不依赖数据库和模型，一两天能写完并测透。

- 把 [风险标签体系](风险标签体系.md) 全部二级标签写成"标签 → 等级"配置；POL、MIN、IPR、OTHER 写成"出现信号就送人审"的规则
- 实现判罚函数：输入各层标签，输出等级、动作、给作者的理由
- 单测覆盖：多标签取最严、账号提级、POL/MIN/IPR/OTHER 送人审、临时策略过期

**验收**：给定任意标签组合，输出确定；单测通过。

### 第 2 步：规则层

- 文本归一化、AC 自动机、导流正则、哈希黑名单
- GEN 元数据标识读取、QLT 黑屏/无声/静态图检测
- 用几十条手写样本（含变体写法）测召回和误杀

**验收**：例 1 能在规则层被拦住，变体写法也能拦住。

### 第 3 步：把服务串起来

- 三张表：`review_job`（任务和各阶段检查点）、决策日志（只增不改）、人审队列
- 接收投递接口（按 `task_id` 去重）、查询接口、回调 outbox
- worker 用租约领取任务，按 ① → ② → ③ → ④ 推进，每完成一层落一次检查点
- 模型层和 Agent 层先用 mock 实现：写一个假的 OpenAI 兼容服务，可以配置延迟、错误率、超时。审核服务只认 OpenAI 兼容接口，之后换成 vLLM 不改代码
- 写一个测试脚本扮演内容与发布模块：按契约投递任务、接收回调、调用查询接口

**验收**：用测试脚本跑通例 1、例 2。不依赖内容与发布模块（见第一节"两个前提"）。

### 第 4 步：链路评测

- 实现第五节 B 的所有场景，写成自动断言

**验收**：全部断言通过。到这里是第一个里程碑：链路是对的、出故障不会乱放行，只是模型层还是假的。

### 第 5 步：评测集与真实模型层

- 用 vLLM 部署 Qwen3.8-27B（见第二节第 4 小节），开启结构化输出
- 建评测集和合成视频集（第五节 A），接入真实模型
- 在开发集上调通过线和驳回线，跑消融实验的前两组

**验收**：效果评测出第一版结果。到这里"必做"档完成。

### 第 6 步：知识库与 Agent 层

- 按第七节拆分原始文档：条款进条款库、案例进判例库、处置与从严内容翻译成判罚配置；公告逐篇判断去处；按字段标注
- 实现 Agent 层：检索工具、引用校验、步数上限、依据缺口记录
- 跑完整消融、检索评测、一致性评测

**验收**：例 3 能走通，并且引用的条款能通过校验。

### 第 7 步：保持有效

- 人审回流：用标注答案模拟人工确认，生成候选规则，经评测把关后合入
- 红队 Agent，跑新热点集和红队攻防评测

### 只写设计，不实现

漂移监测告警、规则更新后回扫、申诉、临时策略的管理界面、人审工作台界面、视频指纹库。设计见第六节和第一节。

**时间有限时的取舍**：第 1～5 步是"必做"，证明链路设计对、出故障不乱放行；第 6～7 步是"加分"，证明 agent 能力。第 7 步里优先做红队攻防，它回答的是"上线一个月后还有没有效"，面试最容易被追问。

## 十、参考论文与开源仓库

以下条目均已核对发表会议与仓库地址（2026-11-16）。专门研究短视频审核的公开论文很少，本方案借鉴的是图像审核、文本审核和 LLM 级联三个方向的成果，再组合成视频审核链路。

### 1. 整体方案：LLM 按策略审核

| 论文 / 仓库 | 借鉴点 |
|---|---|
| [A Holistic Approach to Undesired Content Detection in the Real World](https://arxiv.org/abs/2208.03274)（OpenAI，AAAI 2023），仓库 [openai/moderation-api-release](https://github.com/openai/moderation-api-release)（含 1680 条评测集） | 生产审核系统的标签体系、标注质量控制、正常样本远多于违规样本时的采样与评测、用主动学习挖掘稀有违规样本。对应第五节评测集构建 |
