# MySQL 表

流程说明见 [内容与发布](内容与发布.md)。本文件定义上传凭证、视频主体、计数、送审记录四张表，以及幂等键所需的 Redis 结构。

## 通用约定（MySQL）

```text
使用 MySQL 8.0.16 及以上版本、InnoDB，外键与 CHECK 约束必须生效。
author_id / owner_id 引用 users.id，使用服务端生成的规范小写 UUIDv4。
ID 类与外部标识字段使用 ASCII 字符集与 ascii_bin 比较规则；标题、简介等文本使用 utf8mb4。
所有 DATETIME(3) 均由应用按 UTC 写入；未注明"可空"的字段均为 NOT NULL。
created_at、updated_at 由应用维护。
外键统一采用 ON DELETE RESTRICT、ON UPDATE RESTRICT，物理删除按依赖顺序显式执行。
本模块不建物理外键到互动模块（点赞、评论、收藏）的表，跨模块清理以事件驱动，避免双向依赖。
```

字段类型选择说明：`author_id` 用 `CHAR(36) CHARACTER SET ascii COLLATE ascii_bin`，不用 `VARCHAR(36) utf8mb4`——后者单列占 144 字节，`idx_video_author_status` 会膨胀 4 倍。媒体字段存对象键（`VARCHAR(512)`），不存完整 URL，URL 由读取层按配置拼装。

## 1. upload：上传凭证表（19 字段）

一次成功上传对应一行，视频与封面图共用此表。它同时承担三件事：媒体元数据的可信来源、媒体归属的校验依据、孤儿对象的回收依据。

| 字段 | 类型 | 约束 | 用途 |
| --- | --- | --- | --- |
| id | BIGINT UNSIGNED | 主键，自增 | 上传凭证 ID，对外暴露 |
| owner_id | CHAR(36) ascii_bin | users.id 外键 | 上传者，绑定视频时校验归属 |
| kind | TINYINT UNSIGNED | 默认1，CHECK 限定1-2 | 1视频/2封面图，决定哪些媒体字段有值 |
| media_key | VARCHAR(512) | 可空；kind=1 时必填 | 视频对象键 |
| cover_key | VARCHAR(512) | 可空 | 封面对象键；kind=1 且为空表示由服务端取首帧 |
| content_type | VARCHAR(64) | 无默认 | 探测得到的 MIME，如 video/mp4、image/jpeg |
| codec | VARCHAR(32) | 可空；kind=1 时必填 | 视频编码，如 h264 |
| audio_codec | VARCHAR(32) | 可空 | 音频编码，如 aac；无声视频为空 |
| size_bytes | BIGINT UNSIGNED | CHECK 大于 0 | 文件大小，用于配额统计与限流 |
| duration_ms | INT UNSIGNED | 可空；kind=1 时必填且大于 0 | 时长（毫秒），Feed 展示进度条必需 |
| width | SMALLINT UNSIGNED | 可空；kind=1 时必填且大于 0 | 视频宽度，列表布局占位防抖动 |
| height | SMALLINT UNSIGNED | 可空；kind=1 时必填且大于 0 | 视频高度，判定竖屏/横屏分流 |
| source_sha256 | CHAR(64) ascii_bin | 无默认，索引 idx_upload_source_sha | 原始上传字节指纹，用于去重、上传幂等与凭证冲突判定 |
| sha256 | CHAR(64) ascii_bin | 无默认 | 最终写入对象的字节指纹（faststart/remux 之后），用于对象键与完整性校验 |
| pending_sha | CHAR(64) ascii_bin | 生成列 STORED，可空 | 见下；仅 status=1 时有值，取 source_sha256，用于约束"同一作者最多一条待绑定凭证" |
| status | TINYINT UNSIGNED | 默认1，CHECK 限定1-3 | 1待绑定/2已绑定/3已作废 |
| created_at | DATETIME(3) | 创建时间 | 创建时间，兼作孤儿扫描依据 |
| updated_at | DATETIME(3) | 最近修改时间 | 状态变更时间 |
| expires_at | DATETIME(3) | 无默认 | `created_at + 24h`，逾期未绑定即回收 |

"kind=1 时必填"由应用层校验，不用 CHECK 表达跨列依赖：MySQL 的 CHECK 虽支持跨列，但条件会随业务扩展频繁变动，改约束要重建表；应用层校验配合单测更容易演进。

```text
索引：
- idx_upload_owner_created (owner_id, created_at)：我的上传列表与配额统计
- uk_upload_pending (owner_id, pending_sha)：同一作者最多一条待绑定同源文件凭证。
  生成列 pending_sha = IF(status = 1, source_sha256, NULL)，MySQL 唯一索引不比较 NULL，
  因此已绑定（status=2）的多行同指纹记录不受限制，只有"待绑定"这一种状态被约束住
- idx_upload_source_sha (owner_id, source_sha256, status)：同作者查同源文件历史凭证
- idx_upload_expire (status, expires_at)：孤儿与作废凭证扫描，覆盖 status IN (1,3)

status=3 已作废仅在作者明确放弃凭证时写入，便于排查"为什么这个文件没了"。
后台任务每小时执行孤儿扫描：对 status IN (1,3) AND expires_at < now() 的记录，
  先确认 media_key / cover_key 没有被其他 upload 或 video 行引用（去重可能共享同一对象），
  仅当无引用时才删除对象，然后删除本行记录。
引用检查与对象删除之间用存储侧的"标记-延迟删除"兜底：对象先标记，24 小时后仍无引用才真正删除。
对象键按最终字节内容寻址：media/{owner_id}/{sha256前2位}/{sha256}.mp4；
  封面按 content_type 使用 .jpg 或 .png，key 为 media/{owner_id}/{sha256前2位}/{sha256}.{ext}。
  sha256 取 faststart/remux 之后的最终字节；source_sha256 只用于去重与幂等，不参与对象键。
  同一作者上传相同文件、且最终字节一致时必然落到同一个对象键，并发 Put 写同一份字节，
  "对象只存一份"由存储层保证，不依赖应用层"先查后写"。
  MOV 在本期只做容器重封装为 MP4（流复制，不转码），对象键与 content_type 统一为 .mp4 / video/mp4；
  重封装失败直接拒绝上传，不允许把 MOV 字节写进 .mp4 键。
凭证去重（两阶段，处理并发）：
  1) INSERT upload(status=1)。若撞 uk_upload_pending，说明并发请求已插入待绑定同指纹凭证
  2) 捕获唯一键冲突后回查 (owner_id, source_sha256, status=1)：
     记录未过期 → 返回已有 uploadId，不再落对象
     记录已过期 → 同一事务把旧行置 status=3、expires_at=now()，再插入新行，避免返回即将被回收的凭证
  3) 查不到（对方事务已回滚或已绑定）则重试一次 INSERT
  同指纹记录均已绑定          → 另建一行 upload，media_key 指向同一对象（同一内容键）
去重只按 (owner_id, source_sha256) 判定，不跨用户复用：跨用户复用会让 A 的上传凭证出现在 B 的命名空间里，越权边界变模糊。

kind 由上传接口的 `?kind=video|image` 决定（缺省 video）：video → kind=1，image → kind=2，不接收客户端直接传数值。
kind=2 的封面图上传只填 cover_key、content_type、size_bytes、source_sha256、sha256，媒体字段为空，status 与复用规则不变。
kind=2 仅接受 JPEG/PNG，单张上限 5MB；其他图片格式返回 415，避免为封面引入转码。
media_key、duration_ms、width、height、content_type 一经写入不再修改；video 的 cover_key 是唯一可在草稿/驳回态修改的媒体字段，且只能由 kind=2 的凭证复制。
size_bytes 记录最终写入对象的字节数；faststart/remux 改变大小时以最终值为准。
cover_upload_id 只指向 kind=2 的独立封面凭证。服务端从视频抽帧得到的封面不另建 upload，
cover_upload_id 保持为空，封面对象归主媒体 upload 所有；换封面时不得把主媒体 upload 置为作废。
```

## 2. video：视频主体表（25 字段）

| 字段 | 类型 | 约束 | 用途 |
| --- | --- | --- | --- |
| id | BIGINT UNSIGNED | 主键，自增 | 视频 ID |
| author_id | CHAR(36) ascii_bin | users.id 外键 | 作者 ID |
| upload_id | BIGINT UNSIGNED | upload.id 外键，唯一索引 | 来源上传凭证，用于溯源与去重 |
| title | VARCHAR(64) | 默认 '我发布了新视频，快来看看!' | 标题 |
| description | VARCHAR(1000) | 默认 '' | 简介与话题文本，Feed 展示、搜索与推荐的核心输入 |
| media_key | VARCHAR(512) | 无默认 | 视频对象键，创建后不可变 |
| cover_upload_id | BIGINT UNSIGNED | 可空，upload.id 外键，唯一索引 | 独立封面凭证（kind=2）的来源；服务端自动抽帧时为空，封面属于主媒体 upload |
| cover_key | VARCHAR(512) | 可空 | 封面对象键；只能由 upload 记录的 cover_key 复制而来，不接受客户端直传 |
| duration_ms | INT UNSIGNED | CHECK 大于 0 | 时长，从 upload 复制，不可变 |
| width | SMALLINT UNSIGNED | CHECK 大于 0 | 宽度，不可变 |
| height | SMALLINT UNSIGNED | CHECK 大于 0 | 高度，不可变 |
| status | TINYINT UNSIGNED | 默认0，CHECK 限定0-4 | 0草稿/1待审核/2已发布/3已驳回/4已下架 |
| review_round | INT UNSIGNED | 默认0 | 当前审核轮次，回调按轮次判新旧 |
| reject_reason | VARCHAR(200) | 可空 | 驳回原因，`review_task.reason` 的展示冗余 |
| submitted_at | DATETIME(3) | 可空 | 最近提交审核时间；草稿为空 |
| published_at | DATETIME(3) | 可空 | 首次通过时间，公开列表排序基准 |
| hidden_at | DATETIME(3) | 可空 | 作者隐藏时间；非空表示仅自己可见 |
| offline_at | DATETIME(3) | 可空；status=4 时必填 | 平台下架时间 |
| offline_reason | VARCHAR(200) | 可空 | 平台下架理由，作者可见 |
| deleted_at | DATETIME(3) | 可空 | 作者删除时间，进回收站保留 7 天 |
| is_public | TINYINT | 生成列，STORED | 业务期望的公开状态：已发布且未隐藏、未下架、未删除 |
| public_object_present | TINYINT UNSIGNED | 默认0，CHECK 限定0-1 | 公开桶副本是否已就绪；0未同步/1已就绪 |
| is_playable | TINYINT | 生成列，STORED | 见下；公开桶副本就绪后的可播放状态，列表与播放接口唯一过滤条件 |
| created_at | DATETIME(3) | 创建时间 | 创建时间，草稿列表排序依据 |
| updated_at | DATETIME(3) | 最近修改时间 | 最近编辑时间，仅用于记录修改时刻 |

```text
生成列定义：
is_public TINYINT GENERATED ALWAYS AS (
  IF(status = 2 AND hidden_at IS NULL AND deleted_at IS NULL AND offline_at IS NULL, 1, 0)
) STORED
is_playable TINYINT GENERATED ALWAYS AS (
  IF(is_public = 1 AND public_object_present = 1, 1, 0)
) STORED

状态与时间字段的一致性约束（CHECK，MySQL 8.0.16 支持跨列 CHECK）：
  chk_video_published  CHECK (status <> 2 OR published_at IS NOT NULL)
  chk_video_submitted  CHECK ((status IN (1,2,3,4)) = (submitted_at IS NOT NULL))
  chk_video_rejected   CHECK (status <> 3 OR reject_reason IS NOT NULL)
  chk_video_reject_clear CHECK (status = 3 OR reject_reason IS NULL)
  chk_video_offline    CHECK ((status = 4) = (offline_at IS NOT NULL))
  chk_video_hidden     CHECK (status = 2 OR hidden_at IS NULL)
  chk_video_draft_clean CHECK (
    status NOT IN (0) OR (submitted_at IS NULL AND published_at IS NULL
                          AND offline_at IS NULL AND reject_reason IS NULL)
  )

约束带来的写路径要求（容易踩）：
  1. 审核通过写 status=2 时必须在同一语句里写 published_at，否则 chk_video_published 直接拒绝
  1b. 重新提交写 status=1 时必须清空 reject_reason：chk_video_reject_clear 要求非驳回状态不保留旧原因，
      界面只在 status=3 展示 reject_reason，避免把上一轮原因当成当前结论
  2. 下架写 status=4 时同一语句写 offline_at 并清 hidden_at：chk_video_hidden 要求非 2 状态不得有 hidden_at，
     "隐藏中的视频被下架"必须先清 hidden_at，否则下架失败
  3. 提交审核写 status=1 时同一语句写 submitted_at
  3b. 撤回审核写 status=0 时同一语句清 submitted_at 与 reject_reason：
      否则"驳回 → 提交 → 撤回"留下的 reject_reason 会违反 chk_video_draft_clean
  4. 删除（deleted_at）不改 status，因此不触发上述约束；回收站里的记录仍保留原状态所需的时间字段
  5. 不做"下架时清 published_at"：发布历史需要保留，可见性已由 is_public 的 offline_at 条件保证
  6. 恢复回收站记录时若 status=1，必须在同一语句改回 status=0 并清 submitted_at、reject_reason：
     删除时当前轮任务已置 7，恢复后不会再有 worker 投递，留在待审核会永久卡住

索引：
- uk_video_upload (upload_id)：一张上传凭证只能绑定一个视频；绑定关系只在这一侧，upload 不存 video_id
- uk_video_cover_upload (cover_upload_id)：一张封面凭证只能绑定一个视频，防止并发换封面重复绑定
- idx_video_feed (is_playable, published_at, id)：公开列表与 Feed 游标分页
- idx_video_public_sync (is_public, public_object_present)：公开桶副本对账扫描
- idx_video_author_created (author_id, created_at, id)：我的作品（全部）
- idx_video_author_status (author_id, status, created_at, id)：按状态过滤的作品列表，草稿按创建时间排序命中此索引
- idx_video_recycle (author_id, deleted_at)：回收站列表
- idx_video_purge (deleted_at)：超期清理扫描
- idx_video_pending (status, submitted_at)：待审核最老记录与对账扫描
```

索引设计说明：

- 公开列表不再用 `(status, created_at, id)`。原设计把 `status`、`deleted_at`、`hidden_at` 拆成三个 WHERE 条件，后两个不在索引里，热门作者下会大量回表；用生成列 `is_playable` 把业务可见性与公开桶就绪状态压成一个索引前缀，等值命中后再按 `published_at` 排序，全程不回表。
- `published_at` 必须独立存在。若用 `created_at` 排序，草稿放置数天后通过审核会直接沉到旧内容区，审核耗时变成排序误差。
- 清理扫描走 `idx_video_purge`，但需配合 `status`/`is_public` 判断，实际 SQL 为 `WHERE deleted_at < ? LIMIT 500`，命中后逐条处理，不做一次性全表删。
- `is_public` 与 `is_playable` 都是 STORED 生成列，写路径无需维护；`is_public` 只表达业务期望，`is_playable` 额外要求公开桶副本已就绪，避免"审核已通过但对象还没复制完"时返回 404 播放地址。

### 状态与可见性的关系

五个状态与五个时间字段共同表达"这条视频现在处于什么阶段、谁能看见"：

| 组合 | 语义 | 对外可见 | 作者可编辑 | 可执行动作 |
| --- | --- | --- | --- | --- |
| status=0，deleted_at 空 | 草稿 | 否 | 是 | 编辑、提交、删除 |
| status=1，deleted_at 空 | 待审核 | 否 | 否 | 撤回、删除 |
| status=2，hidden_at 空 | 已发布 | 是 | 否 | 隐藏、删除 |
| status=2，hidden_at 非空 | 已发布但隐藏 | 否 | 否 | 恢复公开、删除 |
| status=3，deleted_at 空 | 已驳回 | 否 | 是 | 编辑后重新提交、删除 |
| status=4，deleted_at 空 | 平台下架 | 否 | 否 | 仅删除，不可恢复公开、不可再提交审核（终态） |
| deleted_at 非空 | 回收站 | 否 | 否 | 7 天内恢复、可再次删除 |

判断维度互不重叠：

- `status` 回答"发布流程走到哪一步"。
- `submitted_at` 回答"这一轮什么时候交出去的"，供审核时长统计与对账，不再兼任状态位。
- `hidden_at` 回答"作者愿不愿意给人看"，与审核结论无关，恢复时不需要重新审核。
- `offline_at` 回答"平台是否判定违规"，与作者意愿无关，作者不能通过隐藏/恢复接口绕过。
- `deleted_at` 回答"是否在回收站"，与上面四者都无关，可叠加在任意状态上。

status=4 是终态，所有状态更新语句都带 `status <> 4`，防止作者通过隐藏/恢复/重新提交绕回可见。

`is_public` 里额外带 `offline_at IS NULL` 是冗余保险：正常路径下 status=4 已足以判定不可见，但如果哪次状态更新漏写、或被人工 SQL 改动，只要 `offline_at` 有值就不会重新变为公开。生成列是数据库层的事实，比任何一条应用代码都可靠。

可见性优先级：`offline_at` > `deleted_at` > `hidden_at`。下架由平台决定，作者的任何操作都不能让它重新可见；删除是作者意愿，恢复后回到原状态（若原状态是下架，则恢复后仍不可见）；隐藏只影响公开可见性，不影响审核与下架结论。

原设计把"下架"并入 `deleted_at` 是错的：下架是平台处置，需要操作人、理由与申诉记录，且**不能让作者用恢复接口一键撤销**；删除是作者意愿，必须可恢复。两者语义、权限、审计要求都不同，合并后管理端接入时只能推翻重建。

### 公开桶副本的一致性

`is_public` 只表示业务期望公开，`public_object_present` 表示公开桶副本是否真的存在。两者由对账任务收敛，读路径用 `is_playable` 同时要求二者成立：

```text
发布（审核通过）：status=2、published_at 写入，public_object_present 保持 0
  对账任务扫描 is_public=1 AND public_object_present=0
  复制私有桶对象到公开桶（key 不变）→ 成功置 present=1，失败保持 0 并告警
  可播放延迟上限由对账周期决定，默认 30 秒

撤销（隐藏、下架、删除）：is_public 变为 0
  对账任务扫描 is_public=0 AND public_object_present=1
  删除公开桶副本 → 成功置 present=0，失败保持 1 并告警
  请求路径同时做一次尽力删除，减少暴露窗口

恢复公开（取消隐藏，或恢复回收站中 status=2 且 hidden_at 为空的记录）：is_public 重新变为 1
  若 present 仍为 1 则立即可播；若撤销时已删除，则由发布对账重新复制
```

对账任务必须幂等：复制前检查目标对象是否存在，删除前检查 `is_public` 仍为 0。公开桶 key 与私有桶一致，复制是覆盖写，不会产生第二份命名空间。

`public_object_present` 是视频级标记，只有 `media_key` 与 `cover_key` 都复制成功后才置 1；任一失败保持 0，下轮同时重试两者。封面为 `cover_key` 为空时只复制视频对象。

标记回写必须带条件，避免与用户操作交叉：
  UPDATE video SET public_object_present=1 WHERE id=? AND is_public=1
  UPDATE video SET public_object_present=0 WHERE id=? AND is_public=0
复制完成时若用户已隐藏，第一条影响 0 行，下轮按"应删除"处理；删除完成时若用户已恢复公开，第二条影响 0 行，下轮按"应复制"处理。

CDN 缓存与对象删除之间存在窗口：对象删除成功不代表边缘节点立即失效，方案要求发布/撤销后调用 CDN 刷新该 key，并在文档与告警中保留"对象删除失败 + CDN 未刷新"两条指标。公开地址不能承诺毫秒级失效，只承诺 `is_playable=0` 后接口不再返回该地址，且对象清理在分钟级完成。

## 4. review_task：送审记录表（13 字段）

一轮审核一行。它既是审核状态记录，也是投递队列（outbox）。

| 字段 | 类型 | 约束 | 用途 |
| --- | --- | --- | --- |
| id | BIGINT UNSIGNED | 主键，自增 | 任务 ID |
| video_id | BIGINT UNSIGNED | video.id 外键 | 关联视频 |
| review_round | INT UNSIGNED | CHECK 大于 0 | 第几轮审核，与 video.review_round 对应 |
| external_task_id | VARCHAR(64) ascii_bin | 可空，唯一索引 | 审核平台返回的任务 ID，回调据此定位 |
| status | TINYINT UNSIGNED | 默认1，CHECK 限定1-7 | 见下表 |
| reason | VARCHAR(200) | 可空 | 驳回原因（权威来源） |
| review_source | VARCHAR(64) | 默认 'platform' | 审核方标识，如 platform / agent，便于多审核方并行 |
| attempt_count | SMALLINT UNSIGNED | 默认0 | 投递尝试次数 |
| next_attempt_at | DATETIME(3) | NOT NULL，默认 CURRENT_TIMESTAMP(3) | 允许被领取的时间；插入时必须可比较，见下 |
| lease_owner | VARCHAR(64) ascii_bin | 可空 | 领取该任务的 worker 批次令牌 |
| lease_expires_at | DATETIME(3) | 可空 | 租约到期时间；到期未完成则由扫尾任务回收 |
| created_at | DATETIME(3) | 创建时间 | 送审记录创建时间 |
| decided_at | DATETIME(3) | 可空 | 审核结论时间 |

status 取值：

| 值 | 含义 | 后续动作 |
| --- | --- | --- |
| 1 | 待投递 | 可被 worker 领取 |
| 2 | 投递中 | 已被某个 worker 领取，持有租约，正在调审核平台 |
| 3 | 审核中 | 已送达平台，等回调或对账 |
| 4 | 通过 | 终态 |
| 5 | 驳回 | 终态 |
| 6 | 投递失败 | 重试超限，告警；作者可撤回后重新提交 |
| 7 | 本地已撤销 | 作者撤回或视频删除时写入；外部可能仍在审，迟到回调只更新本任务结论，不改 video.status |

```text
索引：
- uk_review_external (external_task_id)：回调定位任务，也是回调去重的物理保证
- uk_review_video_round (video_id, review_round, review_source)：同一视频同一轮同一审核方唯一。
  接入内容安全 Agent 时不同 review_source 可并行，不改索引；结论合并规则仍在业务层
- idx_review_dispatch (status, next_attempt_at)：投递 worker 领取待投递任务
- idx_review_lease (status, lease_expires_at)：扫尾任务回收租约过期的"投递中"记录
- idx_review_reconcile (status, created_at)：对账扫描审核中超时记录
- idx_review_video (video_id)：按视频查历史轮次
```

为什么 `review_task` 要加 `review_round` 和 `external_task_id`：

- 没有轮次编号，作者被驳回后改文案重新提交，上一轮的迟到回调会把新一轮结果覆盖掉，视频会莫名变成"已驳回"或"已发布"。有轮次后，回调必须命中 `video.review_round`，否则按过期回调忽略。
- 没有外部任务 ID，回调无从定位，去重也无从实现；原设计给 webhook 标了"支持幂等键"，但表里没有任何字段能承载幂等，等于空承诺。

为什么状态从 3 档扩到 7 档：原设计只有待审/通过/驳回，无法表达"正在投递"、"投递失败"和"作者已撤回"。缺"正在投递"就无法把长耗时的外部调用移出事务；缺"投递失败"会让视频永久卡在待审核且无人知晓；缺"已撤销"会让对账反复扫描已作废记录。

### 送审在事务内还是事务外

结论：**落库在事务内，网络调用在事务外**，中间用"领取 + 租约"衔接，而不是靠行锁跨进程传递。

```text
① 提交审核（业务事务，短）：
   UPDATE video SET status=1, submitted_at=now, review_round=review_round+1
     WHERE id=? AND status IN (0,3) AND deleted_at IS NULL AND status <> 4
   INSERT review_task(video_id, review_round=新轮次, status=1,
                      next_attempt_at=now, lease_owner=NULL, lease_expires_at=NULL)
   COMMIT

② 领取（worker 自己的短事务，不含任何外部调用）：
   生成批次令牌 batchToken（UUID）
   UPDATE review_task
      SET status=2, lease_owner=?batchToken,
          lease_expires_at=now + lease_seconds,
          attempt_count=attempt_count+1
      WHERE status=1 AND next_attempt_at <= now()
      ORDER BY next_attempt_at
      LIMIT 20
   COMMIT
   SELECT ... WHERE lease_owner=?batchToken AND status=2   -- 取回本批次
   单条 UPDATE ... LIMIT 是原子语句：两个 worker 并发执行时，
   后到者看到的行已是 status=2，不会重复领取；不需要 FOR UPDATE，
   也就不会有"锁随事务结束立即释放"的问题。
   lease_seconds 必须覆盖整批最坏耗时：
     lease_seconds = batch_size * dispatch_timeout + 30s
   默认 20 条 × 10s + 30s = 230s。若调大批次或超时，必须同步调大租约；
   否则后面的任务会在本批处理完之前被扫尾回收，出现重复投递。

③ 投递（事务外，可长时间）：
   逐条调用审核平台（带超时，建议 10s），请求头携带稳定幂等键：
     X-Idempotency-Key: review-task-{review_task.id}
   请求体同时携带 client_task_id = review_task.id，回调原样带回，用于外部任务 ID 丢失时定位。
   同一任务重试必须复用同一个键；平台按该键去重并返回同一个 external_task_id。
   平台不支持幂等键时，不得开启自动重投，改为人工对账，避免创建两个外部任务。
   成功 → 任务仍是 2：SET status=3, external_task_id=?, lease_owner=NULL, lease_expires_at=NULL
          任务已被撤回/删除置 7：只写 external_task_id，保持 7，让迟到回调仍可定位
          WHERE id=? AND status IN (2,7) AND lease_owner=?batchToken
   失败 → attempt_count < 5：SET status=1, next_attempt_at=now+退避,
                              lease_owner=NULL, lease_expires_at=NULL
                            WHERE id=? AND status=2 AND lease_owner=?batchToken
          attempt_count >= 5：SET status=6 投递失败, lease_owner=NULL WHERE ...
   条件里带 lease_owner 是必需的：租约若已被扫尾任务回收给别人，本 worker 的迟到写入必须失败。

④ 扫尾（每分钟）：
   UPDATE review_task SET status=1, next_attempt_at=now+30s,
                         lease_owner=NULL, lease_expires_at=NULL
     WHERE status=2 AND lease_expires_at < now()
   处理 worker 崩溃或进程被杀导致的租约悬挂；attempt_count 已在②前递增，
   因此反复崩溃最终会落到 status=6（投递失败），不会无限重试。
```

为什么不能省掉 status=2 与租约：

- 只用 `SELECT ... FOR UPDATE SKIP LOCKED` 再提交事务，锁随提交消失，两个 worker 会领到同一行。
- 把外部调用塞进同一个事务，行锁要持有整个 HTTP 往返时间，等于把 outbox 变成串行队列。
- 只在领取后写 `status=2` 而不带租约，worker 崩溃后这些行永远停在"投递中"，无人能接管。

关于 `next_attempt_at` 必须 NOT NULL：`NULL <= now()` 结果为 NULL（非真），若插入时留空，新任务不会被任何 worker 领取——这是最常见的 outbox 哑火。用默认值 `CURRENT_TIMESTAMP(3)` 保证"插入即可领取"。

对账任务与投递是两条独立链路：前者处理 status IN (3,7) 且已有 external_task_id 的结论回捞，后者处理 status=1/2 的送达；两者的扫描索引分开，互不阻塞。

### 撤回、删除与迟到回调

撤回与删除都把当前轮任务置 7，而不是只处理未送达的 1/2：

```text
撤回：video 1 → 0，清 submitted_at、reject_reason
      当前轮 review_task status IN (1,2,3) → 7
删除：写 deleted_at，当前轮 review_task status IN (1,2,3) → 7
```

回调按任务状态分两种处理，不能只允许 status=3：

```text
定位：先按 external_task_id 查；查不到再用回调中的 client_task_id 查，命中则补写 external_task_id。
      两者都查不到返回 404。client_task_id 覆盖"平台已接收但 worker 在写回前被撤回/删除"的情况。
任务 status=3：正常结论。事务内写任务结果，并以
  UPDATE video SET ... WHERE id=? AND status=1 AND review_round=? AND deleted_at IS NULL
  更新视频；影响行数为 0 说明作者已撤回或删除，只保留任务结论并记 warn。
任务 status=7：作者已撤回或视频已删除但外部仍在审。只写任务 status/decided_at/reason，
  不修改 video.status，避免迟到回调把草稿重新变成已发布。
任务已是 4/5：重复回调，直接返回 200。
```

这样"删除后回调仍可到达"与"撤回后不再公开"可以同时成立。

# Redis key-value

## 通用约定（Redis）

```text
key 中的 {...} 表示需要替换的业务标识。
Hash 的时间字段以十进制字符串保存 Unix 毫秒数。
幂等记录 TTL 24 小时；缓存 TTL 5 分钟。
本期为单主 Redis；需要跨 key 原子性的操作使用 Lua 脚本。
```

## 1. 幂等键记录

类型：Hash（用 Hash 而非 String，便于回填 code 与 body 而不覆盖指纹）。写接口携带 `Idempotency-Key` 时创建。

key：`idem:{userId}:{method}:{path}:{key}`

| value 字段 | 内容 | 作用 |
| --- | --- | --- |
| fingerprint | 请求体（含关键查询参数）的 SHA-256 | 识别"同键不同请求"的重放 |
| state | `running` 或 `done` | 区分首次请求进行中与已完成 |
| code | 首次响应的 HTTP 状态码 | 重放时原样返回 |
| body | 首次响应体（超过 64KB 时置空，仅回放 code） | 重放时原样返回 |

指纹算法（必须规范化，不能直接对原始请求体取哈希）：

```text
application/json：
  对解析后的 JSON 做规范化序列化（key 按字典序、去除空白、数值统一表示）后取 SHA-256。
  理由是等价请求体的字节表示可能不同（字段顺序、缩进），直接哈希会误判为新请求。

multipart/form-data（上传接口）：
  绝对不能对原始请求体取哈希：boundary 每次随机生成，同一份文件每次上传的请求体字节都不同，
  会让幂等完全失效。改为对"语义部分"拼接后取 SHA-256：
    method + "\n" + path + "\n" + kind + "\n" + 文件名 + "\n" + 原始文件字节的 SHA-256
  原始文件字节哈希在读取上传流时顺带算出，对应 upload.source_sha256；
  faststart/remux 之后的最终字节哈希对应 upload.sha256，不参与幂等指纹。
  这样客户端换 boundary 重试仍命中同一条幂等记录，而对象键仍按最终字节校验完整性。

其他 content-type 或空体：对 规范化后的 query + body 原始字节 取 SHA-256。
不含用户身份：userId 已在 key 里，重复计入无意义。
```

```text
创建与判定放在一个 Lua 脚本里原子执行（避免 SET NX 后再 HSET 的类型冲突与竞态）：
  读 HEADER 是否存在
  不存在 → HSET fingerprint=... state=running；PEXPIRE 86400；放行
  存在且 fingerprint 相同、state=done    → 返回缓存的 code 与 body
  存在且 fingerprint 相同、state=running → 409 IDEMPOTENCY_IN_PROGRESS
  存在且 fingerprint 不同                → 409 IDEMPOTENCY_KEY_REUSED
业务成功后回填 state=done、code、body，保留原 TTL（不重置，防止无限续期）。
回填必须发生在业务事务提交之后、响应写出之前：数据库已提交但响应丢失时，
重试应返回 done 与首次 code，不能重复执行。
只有"确定没有产生副作用"的失败（参数校验、事务回滚、未开始写库）才删除该键；
事务已提交但回填阶段失败时保留键并告警，客户端会收到 409 IDEMPOTENCY_IN_PROGRESS，
由 TTL 到期后人工重试，宁可让用户重试一次也不制造重复记录。
4xx 属于确定性失败，保留记录。
进程崩溃导致状态停留在 running 时，TTL 到期自动释放；客户端既可用同一键重试，也可换新键。
未携带 Idempotency-Key 的请求按普通请求处理，不做记录。
Redis 不可用时直接放行当前请求并打告警，不保证去重，避免写路径整体不可用。
```

## 2. 上传配额计数

类型：String（计数器）。用于上传限流，避免单个账号刷存储与带宽。

key：`quota:upload:hour:{userId}`，有效期 1 小时；key：`quota:upload:day:{userId}`，有效期至当日 24 点（UTC）。

```text
固定窗口计数，不做令牌桶：上传是低频重操作，平滑限流没有收益，多存时间戳只增加复杂度。
每次 upload 请求前先校验三个计数，均用 Lua 脚本完成 INCR + 首次 EXPIRE（同一秒内不重复设过期）：
  任一超出（10 次/小时、50 次/日、2GB/日）→ 429 UPLOAD_RATE_LIMITED，返回 Retry-After（到窗口结束的秒数）。
窗口边界突刺（跨窗口最多放行 2 倍）在上传这个量级无实际影响，接受该近似。
失败请求（4xx 校验不通过）不退还配额：重试本身也要消耗带宽，退还会让攻击者用无效请求无限刷。
字节配额不能只在写完后累加：并发上传可以同时通过检查再各自写完，突破 2GB。
改为写入前按 Content-Length 预留（INCRBY 请求声明大小），写完再按实际 size_bytes 修正差额：
  Content-Length 缺失或与实际读取不符 → 400，不进入预留
  预留后超限 → 立即 429，不读取文件体
  写入失败 → 按已读字节回退预留，避免配额被失败请求长期占用
Redis 不可用时按"允许上传但记 warn"降级，不因限流组件故障阻断核心链路。
```
