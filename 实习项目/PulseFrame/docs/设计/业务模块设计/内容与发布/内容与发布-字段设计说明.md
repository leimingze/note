# 内容与发布：字段设计说明

本文逐项解释 `video` 与 `review_task` 两张表每个字段存在的原因、缺失后果，以及取值集合的选择理由，便于后续实现与维护时理解设计意图。

## video 表

### id

为什么：视频的唯一标识，自增主键，同时是对象存储键的前缀（`videos/{id}/`），一处生成、多处引用。

不设：无法唯一区分视频，对象、URL、互动记录都无从关联引用。

### author_id

为什么：作者身份，可见性权限判断和“我的作品/他人作品”列表的过滤键。

不设：无从判断作者，也就无法执行“非作者统一 404”的权限规则。

取值：`CHAR(36) ascii_bin`，与登录模块 `users.id` 一致，大小写敏感匹配。

### title / description

为什么：展示内容；description 还承载话题文本。

不设：列表和详情没有可展示的文字，检索失去来源。

### status

为什么：核心状态机，把“谁能看、谁能编辑、允许哪些操作”收敛到单个字段，便于统一用条件更新做并发控制与状态校验。

不设：无法表达视频处于哪个阶段，未完成、未过审的内容就无法被拦截在公开可见之外。

取值及少一个取值的后果：

- 0 上传中：客户端直传期间占位，挡住不完整视频。去掉：创建到文件传完之间没有中间态，客户端传大文件时记录要么不存在、要么直接漏进草稿，无法识别并清理未完成的废记录。
- 1 草稿：媒体已就绪、可编辑、可提交。去掉：无法在发布前保存并反复编辑标题简介。
- 2 待审核：已提交、等服务端审核结论。去掉：无法表达“已提交、在审”的阶段，撤回、对账、回调定位失去依据，与草稿混淆。
- 3 已驳回：承载驳回原因与重新提交。去掉：作者看不到原因也无法修改重交，闭环断掉。
- 4 已发布：公开且可播放。去掉：谈不上公开可见和进入 Feed。
- 5 已隐藏：作者临时隐藏但可恢复。去掉：作者想隐藏只能删除，丢掉“可恢复、回到原排序”的语义。
- 6 已下架：违规内容不可播放、不可自行恢复的终态。去掉：下架只能靠删除解决，丢失取证并约束作者恢复的限制。

### media_key / cover_key

为什么：对象存储正式视频与封面的键，播放、审核、下架、清理都靠它们定位文件。

不设：接口无法签发播放/封面地址，CDN 无法回源，审核服务无从读对象，清理无从删文件。

取值：存对象 key 而非 URL，因为 key 稳定，而 URL 带签名与时效、随时变化。

### duration_ms / width / height / size_bytes

为什么：确认上传时由媒体探测写入，供展示、布局和限额检查。

不设：页面拿不到分辨率占位，确认接口无法核对大小与时长上限，后续筛选无数据。

### review_round

为什么：记录审核轮次，每次提交 +1，回调按它判断新旧，防止迟到的旧结论覆盖新状态。

不设：作者撤回再提交后，旧轮次回调会把最新状态改坏，结论互相覆盖。

取值：单调递增，旧轮次条件更新影响 0 行，被丢弃。

### reject_reason

为什么：承载驳回原因，作者可见，重新提交时清空，支撑“被驳回后可修改重交”闭环。

不设：作者不知道被拒原因，只能盲目重交。

### offline_reason

为什么：记录平台下架原因，留痕并作者可见。

不设：下架无原因可查，合规与申诉失去依据。

### published_at

为什么：首次审核通过时间，公开列表排序依据。

不设（改用 created_at）：草稿拖几天才通过，一发布就排到旧内容后面，顺序错乱。

取值：首次通过时写入，恢复公开不变。

### deleted_at

为什么：非空表示回收站，可恢复；删除可发生在任意状态，恢复需回到原状态，因此用独立字段而非状态值。

不设：删了就永久消失，或塞进 status 导致恢复不回原状态。

取值：配合 7 天清理。

### created_at

为什么：创建时间，我的作品排序和上传超时清理的时间基准。

不设：无法排序，也无从判断哪条记录超过 1 天未完成。

## review_task 表

### id

为什么：任务 ID，即投递给审核服务的 task_id，两边共用去重。

不设：无法定位单个投递，回调无处归位。

### video_id / review_round

为什么：定位是哪条视频的第几轮审核，联合唯一保证同一轮只有一个任务。

不设唯一约束：同一轮会重复建任务、重复送审，审核服务无法收敛。

### status

为什么：队列状态机，兼作待投递队列，state 为 1 或 2 的行交由 worker 处理。

不设：worker 无法区分待投递/审核中/已完成/失败/取消，无法领取、重试和防重复处理。

取值及少一个取值的后果：

- 1 待投递：提交事务只插一行，由 worker 在事务外投递。去掉：提交接口必须当场调审核服务，审核慢会让事务持锁，或“提交成功但投递失败”让视频永远卡在待审核。
- 2 审核中：表示已送达、等待结论。去掉：无从区分“还没投”和“在等结论”，对账与超时失去坐标。回调可能早于 worker 把任务改为 2，因此 1 也允许写结论。
- 3 / 4 通过、驳回：审核结论载体。去掉：结论无处落库，video 状态无法推进。
- 5 投递失败：多次重试仍失败的终止态。去掉：无限重试或默默丢弃，无法告警。
- 6 已取消：作者撤回/删除后取消本轮。去掉：已取消任务仍会浪费投递，迟到回调也无法被正确忽略。

数值本身只是编码，无业务含义。

### attempt_count

为什么：记录领取次数，达 5 次转投递失败。

不设：无限退避重试，僵尸任务永不放弃，无法收敛。

### next_attempt_at

为什么：下次可领取时间，双重用途——待投递时是重试时间，审核中时是对账时间。

不设：worker 不知道何时领取、何时对账，也无法靠“领取时推后 60 秒”在崩溃后让任务被其他实例接管；任务可能被并发处理或长期不被处理。

### created_at / updated_at / decided_at

为什么：created_at 记录提交时间（算审核时长），decided_at 记录出结论时间（判断任务悬置多久），updated_at 记录最近修改时间（排查用）。

不设：无法统计 roundtrip 与最老未出结论任务，也无法定位长时间未更新的问题行。

### reason

为什么：流转驳回原因，供 `video.reject_reason` 使用。

不设：驳回结论不带原因，video 的驳回原因无处填充。
