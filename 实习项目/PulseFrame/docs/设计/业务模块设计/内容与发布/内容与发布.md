# 内容与发布

短视频内容创建、上传、审核与发布的业务闭环。

## 背景

PulseFrame 定位为 Go 短视频社交平台。平台需要用户发布视频，并让审核通过的视频进入 Feed 与其他用户浏览。没有发布能力，后续的 Feed、播放、互动和推荐都缺少数据来源。

本项目参考 GCFeed 的单向内容业务，其中视频模块覆盖发布、详情、列表、上传和逻辑删除；直播参考项目不具备短视频发布能力，不作为本模块参考。GCFeed 仅作为业务范围与工程思路参考，不直接作为本项目的代码基础，需求、数据模型和接口将从零推导。

发布链路与普通 CRUD 的差别集中在三处，本模块的设计围绕这三点展开：

- 媒体文件大，写入存储与校验的耗时远高于数据库写入，必须明确同步与异步的边界。
- 审核在外部平台完成，结论通过回调返回，回调可能丢失、重复、乱序；不能把内容可见性交给一次网络调用决定。
- "谁能看到"不是一个布尔值：草稿、待审核、已驳回、已发布、平台下架、作者隐藏、作者删除、回收站恢复，这些状态必须彼此正交，否则每个新需求都要改表。

## 需求

### 核心功能

- 用户能够上传视频与封面文件，系统校验容器格式、编码、大小、时长和分辨率，返回带元数据的上传凭证。
- 用户能够基于上传凭证创建视频草稿，填写标题与简介，草稿不对外可见且可反复编辑。
- 用户能够提交审核、撤回审核；被驳回后可查看原因、修改文案后重新提交。
- 视频提交后由业务端异步送往独立审核平台，接收平台回调的通过与驳回结论。
- 用户能够查询视频详情、自己的作品列表（可按状态过滤）和他人公开作品列表（游标分页）。
- 作者能够隐藏或恢复公开自己的作品；隐藏期间仅自己可见。
- 作者能够删除自己的视频，进入回收站保留 7 天，期内可恢复，逾期由清理任务彻底删除。
- 平台侧能够将已发布内容下架（违规处置），下架内容不可由作者自行恢复。

### 非功能指标

以下为设计初值，编码阶段以压测结果校准，校准后回写本文档。

| 指标 | 目标初值 | 说明 |
| --- | --- | --- |
| 上传接口 P95 耗时 | ≤ 8s（100MB H.264） | 含校验与 faststart，同步完成 |
| 创建草稿 P95 | ≤ 100ms | 一次性事务，含幂等键写入 |
| 视频详情 P95 | ≤ 50ms | 单表主键查询 |
| 公开列表 P95（20 条） | ≤ 120ms | 走 `is_public` 覆盖索引 |
| 提交审核接口 P95 | ≤ 120ms | 只落库，不含外部平台调用 |
| 审核结论时效 | P95 ≤ 5 分钟 | 从提交审核到 `status` 落定 |
| 回调丢失兜底 | ≤ 10 分钟 | 对账任务扫描周期 |
| 回收站清理滞后 | ≤ 1 小时 | 清理任务周期 |
| 日发布量 | 1 万条（初期） | 3 年约 1000 万条视频记录 |
| 单视频媒体上限 | 200MB / 10 分钟 | 超限直接 4xx 拒绝 |

一致性要求：

- 创建、提交、回调写状态、删除、恢复均为单表或单事务条件更新，不做跨表无事务写入。
- 视频媒体对象不可变：`media_key`、`duration_ms`、`width`、`height` 创建后不再修改；改媒体只能新建视频。
- 同一幂等键的重复请求返回首次结果，不产生第二条记录。
- 审核回调重复投递结果一致；乱序或过期回调（`review_round` 不是当前轮次）直接忽略并返回成功。

### 数据规模与边界

- 视频元数据按平台规模线性增长，单条记录小（约 600B），使用关系型数据库存储。
- 读多写少，写入集中在少数创作者；列表查询全部按时间游标翻页，不使用 `OFFSET`。
- 媒体文件不落数据库，只存对象键；文件本体在存储系统中。
- 本模块不处理视频创作、剪辑、滤镜、特效和配乐。
- 本模块不做转码：只接受 H.264 + AAC 的 MP4/MOV。客户端上传其他编码（如 iPhone 默认的 H.265）时拒绝并提示导出为 H.264。转码能力作为独立阶段建设，届时新增 `media_transcode_task`，不影响现有表结构。
- 审核在独立平台进行；本模块只保存送审记录与回写结果，后续内容安全 Agent、弹幕审核复用同一套待审实体。

### 暂不处理

- 上传进度与断点续传：短视频单次上传体量小，实现单请求整传，客户端使用 XMLHttpRequest `upload.onprogress` 上报进度，不做服务端轮询、分片与断点续传；失败直接整文件重传。
- 客户端直传对象存储：本期文件过服务端，便于统一校验与清理；`upload` 表已按"上传凭证"设计，后续改为预签名直传只需替换上传通道，绑定与清理逻辑不变。
- 分布式对象存储集群管理、CDN 预热。
- 转码、多码率自适应；封面自动抽帧仅做缺省兜底，不追求画面质量。

## 方案选型

### 视频标识

视频 ID 使用 64 位自增主键。视频创建频率低、生命周期内引用频繁，自增主键便于索引与游标分页；对外接口暴露视频 ID，不承担鉴权职责，权限判断始终基于 `author_id` 与登录态。

`author_id` 与登录模块一致，使用服务端生成的规范小写 UUIDv4，字段以 ASCII 字符集与 `ascii_bin` 比较规则存储。不使用 utf8mb4 存 UUID：36 个字符在 utf8mb4 下占 144 字节，会让作者索引膨胀 4 倍。

### 媒体存储与上传凭证

媒体文件（视频、封面）使用存储接口抽象：写入对象、返回对象键、拒绝超限文件。接入前先用本地磁盘实现支撑开发和联调，接入 S3 兼容对象存储时只替换实现。

表里存**对象键**而不是完整 URL。理由：存储域名、CDN 域名与签名参数会变，存 URL 会导致全表回填；而"媒体不可变"承诺的是对象内容不变，不是 URL 字符串不变。读取层用配置的基址拼出对外地址，需要防盗链时再叠加短时签名。

上传走两步凭证，而不是"先传文件、创建时随便填一个地址"：

```text
1. POST /api/uploads 完成校验与写入，落一行 upload 记录，返回 uploadId 与媒体元数据
2. POST /api/videos 携带 uploadId 创建视频，事务内校验 upload 属于当前作者且状态为待绑定，置为已绑定
```

这样做的原因有两个，都是不落 upload 表就无法解决的：

- 孤儿文件回收。上传成功但用户放弃创建时，对象会永久留在存储里。有 `expires_at` 和状态位，清理任务才能扫描删除。
- 越权回填。媒体地址若由客户端自由提交，作者可以填入他人的对象键、外站链接或已绑定过的对象，造成内容替换与盗链。绑定动作改为服务端按 `uploadId` 反查归属后写入。

### 视频状态

`status` 只表示发布流程，取值收敛为五档：

| 值 | 含义 | 对外可见 | 作者可改文案 | 说明 |
| --- | --- | --- | --- | --- |
| 0 | 草稿 | 否 | 是 | 可反复编辑，未进审核链路 |
| 1 | 待审核 | 否 | 否 | 已提交，可撤回 |
| 2 | 已发布 | 是 | 否 | 审核通过，进入 Feed 候选集 |
| 3 | 已驳回 | 否 | 是 | 作者可见原因，改后可重新提交 |
| 4 | 已下架 | 否 | 否 | 平台处置，作者不可自行恢复 |

与发布相关但与流程无关的时间语义各自独立成列，不塞进枚举：

- `submitted_at`：最近一次提交审核时间，草稿为空。用于对账扫描与审核时长统计。
- `published_at`：首次审核通过时间，**Feed 排序基准**。不能用 `created_at`：用户三天前建的草稿今天才通过审核，按创建时间排序会一进 Feed 就沉底，审核耗时直接变成排序误差。
- `hidden_at`：作者隐藏时间，非空表示仅自己可见。不影响 `status`，也不改审核结论，可随时恢复。
- `deleted_at`：作者删除时间，进回收站，7 天内可恢复。
- `offline_at` / `offline_reason`：平台下架时间与理由。与 `deleted_at` 分开，因为下架是平台处置，不能让作者用恢复接口一键撤销。

草稿为什么用 `status=0` 而不是"`submitted_at` 为空"：用时间字段当状态位会让每条查询都要带 `submitted_at IS NULL` 组合条件，索引与 CHECK 约束也无法表达"待审核必须有 submitted_at"。显式枚举让状态机可读、可校验，代价是多一个取值，而取值是廉价的。

可见性判断收敛成一次表达式，由 MySQL 生成列 `is_public` 承担，读路径只按单一条件过滤：

```text
is_public = (status = 2 AND hidden_at IS NULL AND deleted_at IS NULL)
```

### 审核对接：事务内只落库，投递交给 outbox

送审要调用外部 HTTP 接口，不能放在数据库事务里：持锁期间做网络 IO，审核平台变慢会拖垮写路径。但"提交成功、投递失败"会造成视频卡在待审核且无人知晓。

因此把 `review_task` 本身当作 outbox：

```text
提交审核事务内：video.status 0/3 → 1，写 submitted_at，插入 review_task(status=1 待投递, review_round=n)
事务提交后：投递 worker 拉取待投递记录，调审核平台，成功置 status=2 审核中并写入 external_task_id
投递失败：attempt_count 递增，按指数退避重试；超过上限置 status=5 投递失败并告警
```

对应的可靠性补充：

- 回调丢失：对账任务扫描"审核中且已提交超过 10 分钟"的记录，主动调用审核平台的查询接口拉取结论。
- 回调重复：`external_task_id` 唯一索引配合 `UPDATE ... WHERE status=2` 条件更新，已到终态直接返回 200，不重复写。
- 回调乱序：每轮审核用 `review_round` 编号，回调必须命中当前轮次；作者撤回后重新提交时 `review_round+1`，旧轮次的迟到回调被忽略，不会打翻新一轮结果。
- 送审失败可见：`review_task.status=5` 进入告警与后台列表；作者侧可通过"撤回审核"把视频退回草稿再提交，不必等运维介入。

开发阶段使用本地模拟桩自动通过或驳回，保证链路在真正接入审核平台前可验证。

### 幂等键

写接口统一接受 `Idempotency-Key` 请求头。服务端在 Redis 记录 `(userId, method, path, key) → 请求体指纹 + 响应状态码与响应体`，TTL 24 小时：

- 同键同指纹：直接返回首次响应，不重复执行。
- 同键不同指纹：返回 409 `IDEMPOTENCY_KEY_REUSED`，避免夹带不同参数的重放。
- 首次请求未结束时同键再次到达：返回 409 `IDEMPOTENCY_IN_PROGRESS`，客户端稍后重试即可拿到首次结果。

Redis 不可用时降级策略：部署目标为高可用 Redis，宕机概率很低，但生产可能短暂出现网络抖动或主从切换窗口。此时幂等判断不可用，策略为**直接放行当前请求并打告警**——不保证去重，但避免写路径整体不可用；重复执行造成的多余记录（如重复创建视频）可被用户删除，影响可控。

键值细节见 [数据结构](内容与发布-数据结构.md)。

### 播放优化

上传时校验扩展名、MIME、大小、时长、分辨率与编码，任一项不满足直接拒绝并清理已写入对象。

MP4/MOV 执行 faststart，把 `moov` 前置，便于拖动进度与快速起播：

- 校验阶段先探测 `moov` 是否已在文件头，已在前置则跳过重写。
- 需要重写时流式处理，临时占用不超过一个文件的磁盘空间。
- 重写耗时超过 10s 时降级为原样存储并打点告警，由后续离线任务补做，不阻塞用户请求。该降级路径的前提是播放端能处理 `moov` 后置的普通 MP4。

## 核心流程

### 上传媒体

```text
1. 客户端携带 JWT 与 Idempotency-Key 调用 POST /api/uploads（multipart）
2. 限流：按用户令牌桶校验小时/日配额，超限返回 429
3. 服务端流式写入临时文件，同时计算 sha256；超过大小上限立即中断并删除临时文件
4. 探测容器、编码、时长、分辨率：
   非 MP4/MOV、非 H.264 + AAC、超时长、超分辨率 → 4xx，清理临时文件与已写对象
   同一作者已有相同 sha256 且 status=1（未绑定）的上传 → 直接返回该 uploadId，不重复落对象
   已有相同 sha256 但已绑定 → 不重复落对象，另建一条新 upload 记录复用同一 media_key
5. faststart：moov 后置时重写；超过 10s 降级为原样存储并记 warn
6. 写入存储接口得到 object_key，落 upload 记录（status=1 待绑定，expires_at=now+24h）
7. 返回 uploadId、时长、宽高与建议封面（缺省时服务端取首帧，失败则无封面）
   封面也可单独上传：POST /api/uploads?kind=image，返回仅含 cover_key 的凭证，用于创建后换封面
```

### 创建草稿

```text
1. 客户端携带 JWT 调用 POST /api/videos，body 含 uploadId，title 与 description 可选
2. 事务内：按 uploadId 查询 upload，校验 owner_id = 当前用户且 status=1
3. 从 upload 复制 media_key、duration_ms、width、height 到 video（此后不可变）
4. 同一事务插入 video(status=0) 与 video_stat(计数全零)
5. 更新 upload.status=2 已绑定；绑定关系由 video.upload_id 唯一索引反查，upload 不再存 video_id
   coverUploadId 若提供，按同样规则校验归属与状态后复制 cover_key 到 video
6. 返回视频详情
```

媒体绑定放在创建时而不是提交时：媒体一经确定就不再变化，审核审的就是这个对象；允许在提交阶段再换媒体等于允许"过了审核再换内容"。

### 编辑、撤回与重新提交

```text
1. PATCH /api/videos/{videoId}：仅 status ∈ {0,3} 可调用，只允许改 title、description、coverUploadId
   coverUploadId 同样走 upload 归属校验，不接受客户端直传对象键
   status=3 编辑后仍为 3，不清空 reject_reason；其余状态返回 409 VIDEO_NOT_EDITABLE
2. POST /api/videos/{videoId}/submit：status ∈ {0,3} → 1
   校验完整性（标题长度、媒体已绑定、未删除），未通过返回 422
   事务内写 video(status=1, submitted_at=now)，published_at 保持
   并插入 review_task(review_round = 上一轮 + 1, status=1 待投递)
3. POST /api/videos/{videoId}/withdraw：仅 status=1 → 0，清 submitted_at，
   当前轮 review_task 置 6 已撤销；已产生外部任务的，回调到达后按乱序规则忽略
```

### 审核回调

```text
1. POST /api/review/webhook：校验签名与时间窗口（±5 分钟），失败返回 401
2. 按 external_task_id 查 review_task，不存在返回 404（不静默吞掉，便于平台侧发现配置错误）
3. 校验 review_round 等于 video 当前轮次且 review_task.status=2：
   不满足 → 直接返回 200 并记一条 warn 指标（重复或过期回调）
4. 事务内：review_task.status=3/4、decided_at、reason
   status=3 通过：video.status=2，published_at = COALESCE(published_at, now)，清 reject_reason
   status=4 驳回：video.status=3，reject_reason=reason，published_at 保持
   视频已删除（deleted_at 非空）：照常写 status 与 reason，但 is_public 仍为 0，
   恢复时按最新审核结论展示，不会因删除期间通过审核而"恢复即违规可见"
5. 返回 200
```

### 状态流转

```text
创建草稿        0
提交审核        0/3 → 1        （写 submitted_at、review_round+1）
撤回审核        1 → 0          （清 submitted_at，撤销本轮任务）
审核通过        1 → 2          （写 published_at，清 reject_reason）
审核驳回        1 → 3          （写 reject_reason）
平台下架        2 → 4          （写 offline_at / offline_reason，作者不可恢复）
删除            任意 → 回收站  （deleted_at 非空，撤销在途审核任务，7 天内可恢复）
恢复            回收站 → 原状态（清 deleted_at）
超期清理        回收站 → 物理删除（清媒体与关联记录）
隐藏/恢复公开   仅翻转 hidden_at，不改 status
```

不允许的转换一律返回 409，由条件更新（`WHERE status IN (...)`）在数据库层保证，不依赖应用层先查后写。

注意 4（已下架）只能进不能出：下架后再提交审核、再隐藏、再恢复公开都不允许，状态更新条件里统一带 `status <> 4`。作者对下架内容只能删除；若要申诉，走后续管理模块的申诉流程，不在本模块状态机内。

## 接口设计

| 方法 | 路径 | 作用 | 鉴权 | 幂等键 |
| --- | --- | --- | --- | --- |
| POST | /api/uploads | 上传媒体文件，返回上传凭证 | JWT | 支持 |
| POST | /api/videos | 基于上传凭证创建草稿 | JWT | 支持 |
| PATCH | /api/videos/{videoId} | 更新草稿/驳回稿的标题、简介、封面凭证 | JWT(作者) | 支持 |
| POST | /api/videos/{videoId}/submit | 提交审核 | JWT(作者) | 支持 |
| POST | /api/videos/{videoId}/withdraw | 撤回审核，退回草稿 | JWT(作者) | 支持 |
| PATCH | /api/videos/{videoId}/visibility | 隐藏或恢复公开 | JWT(作者) | 支持 |
| GET | /api/videos/{videoId} | 查询视频详情 | 作者或公开 | 无 |
| GET | /api/users/{userId}/videos | 查询他人公开作品列表 | 公开 | 无 |
| GET | /api/users/me/videos | 查询我的作品列表，可按 status 过滤 | JWT | 无 |
| DELETE | /api/videos/{videoId} | 删除自己的视频（进回收站） | JWT(作者) | 支持 |
| POST | /api/videos/{videoId}/restore | 从回收站恢复 | JWT(作者) | 支持 |
| POST | /api/review/webhook | 审核平台回调结果 | HMAC 签名 | 无需（轮次 + 唯一索引保证） |

分页与可见性约定：

- 列表统一游标分页：`?cursor=<base64(排序键,id)>&limit=20`，`limit` 上限 50，返回 `next_cursor` 与 `has_more`。公开列表以 `(published_at, id)` 为键，排序稳定且不受新内容插入影响。
- `GET /api/videos/{videoId}` 的"公开"是相对作者而言：作者可见自己任意状态的视频（含草稿、待审、驳回、隐藏），他人只能看到 `is_public=1`，否则统一 404，不区分"无权限"与"不存在"，避免探测。
- `GET /api/users/me/videos` 默认排除回收站记录，`?scope=recycle` 单独查询回收站。
- 字段冲突时的优先级（从高到低）：`offline_at` > `deleted_at` > `hidden_at` > 排序可见。即平台下架最优先，作者无法用隐藏/恢复绕过；回收站次之，下架内容进回收站再恢复仍是下架态。

| 错误码 | HTTP | 触发场景 |

| UPLOAD_TOO_LARGE | 413 | 超过 200MB |

## 非功能设计

- 上传限流与配额：按用户做令牌桶（10 次/小时、50 次/日）与总字节配额，防止刷存储与带宽。超限返回 429 并带 `Retry-After`。
- 上传失败清理：写入前生成临时文件，任一步失败在 `defer` 中删除；已写入存储的对象按 `object_key` 反向删除；清理动作本身失败只记日志，交给孤儿扫描兜底。
- 事务边界：创建与提交只做数据库写入，不发起外部调用；送审由 worker 在事务外执行。创建时 `video` + `video_stat` 同事务，提交时 `video` + `review_task` 同事务。
- 状态更新用条件更新：`UPDATE video SET status=2 WHERE id=? AND status=1`，受影响行数为 0 视为冲突，避免并发提交与并发回调互相覆盖。所有状态变更语句统一附加 `AND status <> 4 AND deleted_at IS NULL`（删除接口本身除外），把不可见与终态约束下沉到数据库。
- 回调安全：HMAC-SHA256 签名 + 5 分钟时间窗口 + 时间戳去重，只允许审核平台写入结论；驳回原因裁剪到 200 字符并在渲染前转义。
- 删除终止在途审核：删除时同一事务把该视频当前轮 `review_task.status=1/2` 置 6 已撤销，避免任务被继续投递、白占审核平台配额；已投递到平台的，迟到回调按"视频已删除"分支处理。
- 权限：所有写接口以登录态中的 userId 与 `video.author_id` 比对，非作者返回 403；删除与恢复额外校验当前状态，避免越权操作他人内容。
- 数据一致性：`review_task.reason` 为权威，`video.reject_reason` 是展示冗余，两者在同一事务内写入；`video_stat` 计数由互动模块维护，本模块只在创建时初始化。
- 隐藏与排序：隐藏不改变 `published_at`，恢复后回到原时间位置，不做"再发一次"处理。
- 清理任务：每小时扫描 `deleted_at < now-7d` 的记录，按依赖顺序物理删除 `review_task`、`video_stat`、`video`，再删存储对象；任务使用分布式锁保证单实例执行，多删少删都以数据库为准，残留对象由孤儿扫描补删。
- 孤儿扫描：清理"待绑定且 `expires_at < now`"的 upload 记录。因去重会共享对象，删除对象前必须确认该键无其他引用（upload 或 video 均算），否则只删记录不删对象；对象侧采用标记后延迟 24 小时再删的两阶段删除，避免与并发绑定竞争。
- 可观测性指标：`upload_total{result}`、`upload_bytes`、`upload_seconds`、`probe_seconds`、`faststart_seconds`、`video_submit_total{result}`、`review_dispatch_total{result}`、`review_callback_total{result}`、`review_roundtrip_seconds`（提交到结论的直方图）、`review_task_oldest_pending_seconds`、`purge_lag_seconds`、`orphan_upload_count`。告警依据：待审核最老记录超过 30 分钟、投递失败数大于 0、清理滞后超过 2 小时。

## 演进路径

按规模递增，每一档都在前一档验证完成后再启用：

1. 单实例 + 主从读：当前设计即适用，读请求走只读副本，写走主库。
2. 详情读缓存：视频详情是典型读扩散接口，热点视频的 `GET /api/videos/{id}` 加 Redis 缓存，key `video:detail:{videoId}`，TTL 5 分钟，删除/下架/隐藏时主动删除。列表不做缓存，避免游标失效。
3. Feed 写入扩散：当前 Feed 直接查 `video` 表；内容量与关注关系变大后，改为发布时写发件箱（`feed_outbox` 按作者维度），读时合并关注列表，本模块只需在审核通过时投递一条事件。
4. 存储与播放：接入对象存储 + CDN，直传预签名 URL；转码独立服务产出多码率，`video` 增加 `playback_manifests` 关联表，不改现有列。
5. 审核平台扩展：`review_task` 已按轮次与外部队列建模，接入内容安全 Agent 时新增 `reviewer` 字段区分审核方，同一视频可并行多次审核，结论合并规则在业务层实现。
