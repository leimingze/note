# 内容与发布

短视频上传、审核与发布的业务闭环。

## 背景

PulseFrame 定位为 Go 短视频社交平台。平台需要用户发布视频，并让审核通过的视频进入 Feed 供其他用户浏览。没有发布能力，后续的 Feed、播放、互动和推荐都缺少数据来源。

本项目参考 GCFeed 的视频模块（发布、详情、列表、上传和逻辑删除）确定业务范围，需求、数据模型和接口从零推导，不复用其代码。

本模块的压力不在发布写路径。日发布 1 万条时写入峰值不到 1 QPS，真正需要设计的是三处：

- 媒体文件大。200MB 的文件如果经过业务服务，每次上传占用一个连接几十秒，带宽和临时磁盘会先于 CPU 耗尽。
- 读远多于写。详情、作品列表和 Feed 的读取量是发布量的上万倍，读路径必须基本不打到 MySQL 主库。
- 审核由独立部署的审核服务完成（本项目自建，属于审核与基础后台模块）。跨服务的投递和回调可能失败、重复、乱序，可见性不能依赖一次网络调用的结果。

设计原则：每个机制都要对应一个具体问题。能用数据库唯一键、条件更新和对象存储自带能力解决的，不再增加组件和后台任务。

## 需求

### 核心功能

- 用户上传视频与封面，服务端校验格式、编码、大小、时长和分辨率。
- 用户基于已上传的文件创建草稿，填写标题与简介，草稿不对外可见且可反复编辑。
- 用户提交审核、撤回审核；被驳回后可查看原因、修改后重新提交。
- 视频提交后异步送往审核服务，接收审核服务回调的通过与驳回结论。
- 用户查询视频详情、自己的作品列表（可按状态过滤）和他人公开作品列表（游标分页）；本模块为 Feed 模块提供按 ID 批量查询视频。
- 作者隐藏或恢复公开自己的作品，隐藏期间仅自己可见。
- 作者删除视频后进入回收站保留 7 天，期内可恢复，逾期彻底删除。
- 平台下架违规内容，下架后立即不可播放，作者不能自行恢复。

### 容量估算

按初期目标 DAU 100 万、人均每天浏览 100 条视频估算，上线后以监控数据校准：

| 项目 | 估算 | 对设计的影响 |
| --- | --- | --- |
| 视频详情读取 | 1 亿次/天，均值约 1,200 QPS，峰值按 5 倍约 6,000 QPS | 详情必须走 Redis 缓存，MySQL 只承担未命中 |
| 视频发布 | 1 万条/天，峰值不到 1 QPS | 写路径不需要队列、削峰或分库 |
| 上传流量 | 1 万条 × 平均 30MB，约 300GB/天 | 客户端直传对象存储，字节不经过业务服务 |
| 播放流量 | 与浏览次数同量级 | 全部由 CDN 承担，业务服务只签发播放地址 |
| 视频记录 | 3 年约 1,100 万行，单行约 500B | 单表即可，不分库分表 |

### 非功能指标

| 指标 | 目标初值 | 说明 |
| --- | --- | --- |
| 详情与批量详情 P99 | ≤ 20ms | 缓存命中路径 |
| 他人公开作品列表 P99 | ≤ 50ms | 从库覆盖索引取 ID，再批量读缓存 |
| 创建视频（申请上传地址）P95 | ≤ 50ms | 只做配额检查、插入一行和本地签名 |
| 上传完成确认 P95 | ≤ 5s | 含媒体探测与对象存储内部复制，以压测校准 |
| 提交审核 P95 | ≤ 100ms | 只落库，不调用审核服务 |
| 审核结论时效 P95 | ≤ 5 分钟 | 从提交到 `status` 落定 |
| 回调丢失兜底 | ≤ 10 分钟 | 对账周期 |
| 隐藏与删除生效 | 接口立即不再返回播放地址，已签发地址 1 小时内过期 | 签名地址有效期决定 |
| 下架生效 | 接口返回后不可播放 | 对象被移走并刷新 CDN |
| 单视频上限 | 200MB / 10 分钟 | 超限直接 4xx |

### 数据规模与边界

- 视频元数据使用 MySQL 单表存储，媒体文件只存对象键，文件本体在对象存储。
- 列表全部按时间游标翻页，不使用 `OFFSET`。
- 本模块不做转码：只接受 H.264 视频、AAC 音轨（允许无声）、`moov` 在文件头的 MP4。短视频 App 由客户端完成录制和导出，导出格式由客户端保证；不满足时拒绝并返回原因。转码作为独立阶段建设。
- 封面由客户端选帧后上传，服务端不抽帧。
- 点赞、评论、收藏、播放等计数归互动模块，本模块不建计数表。
- 本模块不处理剪辑、滤镜、特效和配乐。

### 暂不处理

- 断点续传与分片上传：短视频单文件不超过 200MB，失败整文件重传。
- 转码与多码率、服务端抽帧封面。
- Feed 的候选集与排序：由 Feed 模块设计，本模块只提供按 ID 批量查询视频。
- 管理后台与申诉流程：本模块只提供内部下架接口。

## 方案选型

### 视频标识

视频 ID 使用 64 位自增主键。发布写入量低，自增 ID 足够；ID 递增也便于游标分页。权限判断始终基于 `author_id` 与登录态，不依赖 ID 不可猜测。`author_id` 与登录模块一致，使用 `CHAR(36) ascii_bin` 存 UUID。

### 上传：客户端直传对象存储

候选方案：

| 方案 | 优点 | 问题 |
| --- | --- | --- |
| 文件经过业务服务再写存储 | 校验集中 | 每次上传占用连接与临时磁盘几十秒，上传高峰会拖垮读接口所在的实例 |
| 客户端直传对象存储，服务端事后校验 | 业务服务只处理元数据，文件字节不经过业务服务 | 需要防止客户端上传后替换文件 |

选择直传。流程分三步：

```text
1. POST /api/videos：插入一行 video(status=0 上传中)，返回视频与封面的预签名上传凭证
   临时 key：upload/{videoId}/media.mp4、upload/{videoId}/cover.{jpg|png}
   凭证有效期 30 分钟，用 POST Policy 限定 content-length-range 与 Content-Type
2. 客户端直传对象存储
3. POST /api/videos/{videoId}/complete：服务端校验两个临时对象，
   通过后在存储内部复制到正式 key，video 进入 status=1 草稿
   正式 key：videos/{videoId}/media.mp4、videos/{videoId}/cover_{版本}.{jpg|png}
```

为什么要从临时 key 复制到正式 key：预签名凭证在有效期内可以重复使用，客户端可以在校验通过后再上传一次，把已审核的内容替换掉。正式 key 只有服务端能写，审核审的对象和最终播放的对象保证是同一份。

为什么不建上传凭证表：每个视频只有一个媒体文件和一个封面，key 由 `videoId` 决定，对象和视频一一对应。没有共享对象，删除时不需要引用计数。没完成上传的临时对象由存储桶生命周期规则在 1 天后自动删除，不需要孤儿扫描任务。

封面带版本号是因为 CDN 会缓存旧封面。换封面写入新 key，删除旧 key，客户端拿到新地址后不会命中 CDN 上的旧图。

### 播放地址与可见性

只用一个私有存储桶，CDN 回源访问它，并开启 CDN URL 签名鉴权（带过期时间的签名）。客户端无法直接访问存储桶，必须拿到业务服务签发的地址。

```text
签名在响应时计算，不进缓存：详情缓存只存对象键，接口层按当前查看者的可见性签发地址
签名有效期 1 小时，签名时间戳按 10 分钟取整，同一视频的地址在 10 分钟内不变
CDN 缓存键忽略签名参数，签名地址变化不影响 CDN 命中率
```

可见性规则只有一条：`status = 4 已发布 AND deleted_at IS NULL` 时对所有人可见；其余状态只对作者可见；对其他人统一返回 404，不区分"不存在"与"无权限"。

撤销可见性分两种：

- 隐藏与删除：接口立即不再签发地址，已签发的地址最多 1 小时后过期。作者的这类操作接受这个时间差。
- 平台下架：违规内容需要立即不可播放。下架接口在更新数据库后，把正式对象移到 `offline/{videoId}/`（保留取证），再调用 CDN 刷新该视频的 URL。

不再按视频复制一份公开对象。上一版用"私有桶 + 公开桶复制"控制可见性，每个视频多存一份文件，还需要一个同步任务和一组状态字段维护两个桶的一致性。签名地址只靠一次签名计算就能实现同样的访问控制。

### 视频状态

状态集中在一个 `status` 字段，回收站单独用 `deleted_at` 表示，因为删除可以发生在任何状态，恢复时需要回到原状态。

`status=0 上传中` 服务于“先建记录拿凭证、直传对象、再确认”的两阶段上传：客户端直传大文件需要几十秒甚至更久，这段时间媒体不完整，必须有一个中间态把视频挡在草稿和公开可见之外，并让超时清理任务能识别“还没完成的废记录”。它不能并入草稿，因为草稿意味着媒体已就绪、可编辑，而上传中并没有可编辑的内容。

| 值 | 含义 | 他人可见 | 作者可编辑 | 允许的操作 |
| --- | --- | --- | --- | --- |
| 0 | 上传中 | 否 | 否 | 确认上传、删除 |
| 1 | 草稿 | 否 | 是 | 编辑、提交、删除 |
| 2 | 待审核 | 否 | 否 | 撤回、删除 |
| 3 | 已驳回 | 否 | 是 | 编辑、重新提交、删除 |
| 4 | 已发布 | 是 | 否 | 隐藏、删除 |
| 5 | 已隐藏 | 否 | 否 | 恢复公开、删除 |
| 6 | 已下架 | 否 | 否 | 删除（终态，作者不能恢复） |

隐藏用状态值而不是 `hidden_at` 字段：隐藏只能从已发布进入，也只能回到已发布，是状态机里的一条边。做成单独字段后，还要额外约束"非发布状态不能有隐藏标记"。

`published_at` 记录首次审核通过时间，作为公开列表排序依据。不用 `created_at` 排序，否则草稿放几天再通过审核，一发布就排在旧内容后面。

所有状态变更写成条件更新，以影响行数判断是否冲突：

```sql
UPDATE video SET status = 2, reject_reason = '', review_round = review_round + 1
WHERE id = ? AND author_id = ? AND status IN (1, 3) AND deleted_at IS NULL;
-- 影响 0 行：视频不存在、不属于当前用户或状态不允许，返回 409
```

允许的状态转换写在一个 Go 函数里，接口层不直接拼状态条件，单测覆盖每一条边。

### 审核对接

审核服务由本项目自己实现，属于"审核与基础后台"模块，独立部署、使用自己的数据库。两个模块之间的接口契约在这里定义，审核服务实现时必须遵守：

```text
投递：POST /internal/review/tasks
  body：task_id（本模块 review_task.id）、video_id、review_round、title、description、media_key、cover_key
  审核服务以 task_id 为唯一键：重复投递返回 200，不新建任务
  审核服务用只读凭证按 media_key、cover_key 读取私有桶
回调：审核服务出结论后调用 POST /internal/review/callback
  body：task_id、result（pass|reject）、reason
  回调失败由审核服务按退避重试
查询：GET /internal/review/tasks/{task_id}，返回结论或"审核中"，供本模块对账
鉴权：双方调用都携带服务间凭证
```

任务 ID 由本模块生成，两边共用，因此不需要保存审核服务返回的任务 ID，也不会出现"本地还没记下对方的任务 ID，回调就先到了"的定位问题。

不共享数据库表：两个模块共用一张表，任何一方改表结构都会影响另一方，也违背各模块只写自己数据的约定。本期基座没有消息队列，用 HTTP 投递加回调就够了；以后基座引入消息队列时，把 worker 的 HTTP 调用换成发送消息，表结构和状态不用改。

送审不能放进数据库事务：审核服务变慢会让事务长时间持锁。直接在提交接口里调用又会出现"提交成功、投递失败"，视频永远停在待审核。因此把 `review_task` 表当作待投递队列：提交事务内只插入一行任务，由 worker 在事务外投递。

```text
① 提交审核（一个事务）：
   video：status 1/3 → 2，review_round + 1，清 reject_reason
   review_task：插入 (video_id, review_round, status=1 待投递, next_attempt_at=now)

② worker 领取（短事务，不做外部调用）：
   SELECT id FROM review_task WHERE status IN (1,2) AND next_attempt_at <= now
     ORDER BY next_attempt_at LIMIT 20 FOR UPDATE SKIP LOCKED
   UPDATE review_task SET next_attempt_at = now + 60s, attempt_count = attempt_count + 1 WHERE id IN (...)
   COMMIT

③ 事务外处理：
   status=1 待投递 → 调用投递接口
     成功 → UPDATE ... SET status=2 审核中, next_attempt_at = now + 10min WHERE id=? AND status=1
            影响 0 行说明任务已被取消或回调已先到，不覆盖
     失败 → attempt_count < 5：next_attempt_at = now + 指数退避；否则 status=5 投递失败并告警
   status=2 审核中且到期 → 调用查询接口对账
     已有结论 → 按回调同样的逻辑落库；仍在审 → next_attempt_at = now + 10min
```

worker 不需要单独的"投递中"状态和租约字段。领取时把 `next_attempt_at` 推后 60 秒，其他 worker 在这 60 秒内不会再领到这一行；worker 中途崩溃，60 秒后任务自动重新可领。`attempt_count` 在领取时递增，反复崩溃也会在 5 次后落到投递失败。多个 worker 实例并行时由 `SKIP LOCKED` 跳过彼此锁住的行，不需要分布式锁。

重复投递（例如审核服务已接收但响应超时）由审核服务按 `task_id` 去重。

回调处理：

```text
1. 校验服务间凭证，失败 401
2. 按 task_id 查任务，查不到 404
3. 一个事务内：
   UPDATE review_task SET status = 3 通过/4 驳回, reason, decided_at
     WHERE id = ? AND status IN (1, 2)
   影响 0 行 → 重复回调或任务已取消，返回 200
   UPDATE video SET status = 4/3, published_at = COALESCE(published_at, now), reject_reason
     WHERE id = ? AND status = 2 AND review_round = 任务轮次 AND deleted_at IS NULL
   影响 0 行 → 作者已撤回、删除或已重新提交，只保留任务结论
4. 事务提交后：通过时写入详情缓存（见"发布时预热缓存"），驳回时删除详情缓存；返回 200
```

任务 `status=1` 也允许写结论：审核服务可能在 worker 把任务改成审核中之前就完成回调。

`review_round` 用于防止迟到的旧结论覆盖新状态：每次提交 +1，回调携带自己那一轮的轮次，更新视频时用 `WHERE status=2 AND review_round=?` 匹配当前轮次。旧轮次的值对不上，更新影响 0 行，被丢弃，只保留任务结论。因此作者撤回后再提交，旧轮次的回调永远动不了新一轮状态。

回调乱序与迟到由第 3 步视频更新的条件处理：作者撤回或删除后视频不再是待审核，重新提交后轮次已经加 1，旧回调都无法改动视频。撤回和删除只需把还没投递的任务（`status=1`）置为 6 已取消，避免浪费一次投递；已送达审核服务的任务不用处理。

审核服务完成前，本模块自带一个实现同一契约的模拟审核服务，按配置自动通过、驳回、失败、延迟或丢弃回调，用于验证重试与对账。

### 读路径与缓存

详情、作品列表和 Feed 的视频卡片都读同一份视频详情缓存：

```text
key：video:{videoId}，值为 JSON，含展示所需字段与 status、deleted_at
TTL：10 分钟 + 0~60 秒随机，避免同一批 key 同时过期
单条读取：GET；批量读取：MGET，未命中的 ID 用一条 WHERE id IN (...) 查库后用 pipeline 回填
未命中查主库：按主键读取，成本低；读从库可能读到旧数据，再写进缓存会延长不一致时间
不存在的 ID：缓存空值 1 分钟，防止用随机 ID 反复穿透到数据库
同一实例内并发未命中同一 key：用 singleflight 合并为一次查库
```

缓存更新采用"先更新数据库，再删除缓存"。删除失败只记日志，最长不一致时间为 TTL 10 分钟；下架这种必须立即生效的操作还有移走对象兜底，不依赖缓存删除成功。

缓存里只存对象键，不存签名地址。可见性判断与签名在接口层完成，作者和其他人读同一份缓存，结果不同。

单个热门视频的详情 key 峰值可能达到每秒数千次读取，单个 Redis 节点可以承受，本期不加进程内缓存。监控到单 key 成为瓶颈时，再加 1~5 秒的进程内缓存。

### 发布时预热缓存

大 V 的视频发布后会立刻出现在大量粉丝的 Feed 里。如果这时缓存为空，每个服务实例都会查一次数据库，因为 singleflight 只能合并同一实例内的并发请求。

预热做法：视频变为公开时（审核通过、恢复公开），在事务提交后用最新数据直接 SET `video:{videoId}`，而不是删除缓存。

预热对所有视频都做，不按粉丝数筛选。每天只有约 1 万条发布，每条多写一次 Redis，成本可以忽略；按粉丝数筛选还要依赖关系模块的粉丝数，反而更复杂。大 V 的视频自然也被覆盖。

预热写入和普通的未命中回填有同样的竞态：读出数据后、写入缓存前，作者恰好删除了视频，缓存里会留下旧数据，最长到 TTL 过期。这与"已签发的播放地址 1 小时内过期"在同一个量级，可以接受；下架有移走对象兜底，不受影响。

进程内缓存的预热放到演进路径：启用进程内缓存后，粉丝数达到阈值的作者发布新视频时，再通知各实例提前加载。

作品列表分两步：先在 MySQL 从库用覆盖索引查出一页视频 ID，再批量读详情缓存。列表本身不缓存，因为游标分页的中间页命中率低。从库延迟只会让刚发布的视频晚一两秒出现在列表里，可以接受。

### 重复请求

不建通用幂等中间件，每个写接口靠自身语义处理重试：

- 状态类接口（确认上传、提交、撤回、隐藏、恢复公开、删除、恢复）：条件更新影响 0 行时重新读取视频；当前状态已经是目标状态就返回 200 和当前详情，否则返回 409。客户端重试同一个操作总能拿到成功结果。
- 创建视频：重复请求会多出一条"上传中"记录。它不可见、不占正式存储，1 天后由清理任务删除，不需要专门去重。
- 审核回调：任务状态条件更新保证同一结论只落一次。

### 可用性与降级

- 业务服务无状态，多实例部署；后台 worker 与清理任务在每个实例都运行，靠 `SKIP LOCKED` 和幂等操作避免冲突，不需要选主或分布式锁。
- MySQL 主从部署，列表读从库，写与缓存未命中读主库。
- Redis 不可用时：详情读取直接查数据库，由基座的单实例并发保护限制压到 MySQL 的请求数；上传频率限制放行并告警。
- 审核服务不可用：提交接口不受影响，任务按退避重试，最终投递失败的任务告警，作者可撤回后重新提交。
- 对象存储不可用：上传与确认失败；已在 CDN 缓存的视频继续可播。

## 核心流程

### 创建视频与上传

```text
1. POST /api/videos，body 可带 title、description、coverType(jpg|png)
2. 上传频率限制：每用户 10 次/小时、50 次/日（Redis 固定窗口计数），超限 429 并带 Retry-After
3. 插入 video(status=0 上传中)，返回 videoId 与两个预签名上传凭证（视频、封面）
4. 客户端直传对象存储
5. POST /api/videos/{videoId}/complete
   a) 条件：作者本人、status=0、未删除
   b) HEAD 两个临时对象：大小在上限内，封面 ≤ 5MB 且为 JPEG/PNG
   c) 用 ffprobe 通过一个短时签名地址读取视频头部：容器 MP4、视频 H.264、音频 AAC 或无声、
      moov 在文件头、时长 ≤ 10 分钟、分辨率在上限内
      不满足 → 422 UPLOAD_MEDIA_INVALID，返回具体原因，视频保持 status=0，客户端可重新上传后再确认
   d) 存储内部复制临时对象到正式 key，删除临时对象
   e) UPDATE video SET status=1, media_key, cover_key, duration_ms, width, height, size_bytes
        WHERE id=? AND status=0
6. 返回视频详情
```

第 5 步重复调用是安全的：复制同一个对象到同一个 key 结果相同；视频已经是草稿时直接返回当前详情。

只读取视频头部，不下载整个文件：`moov` 在文件头时，ffprobe 读取前几百 KB 就能拿到编码、时长和分辨率。`moov` 在文件末尾直接拒绝，因为这种文件需要下载完才能播放，起播慢。

### 编辑、提交与撤回

```text
PATCH /api/videos/{videoId}：仅 status ∈ {1, 3} 可改 title、description
换封面：POST /api/videos/{videoId}/cover 返回新封面的预签名凭证（临时 key），
       再调用 POST /api/videos/{videoId}/cover/complete 校验、复制到 cover_{n+1}，更新 cover_key 后删除旧封面
       仅 status ∈ {1, 3} 可换，审核通过的视频不能换封面，避免绕过审核
       status=3 编辑后仍为 3，reject_reason 保留供作者参考，重新提交时清空

POST /api/videos/{videoId}/submit：见"审核对接"，status 1/3 → 2

POST /api/videos/{videoId}/withdraw：status 2 → 1；
  同一事务把本轮 status=1 待投递的任务置为 6 已取消
```

### 隐藏、删除、恢复与下架

```text
隐藏：            status 4 → 5，删除缓存
恢复公开：        status 5 → 4，删除缓存；published_at 不变，回到原排序位置
删除：            写 deleted_at，status 不变；待审核时同一事务取消本轮待投递任务；删除缓存
恢复：            deleted_at 非空且未超过 7 天 → 清 deleted_at；
                  若 status=2 待审核，同一语句改回 status=1，因为删除时任务可能已被取消
下架（内部接口）：status 4/5 → 6，写 offline_reason，删除缓存，
                  移动正式对象到 offline/{videoId}/，刷新 CDN，写审计日志
```

下架后作者仍可删除。下架状态 6 没有出边，作者的隐藏、恢复公开、提交接口都会因为条件不满足而返回 409，回收站恢复后仍是 6。

删除与下架是两个独立维度：删除是作者行为、走回收站（写 `deleted_at`，status 不变，7 天内可恢复）；下架是平台行为、走 `status=6`（终态，作者不能自行恢复）。它们可叠加——作者仍可删除已下架的视频，但恢复后状态还是 6，不会自动变回已发布。

下架的第二步（移动对象、刷新 CDN）失败时，接口返回 500，调用方重试。数据库已经是下架状态，重试时条件更新影响 0 行但仍继续执行移动对象和刷新 CDN，直到成功。

### 清理任务

一个后台任务，每小时执行一次，每批处理 500 条：

```text
1. 回收站超期：deleted_at < now - 7 天
   删除 videos/{videoId}/ 下的对象（下架视频同时删除 offline/{videoId}/）→ 删除 review_task → 删除 video
   对象先删、记录后删：中途失败时记录还在，下次重试；对象删除对不存在的 key 是幂等的
2. 未完成上传：status=0 且 created_at < now - 1 天 → 删除 video 记录
   临时对象由存储桶生命周期规则自动删除
```

多个实例同时执行时，两个实例可能处理同一批记录，删除操作都是幂等的，结果一致。

## 接口设计

| 方法 | 路径 | 作用 | 鉴权 |
| --- | --- | --- | --- |
| POST | /api/videos | 创建视频并获取上传凭证 | JWT |
| POST | /api/videos/{videoId}/complete | 确认上传完成，校验媒体 | JWT(作者) |
| PATCH | /api/videos/{videoId} | 修改标题、简介 | JWT(作者) |
| POST | /api/videos/{videoId}/cover | 获取换封面的上传凭证 | JWT(作者) |
| POST | /api/videos/{videoId}/cover/complete | 确认封面上传 | JWT(作者) |
| POST | /api/videos/{videoId}/submit | 提交审核 | JWT(作者) |
| POST | /api/videos/{videoId}/withdraw | 撤回审核 | JWT(作者) |
| PUT | /api/videos/{videoId}/visibility | 隐藏或恢复公开，body `{"hidden": true}` | JWT(作者) |
| DELETE | /api/videos/{videoId} | 删除到回收站 | JWT(作者) |
| POST | /api/videos/{videoId}/restore | 从回收站恢复 | JWT(作者) |
| GET | /api/videos/{videoId} | 视频详情，含签名播放地址与封面地址 | 可选 JWT |
| GET | /api/users/{userId}/videos | 他人公开作品列表 | 可选 JWT |
| GET | /api/users/me/videos | 我的作品，`?status=` 过滤，`?scope=recycle` 查回收站 | JWT |
| POST | /internal/videos/batch | 按 ID 批量取公开视频，供 Feed 模块调用，单次 ≤ 50 个 | 服务间凭证 |
| POST | /internal/videos/{videoId}/offline | 平台下架，body 含 operator_id、reason | 服务间凭证 |
| POST | /internal/review/callback | 审核服务回调结论 | 服务间凭证 |

约定：

- 列表统一游标分页：`?cursor=<base64(排序值,id)>&limit=20`，`limit` 上限 50，返回 `next_cursor`。公开列表按 `(published_at, id)` 倒序，我的作品按 `(created_at, id)` 倒序。
- 详情与列表返回的播放和封面地址都经过同一个可见性判断与签名函数，接口不返回裸对象键。
- 批量接口按请求的 ID 顺序返回，不可见或不存在的 ID 直接跳过。
- 作者身份一律取自登录态，不取请求参数。

主要错误码：

| 错误码 | HTTP | 触发场景 |
| --- | --- | --- |
| UPLOAD_RATE_LIMITED | 429 | 超出上传次数限制 |
| UPLOAD_OBJECT_MISSING | 422 | 确认上传时临时对象不存在 |
| UPLOAD_MEDIA_INVALID | 422 | 大小、格式、编码、时长、分辨率不满足，响应里带具体原因 |
| VIDEO_NOT_FOUND | 404 | 视频不存在或对当前用户不可见 |
| VIDEO_STATE_CONFLICT | 409 | 当前状态不允许该操作 |

## 可观测性

指标：

- `video_upload_complete_total{result}`、`video_upload_complete_seconds`
- `video_detail_cache_total{result=hit|miss}`
- `review_dispatch_total{result}`、`review_callback_total{result}`、`review_roundtrip_seconds`（提交到结论）
- `review_task_oldest_pending_seconds`：最老的未出结论任务等待时长
- `video_cleanup_lag_seconds`

告警：最老未出结论任务超过 30 分钟、出现投递失败任务、详情缓存命中率低于 90%、清理滞后超过 2 小时、下架接口失败。

## 演进路径

每一步在上一步的监控数据证明需要时再做：

1. 热点视频进程内缓存：单个 Redis key 的读取成为瓶颈时，加 1~5 秒的本地缓存。同时为大 V 做进程内预热：粉丝数达到阈值（初值 100 万，可配置，粉丝数来自关系模块）的作者发布新视频时，通过 Redis Pub/Sub 通知各实例把该视频加载进进程内缓存。
2. 转码与多码率：新增转码任务表，确认上传后异步转码，完成后才允许提交审核；放宽编码限制，接受 H.265。
3. 视频事件：Feed、推荐、搜索需要感知发布与下架时，在状态变更事务里写事件表，由 worker 投递到消息队列，复用审核投递的写法。
4. 分库：视频表超过 5,000 万行或写入成为瓶颈时，按 `video_id` 分库，作者维度的列表改为单独的作者-视频索引表。
