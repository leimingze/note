# 日志与指标设计

## 目标

日志用于回答“某个请求发生了什么”，指标用于回答“服务整体是否正常”。两者都由项目基座提供，业务模块只补充业务名称、操作名称和错误分类，不直接创建输出器或修改采集规则。

本方案基于当前已有的 `slog` JSON 日志、请求 ID、访问日志、异常恢复、健康探针和 MySQL/Redis 连接池。第一阶段只观察 HTTP 请求、进程生命周期和外部依赖，暂不记录用户行为明细。

## 当前已有能力

| 能力 | 当前实现 | 说明 |
| --- | --- | --- |
| 结构化日志 | `backend/logging/logger.go` | 使用 `slog` 输出 JSON，支持 `debug`、`info`、`warn`、`error` |
| 请求关联 | `backend/middleware/request_id.go` | 透传合法的 `X-Request-ID`，否则生成安全随机 ID |
| 访问日志 | `backend/middleware/access_log.go` | 记录方法、路由、状态码、耗时和请求 ID |
| 异常日志 | `backend/middleware/recovery.go` | 记录 panic、请求 ID 和调用栈，并返回统一错误 |
| 健康检查 | `backend/server/health.go` | 提供 `/livez` 和 `/readyz`，当前只表示进程生命周期状态 |
| 指标 | 暂无 | 当前没有 `/metrics`、请求指标或连接池指标 |

## 日志设计

### 日志类别

| 类别 | 级别 | 必要字段 | 触发时机 |
| --- | --- | --- | --- |
| 服务启动 | `info` | `service`、`environment`、`address` | HTTP 服务开始监听前后 |
| 服务退出 | `info` | `service`、`reason`、`duration_ms` | 收到退出信号并完成关闭 |
| 配置或初始化失败 | `error` | `component`、`error_type`、`error` | 配置、MySQL、Redis 或路由创建失败 |
| HTTP 访问 | `info` | `request_id`、`method`、`route`、`status`、`duration_ms` | 请求处理完成 |
| HTTP 业务错误 | `warn` | `request_id`、`route`、`status`、`error_code` | 可预期的客户端或业务错误 |
| 外部依赖错误 | `error` | `request_id`、`dependency`、`operation`、`error_type`、`duration_ms` | 数据库、Redis 或外部服务调用失败 |
| 未恢复异常 | `error` | `request_id`、`route`、`panic`、`stack` | 请求链路发生 panic |

### 公共字段

应用日志统一使用以下字段：

- `time`、`level`、`msg`：由 `slog` 自动写入。
- `service`：固定为 `pulseframe-api`。
- `environment`：来自 `APP_ENV`。
- `request_id`：请求范围内的关联标识；没有 HTTP 请求时不伪造。
- `component`：`config`、`mysql`、`redis`、`http` 或具体业务组件。
- `error_type`：稳定的错误类别，例如 `config_invalid`、`dependency_unavailable`、`response_invalid`。

路由日志使用 Gin 的模板路径，例如 `/users/:id`。未匹配路由时使用 `/unknown`，不把完整查询字符串写入日志。耗时统一使用整数毫秒；指标保留更高精度。

### 敏感信息

以下内容禁止写入日志和指标标签：密码、数据库连接串、Redis 密码、Cookie、Authorization、Access Token、Refresh Token、OAuth `code`、OAuth `state`、用户密码、完整 SQL 参数、原始 IP 和个人身份信息。

错误日志记录稳定的错误类别和底层错误摘要。底层错误必须先经过分类，避免把认证信息或第三方响应原文直接写入日志。

### 输出方式

应用继续向标准输出写 JSON，由运行环境负责采集、检索和保存。代码不直接写业务日志文件，也不在请求处理中创建新的日志器。启动时使用 `logger.With("service", "pulseframe-api", "environment", cfg.Environment)` 生成带公共字段的日志器，并把它传给路由和依赖模块。

## 指标设计

第一阶段采用 Prometheus 指标模型，并在同一个 HTTP 服务提供 `GET /metrics`。指标只使用有限集合标签，禁止把请求 ID、用户 ID、用户名、IP、完整 URL 或错误原文作为标签。

### HTTP 指标

| 指标 | 类型 | 标签 | 含义 |
| --- | --- | --- | --- |
| `pulseframe_http_requests_total` | Counter | `method`、`route`、`status` | 已完成请求数量 |
| `pulseframe_http_request_duration_seconds` | Histogram | `method`、`route`、`status` | 请求处理耗时分布 |
| `pulseframe_http_requests_in_flight` | Gauge | 无或 `route` | 当前正在处理的请求数量 |
| `pulseframe_http_response_errors_total` | Counter | `route`、`status`、`error_code` | 已返回的统一错误数量 |

`route` 使用注册路由模板，未匹配路径统一为 `/unknown`。`status` 使用 HTTP 状态码字符串。`error_code` 只使用固定错误码集合，不能使用用户输入或底层错误文本。

### 依赖指标

| 指标 | 类型 | 标签 | 含义 |
| --- | --- | --- | --- |
| `pulseframe_dependency_operations_total` | Counter | `dependency`、`operation`、`result` | MySQL、Redis 等依赖操作数量 |
| `pulseframe_dependency_operation_duration_seconds` | Histogram | `dependency`、`operation`、`result` | 依赖操作耗时分布 |
| `pulseframe_dependency_errors_total` | Counter | `dependency`、`operation`、`error_type` | 依赖错误数量 |
| `pulseframe_dependency_ready` | Gauge | `dependency` | 最近一次可用性状态，1 表示可用，0 表示不可用 |

`operation` 使用固定名称，例如 `mysql_ping`、`mysql_query`、`redis_ping`、`redis_command`。业务层对 Redis 命令进行分类时使用 `get`、`set`、`delete` 等有限集合，不记录完整 key。

### 连接池指标

MySQL 定期读取 `sql.DB.Stats()`，Redis 定期读取 `Client.PoolStats()`。采集器只发布数值，不在每次采集时写日志。

| 指标 | 来源 | 含义 |
| --- | --- | --- |
| `pulseframe_mysql_open_connections` | `sql.DB.Stats` | 当前打开连接数 |
| `pulseframe_mysql_in_use_connections` | `sql.DB.Stats` | 当前使用中的连接数 |
| `pulseframe_mysql_idle_connections` | `sql.DB.Stats` | 当前空闲连接数 |
| `pulseframe_mysql_wait_count_total` | `sql.DB.Stats` | 等待连接累计次数 |
| `pulseframe_mysql_wait_duration_seconds_total` | `sql.DB.Stats` | 等待连接累计时长 |
| `pulseframe_redis_pool_total_connections` | `PoolStats` | Redis 连接总数 |
| `pulseframe_redis_pool_idle_connections` | `PoolStats` | Redis 空闲连接数 |
| `pulseframe_redis_pool_timeouts_total` | `PoolStats` | 获取 Redis 连接超时次数 |

连接池指标使用 `component` 或固定指标名区分依赖，不使用地址、端口、用户名等高基数字段。

### 进程和生命周期指标

| 指标 | 类型 | 含义 |
| --- | --- | --- |
| `pulseframe_process_ready` | Gauge | HTTP 服务是否已开始接收请求 |
| `pulseframe_startup_failures_total` | Counter | 配置或依赖初始化失败次数 |
| `pulseframe_shutdown_total` | Counter | 服务进入退出流程的次数 |

`/readyz` 与 `pulseframe_process_ready` 仍表示进程是否完成启动。MySQL 或 Redis 在启动后发生故障时，由依赖错误指标和日志反映；是否从就绪状态摘除，需要后续确定持续探活策略后再实现。

## 采集与生命周期

后续实现按以下职责划分：

| 文件 | 变更 | 职责 |
| --- | --- | --- |
| `backend/config/metrics.go` | 新增 | 指标开关、监听路径、采集间隔和配置校验 |
| `backend/config/config.go` | 修改 | 接入指标配置 |
| `backend/metrics/registry.go` | 新增 | 创建并持有 Prometheus Registry，注册 HTTP、依赖和连接池指标 |
| `backend/metrics/collector.go` | 新增 | 定期读取 MySQL、Redis 连接池统计，退出时停止采集 |
| `backend/middleware/metrics.go` | 新增 | 记录请求数量、耗时、状态码和进行中的请求数 |
| `backend/server/router.go` | 修改 | 注册 `/metrics`，并保证路由标签使用模板路径 |
| `backend/internal/app/dependencies.go` | 修改 | 持有指标注册表和采集器，初始化失败时清理，退出时停止采集 |
| `backend/internal/app/run.go` | 修改 | 创建带公共字段的日志器和指标依赖，并安排生命周期顺序 |
| `backend/test/metrics_test.go` | 新增 | 验证指标注册、请求记录、连接池采集和关闭行为 |

指标采集器必须由应用依赖对象持有，不能使用包级可变全局注册表。HTTP 服务停止并完成请求后，先停止指标采集，再关闭 MySQL 和 Redis；指标端点在退出流程开始后不再接收新请求。

## 告警依据

第一阶段只定义可观测量，不在代码中写死告警阈值。部署侧可以根据实际容量设置：

- HTTP 错误率和 P95/P99 延迟持续升高；
- `requests_in_flight` 接近进程并发上限；
- MySQL 等待连接次数或等待时长持续增加；
- Redis 连接池超时次数增加；
- 依赖错误率升高但 HTTP 请求仍持续成功；
- `pulseframe_process_ready` 为0或启动失败次数增加。

## 当前结论

日志基础能力已经存在，下一步只需补充公共字段和敏感信息过滤规则。指标能力尚未编写，确定采用 Prometheus 模型后，再按上述文件职责实现指标注册、HTTP 中间件和连接池采集。重试、熔断、限流和降级仍由业务模块或部署治理决定，不放入本次日志与指标基础代码。
