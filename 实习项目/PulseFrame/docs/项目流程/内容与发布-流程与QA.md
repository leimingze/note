# 内容与发布模块：流程与面试 QA

## Q1：请先说明这个模块的整体流程。

内容与发布模块负责把一条短视频从上传中推进到已发布或已驳回，同时提供详情、我的作品、公开作品和内部批量查询。写链路是：用户提交标题、简介和封面类型，服务端校验参数并检查上传次数，在 MySQL 写入 `status=0` 的视频记录，再签发视频和封面的直传凭证。客户端直接把文件上传到 SeaweedFS，完成后调用确认接口。服务端先复制到正式对象键，再校验大小、封面类型和视频编码，调用审核接口，最后用条件更新写入终态。

读链路是：列表先从 MySQL 取出一页视频 ID，再批量读取 Redis 详情缓存，未命中的 ID 回源 MySQL 并回填。接口根据当前查看者判断可见性，再为视频和封面实时签发一小时有效的私有桶地址。MySQL 保存状态和元数据，Redis 承担详情缓存与上传限流，SeaweedFS 保存媒体对象，三者职责分开。

## Q2：MySQL 表为什么只有一张 `video` 表？

本期发布的峰值很低，设计估算日均只有一万条视频，二十秒短视频的单行元数据也很小，因此一张表可以同时保存内容、对象键、媒体信息和发布状态。视频文件本体不进入 MySQL，表里只存 `media_key`、`cover_key` 这类稳定对象键，签名地址在读取时临时生成。

表里的状态字段把“谁能看、能否再次确认”集中到一行记录；`published_at` 用于公开列表排序，`created_at` 用于作者作品排序；宽高、时长和大小在确认上传后写入，供客户端布局和后续治理使用。点赞、评论、播放数没有放进视频表，因为这些高频计数会反复修改视频行，也会增加详情缓存的失效频率。

## Q3：表的索引是怎么设计的？

公开作品列表使用 `(author_id, status, published_at, id)`。查询先按作者和已发布状态做等值过滤，再按发布时间和视频 ID 倒序，并且只取 `id` 与 `published_at`，因此可以直接读取这个联合索引，不需要先回表再排序。我的作品列表使用 `(author_id, created_at, id)`，按作者过滤后按创建时间和 ID 倒序取 ID。

我的作品虽然支持状态过滤，但没有给每种状态再建一套索引。单个作者的内容量有限，在已有作者时间索引上回表过滤状态，维护成本低于增加多套二级索引。主键采用自增 `BIGINT`，写入顺序稳定，同时可以直接用在对象键和游标条件里。

## Q4：为什么列表使用游标分页，不使用 `OFFSET`？

公开列表按 `published_at` 和 `id` 倒序，游标把上一页最后一个位置编码成 `base64(时间, id)`。下一页条件使用 `published_at < ? OR (published_at = ? AND id < ?)`，即使多条视频的发布时间完全相同，也能依靠 ID 保持稳定顺序。查询取 `limit + 1` 条，多出来的一条只用于判断是否存在下一页，实际最多返回 `limit` 条。

这种分页不会随着页码增加而扫描并丢弃大量前置记录，也避免翻页期间有新视频发布后使用 `OFFSET` 产生重复或跳过。默认每页二十条，单次最多五十条；游标格式、状态值和分页上限都在接口边界校验，非法输入返回 400。

## Q5：为什么视频和封面不经过业务服务？

短视频平均约十五 MB，如果文件字节经过业务服务，会长期占用 HTTP 连接、网关带宽和进程内存，而业务服务真正需要处理的只有元数据与校验结果。创建视频时，服务端签发 SeaweedFS 的 POST Policy，限制对象键、最小和最大长度、视频类型或封面的 JPEG/PNG 类型，以及三十分钟有效期。

客户端分别上传到 `upload/{videoId}/media.mp4` 和 `upload/{videoId}/cover`。业务服务不接收大文件，只处理确认请求。临时对象和正式对象都使用视频 ID 作为前缀，一个视频对应一组固定对象，因此不需要额外维护上传凭证表；未完成上传的临时对象由存储桶生命周期规则清理。

## Q6：上传限流为什么使用 Redis 滑动窗口？

创建视频前先检查小时窗口 `rate:upload:h:{userId}`，上限十次；通过后再检查天窗口 `rate:upload:d:{userId}`，上限五十次。小时窗口更紧，先检查它可以避免已经超过小时额度时继续消耗更宽的天额度。限流使用 Redis ZSET，由 Lua 脚本依次清理窗口外记录、检查数量、写入本次记录并刷新过期时间，多个服务实例共享同一份额度。

脚本使用 Redis 的 `TIME`，避免不同业务机器的时钟差影响窗口判断。业务层把 Redis 限流错误记录为告警后放行，因为限流服务故障时让上传全部不可用，影响会大于短时间少一层保护；正常超限仍返回 `429 UPLOAD_RATE_LIMITED`。

## Q7：为什么确认上传要先复制，再校验正式对象？

预签名凭证在三十分钟内可以重复使用。如果客户端先上传一份合格文件，服务端校验通过后再复制，客户端仍可能在复制前替换临时对象，形成检查后修改的时间窗口。当前流程先把临时对象复制到 `videos/{videoId}/` 下的正式键，而客户端没有正式键的写权限，随后只对正式对象做大小、封面类型和媒体探测。

服务端读取正式视频的前 512KB，通过 HTTP Range 交给 `ffprobe`，避免下载完整视频。视频进入 `video` 表的大小来自正式对象元数据，宽高、时长和编码来自正式对象的探测结果。这样校验对象与被发布对象保持为同一份内容。

## Q8：视频状态机怎么设计？

状态值有四个：`0` 上传中、`1` 待审核、`2` 已发布、`3` 已驳回。上传中允许进入待审核、已发布或已驳回；待审核允许进入已发布或已驳回；已发布和已驳回是当前终态，不能继续确认。状态一为本期同步假审核之后的真实异步审核预留，当前默认实现会从上传中直接进入已发布或已驳回。

审核接口只返回是否通过和驳回原因，业务层据此决定目标状态。通过时写入 `published_at` 并预热详情缓存；驳回时写入经过长度限制的 `reject_reason` 并删除旧缓存。真实审核服务、异步任务和回调目前没有实现，审核依赖被保留为接口，后续可以沿用状态一继续扩展。

## Q9：两个确认请求同时到达时，怎样避免重复发布？

确认请求先读取视频并校验作者。若记录已经是已发布或已驳回，直接返回当前详情；若仍处于上传中，就继续复制、探测和审核。最终写入使用 `WHERE id = ? AND author_id = ? AND status = 0` 的条件更新，两个请求中只有一个能够影响一行。

没有更新成功的请求会重新读取该视频。只要作者匹配且状态已经到达已发布或已驳回，就返回当前终态详情；如果状态仍不允许确认，则返回 `409 VIDEO_STATE_CONFLICT`。这种做法依靠单个条件更新和 InnoDB 行锁完成状态竞争控制，不需要额外的幂等记录表。媒体校验失败时数据库仍保持 `status=0`，客户端可以重新上传后再次确认。

## Q10：Redis 缓存保存什么，怎样写入和失效？

详情缓存键是 `video:{videoId}`，值为 JSON，保存展示字段、状态、正式对象键、媒体信息和时间字段，不保存签名地址，因为签名地址会过期，而且是否可见取决于当前查看者。普通缓存有效期是十分钟加零到六十秒随机值，不存在视频的键写入 `{}` 并保留一分钟，减少随机 ID 持续查询 MySQL。

审核通过后直接把新记录写入缓存，减少第一次详情请求回源；审核驳回时删除可能存在的上传中旧值。读取单条记录使用 `GET`，批量接口使用一次 `MGET`，未命中的 ID 用一条 `WHERE id IN (...)` 查询，最后通过 Pipeline 批量回填正常值和空值。批量接口最多五十个 ID，减少网络往返次数。

## Q11：Redis 发生故障会影响发布和读取吗？

缓存被定义为可丢失组件。详情 `MGET` 失败时，业务层把全部 ID 当作未命中并回源 MySQL，发布确认不会被阻断；缓存写入或删除失败只记录告警，因为 MySQL 仍是元数据的可靠来源。上传限流在运行期遇到 Redis 错误时同样告警放行，避免一项辅助能力故障直接阻断全部创建操作。

启动阶段仍会建立 Redis 客户端并执行连通性探测，配置错误或启动探测失败会直接终止服务。这里的区别是：启动配置错误需要尽早暴露，运行期缓存或限流故障需要保留核心业务能力。

## Q12：列表为什么不缓存整页结果？

公开列表和我的作品都先通过 MySQL 索引查询一页视频 ID，再复用详情缓存批量读取元数据。列表本身不缓存，因此新视频发布后不需要维护大量作者、状态、游标组合对应的列表缓存，也不会因为第一页、第二页使用不同游标而生成大量低命中缓存。

分页结果主要由 MySQL 索引负责，展示字段和对象键由 Redis 详情缓存负责。两者使用的数据边界清晰：MySQL 决定有哪些视频以及顺序，Redis 决定已查询视频的详情能否复用。批量查询会先去重 ID，再按原请求顺序组装可见结果。

## Q13：公开与私密内容怎样隔离？

只有 `status=2` 的视频对所有人可见。上传中、待审核和已驳回只能由作者查看；其他人访问这些记录和不存在的记录时统一返回 `404 VIDEO_NOT_FOUND`，避免通过不同错误码判断某个视频是否存在。驳回原因只返回给作者，其他查看者拿不到该字段。

SeaweedFS 桶保持私有，响应中不返回裸对象键。详情、作品列表和批量查询共用同一套可见性判断与地址签名逻辑，所以同一份缓存可以同时服务作者和普通访问者。签名地址有效一小时，缓存中的对象键不会因为签名过期失效。

## Q14：媒体规格是怎么检查的？

对象元数据先检查视频大小不超过 50MB，封面不超过 5MB，封面类型必须是 JPEG 或 PNG。视频探测要求 MP4 容器、H.264 视频编码、AAC 音轨或无声、时长不超过 20 秒、宽高不超过 1920×1080。`ffprobe` 只接收文件头部，不读取完整文件。

当前方案要求 MP4 的 `moov` 信息位于文件头部，这也是快速起播的要求。超过时长、分辨率、编码或容器限制时返回 `422 UPLOAD_MEDIA_INVALID` 和具体原因，记录继续保持上传中。模块不做转码，也不下载完整视频重新封装，符合当前“只接收可上架格式”的范围。

## Q15：当前实现与设计文档还有哪些明确缺口？

真实异步审核、回调、后台治理、草稿编辑、隐藏下架、转码和热点本地缓存都没有实现，这些属于设计文档中明确列出的后续范围。真实审核服务接入后，可以利用现有待审核状态、审核接口和缓存预热或删除逻辑继续扩展。

另有一个错误映射缺口：设计规定确认上传时临时对象不存在应返回 `422 UPLOAD_OBJECT_MISSING`，业务层也能识别存储层的 `ErrNotFound`，但当前 S3 的 `Copy` 没有把源对象不存在转换成这个错误，因此该场景可能进入通用的存储不可用分支并返回 503。该问题应在存储实现中补齐，现有文档和流程画布已将它标出。
