# 项目记忆

最后更新：2026-09-24

## 项目目标

PulseFrame 是从零设计和实现的 Go 视频社交平台后端，目标功能包括短视频内容分发、用户互动、短视频弹幕、直播房实时互动、内容安全 Agent 和云原生工程能力。

项目主要用于系统学习，并沉淀可用于 Go 后端、AI Agent 和云原生岗位面试的工程经验。重点是完整经历需求分析、方案选型、实现、数据验证和复盘，而不是堆叠技术组件。

## 已确认的用户需求

- GCFeed 等开源项目只作为业务和工程思路参考，不复用其代码；PulseFrame 从零设计和实现。
- 每个功能模块在实现前都要说明背景、需求和方案选型，并提供能够用于面试回答的表达。
- 核心功能尽量使用来源、版本和许可明确的公开真实数据进行验证；合成数据只补充边界、故障和极端负载场景。
- 重要设计必须有待解决的问题、对照基线、评价指标和可复现验证结果；工业方案由需求、规模和证据驱动。
- 视频阶段只实现上传、发布和必要的基础处理，不实现剪辑、裁切、滤镜、特效或配乐。
- 目录职责在目录树中使用行尾注释说明；不提前创建没有实现内容的空业务模块或空服务。

## 当前策略

功能按以下顺序推进：

1. 总体架构与工程基础。
2. 用户与认证。
3. 视频上传与发布。
4. 审核与基础后台。
5. Feed 与播放。
6. 互动、关系与通知。
7. 行为采集与推荐。
8. 搜索与发现。
9. 短视频弹幕。
10. 内容安全 Agent。
11. 直播与实时弹幕。
12. 运营、云原生与系统治理。

当前阶段已完成工程基础、用户与认证模块的 Go 后端和 Vue + TypeScript 网页端首版；已完成首轮真实 MySQL/Redis 迁移与前后端端到端验证，容量和故障验证尚未完成。

用户与认证模块第一版采用用户名密码、MySQL 8.4、限定在仓储层的 GORM、Argon2id、Redis 不透明会话与共享限流；网页 API 使用 HttpOnly Cookie、精确来源的凭据型 CORS 和 CSRF 防护。原生手机端尚未实施，未来通过 Bearer 凭据接入同一认证用例。消息系统、其他模块的缓存与部署平台仍须在相关模块设计时，依据业务需求、数据特征、规模预估、候选方案比较和实验结果决定。

- 已提供 `GET /livez` 和 `GET /readyz`。
- 已覆盖配置单元测试、HTTP 链路测试和真实临时端口的服务生命周期测试。
- 认证后端已实现用户仓储、Argon2id 并发限制、Redis 会话与共享限流、注册/登录/本人信息/CSRF/退出接口及凭据型 CORS。
- 网页端调用真实认证 API，提供注册、登录、会话恢复与 CSRF 保护的当前设备退出；前端自动化测试使用隔离合成账号和受控 HTTP 响应，无运行时模拟登录路径。
- 前端已通过类型检查、7 项 Vitest 测试、生产构建和 npm audit；当前锁定 Vitest 4.1.11，依赖审计未发现漏洞。
- 启动配置拒绝 MySQL `root`、要求明确数据库和非 root 用户，并要求 Redis ACL 用户名与密码；认证 API 只为精确 `WEB_ORIGIN` 开放凭据型 CORS。
- 当前已通过 `go test -timeout=60s ./...`、`go test -race -timeout=60s ./...` 和 `go vet ./...`；自动化测试使用 `sqlmock`、`miniredis` 和 HTTP 测试路由。
- 已在真实 MySQL 8.4.11 专用 `pulseframe` 数据库执行 `0001_create_users.sql`；`pulseframe_app` 仅有该库的 `SELECT`/`INSERT` 权限，`pulseframe_migrator` 仅有建表所需的受限 DDL 权限。
- 已创建 Redis ACL 用户 `pulseframe_api`，限制在 `pulseframe:auth:*` 键前缀和认证会话/限流命令；已验证它不能读取其他前缀的键。
- 通过真实 MySQL、Redis 和 Vite 代理验证注册、重复注册、错误/正确登录、本人信息、CSRF 退出和退出后会话失效；两条合成测试账号已删除。测试没有使用或导入公开用户数据集。

## 当前资源与环境

- 后端路径：`backend/`。
- 前端路径：`frontend/`；本地 Vite 代理目标为 `127.0.0.1:8081`，启动后端时设置相同 HTTP_ADDR 并按实际网页端口设置 WEB_ORIGIN。
- Go 模块名：`pulseframe`。
- 当前 Go 版本：`1.26`。
- 核心 API 当前使用 Gin `v1.11.0`，默认监听 `:8080`。
- MySQL 与 Redis 通过 SSH 隧道映射到本机 `127.0.0.1:13306` 和 `127.0.0.1:16379`；远端容器端口分别为 `30052` 和 `30054`。网页本机当前使用 `5174`，Vite 代理目标为 API `127.0.0.1:8081`；`5173` 被另一个项目占用。
- 本地开发连接配置位于权限 `600`、已被 Git 忽略的 `backend/.env.local`；源码、文档和记忆不保存应用凭据。MySQL 远端账户和 Redis `default` ACL 账户实际认证方式不同，后者使用密码认证且没有名为 `root` 的 ACL 用户；API 使用专用账号。
- 本轮排查期间曾向 Redis 公网映射端口发送一次明文密码认证探测；之后已切换至 SSH 隧道。没有证据显示凭据被第三方获取；未擅自轮换共享 Redis `default` 凭据，避免中断其他客户端。
- 首轮集成仅确认专用账号权限、迁移和功能链路，不代表故障切换或容量达标。尚未检查或收紧远端服务端口的网络访问策略，也未验证 Redis 淘汰、持久化和依赖故障行为。
- 启动和环境变量说明见 `backend/README.md`。

## 架构方向

- 采用单仓库模块化架构，普通业务模块初期由核心 API 统一承载。
- 预留四类部署边界：核心 API、事件 Worker、直播网关、内容安全 Agent。
- 只有运行方式、容量或故障边界出现真实差异时才创建和独立部署特殊工作负载。
- Gin 仅用于服务启动层和业务模块的 HTTP Adapter；Application 与 Domain 不得依赖 `gin.Context`。
- 事件 Worker 不使用 Gin；直播网关、服务间通信和 Agent 接入方式留到对应模块根据需求选型。
- 每个模块拥有自身数据的写入权，跨模块协作通过公开接口或事件完成。
- 详细决策见 `memory/decisions/ADR-0001-modular-deployment-boundaries.md`。

## 产品与体验方向

- 第一阶段先形成注册登录、视频发布审核和 Feed 播放的短视频基础闭环。第一版账号仅支持用户名密码与网页端；未建立可信恢复渠道前不宣称可开放公众注册。
- 后续补充用户互动、推荐、搜索、短视频时间轴弹幕、直播房实时弹幕和统一内容治理。
- 创作者、普通用户和管理人员必须能够看到与其权限匹配且可理解的业务状态和失败原因。

## 安全边界

- 内容安全 Agent 可以分析内容、查询必要上下文并给出处置建议，但不能绕过审核模块直接修改核心业务数据。
- 永久封禁等高影响操作不能仅由模型自主决定，必须具有明确权限边界和人工复核路径。
- 认证、服务身份、权限、输入校验和管理操作审计须在各模块设计中显式处理。
- 配置与凭据分离；源码和项目记忆中都不得保存凭据。

## 开放问题

- 首轮真实集成使用共享远端实例上的专用数据库、MySQL 账号和 Redis 键前缀，仍需进行依赖故障与容量验证，并收紧远端端口网络访问、核实 Redis 淘汰和持久化配置；协调其他 Redis 消费者后轮换 `default` 凭据；公网开放前还需可信账号恢复渠道。
- 第一版没有封禁、角色授予、全设备退出或交易接口；增加这些能力时必须设计 MySQL 权威账号状态与 Redis 会话撤销的一致性和高风险操作的再次验证。
- 视频存储、上传协议、媒体基础处理、内容审核和分发方案尚待分模块设计。
- 认证模块公开数据集调研结论记录于 memory/research/2026-09-24-auth-test-data.md；用于推荐、内容审核、弹幕和容量实验的数据集仍待按模块调研并核验许可。
- 事件 Worker、直播网关和内容安全 Agent 的创建时机及具体通信方案仍需由真实需求和验证结果决定。
