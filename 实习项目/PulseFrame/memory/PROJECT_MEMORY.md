# 项目记忆

最后更新：2026-09-23

## 项目目标

PulseFrame 是从零设计和实现的 Go 视频社交平台后端，目标功能包括短视频内容分发、用户互动、短视频弹幕、直播房实时互动、内容安全 Agent 和云原生工程能力。

项目主要用于系统学习，并沉淀可用于 Go 后端、AI Agent 和云原生岗位面试的工程经验。重点是完整经历需求分析、方案选型、实现、数据验证和复盘，而不是堆叠技术组件。

## 已确认的用户需求

- GCFeed 等开源项目只作为业务和工程思路参考，不复用其代码；PulseFrame 从零设计和实现。
- 每个功能模块在实现前都要说明背景、需求和方案选型，并提供能够用于面试回答的表达。
- 核心功能尽量使用来源、版本和许可明确的公开真实数据进行验证；合成数据只补充边界、故障和极端负载场景。
- 重要设计必须有待解决的问题、对照基线、评价指标和可复现验证结果；工业方案由需求、规模和证据驱动。
- 视频阶段只实现上传、发布和必要的基础处理，不实现剪辑、裁切、滤镜、特效或配乐。
- 目录职责在目录树中使用行尾注释说明；不提前创建没有实现内容的空业务模块或空服务。

## 当前策略

功能按以下顺序推进：

1. 总体架构与工程基础。
2. 用户与认证。
3. 视频上传与发布。
4. 审核与基础后台。
5. Feed 与播放。
6. 互动、关系与通知。
7. 行为采集与推荐。
8. 搜索与发现。
9. 短视频弹幕。
10. 内容安全 Agent。
11. 直播与实时弹幕。
12. 运营、云原生与系统治理。

当前阶段已完成工程基础和 `设计文档/03-用户与认证模块设计.md`；用户与认证模块尚未实现，下一步按设计实现并验证。

用户与认证模块首期设计选择 PostgreSQL、GORM、Argon2id 和数据库会话摘要，尚未实现或完成容量验证。缓存、消息系统、通信协议和部署平台仍须在相关模块设计时，依据业务需求、数据特征、规模预估、候选方案比较和实验结果决定。

## 当前资源与环境

- 后端路径：`backend/`。
- Go 模块名：`pulseframe`。
- 当前 Go 版本：`1.26`。
- 核心 API 当前使用 Gin `v1.11.0`，默认监听 `:8080`。
- 当前未接入数据库、缓存、消息系统或其他外部存储。
- 启动和环境变量说明见 `backend/README.md`。

## 架构方向

- 采用单仓库模块化架构，普通业务模块初期由核心 API 统一承载。
- 预留四类部署边界：核心 API、事件 Worker、直播网关、内容安全 Agent。
- 只有运行方式、容量或故障边界出现真实差异时才创建和独立部署特殊工作负载。
- Gin 仅用于服务启动层和业务模块的 HTTP Adapter；Application 与 Domain 不得依赖 `gin.Context`。
- 事件 Worker 不使用 Gin；直播网关、服务间通信和 Agent 接入方式留到对应模块根据需求选型。
- 每个模块拥有自身数据的写入权，跨模块协作通过公开接口或事件完成。
- 详细决策见 `memory/decisions/ADR-0001-modular-deployment-boundaries.md`。

## 产品与体验方向

- 第一阶段先形成注册登录、视频发布审核和 Feed 播放的短视频基础闭环。
- 后续补充用户互动、推荐、搜索、短视频时间轴弹幕、直播房实时弹幕和统一内容治理。
- 创作者、普通用户和管理人员必须能够看到与其权限匹配且可理解的业务状态和失败原因。

## 安全边界

- 内容安全 Agent 可以分析内容、查询必要上下文并给出处置建议，但不能绕过审核模块直接修改核心业务数据。
- 永久封禁等高影响操作不能仅由模型自主决定，必须具有明确权限边界和人工复核路径。
- 认证、服务身份、权限、输入校验和管理操作审计须在各模块设计中显式处理。
- 配置与凭据分离；源码和项目记忆中都不得保存凭据。
