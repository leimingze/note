# ADR-0001：采用模块化单仓库并按工作负载保留部署边界

日期：2026-09-21
状态：已采纳

## 背景

PulseFrame 需要逐步承载普通业务请求、后台异步任务、直播长连接和内容安全 Agent。四类工作负载在连接模型、资源使用、扩缩容方式和故障影响上存在差异，但项目早期尚没有为每个业务模块承担微服务开发、测试、部署和数据一致性成本的依据。

目录需要表达清晰的业务职责，也要为后续独立扩容和故障隔离留出空间。目录整齐或展示技术栈本身不能成为拆分服务的理由。

## 决策

项目采用单仓库模块化架构。账号、视频、审核、Feed、互动等普通业务模块先由核心 API 统一承载，并通过明确接口维护模块边界。

项目保留四类部署边界：

- 核心 API：承载普通业务接口。
- 事件 Worker：承载可靠异步任务和后台处理。
- 直播网关：承载长连接、实时消息和连接治理。
- 内容安全 Agent：承载内容分析、上下文查询、风险判断和受限工具调用。

Gin 只用于核心 API 的启动层和 HTTP Adapter。Application 与 Domain 不依赖 `gin.Context`。其他部署单元根据各自运行特征在进入实现阶段时独立选型。

## 影响

- 初期只运行核心 API，降低本地开发、测试和业务一致性成本。
- 业务模块必须保持清晰的数据所有权和依赖方向，不能借同进程运行直接修改其他模块数据。
- 事件 Worker、直播网关和内容安全 Agent 只在出现真实业务需求时创建，不生成空工程。
- 独立部署不自动意味着独立仓库、独立数据库或微服务化。
- 后续拆分需要增加契约、超时、幂等、身份传递、可观测性和故障处理成本。

## 替代方案

- 单体按技术层组织：起步文件较少，但业务增长后领域边界容易混乱，因此不采用。
- 每个业务模块从一开始独立微服务：隔离能力强，但当前缺少规模依据，并会显著提高开发、测试、部署和一致性成本，因此暂不采用。

## 证据

- `PulseFrame项目总纲.md` 定义了从零学习、按证据选型和避免技术堆砌的要求。
- `设计文档/01-总体架构与目录设计.md` 比较了三种组织方案，并定义了部署单元和治理基线。
- `设计文档/02-工程基础设计.md` 明确当前阶段仅建设核心 API，不提前创建其他部署单元。
- 当前代码只实现 `backend/cmd/pulseframe-api/` 及通用平台能力，尚不存在拆分其他服务的运行证据。

## 后续约束

- 新业务模块优先在核心 API 内按领域边界实现，不因展示微服务技术而独立部署。
- 出现可靠异步处理、直播长连接或 Agent 工作负载时，先完成对应模块设计和验证，再创建部署单元。
- 每次拆分都必须用真实业务数据、公开数据集回放、容量测试或故障演练证明其吞吐、延迟、资源隔离或恢复收益。
- 当模块边界无法维持、容量瓶颈明确或故障隔离要求改变时，重新评估本决策并记录新的 ADR。
