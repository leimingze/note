# PulseFrame 项目总纲

## 文档目的

本文档只定义项目目标、功能范围、质量要求和实施约束，不预先确定各模块的具体技术方案。

数据库、缓存、消息系统、通信协议、服务拆分方式和部署平台等选型，应在对应模块进入设计阶段后，根据业务需求、数据特征、规模预估、候选方案对比和实验结果决定，并记录在独立的模块设计文档中。

## 项目定位

PulseFrame 是一个从零设计并实现的 Go 视频社交平台后端，逐步建设短视频内容分发、用户互动、短视频弹幕、直播房实时互动、内容安全 Agent 和云原生工程能力。GCFeed 仅作为业务范围和工程思路的参考项目之一。

项目主要用于学习和形成可用于 Go 后端、AI Agent 与云原生岗位面试的工程经验。重点是围绕真实业务问题完成需求分析、方案设计、工程实现和数据验证，而不是堆叠技术组件。

## 功能需求

### 视频发布与审核

- 用户能够上传并发布视频，填写标题、简介、封面等信息，并查看上传和内容状态。
- 当前阶段只建设视频上传、发布及其必要的基础处理能力，不建设剪辑、裁切、滤镜、特效、配乐等视频创作与编辑功能。
- 视频应具有待审核、已发布、审核未通过和已下架等明确状态。
- 未通过发布条件的视频不能进入公开内容分发流程。
- 创作者能够查看审核结果；审核未通过时，应提供可理解的原因。
- 管理人员能够处理审核任务，并查询相关操作记录。

### 短视频 Feed

- 用户能够连续浏览公开视频，并获得稳定、无明显重复的加载体验。
- 系统应提供时间线、关注内容、热门内容和个性化推荐等浏览场景。
- 个性化内容分发应能够利用用户的观看和互动行为，并处理新用户或行为不足的情况。
- 用户能够对视频进行点赞、收藏和评论，并查看准确的互动状态与数量。
- 用户能够关注或取消关注创作者，并在关注内容中看到相应更新。

### 短视频弹幕

- 用户能够在视频指定播放位置发送弹幕，并在播放到相应位置时看到弹幕。
- 客户端能够按播放区间加载弹幕，支持拖动进度和继续播放等场景。
- 用户能够删除本人弹幕、举报违规弹幕，并按需隐藏弹幕。
- 系统应在热门视频和弹幕密集场景下保持可接受的加载速度和播放体验。
- 弹幕内容应接入统一的内容治理和审核流程。

### 直播房与实时弹幕

- 主播能够创建、开始和结束直播房，用户能够进入和离开直播房。
- 房间内用户能够实时发送和接收弹幕，并看到必要的房间状态和在线信息。
- 弹幕应具有可识别的先后关系，避免因重复处理造成重复展示。
- 用户短暂断线后能够恢复连接，并补回断线期间缺失的必要消息。
- 用户能够查询允许保留的历史弹幕；直播结束后，相关记录应按照平台规则处理。
- 系统应限制异常发送行为，并避免单个异常连接影响房间内其他用户。
- 主播或管理人员能够执行禁言、删除弹幕和移出房间等治理操作。

### 内容安全 Agent

- 内容安全 Agent 应覆盖视频信息、评论、短视频弹幕和直播弹幕等内容类型。
- 系统能够识别疑似违规内容，给出风险类别、判断依据和建议处置方式。
- 不确定或高风险内容能够进入人工审核流程，并保留上下文供审核人员判断。
- 自动处置能力必须具有明确的权限边界；永久封禁等高影响操作不能仅由模型自主决定。
- 系统应保存判断过程、处置结果和人工复核结果，支持审计、申诉和效果评估。
- 内容治理效果应能够通过误判、漏判、处理时延等指标持续评估。

### 运营与管理

- 管理人员能够查询和处理内容审核、用户举报及直播治理任务。
- 关键管理操作应具有身份校验、权限控制和完整的操作记录。
- 管理人员能够查询任务状态、处理结果和必要的统计信息。

## 模块实施顺序

### 第一阶段：短视频基础闭环

1. **总体架构与工程基础**：确定模块边界、部署单元、目录和分布式治理规范，再建立最小项目骨架。
2. **用户与认证**：完成注册、登录、身份校验、账号状态和基础权限。
3. **视频上传与发布**：完成视频上传、信息填写、内容状态和删除；不包含视频编辑。
4. **审核与基础后台**：完成待审核、通过、驳回、下架和审核记录。
5. **Feed 与播放**：让审核通过的视频能够被稳定浏览和播放。

### 第二阶段：互动与内容分发

6. **互动、关系与通知**：完成点赞、收藏、评论、关注和站内通知。
7. **行为采集与推荐**：记录用户观看和互动行为，完成推荐与效果验证闭环。
8. **搜索与发现**：支持按视频、用户和话题查找内容。

### 第三阶段：实时互动与内容安全

9. **短视频弹幕**：完成时间轴弹幕、查询、删除、举报和治理。
10. **内容安全 Agent**：先覆盖视频、评论和短视频弹幕，并接入人工复核。
11. **直播与实时弹幕**：完成直播房、直播媒体、实时互动和直播治理，并将内容安全能力扩展到直播场景。

### 第四阶段：工程化完善

12. **运营、云原生与系统治理**：完善运营能力、部署、可观测性、容量验证和故障恢复。

## 工程与运行要求

- 系统应保证关键业务状态和用户可见结果的一致性，明确处理重复请求、并发操作和部分失败。
- 核心链路应具备明确的错误反馈、超时处理、失败恢复和必要的数据修复能力。
- 系统应支持可重复部署、环境隔离、配置管理、健康检查、平滑升级和容量扩展。
- 系统应能够观察关键指标、日志和请求链路，并对重要异常提供告警依据。
- 系统应通过权限控制、输入校验、敏感信息保护和操作审计满足基本安全要求。
- 各模块的吞吐、延迟、可用性和数据规模目标，应在模块需求分析阶段明确，不在总纲中预设数值。

## 数据验证与工业落地要求

- 每个核心功能都应尽量使用真实数据完成验证；缺少自有业务数据时，优先寻找许可明确的公开数据集，并记录数据来源、版本、许可、清洗方式和适用边界。
- 测试数据应覆盖真实业务分布和关键边界场景。合成数据可以补充极端流量、异常输入和故障场景，但不能单独作为设计有效性的依据。
- 每项重要设计都应先明确待解决的问题、对照基线和评价指标，再通过离线实验、流量回放、集成测试或性能测试给出可复现结果。
- 验证结果应说明方案带来的收益、成本和适用条件，并保留必要的测试程序、配置与结果记录。
- 功能完成标准不止是接口可用，还应覆盖正确性、并发与一致性、失败恢复、安全、可观测性和必要的容量验证。
- 技术方案应优先参考成熟的生产实践，但必须与实际需求和规模匹配，不能为了体现“工业级”而引入没有问题依据的组件。

## 学习与设计要求

- GCFeed 只作为阅读、比较和验证设计思路的参考项目，不直接作为本项目的代码基础。需求、架构、数据模型、接口和实现都应从零推导，不能以照搬原项目实现代替设计过程。
- 本项目不以直接生成完整代码和功能结果为唯一目标。每个模块都应保留需求分析、方案设计、实现验证和复盘过程，确保技术选择可以被理解和解释。
- 每个功能模块进入实现前，应先说明**背景**：业务场景、现有问题、建设原因，以及不处理可能产生的影响。
- 每个功能模块应明确**需求**：核心功能、非功能指标、数据规模、边界条件和暂不处理的范围。
- 每个功能模块应完成**方案选型**：比较可行方案及其优缺点，说明最终选择、关键权衡、未选择其他方案的原因，以及未来的演进条件。
- 设计讲解采用面试回答的口吻，重点回答“为什么做、为什么这样设计、核心流程是什么、难点在哪里、如何保证正确性与可靠性、如何用数据验证、规模扩大后如何演进”。
- 模块完成后应对照原设计进行复盘，记录实际实现、测试结果、暴露的问题和后续改进，确保设计文档与最终代码一致。
