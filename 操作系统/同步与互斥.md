# 临界资源
被多个线程/进程共享、一次只能被一个使用者访问的资源本身

# 临界区
访问临界资源的那一段代码（各个进程自身的代码段，每个并发进程都有自己的临界区）

# 同步的基本准则
1. 空闲让进：没人用，别拦着
2. 忙则等待：有人用，必须等着
3. 优先等待：不能让你一直等待
4. 让权等待：等的时候别站着cpu
使用场景：同一进程内的线程、不同进程之间

# 互斥锁
互斥锁只有两种状态：未上锁、已上锁

有三个原子动作：
```text
加锁
if 锁是空闲：
    我拿走，进去
else：
    我排队等着（或者自旋）

解锁
把锁还回去
叫醒一个正在等的线程

尝试加锁
能拿到就拿到，拿不到立刻返回
不阻塞
```

使用场景：修改共享变量
不合适：读多写少（读写锁）、锁粒度极小且竞争极高（考虑自旋锁）

# 自旋锁
忙等锁：线程在被锁占用时，不放弃cpu，循环检测锁状态，直到拿到锁（违背让权等待）
优点：无上下文切换、延迟低
缺点：空转浪费cpu 

# 为什么锁一下就放，适合自旋锁
临界区极短，自旋锁原地空转也很短，并且全程在用户态，零切换，快。
如果是互斥锁，等锁成本远小于切换成层本（需要唤醒线程）

# 临界区长为什么自旋锁是灾难
自旋锁：因为其他线程没有挂起，一直在空转等待。
互斥锁：其他线程挂起了，cpu跑去干别的事了。

# 读写锁
1. 多个读者可以同时持有锁。
2. 写者必须独占
3. 读者和写者互斥

读者拿锁 → 计数器 +1
再来读者 → 计数器 +1，直接进
写者来了 → **必须等所有读者走光**
读者走   → 计数器 -1，归零后唤醒写者

读者源源不断来
写者来了 → 等 → 又有读者来 → 写者继续等 → 饿死

解决方案：
- 写优先：写者来了，新读者不许进，等现有读者走完（只要写者在等，所有新读者全部被挡。写者之间还可以连续插队。）
- 公平队列：先来先服务，不管读还是写（写不插队）
- 限读：限制同时读的最大数量


使用场景：
- 读多写少：配置缓存、路由表等
不适合
- 读写查不多
- 临界区极短：互斥锁更简单，读写锁维护成本高：要维护读者计数
