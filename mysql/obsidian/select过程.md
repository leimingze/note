## SELECT 过程：从查询用户姓名理解 SQL 执行流程

- **执行一条 SELECT 时，MySQL 怎样把 SQL 变成查询结果？**
  > 场景：用户账户服务执行 `SELECT name FROM t_user WHERE id = 1;`，希望取得指定用户的姓名。
  >
  > 原理：一次查询通常经过连接与会话管理、SQL 解析、语义准备、优化和执行。Server 层负责理解 SQL 并组织执行，存储引擎提供相应的数据访问能力，结果再通过连接返回客户端。[补] 以下以 MySQL 8.0/8.4 和 InnoDB 的普通查询为背景，假设示例表存在且 id 是主键；不同语句、索引和会话状态会改变具体执行路径。
  >
  > 记忆句：这就是 SELECT 执行：先确认通信与访问条件，再理解语句、选择计划、读取数据并返回结果。
  >
  > 追问：连接器负责什么？查询缓存是否仍然存在？SQL 怎样被解析和准备？优化器怎样选择路径？执行器怎样取得记录？结果怎样返回客户端？
  >
  > 答案：关于连接器，后续子节点「连接器怎样为查询建立可用的会话？」的「原理」说明了认证与会话管理；关于查询缓存，子节点「查询缓存为什么不能作为 MySQL 8.0 查询的必经阶段？」的「原理」说明了版本变化；关于解析和准备，子节点「解析器怎样理解 SQL 中的关键字、字段与结构？」及其子节点「预处理与语义准备阶段要核对什么？」的「原理」分别说明了语法解析与对象核对；关于计划选择，子节点「优化器怎样从可用执行方式中选择查询计划？」的「原理」说明了成本估算；关于取得记录，子节点「执行器怎样按照计划向存储引擎取得用户记录？」的「原理」说明了引擎访问与计算；关于结果返回，子节点「查询结果怎样返回客户端，是否必须等所有行都算完？」的「原理」说明了结果产生、传输与客户端读取。

  - **连接器怎样为查询建立可用的会话？**
    > 场景：账户服务第一次连接数据库，需要提交账号与认证信息，然后才能发送查询。
    >
    > 原理：连接器参与建立和管理客户端连接、认证用户并维护会话状态。认证成功表示连接身份通过检查，不表示该用户可以读取所有表；后续语句仍需满足相应权限和访问规则。连接还可能受连接数、超时和网络状态等条件影响。
    >
    > 记忆句：这就是连接器：确认连接身份，管理会话，为后续 SQL 提供通信环境。
    >
    > 追问：连接池复用已有连接时，每次 SELECT 都要重新建立连接吗？
    >
    > 答案：后续子节点「连接池复用连接，会省略哪些工作，又保留哪些工作？」的「原理」回答了这个问题：有效连接可以复用，省去新建连接和完整认证，查询处理及会话状态管理仍需继续。

    - **连接池复用连接，会省略哪些工作，又保留哪些工作？**
      > 场景：账户服务从连接池取得一条已经认证的数据库连接，连续查询多个用户。
      >
      > 原理：[补] 复用有效连接通常可以省去每次请求的新建连接和完整认证过程，但 SQL 仍需执行相应的准备、优化与数据访问。会话中的事务、隔离级别、字符集和其他设置可能影响后续语句，连接池需要按约定管理这些状态。连接复用与预处理语句是不同机制，不能据此断言所有 SQL 都无需再次解析。
      >
      > 记忆句：这就是连接复用：重复使用通信会话，查询语义和事务状态仍然需要正确处理。
      >
      > 追问：自测：连接可以正常取得，但查询报告表访问被拒绝，为什么应继续检查语句权限？
      >
      > 答案：取得连接只表明连接可用、身份认证通过；访问某张表还需要相应的语句权限。应检查当前账号对目标对象及操作的授权，不能用连接成功推断查询已获准。

  - **查询缓存为什么不能作为 MySQL 8.0 查询的必经阶段？**
    > 场景：账户服务多次发送相同 SELECT，开发者希望判断能否直接复用先前的完整结果。
    >
    > 原理：旧版本 MySQL 曾有 Query Cache，用于保存满足缓存条件的查询结果；相关表变化会使缓存失效，维护和并发成本也限制了收益。该功能在 MySQL 5.7 后期被弃用，并于 MySQL 8.0 移除。因而分析 MySQL 8.0/8.4 的普通执行流程时，不应安排一次内置 Query Cache 命中检查作为通用阶段。
    >
    > 记忆句：这就是查询缓存的版本条件：旧流程中曾有结果缓存，MySQL 8.0 已移除这个模块。
    >
    > 追问：没有 Query Cache，为什么第二次执行同一查询仍可能更快？
    >
    > 答案：后续子节点「Buffer Pool 命中和完整查询结果缓存有什么区别？」的「原理」回答了这个问题，说明页缓存命中可以减少存储读取，连接复用等因素也可能减少耗时。

    - **Buffer Pool 命中和完整查询结果缓存有什么区别？**
      > 场景：第一次按用户主键查询需要读取数据页，第二次查询时相关页已经在内存中。
      >
      > 原理：[补] InnoDB Buffer Pool 缓存页及相关管理信息，命中后可以减少相应的存储读取，但执行器仍需按照查询计划处理记录、可见性和结果。它没有直接保存每条 SELECT 的完整最终答案。操作系统缓存、连接复用等因素也可能影响耗时，因此仅凭第二次更快不能判断命中了某种结果缓存。
      >
      > 记忆句：这就是页缓存与结果缓存的区别：前者减少取页成本，后者复用已计算的查询答案。
      >
      > 追问：自测：为什么数据页已经在 Buffer Pool 中，也不代表这次 SELECT 可以跳过权限和事务可见性判断？
      >
      > 答案：缓存命中只解决页面从哪里取得；账号能否查询、当前事务可以读取哪个版本，仍分别受权限和事务读取规则约束。页面在内存中不会改变这些条件。

  - **解析器怎样理解 SQL 中的关键字、字段与结构？**
    > 场景：MySQL 收到 `SELECT name FROM t_user WHERE id = 1;`，需要先理解它表达的是哪一种操作。
    >
    > 原理：词法分析识别关键字、标识符、运算符和字面量等记号，语法分析检查记号之间是否符合 SQL 语法，并形成后续模块可处理的内部结构。语法树可以表达选择列、表引用和条件表达式，但语法正确并不意味着相关表或列一定存在，也不意味着访问已经获准。
    >
    > 记忆句：这就是 SQL 解析：识别组成元素，检查语法关系，把文本转化为可以继续分析的结构。
    >
    > 追问：语法通过后，谁负责确认表和字段实际存在？
    >
    > 答案：后续子节点「预处理与语义准备阶段要核对什么？」的「原理」回答了这个问题，说明语义准备按当前数据库及元数据核对表、列、名称歧义和使用条件。

    - **预处理与语义准备阶段要核对什么？**
      > 场景：语句在语法上合法，但开发者可能写错表名，或在多表查询中使用了无法唯一确定的列名。
      >
      > 原理：语义准备按当前数据库和表元数据解析对象与列的引用，检查存在性、名称歧义和相关使用条件，并处理通配符等结构。权限检查会结合语句准备与执行过程进行，不能只凭建立连接时认证成功就跳过。这里按职责说明流程，具体函数边界与检查时点可能随语句类型和版本变化。
      >
      > 记忆句：这就是语义准备：确认 SQL 所引用的对象及操作在当前上下文中有明确含义。
      >
      > 追问：`SELECT *` 中的星号怎样展开，是否总会包含表里的每一列？
      >
      > 答案：后续子节点「SELECT 星号展开时，为什么要区分可见列与不可见列？」的「原理」回答了这个问题，说明星号按元数据展开，MySQL 8.0.23 及之后默认不把不可见列纳入星号结果。

      - **SELECT 星号展开时，为什么要区分可见列与不可见列？**
        > 场景：账户表增加了一列供内部使用，维护者把它定义为不可见列，同时已有业务仍执行 `SELECT *`。
        >
        > 原理：通配符会按所引用表的元数据展开为相应列列表。[补] MySQL 从 8.0.23 开始支持不可见列，`SELECT *` 默认不包含这些列；需要读取时可以显式指定列名。因此“星号等于所有物理列”不是通用规则，表别名、表结构和可见性定义都应纳入判断。
        >
        > 记忆句：这就是星号展开：按表定义选择相应可见列，不替代对列名和列属性的明确理解。
        >
        > 追问：自测：为什么为账户表增加一个不可见列，不一定会改变原有 SELECT 星号查询返回的列数？
        >
        > 答案：支持不可见列的版本会在星号展开时排除这类列，所以仅增加不可见列通常不会增加星号查询的返回列数；显式指定该列名仍可以读取它。

  - **优化器怎样从可用执行方式中选择查询计划？**
    > 场景：账户表可能有主键和其他索引，同一查询条件可能存在不同的数据访问方式。
    >
    > 原理：优化器根据语句语义、可用索引、统计信息和成本模型，在其考虑的候选计划中选择估算成本较低的执行方式。计划可以确定访问路径、多表连接顺序，以及部分排序、分组和条件处理方式。估算成本不等于实际耗时，优化器也不保证穷举所有计划并找到任何环境下的绝对最快方案。
    >
    > 记忆句：这就是查询优化：利用元数据和统计信息，为当前语句选择一个预期合适的执行计划。
    >
    > 追问：主键查询和其他条件查询为什么可能采用不同路径？怎样检查估计与实际执行是否一致？
    >
    > 答案：第一问由后续子节点「有索引为什么也不代表每条 SELECT 都会使用它？」的「原理」回答，说明索引可用性、匹配行数及回表成本怎样影响路径；第二问由子节点「EXPLAIN 与 EXPLAIN ANALYZE 怎样帮助理解查询过程？」的「原理」回答，说明如何比较计划估计与执行统计。

    - **有索引为什么也不代表每条 SELECT 都会使用它？**
      > 场景：按 `id=1` 查询用户时可使用主键；另一个查询需要读取大部分用户，即使存在某个条件索引也可能不适合使用。
      >
      > 原理：[补] 索引是否可用取决于查询条件、索引列及表达式等因素，是否值得使用还与估计匹配行数、回表成本、覆盖能力和排序要求相关。主键等值查找通常能直接定位很少的记录；若某个二级索引匹配大量行并需要大量回表，其他访问方式可能具有更低估算成本。
      >
      > 记忆句：这就是索引选择：先判断路径能否使用，再判断用它访问所需数据是否合算。
      >
      > 追问：自测：为什么“某个字段已经建立索引”不足以保证所有包含该字段的查询都会更快？
      >
      > 答案：查询条件可能无法使用该索引；即使能够使用，匹配行数很多、回表较多或不能满足排序要求时，索引路径的成本也可能更高。需要结合具体语句及数据分布判断。

    - **EXPLAIN 与 EXPLAIN ANALYZE 怎样帮助理解查询过程？**
      > 场景：账户查询变慢，需要比较优化器预计读取多少行与实际执行情况。
      >
      > 原理：[补] EXPLAIN 展示计划及估计信息，适合查看访问路径和预期处理方式。MySQL 8.0.18 起提供 EXPLAIN ANALYZE，它会执行所支持的语句并报告实际执行统计；对 SELECT 使用时应考虑查询本身的资源消耗。估计与实际差距较大时，可以结合统计信息、数据分布、索引和执行环境分析，不能只凭一个计划字段断定根因。
      >
      > 记忆句：这就是执行计划验证：用计划解释选择，用实际统计检查估计是否符合当前数据与环境。
      >
      > 追问：自测：为什么执行 EXPLAIN ANALYZE 一个高成本查询之前，需要知道它会真正运行查询？
      >
      > 答案：它通过运行查询取得统计信息，因此会消耗查询所需的 CPU、内存和 I/O，并可能与在线请求竞争资源。评估时需要考虑执行时段和当前负载。

  - **执行器怎样按照计划向存储引擎取得用户记录？**
    > 场景：计划已选定按主键查询，执行器开始取得 `id=1` 对应的姓名。
    >
    > 原理：执行器按照计划组织各项操作，通过存储引擎接口读取相应记录，并完成计划要求的过滤、连接、聚合或结果构造等工作。哪些条件由引擎处理、哪些由 Server 层处理，取决于访问方式和可用优化。不能把所有查询都理解成“把整张表交给执行器，然后才处理条件”。
    >
    > 记忆句：这就是执行阶段：把计划中的访问与计算操作真正运行起来，按约定取得查询结果。
    >
    > 追问：InnoDB 怎样找到主键记录？读取缓存中的记录时，还需要遵守哪些事务规则？
    >
    > 答案：第一问由后续子节点「InnoDB 按主键查询时，怎样从索引走到数据页？」的「原理」回答，说明聚簇索引定位与页面读取；第二问由子节点「为什么读取了当前数据页，还不能直接把其中的值作为结果？」的「原理」回答，说明 Read View、undo 及相应锁规则如何约束返回内容。

    - **InnoDB 按主键查询时，怎样从索引走到数据页？**
      > 场景：示例表以 id 为主键，账户服务请求 `id=1` 的用户姓名。
      >
      > 原理：[补] InnoDB 沿聚簇索引的 B+ 树结构定位相应记录。访问所需页时，先利用 Buffer Pool 中已有的页；未缓存且确实需要读取的页再从存储加载。聚簇索引叶子记录保存行的主要内容，较长字段可能涉及页外存储；单行查询也可能访问多个索引层级及相关页，不能推定永远只有一次磁盘 I/O。
      >
      > 记忆句：这就是主键访问：索引确定记录位置，缓存与存储共同提供访问所需的页。
      >
      > 追问：自测：索引树高三层，是否就能断定每次主键查询一定发生三次磁盘读取？
      >
      > 答案：不能。路径上的页面可能已在 Buffer Pool 中，命中时无需为该页再次读取存储；较长字段等情况还可能需要访问额外页面。树高描述索引层级，不能直接等同于磁盘读取次数。

    - **为什么读取了当前数据页，还不能直接把其中的值作为结果？**
      > 场景：账户页中的姓名刚被另一个事务修改，而当前查询按照 RR 或 RC 进行普通一致性读。
      >
      > 原理：[补] 找到记录位置后仍需按读取方式判断事务可见性。InnoDB 普通一致性读可结合 Read View 与 undo 选择可见版本；加锁查询则要按相应锁规则处理当前记录和冲突。缓存命中只说明页已在内存中，不决定当前事务有权读取哪个版本，也不能保证查询不需要等待其他资源。
      >
      > 记忆句：这就是位置与可见性的区别：先找到记录，再按当前事务规则确定可以返回的内容。
      >
      > 追问：自测：两个事务访问同一个缓存页，为什么仍可能合法地读到不同姓名版本？
      >
      > 答案：两个事务的一致性读可能使用不同 Read View，能够看见的提交范围随之不同。InnoDB 可沿 undo 还原各自可见的版本，因此读取同一缓存页也可能返回不同姓名。

  - **查询结果怎样返回客户端，是否必须等所有行都算完？**
    > 场景：查询一名用户只返回少量数据，另一个查询却可能返回大量用户并执行排序。
    >
    > 原理：执行器将满足查询语义的结果通过数据库协议返回客户端。[补] 某些计划可以逐步产生并发送结果，另一些排序、聚合或中间结果处理需要先完成一定计算；客户端驱动也可能缓存结果。服务端计算、网络发送和客户端消费速度共同影响整体耗时，不能把“引擎找到记录”直接等同于“应用已收到全部结果”。
    >
    > 记忆句：这就是结果返回：执行计划产出数据，通过连接传输，再由客户端读取和使用。
    >
    > 追问：自测：数据库计算耗时较短，但客户端迟迟读不完结果时，为什么还要检查返回数据量和客户端消费速度？
    >
    > 答案：整体耗时还包含网络传输和客户端读取处理。结果较多、网络吞吐有限或客户端处理较慢，都会延长读取时间，即使服务端计算本身很快。
