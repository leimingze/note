## SELECT 过程：从查询用户姓名理解 SQL 执行流程

- **执行一条 SELECT 时，MySQL 怎样把 SQL 变成查询结果？**
  > 场景：用户打开个人资料页，账户服务发送 `SELECT name FROM t_user WHERE id = 1;`。表里已经保存了这名用户，应用需要收到他的姓名，才能显示页面。
  >
  > 原理：MySQL 需要先有可用的连接和会话，才能接收查询。收到 SQL 后，Server 层负责理解语句、确认表和列、选择执行计划，再安排读取与计算；存储引擎负责按要求访问数据。结果最终通过连接返回应用。[补] 本文使用 MySQL 8.0/8.4 和 InnoDB，示例表已存在且 id 是主键。不同语句、索引和会话状态，会让具体执行路径有所变化。
  >
  > 记忆句：这就是 SELECT 执行：先确认通信与访问条件，再理解语句、选择计划、读取数据并返回结果。
  >
  > 追问：连接器负责什么？查询缓存是否仍然存在？SQL 怎样被解析和准备？优化器怎样选择路径？执行器怎样取得记录？结果怎样返回客户端？
  >
  > 答案：关于连接器，后续子节点「连接器怎样为查询建立可用的会话？」的「原理」说明了认证与会话管理；关于查询缓存，子节点「查询缓存为什么不能作为 MySQL 8.0 查询的必经阶段？」的「原理」说明了版本变化；关于解析和准备，子节点「解析器怎样理解 SQL 中的关键字、字段与结构？」及其子节点「预处理与语义准备阶段要核对什么？」的「原理」分别说明了语法解析与对象核对；关于计划选择，子节点「优化器怎样从可用执行方式中选择查询计划？」的「原理」说明了成本估算；关于取得记录，子节点「执行器怎样按照计划向存储引擎取得用户记录？」的「原理」说明了引擎访问与计算；关于结果返回，子节点「查询结果怎样返回客户端，是否必须等所有行都算完？」的「原理」说明了结果产生、传输与客户端读取。

  - **连接器怎样为查询建立可用的会话？**
    > 场景：账户服务刚启动，尚未连接数据库。它提交数据库账号和认证信息，等待连接成功后，才发送查询用户姓名的 SQL。
    >
    > 原理：连接器负责建立和管理连接，核对账号身份，并保存这条连接的会话状态，例如当前数据库和相关设置。认证成功后，应用获得发送 SQL 的通信通道。每条语句仍要满足相应访问权限，账号连接成功不代表可以读取所有表。连接数达到限制、连接超时或网络中断，也会影响会话能否使用。
    >
    > 记忆句：这就是连接器：确认连接身份，管理会话，为后续 SQL 提供通信环境。
    >
    > 追问：连接池复用已有连接时，每次 SELECT 都要重新建立连接吗？
    >
    > 答案：后续子节点「连接池复用连接，会省略哪些工作，又保留哪些工作？」的「原理」回答了这个问题：有效连接可以复用，省去新建连接和完整认证，查询处理及会话状态管理仍需继续。

    - **连接池复用连接，会省略哪些工作，又保留哪些工作？**
      > 场景：查询用户 1 的请求结束后，连接被归还到连接池。查询用户 2 的下一个请求取出同一条仍然有效的连接，希望直接发送 SQL。
      >
      > 原理：[补] 有效连接已经完成建立和认证，下一个请求通常可以继续使用它，省去重新连接的开销。新 SQL 仍需完成相应的准备、优化和数据访问。连接还可能保留前一个请求的事务、隔离级别或字符集设置，连接池需要正确结束事务、重设必要状态，防止影响后续请求。复用连接本身不会让 SQL 自动成为已准备好的语句，是否再次解析还要看语句的使用方式。
      >
      > 记忆句：这就是连接复用：重复使用通信会话，查询语义和事务状态仍然需要正确处理。
      >
      > 追问：自测：连接可以正常取得，但查询报告表访问被拒绝，为什么应继续检查语句权限？
      >
      > 答案：取得连接只表明连接可用、身份认证通过；访问某张表还需要相应的语句权限。应检查当前账号对目标对象及操作的授权，不能用连接成功推断查询已获准。

  - **查询缓存为什么不能作为 MySQL 8.0 查询的必经阶段？**
    > 场景：账户服务连续两次查询用户 1 的姓名。开发者照着旧教程，在 MySQL 8.0 中寻找“查询缓存命中后直接返回结果”的步骤，却找不到这个模块。
    >
    > 原理：MySQL 8.0 已移除 Query Cache，所以这一步不属于 MySQL 8.0/8.4 的通用查询流程。旧版本曾把符合条件的查询结果保存在 Query Cache 中，命中时可以复用结果。相关表一旦变化，缓存结果就可能需要失效；频繁维护和并发协调会消耗资源，限制它的收益。这个功能在 MySQL 5.7 后期已被弃用。
    >
    > 记忆句：这就是查询缓存的版本条件：旧流程中曾有结果缓存，MySQL 8.0 已移除这个模块。
    >
    > 追问：没有 Query Cache，为什么第二次执行同一查询仍可能更快？
    >
    > 答案：后续子节点「Buffer Pool 命中和完整查询结果缓存有什么区别？」的「原理」回答了这个问题，说明页缓存命中可以减少存储读取，连接复用等因素也可能减少耗时。

    - **Buffer Pool 命中和完整查询结果缓存有什么区别？**
      > 场景：第一次查询用户 1 时，相关页面还没缓存，需要从存储设备读取。第二次发送相同 SQL 时，这些页仍在内存中，查询明显更快。
      >
      > 原理：[补] Buffer Pool 是 InnoDB 保存缓存页及相关管理信息的内存区域。所需页已经存在时，可以直接访问，减少从存储设备取页的等待。执行器仍要按计划处理记录并生成结果，InnoDB 还要按事务规则判断哪个版本可见；缓存页没有直接替每条 SELECT 保存最终答案。操作系统缓存和连接复用也可能减少耗时，所以仅凭第二次更快，无法确定原因就是结果缓存。
      >
      > 记忆句：这就是页缓存与结果缓存的区别：前者减少取页成本，后者复用已计算的查询答案。
      >
      > 追问：自测：为什么数据页已经在 Buffer Pool 中，也不代表这次 SELECT 可以跳过权限和事务可见性判断？
      >
      > 答案：缓存命中只解决页面从哪里取得；账号能否查询、当前事务可以读取哪个版本，仍分别受权限和事务读取规则约束。页面在内存中不会改变这些条件。

  - **解析器怎样理解 SQL 中的关键字、字段与结构？**
    > 场景：MySQL 收到 `SELECT name FROM t_user WHERE id = 1;` 这段文本。它需要识别这是查询，返回列是 name，表是 t_user，条件是 id 等于 1。
    >
    > 原理：词法分析先识别 SELECT 等关键字、表名与列名、等号和数值 1，这些组成元素称为记号。语法分析再检查它们的组合是否符合 SQL 规则，形成语法树等内部结构，让后续模块知道要查哪张表、返回什么列、使用什么条件。这个阶段能判断语句怎么组织；即使语法合法，表和列也可能不存在，访问权限也还需要检查。
    >
    > 记忆句：这就是 SQL 解析：识别组成元素，检查语法关系，把文本转化为可以继续分析的结构。
    >
    > 追问：语法通过后，谁负责确认表和字段实际存在？
    >
    > 答案：后续子节点「预处理与语义准备阶段要核对什么？」的「原理」回答了这个问题，说明语义准备按当前数据库及元数据核对表、列、名称歧义和使用条件。

    - **预处理与语义准备阶段要核对什么？**
      > 场景：开发者把 t_user 写成了 t_users，SQL 语法仍然成立，却找不到这张表。另一条多表查询只写 name，而两张表都有 name，需要进一步确定它指哪一列。
      >
      > 原理：语义准备根据当前数据库及表定义，把 SQL 中的名称对应到具体对象。它检查表和列是否存在、列名是否有歧义，并处理星号等通配符及相关使用条件。权限也会在语句准备和执行过程中检查，连接时认证通过不代表这些检查可以省去。这里按职责理解流程，具体检查放在哪个函数、哪个时点，会随语句类型和版本变化。
      >
      > 记忆句：这就是语义准备：确认 SQL 所引用的对象及操作在当前上下文中有明确含义。
      >
      > 追问：`SELECT *` 中的星号怎样展开，是否总会包含表里的每一列？
      >
      > 答案：后续子节点「SELECT 星号展开时，为什么要区分可见列与不可见列？」的「原理」回答了这个问题，说明星号按元数据展开，MySQL 8.0.23 及之后默认不把不可见列纳入星号结果。

      - **SELECT 星号展开时，为什么要区分可见列与不可见列？**
        > 场景：账户表原来有 id 和 name，维护者新增了仅供内部使用的不可见列 internal_tag。已有业务继续执行 `SELECT *`，希望查询结果仍只有原来的两列。
        >
        > 原理：MySQL 会按查询引用的表及其定义，把星号展开为相应的可见列列表。[补] MySQL 8.0.23 开始支持不可见列，`SELECT *` 默认不会展开 internal_tag，所以这个例子仍返回 id 和 name。需要该列时可以显式写出列名。判断星号最终包含哪些列，需要结合表别名、表结构和列的可见性。
        >
        > 记忆句：这就是星号展开：按表定义选择相应可见列，不替代对列名和列属性的明确理解。
        >
        > 追问：自测：为什么为账户表增加一个不可见列，不一定会改变原有 SELECT 星号查询返回的列数？
        >
        > 答案：支持不可见列的版本会在星号展开时排除这类列，所以仅增加不可见列通常不会增加星号查询的返回列数；显式指定该列名仍可以读取它。

  - **优化器怎样从可用执行方式中选择查询计划？**
    > 场景：账户表既有 id 主键，也有邮箱索引。按邮箱查姓名时，MySQL 可以考虑使用邮箱索引，也可以考虑扫描表，需要判断哪条路径预计成本更低。
    >
    > 原理：优化器会考虑 SQL 要求、可用索引和表的统计信息，估计候选执行方式需要读取多少数据、完成多少工作，再选择估算成本较低的计划。计划决定如何访问数据、多表如何连接，以及部分排序、分组和条件处理方式。统计信息和成本模型只是估计工具，选择的计划不保证在当前环境中最快，也不代表优化器已经穷举全部可能方案。
    >
    > 记忆句：这就是查询优化：利用元数据和统计信息，为当前语句选择一个预期合适的执行计划。
    >
    > 追问：主键查询和其他条件查询为什么可能采用不同路径？怎样检查估计与实际执行是否一致？
    >
    > 答案：第一问由后续子节点「有索引为什么也不代表每条 SELECT 都会使用它？」的「原理」回答，说明索引可用性、匹配行数及回表成本怎样影响路径；第二问由子节点「EXPLAIN 与 EXPLAIN ANALYZE 怎样帮助理解查询过程？」的「原理」回答，说明如何比较计划估计与执行统计。

    - **有索引为什么也不代表每条 SELECT 都会使用它？**
      > 场景：查询 `id=1` 只需要定位一名用户，主键通常很合适。另一个查询要读取大部分用户的个人简介，即使筛选字段有二级索引，逐条取得完整记录也可能很费时。
      >
      > 原理：[补] 先看查询条件、索引列及表达式是否允许使用这条索引，再比较访问成本。主键等值查询通常直接找到少量记录。二级索引如果没有保存需要的列，就要再根据聚簇键取得完整记录，这一步叫回表；匹配行很多时，大量回表可能使它比扫描表更贵。索引是否包含所需列、能否满足排序要求，也会影响计划选择。
      >
      > 记忆句：这就是索引选择：先判断路径能否使用，再判断用它访问所需数据是否合算。
      >
      > 追问：自测：为什么“某个字段已经建立索引”不足以保证所有包含该字段的查询都会更快？
      >
      > 答案：查询条件可能无法使用该索引；即使能够使用，匹配行数很多、回表较多或不能满足排序要求时，索引路径的成本也可能更高。需要结合具体语句及数据分布判断。

    - **EXPLAIN 与 EXPLAIN ANALYZE 怎样帮助理解查询过程？**
      > 场景：按邮箱范围查询用户突然变慢。执行计划预计只处理少量记录，运行时却可能读了很多页，需要检查估计与当前数据是否相符。
      >
      > 原理：[补] EXPLAIN 展示优化器选择的计划和估计信息，可以看到准备使用哪种访问路径、预计处理多少行。MySQL 8.0.18 起提供 EXPLAIN ANALYZE，它会运行所支持的语句，再报告执行耗时、行数等统计，因此执行高成本 SELECT 时仍会消耗相应资源。把估计与执行统计比较后，再结合数据分布、统计信息、索引和运行环境找原因，单个计划字段通常不足以确定根因。
      >
      > 记忆句：这就是执行计划验证：用计划解释选择，用实际统计检查估计是否符合当前数据与环境。
      >
      > 追问：自测：为什么执行 EXPLAIN ANALYZE 一个高成本查询之前，需要知道它会真正运行查询？
      >
      > 答案：它通过运行查询取得统计信息，因此会消耗查询所需的 CPU、内存和 I/O，并可能与在线请求竞争资源。评估时需要考虑执行时段和当前负载。

  - **执行器怎样按照计划向存储引擎取得用户记录？**
    > 场景：优化器已经为 `SELECT name FROM t_user WHERE id = 1;` 选择主键访问。执行器接到计划，开始向 InnoDB 请求用户 1 的记录，并准备返回姓名。
    >
    > 原理：执行器按计划调用存储引擎的访问接口，取得所需记录，并完成计划要求的过滤、连接、聚合及结果构造。在这个主键查询中，可以让引擎按 id 定位目标记录，无需先读取整张表。更复杂的查询中，部分条件可以交给引擎处理，其余由 Server 层处理，具体分工取决于访问方式及采用的优化。
    >
    > 记忆句：这就是执行阶段：把计划中的访问与计算操作真正运行起来，按约定取得查询结果。
    >
    > 追问：InnoDB 怎样找到主键记录？读取缓存中的记录时，还需要遵守哪些事务规则？
    >
    > 答案：第一问由后续子节点「InnoDB 按主键查询时，怎样从索引走到数据页？」的「原理」回答，说明聚簇索引定位与页面读取；第二问由子节点「为什么读取了当前数据页，还不能直接把其中的值作为结果？」的「原理」回答，说明 Read View、undo 及相应锁规则如何约束返回内容。

    - **InnoDB 按主键查询时，怎样从索引走到数据页？**
      > 场景：账户表以 id 为主键，用户 1 的姓名保存在聚簇索引的某个叶子页中。InnoDB 收到查询请求，需要沿索引找到该页，并取得其中的记录。
      >
      > 原理：[补] 聚簇索引用 B+ 树按键值组织数据，InnoDB 从上层页面逐步缩小查找范围，直到找到目标叶子记录。访问每一页时，先使用 Buffer Pool 中已有的内容；所需页尚未缓存时，才从存储加载。叶子记录保存行的主要内容，较长字段还可能需要读取页外内容。查询一行也可能经过多个索引层级，所以不能直接认定只发生一次磁盘 I/O。
      >
      > 记忆句：这就是主键访问：索引确定记录位置，缓存与存储共同提供访问所需的页。
      >
      > 追问：自测：索引树高三层，是否就能断定每次主键查询一定发生三次磁盘读取？
      >
      > 答案：不能。路径上的页面可能已在 Buffer Pool 中，命中时无需为该页再次读取存储；较长字段等情况还可能需要访问额外页面。树高描述索引层级，不能直接等同于磁盘读取次数。

    - **为什么读取了当前数据页，还不能直接把其中的值作为结果？**
      > 场景：用户 1 原名为 xiaohong，事务 A 把姓名改为 xiaolin，但还没提交。事务 B 在 READ COMMITTED 下执行普通 SELECT，此时同一缓存页里已有新姓名，B 却仍应读取已提交的旧姓名。
      >
      > 原理：[补] 普通一致性读需要判断记录版本是否可见。Read View 保存判断哪些事务修改可以看见的依据，undo 保存还原旧版本所需的信息。B 发现当前版本来自未提交的 A，就可以借助 undo 找到自己可见的旧姓名；在 READ COMMITTED 和 REPEATABLE READ 下，读视图的建立时机会影响结果。`SELECT ... FOR UPDATE` 等加锁查询还要按相应锁规则读取并处理冲突。缓存命中只减少从存储读取页面的等待，不会取消这些判断，也不保证查询无需等待其他资源。
      >
      > 记忆句：这就是位置与可见性的区别：先找到记录，再按当前事务规则确定可以返回的内容。
      >
      > 追问：自测：两个事务访问同一个缓存页，为什么仍可能合法地读到不同姓名版本？
      >
      > 答案：两个事务的一致性读可能使用不同 Read View，能够看见的提交范围随之不同。InnoDB 可沿 undo 还原各自可见的版本，因此读取同一缓存页也可能返回不同姓名。

  - **查询结果怎样返回客户端，是否必须等所有行都算完？**
    > 场景：个人资料查询只返回一个姓名，通常很快读完。导出报表却要返回大量用户并按条件排序，即使数据库已经开始产生记录，应用仍可能很久才接收完。
    >
    > 原理：执行器把符合 SQL 要求的结果通过数据库协议交给客户端。[补] 能逐步产生结果的计划，可以边处理边发送；某些排序、聚合或中间结果操作，需要先完成一部分计算才能输出。客户端驱动也可能先缓存结果，再交给应用读取。因此总耗时包括服务端计算、网络传输和客户端消费，引擎已经找到记录并不代表应用已经收到全部数据。
    >
    > 记忆句：这就是结果返回：执行计划产出数据，通过连接传输，再由客户端读取和使用。
    >
    > 追问：自测：数据库计算耗时较短，但客户端迟迟读不完结果时，为什么还要检查返回数据量和客户端消费速度？
    >
    > 答案：整体耗时还包含网络传输和客户端读取处理。结果较多、网络吞吐有限或客户端处理较慢，都会延长读取时间，即使服务端计算本身很快。
