## MySQL 日志

本文以 MySQL 8.0/8.4、InnoDB 表、已启用 binlog 为背景。InnoDB 是负责保存和读写表数据的存储引擎；MySQL Server 负责接收 SQL、组织执行，并记录 binlog。

贯穿全文的是同一次改名：用户 `id=1` 原来的姓名是 `xiaohong`，现在执行：

```sql
UPDATE t_user SET name = 'xiaolin' WHERE id = 1;
```

### 1. 从一次改名认识三类日志

**事务是一组一起提交或撤销的操作。** 执行 `COMMIT` 表示确认这组修改，执行 `ROLLBACK` 表示取消。开启自动提交时，一条独立的 UPDATE 通常就构成一个事务，语句成功完成后自动提交。

MySQL 修改这行数据时，需要先找到它所在的**数据页**。数据页是 InnoDB 读写数据的基本单位，默认大小为 16 KiB，一页通常保存多条记录。InnoDB 把常用页面缓存在内存中的 **Buffer Pool** 里；页面不在内存时，先从数据文件读取。

更新首先改变 Buffer Pool 里的姓名。内存中的页面已经变化、数据文件中的页面还没同步变化时，这个内存页叫**脏页**。后续把它写回数据文件，叫**刷脏页**。

此时有三个需要分别解决的问题：改名可能被取消；内存可能因故障丢失；其他数据库副本也需要得到这次改名。因此需要三类日志：

| 日志 | 谁记录 | 保存什么 | 在改名中的作用 |
| --- | --- | --- | --- |
| undo log，回滚日志 | InnoDB | 撤销修改所需的旧值和相关信息 | 取消时恢复 `xiaohong`；查询需要历史版本时重建旧姓名 |
| redo log，重做日志 | InnoDB | 数据页及引擎内部操作的修改记录 | 重启时补回数据文件中尚未保存的修改 |
| binlog，二进制日志 | MySQL Server | SQL 或行变更等事件 | 把改名传给副本；配合备份恢复历史数据 |

**内存中的数据已修改、事务已提交、数据页已写回，是三个不同的状态。** 日志把它们联系起来：事务可以先提交，数据页稍后写回；未提交事务的脏页也可能提前写回，故障后再撤销其中未提交的修改。

### 2. undo：撤销修改，也提供历史版本

#### 2.1 回滚怎样恢复旧姓名

InnoDB 把姓名改成 `xiaolin` 时，会保留撤销这次修改所需的信息，包括旧姓名 `xiaohong`。随后执行 `ROLLBACK`，引擎就根据 undo 撤销修改；相关索引的变化也需要恢复。一个事务有多次修改时，回滚按相反的次序撤销。

undo 按需要保存旧字段值和相关信息，每次更新无需复制整张数据页。插入记录的撤销动作是取消插入；删除记录则需要保留恢复该记录所需的信息。

这让一组事务操作能够全部完成，或全部撤销，帮助保证事务的**原子性**。

#### 2.2 MVCC 让不同查询读取各自可见的版本

事务 A 已经把姓名改成 `xiaolin`，还没提交。事务 B 此时查询姓名，不应该读到 A 尚未确认的修改。InnoDB 可以根据 undo 重建此前已提交的 `xiaohong`，提供给 B 读取，通常无需等待 A 提交。

这就是 **MVCC（Multi-Version Concurrency Control，多版本并发控制）**：保留重建历史记录所需的信息，让并发事务按可见性规则读取合适的版本。这里的**可见**表示某次修改允许被当前查询读取。

按这套规则读取的普通查询叫**一致性读**，也常称为快照读。下面讨论读提交和可重复读这两种隔离级别下的一致性读；隔离级别规定一个事务能看见其他事务的哪些修改。快照只需记录版本判断信息，并保留仍被需要的历史材料，无需在查询时复制整个数据库。

#### 2.3 MVCC 依赖的三部分

| 组成 | 保存的信息 | 作用 |
| --- | --- | --- |
| 记录中的隐藏字段 | `DB_TRX_ID` 标识产生该版本的事务；`DB_ROLL_PTR` 指向相关 undo | 知道是谁修改的，以及去哪里寻找旧版本 |
| undo 版本链 | 重建前一个版本所需的信息，以及继续寻找更早版本的关联信息 | 当前版本不可见时，逐步还原旧版本 |
| Read View，读视图 | 创建时哪些读写事务还未结束，以及事务 ID 的判断边界 | 判断某个版本是否允许当前查询读取 |

隐藏字段由 InnoDB 维护，应用无需自己建列。**版本链**指的是沿 undo 逐步还原更早记录的关系，查询时可以按需重建历史记录。查询重建旧姓名不会把当前数据页中的 `xiaolin` 改回去；只有回滚才会撤销修改。

隔离级别决定何时创建或复用 Read View，后台清理机制决定历史信息何时可以回收。它们共同支持 MVCC 工作。

#### 2.4 Read View 怎样判断能读哪个版本

事务 ID 用来标识读写事务，通常按分配顺序增长，但它不代表提交顺序。**活跃事务**是已经开始、尚未提交或回滚结束的事务。

Read View 保存创建者身份、创建时其他活跃读写事务的 ID 集合，以及两个边界：低边界通常取该集合的最小 ID，高边界取当时下一个可分配的事务 ID。集合为空时，低边界等于高边界。

检查一个记录版本时，按以下顺序判断：

1. **当前事务自己产生的版本，可以读取。**
2. 其他事务的 ID 小于低边界，说明它在视图创建前已经结束，其保留下来的版本可以读取。
3. ID 大于或等于高边界，说明它在视图创建后才取得 ID，这个版本不可见。
4. ID 位于两个边界之间，就查活跃集合：在集合里，表示当时尚未提交，版本不可见；不在集合里，表示当时已经提交，版本可见。

例如，B 创建视图时，活跃集合是 `{20, 22}`，低边界是 20，高边界是 25。对于其他事务产生的版本，事务 18 的版本可见，事务 20 的版本不可见，事务 21 的版本可见，事务 25 的版本不可见。

再回到改名：旧姓名由事务 10 写入并提交，A 的事务 ID 是 20。B 创建视图时 A 还未提交，因此当前的 `xiaolin` 不可见。B 沿 `DB_ROLL_PTR` 找到 undo，重建事务 10 的 `xiaohong`，确认可见后读取它。如果前一个版本仍不可见，就继续还原更早的版本。

版本的前后关系由 undo 指针确定，事务 ID 沿版本链不保证逐项减小。引擎选定第一个可见版本后，再判断删除标记和查询条件；该版本不满足 `WHERE` 时，这行不返回，不会继续寻找更早的匹配版本。

新插入的行如果没有可见版本，查询就看不到它。删除操作通常先给记录加删除标记：删除对旧视图还不可见时，查询仍可读取删除前的版本；可见版本已经被删除时，查询把这行视为不存在。

#### 2.5 读提交与可重复读的区别在于视图创建时机

假设 B 第一次查询读到 `xiaohong`，A 随后改名并提交，B 自己没有修改这行，又在同一事务内查询一次：

| 隔离级别 | Read View 的使用方式 | B 第二次读到的姓名 |
| --- | --- | --- |
| READ COMMITTED，RC，读提交 | 每次一致性读语句创建新视图 | `xiaolin`，新视图能看见 A 已提交的修改 |
| REPEATABLE READ，RR，可重复读 | 通常在第一次一致性读时创建视图，之后复用 | `xiaohong`，旧视图继续使用原来的可见性判断 |

RR 的旧视图不会因 A 后来提交就自动更新。普通 `BEGIN` 也不等于已经创建视图：B 开始事务后，直到 A 提交才第一次普通查询，仍可能读到新姓名。RR 下可用 `START TRANSACTION WITH CONSISTENT SNAPSHOT` 在事务开始时建立一致性快照。

自己的修改仍按自身可见规则处理。`UPDATE`、`SELECT ... FOR UPDATE` 等写入或加锁读取需要锁来协调并发访问，可能等待其他事务释放冲突锁。**MVCC 主要帮助提供隔离性、减少普通读取与写入之间的等待；它不能代替写入时的锁。**

#### 2.6 undo 何时可以清理

事务 A 提交后，B 的旧视图可能还需要 `xiaohong`，相关 undo 因此需要继续保留。等到这些历史版本不再被需要，后台 **purge** 才能清理更新留下的历史信息。

长时间保留旧视图会延迟清理，使 undo 和历史记录积累。undo 本身也保存在 InnoDB 的页面中，这些页面的修改同样需要 redo 保护，保证重启后仍有撤销修改所需的信息。

### 3. redo：让提交无需等待所有数据页写完

#### 3.1 多写一份日志为什么能提高效率

一次事务可能修改分散在许多页面上的记录。如果提交必须等待这些数据页逐个写完，就需要等待大量页面写入。redo 把修改记录连续写入日志，数据页则可以稍后写回；同一页的多次修改也有机会合并为一次写回。

因此，增加 redo 虽然增加了日志写入，却减少了提交时必须等待的数据页写入。日志连续追加也通常比频繁写入分散的页面更有效率，具体收益取决于设备和负载。

在可靠的日志同步设置下，提交前保存好必要日志，即使数据文件里还是 `xiaohong`，重启后也能根据 redo 补回 `xiaolin`。这帮助保证事务的**持久性**：已经确认提交的修改，在约定的故障条件下仍能保留。

#### 3.2 WAL 规定日志与数据页的保存顺序

**WAL（Write-Ahead Logging，预写日志）要求：某次修改后的数据页写入持久存储之前，对应 redo 必须已经可靠保存。** 这样，即使数据页尚未写完就发生故障，恢复过程仍有日志可用。

内存页修改和 redo 生成由引擎协调进行。WAL 约束的是日志与数据页的持久化顺序，无需每修改一次内存页就同步一次磁盘。脏页可以在事务提交前或提交后写回；事务结果仍由提交记录决定。

redo 描述页面及引擎内部操作的变化，其格式随操作类型而异，不能把所有 redo 都理解成完整 SQL 或某个字节的前后值。数据页只写入一部分时，还需要 **doublewrite（双写）** 等页面保护机制：先保留可恢复的页面副本，再写最终数据页，恢复时用完整页面配合 redo 继续处理。

#### 3.3 日志缓冲、写入文件与同步磁盘

redo 产生后先进入内存中的 **redo log buffer**。后续的保存分为两个动作：

1. **写入日志文件**：常见情况下，数据先进入操作系统的文件缓存。此时 MySQL 进程退出，操作系统仍可能保留这些数据。
2. **同步到持久存储**：通过 `fsync` 等同步操作，要求操作系统和设备完成持久保存。主机掉电后能否保留数据，需要这一步以及设备正确兑现同步要求。

因此，“调用了文件写入”与“掉电后仍能读取”是不同的保证。下面用“同步”表示等待持久保存完成。

`innodb_flush_log_at_trx_commit` 决定事务提交时等待到哪一步：

| 值 | 提交时的 redo 行为 | 主要风险 |
| --- | --- | --- |
| `1` | 写入并等待必要 redo 同步完成 | 常用可靠配置，持久性仍依赖设备正确完成同步 |
| `2` | 写入操作系统缓存，后台周期性同步 | 主机或操作系统故障可能丢失近期提交 |
| `0` | 提交时可仍留在进程内的日志缓冲，由后台周期性写入并同步 | MySQL 进程故障也可能丢失近期提交 |

后台通常按周期处理日志，但调度和 I/O 延迟会改变完成时间，不能保证损失严格限于一秒。提交、后台周期任务、日志缓冲空间不足，以及数据页写回前的 WAL 要求，都可能促使 redo 写出或同步；它们等待到的阶段取决于触发原因和配置。

#### 3.4 redo 空间怎样循环使用

redo 只有有限容量。**write position** 表示新日志写到哪里，**checkpoint（检查点）** 标记恢复仍需保留日志的起始位置。随着相关脏页写回，较早的 redo 不再被恢复需要，检查点就能向前推进，相应日志空间可以被后续写入覆盖。

![redo 空间与检查点](../assets/image13.png)

图中的环表示空间会循环复用。理解时关注“哪些日志仍被恢复需要、哪些空间已经可以复用”，图中的方向和颜色只是表达方式。

如果新日志生成得很快，脏页写回却跟不上，可复用空间会越来越少。接近容量限制时，更新可能等待后台刷新和检查点推进。旧记录可以被覆盖，无需先逐条擦除。

MySQL 8.0.30 起主要通过 `innodb_redo_log_capacity` 配置 redo 总容量。增大容量可以缓解短时间的写入高峰；持续更新量长期超过设备能力时，仍需减少写入或提高设备处理能力。

#### 3.5 undo 与 redo 在恢复中怎样配合

恢复时，redo 可能补回已提交和未提交事务的页面修改，也包括 undo 页的修改。随后根据事务结果，保留已提交修改，用 undo 撤销未提交修改。因此可以把两者联系起来理解：**redo 恢复页面变化，undo 撤销不应保留的事务修改。**

### 4. binlog：把变更提供给复制与历史恢复

#### 4.1 binlog 与 redo 保存不同层面的信息

redo 面向 InnoDB 的页面恢复；binlog 面向 MySQL 的变更事件。`STATEMENT` 格式记录语句，`ROW` 格式记录行变更，`MIXED` 按规则选择。行事件包含哪些字段，还会受到相关配置影响。

| 对比项 | redo | binlog |
| --- | --- | --- |
| 所属层 | InnoDB | MySQL Server |
| 主要内容 | 页面及引擎内部操作的修改 | SQL 或行变更等事件 |
| 文件使用 | 有限空间内循环复用 | 追加写入，达到轮换条件后使用新文件，旧文件按保留策略清理 |
| 主要用途 | 本机故障后的页面恢复 | 主从复制、配合备份进行时间点恢复 |

例如，误删用户后要恢复到删除前，需要先还原合适的完整备份，再连续应用备份之后、误删之前的 binlog。binlog 记录变更，**时间点恢复还需要作为起点的数据备份，以及连续可用的日志**。

#### 4.2 binlog 在提交时写入并按配置同步

事务执行期间，变更事件先进入当前会话用于缓存该事务的 **binlog cache**。缓存超过内存容量时，可能使用临时文件。提交时，MySQL 把事务事件写入 binlog，再根据 `sync_binlog` 决定何时同步。

| `sync_binlog` | 同步方式 |
| --- | --- |
| `1` | 每个提交组写完后同步；一个组可以包含多个事务 |
| `0` | 由操作系统决定何时同步，故障时可能丢失近期日志 |
| `N > 1` | 累积 N 个提交组后同步，组之间存在尚未同步的日志 |

**组提交**是把多个并发事务的日志集中处理，让它们共享一次同步，减少每个事务的平均等待成本。因此 `sync_binlog=1` 并不要求每个事务都单独调用一次 `fsync`。

事务的事件按完整事务组织，但故障仍可能使文件尾部只写入一部分。恢复时必须识别有效、完整的事务提交记录，不能把“按事务组织”理解成任意一次文件写入都不会中断。

### 5. 把三类日志串进完整的 UPDATE 过程

#### 5.1 执行阶段：修改数据并生成日志

继续使用 `xiaohong` 改为 `xiaolin` 的例子：

1. **开始事务，查找记录。** Server 组织语句执行，InnoDB 通过主键找到 `id=1`。数据页不在 Buffer Pool 时，先读取到内存；修改前取得需要的锁。
2. **保留撤销信息。** 生成 undo，保存恢复 `xiaohong` 所需的信息。
3. **更新内存页并生成 redo。** 姓名变成 `xiaolin`，页面成为脏页；记录的数据修改及相关 undo 页修改都受到 redo 保护。
4. **缓存 binlog 事件。** Server 把这次变更写入事务的 binlog cache。

到这里，改名已经在内存中执行，事务尚未完成提交。接下来需要让 InnoDB 和 binlog 对这个事务的结果保持一致。

#### 5.2 两阶段提交：协调引擎与 binlog 的提交决定

假如引擎已经确认提交，binlog 却没有这次改名，本机可能保留 `xiaolin`，副本却收不到变更。反过来，binlog 已记录提交，引擎却决定撤销，也会产生不一致。

MySQL 使用**内部两阶段提交**协调两者：“准备”表示引擎已准备好完成事务，最终结果等待 binlog 的提交证据；“提交”表示确认保留修改。这里讨论的是本机引擎与 binlog 的协调。

以下按 `innodb_flush_log_at_trx_commit=1`、`sync_binlog=1` 和设备正确完成同步说明关键顺序；组提交可以合并多个事务的同步操作：

| 步骤 | 动作 | 这一步解决的问题 |
| --- | --- | --- |
| 1. Prepare，准备 | InnoDB 进入 prepared 状态，使必要 redo 和准备状态可恢复 | 故障后能够恢复事务内容，并继续判断提交结果 |
| 2. 写入并同步 binlog | Server 保存完整事务事件及提交记录 | 为这个事务留下可恢复的提交决定 |
| 3. Commit，提交 | InnoDB 完成提交，Server 随后向客户端返回成功 | 确认本机保留修改，结束事务 |

数据页无需在这三个步骤中全部写回。最后的引擎提交标记也无需为了每个事务再单独同步一次：必要 redo 与完整 binlog 已可靠保存时，重启后可以据此完成提交。

#### 5.3 中途故障时怎样决定提交还是回滚

恢复按磁盘上可读取的有效日志判断：

| 恢复时找到的证据 | 处理结果 |
| --- | --- |
| 普通内部事务尚未进入可恢复的 prepared 状态，也未提交 | 撤销未提交修改 |
| 事务处于 prepared，找不到对应的完整有效 binlog 提交记录 | 回滚 |
| 事务处于 prepared，存在对应的完整有效 binlog 提交记录 | 完成提交 |
| 引擎已经有效记录提交 | 保留已提交修改 |

两边通过事务标识关联同一个事务。判断依据是有效日志内容；即使 `fsync` 还没有返回，数据也可能已经保存，不能只根据故障发生在某次函数调用之前或之后猜测结果。降低日志同步要求会改变故障时的保证。

客户端在提交时断线，同样不能证明事务失败：数据库可能已经提交，只是响应没有送达。需要可靠重试时，可把唯一请求编号及处理结果与业务修改放在同一事务内保存，并用唯一约束防止重复处理；重连后按编号确认结果。

#### 5.4 两阶段提交的主要成本

提交需要协调引擎和 binlog，还要等待必要的日志写入与同步。存储同步慢、提交过于频繁时，提交延迟就会增加。使用半同步复制时，主库还要等待指定数量的副本保存日志并回复确认，因此还会产生网络等待。

组提交可以让并发事务共享同步。批量更新也可在业务允许时使用适量事务批次，减少提交次数；事务过大会延长锁占用，增加 undo、临时文件、复制和回滚工作。因此应结合提交延迟、事务大小和设备能力选择批次。

### 6. 主从复制：副本接收并执行 binlog

主库负责接收业务写入，副本保存另一份数据。复制既要把日志传过去，也要让副本执行日志中的变更，这两个进度可能不同。

![主从复制过程](../assets/image14.png)

1. 主库执行事务并记录 binlog，向已连接的副本发送日志事件。
2. 副本的接收线程把事件写入 **relay log（中继日志）**，用于保存收到但尚未全部执行的变更。
3. 副本的应用线程读取 relay log，执行相应变更，让用户姓名也变成 `xiaolin`。应用过程可以使用并行工作线程。

**收到日志不等于已经完成修改。** 主库刚返回成功就立即查询副本，仍可能读到旧姓名，这就是复制延迟的一种表现。

| 复制方式 | 主库向客户端返回成功前等待什么 | 需要理解的条件 |
| --- | --- | --- |
| 异步复制，默认方式 | 不等待副本确认 | 故障切换时，若新主库缺少近期事务，可能丢失这些修改 |
| 半同步复制 | 正常启用时，等待配置要求数量的副本确认接收，并按要求写入和同步 relay log | 确认通常不代表副本已执行；超时可能转为异步 |
| 同步复制 | 取决于具体方案，需要等待约定节点达到约定阶段 | 必须明确等待哪些节点，以及等待接收、持久保存还是执行完成 |

半同步从 MySQL 5.5 起已经提供。它降低主库故障时丢失近期事务的风险，但最终保证仍受超时转换、故障范围和切换到哪个副本影响。不能据此保证任何故障下都不丢数据。

同步方案如果要求等待所有目标副本，较慢的副本就会增加提交等待；必须等待的副本不可用时，还可能阻止提交。这些影响取决于该方案要求哪些副本参与确认。

增加副本可以分担读取，但也增加主库发送日志的网络和线程开销。副本还要消耗资源接收、保存和执行变更，因此数量需要结合读负载、复制延迟及运维成本选择。

### 7. 异常重启：恢复页面，再处理未完成事务

正常关闭时，数据库有机会完成相关保存；突然断电时，内存中的修改可能消失，数据文件和日志文件也可能处于不同进度。

重启后，InnoDB 从检查点相关位置开始恢复，用有效 redo 补回必要页面修改，包括恢复 undo 页；再结合事务状态及 binlog 的有效提交证据，完成应提交的事务，撤销未提交事务。存在页面部分写入时，还需要相应页面保护机制参与恢复。

因此，异常启动可能出现恢复日志、明显磁盘读写和较长启动时间。大量 redo 或大事务回滚都会增加恢复工作；部分回滚可能继续在后台进行，数据库开始接收连接后仍可能出现资源占用或锁等待。

如果启动立即退出，就按错误日志检查磁盘空间、文件路径与权限、版本兼容性或页面损坏。保留日志和数据文件，依据错误原因处理；强制恢复模式主要用于故障排查及导出可读数据，不宜用于日常业务运行。

### 8. 磁盘 I/O 高：按产生读写的原因处理

I/O 高表示磁盘读写繁忙，还需要结合读写量和请求延迟判断原因。**等待事件**说明数据库正在等待什么工作，例如读取数据页或同步日志；**执行计划**说明查询准备通过哪些索引、扫描方式等取得数据。两者可以帮助定位读写来自哪里。

| 观察到的情况 | 可能的原因 | 对应处理 |
| --- | --- | --- |
| 查询读取大量数据页 | 扫描范围过大、索引不合适、常用页面缓存不足 | 检查执行计划和扫描行数，优化 SQL 与索引；有内存余量时调整 Buffer Pool |
| 修改很快，提交等待较久 | 日志同步慢，或小事务提交过于频繁 | 查看同步延迟，采用适量批次，利用并发组提交；评估存储能力 |
| redo 可用空间持续减少，更新等待 | 脏页写回跟不上日志生成 | 观察新日志位置与检查点之间仍需保留的日志量、脏页数量和写入延迟；按负载调整 redo 容量与刷新能力 |
| undo 长时间积累 | 旧读视图持续需要历史版本 | 查找长事务及长时间运行的查询，缩短不必要的事务持续时间 |
| 临时文件读写较多 | 大事务超过 binlog 缓存容量，或排序、分组使用磁盘空间 | 检查缓存和临时表统计，优化事务大小及查询；结合内存余量调整配置 |
| binlog 占用持续增长 | 保留时间较长，或副本、备份流程仍需旧日志 | 核对恢复与复制需求，再使用日志管理方式清理 |

`innodb_io_capacity` 等参数用于影响后台刷新能力，应参考设备在当前负载下能持续提供的 IOPS，即每秒 I/O 操作次数。增大 Buffer Pool 要为其他内存用途留出空间；增加索引也会增加更新成本。

降低 redo 或 binlog 的同步频率会改变故障时的数据保证，不能仅按延迟决定。调整后应在相近负载下比较处理量、提交延迟、磁盘等待和复制延迟；更换设备时，也要确认设备能够正确完成同步请求。
