## MySQL 日志

假设我们要把用户 id=1 的姓名从 xiaohong 改成 xiaolin。对应的语句是 UPDATE t_user SET name = 'xiaolin' WHERE id = 1。修改过程中，用户可能取消操作，数据库可能突然断电，其他数据库副本也需要同步新姓名。MySQL 用不同的日志处理这些事情。

undo 保存撤销修改所需的信息，既能用于回滚，也能帮助查询读取旧姓名。redo 保存页面修改记录，重启后可以补回尚未写进数据文件的变化。binlog 记录变更事件，用来同步副本，也能配合备份恢复历史数据。

这里讨论 MySQL 8.0 和 8.4，表使用 InnoDB，并且开启了 binlog。InnoDB 负责保存和读写表数据；MySQL Server 负责接收 SQL、组织执行，并记录 binlog。

### 1. 从一次改名认识三类日志

事务就是一组需要一起确认或一起撤销的操作。执行 COMMIT，表示确认修改；执行 ROLLBACK，表示取消修改。开启自动提交时，一条独立的 UPDATE 通常就是一个事务，语句成功完成后会自动提交。

修改用户姓名时，InnoDB 先找到这行数据所在的数据页。你可以把数据页理解成数据库一次读取或写回的一块数据，默认大小是 16 KiB，一页通常放着多条记录。

常用的数据页会保存在内存里的 Buffer Pool 中。如果要修改的页面还没在内存里，就先从数据文件读进来。改名首先改的是这个内存页，数据文件不一定马上跟着变化。

内存里的页面已经改过，数据文件里的页面还没同步更新，这个内存页就叫脏页。把它写回数据文件，就叫刷脏页。

假如改完姓名又取消，undo 会提供恢复 xiaohong 所需的信息。假如事务已经提交，但数据页还没写回就断电，redo 可以帮助重启后的数据库补回 xiaolin。假如还有副本需要同步，主库就通过 binlog 把这次改名传过去。

undo 和 redo 都由 InnoDB 记录，binlog 由 MySQL Server 记录。它们分别保存撤销信息、页面修改记录和变更事件，因此各自解决的问题不同。

这里要分清三个时点：内存中的姓名改好了，事务提交了，数据页写回了。这三件事不一定同时发生。事务可以先提交，数据页稍后写回；未提交事务的脏页也可能提前写回，故障恢复时再撤销其中未提交的修改。

### 2. undo：撤销修改，也提供历史版本

undo 留下了撤销修改所需的信息。改名事务取消时，数据库用它恢复旧姓名；其他事务需要读取旧姓名时，也可以用它重建历史版本。两种用途都依赖旧数据，但动作不同。回滚会撤销当前修改，普通查询只是构造出自己需要读取的旧记录，不会把当前数据改回去。

#### 2.1 回滚怎样恢复旧姓名

把 xiaohong 改成 xiaolin 时，InnoDB 会保留撤销这次修改所需的信息，包括旧姓名 xiaohong。随后执行 ROLLBACK，引擎就根据 undo 恢复旧姓名，相关索引的修改也要一起恢复。

如果一个事务改了多次，回滚就按相反的次序撤销。如果之前插入了一行，回滚要取消这次插入；如果之前删除了一行，就需要恢复被删除的记录。

undo 按需要保存旧字段值和相关信息，每次更新无需复制整张数据页。它帮助数据库做到一组操作全部完成，或者全部撤销，这就是事务原子性的一部分保障。

#### 2.2 MVCC 让不同查询读取各自可见的版本

事务 A 把姓名改成了 xiaolin，但还没提交。事务 B 这时查询姓名，不应该读到 A 尚未确认的修改。InnoDB 可以用 undo 重建此前已提交的 xiaohong，让 B 读取它，通常无需等 A 提交。

这种让并发事务读取合适数据版本的机制，叫 MVCC，全称是 Multi-Version Concurrency Control，中文叫多版本并发控制。说某个版本“可见”，就是当前查询允许读取这个版本。

按这些规则读取的普通查询，叫一致性读，也常叫快照读。快照需要保存版本判断信息，并保留仍会用到的历史材料，无需在查询时复制整个数据库。

这里讨论读提交和可重复读这两种隔离级别。隔离级别决定一个事务能看到其他事务的哪些修改。这两种级别都会使用 MVCC，但创建读视图的时机不同。

#### 2.3 MVCC 依赖的三部分

数据库要找到合适的版本，需要知道三件事：当前版本是谁改的，旧版本在哪里，当前查询允许读到哪次修改。InnoDB 用隐藏字段、undo 版本链和 Read View 配合完成这些判断。

记录里的 DB_TRX_ID 标识产生这个版本的事务，DB_ROLL_PTR 指向相关 undo。它们由 InnoDB 维护，应用无需自己建这两列。

undo 保留重建前一个版本所需的信息，还保留继续寻找更早版本的关联信息。沿着这些信息，可以从当前姓名逐步还原到以前的姓名，这种关系就叫版本链。

Read View 的中文是读视图。它记住创建时哪些读写事务还没结束，再结合事务 ID 判断哪些版本可以读。当前版本不能读，就沿 undo 找前一个版本，然后继续判断。

隔离级别决定什么时候新建或复用读视图。后台清理机制则负责回收已经没有查询需要的历史信息。查询重建旧记录时，当前页面仍然可以保留新姓名。

#### 2.4 Read View 怎样判断能读哪个版本

每个读写事务都有用来标识自己的事务 ID。ID 通常按分配顺序增长，但先拿到 ID 的事务不一定先提交。已经开始、还没提交或回滚结束的事务，叫活跃事务。

Read View 会记住自己的创建者、创建时其他活跃读写事务的 ID，以及两个判断边界。低边界通常是活跃集合中的最小 ID，高边界是当时下一个可分配的 ID。如果活跃集合为空，低边界就等于高边界。

判断版本时，先看是不是当前事务自己的修改。自己的修改可以读取。

对于其他事务产生的版本，ID 小于低边界，说明对应事务在视图创建前已经结束，保留下来的版本可以读。ID 大于或等于高边界，说明它在视图创建后才取得 ID，这个版本不能读。

如果 ID 在两个边界之间，就检查它在不在活跃集合里。在集合里，表示创建视图时还没提交，不能读；不在集合里，表示当时已经提交，可以读。

比如 B 创建视图时，活跃事务是 20 和 22，低边界是 20，高边界是 25。那么，其他事务产生的版本中，18 的版本可以读，20 的版本不能读，21 的版本可以读，25 的版本不能读。

回到改名的例子。旧姓名由事务 10 写入并提交，A 的事务 ID 是 20。B 建立视图时 A 还没提交，所以当前的 xiaolin 不能读。B 就通过 DB_ROLL_PTR 找到 undo，还原事务 10 的 xiaohong，确认可以读以后返回它。如果还原出的版本仍不能读，就继续寻找更早的版本。

版本的前后关系由 undo 指针决定，不能假设沿版本链看到的事务 ID 一定越来越小。找到第一个可见版本后，才根据这个版本判断删除标记和查询条件。如果它不符合 WHERE 条件，这行就不返回，也不会继续找更早的版本来凑出匹配结果。

新插入的行如果没有任何可见版本，当前查询就看不到它。删除通常先给记录加删除标记。如果这次删除对旧视图还不可见，查询仍能读取删除前的记录；如果选中的可见版本已经删除，就把这行看作不存在。

#### 2.5 读提交与可重复读的区别在于视图创建时机

假设 B 第一次查询读到 xiaohong。随后 A 把姓名改成 xiaolin 并提交，B 自己没有修改这行，又在同一个事务里查询一次。

使用读提交时，B 的每次一致性读语句都会建立新的 Read View。第二次查询建立视图时，A 已经提交，所以能看到 xiaolin。读提交的英文是 READ COMMITTED，简称 RC。

使用可重复读时，B 通常在第一次一致性读时建立 Read View，后续继续使用它。旧视图对 A 的判断不会因为 A 后来提交就改变，所以第二次仍读到 xiaohong。可重复读的英文是 REPEATABLE READ，简称 RR。

执行 BEGIN 只是开始事务，不一定立即建立视图。比如 B 先开始事务，等 A 提交以后才第一次普通查询，即使使用 RR，也可能看到新姓名。RR 下使用 START TRANSACTION WITH CONSISTENT SNAPSHOT，可以在事务开始时建立一致性快照。

当前事务自己的修改仍然可以读取。UPDATE 和 SELECT ... FOR UPDATE 这类写入或加锁读取还需要锁来协调并发操作，可能等待其他事务释放冲突锁。MVCC 主要帮助提供隔离性，减少普通读取与写入之间的等待，写入之间的冲突仍然需要锁处理。

#### 2.6 undo 何时可以清理

A 提交了改名，B 的旧视图可能还需要 xiaohong，所以相关 undo 需要继续保留。等到这些历史版本不再被需要，后台的 purge 才能清理更新留下的历史信息。purge 就是这里负责清理旧版本的机制。

如果一个事务长时间保留旧视图，历史信息就可能一直无法清理，undo 也会持续积累。

undo 本身也保存在 InnoDB 的页面中。这些页面的修改同样需要 redo 保护，否则重启后可能找不到撤销未提交修改所需的信息。

### 3. redo：让提交无需等待所有数据页写完

更新先改变内存中的数据页，redo 记录这些页面的修改。提交时，在可靠的日志同步设置下，把必要日志保存好，数据页就可以稍后再写回。

如果中途断电，数据库重启后可以根据日志补回尚未写进数据文件的变化。因此，提交无需等所有修改过的数据页都写完。

#### 3.1 多写一份日志为什么能提高效率

假设一次事务修改了很多用户，他们分布在不同数据页上。如果提交必须等这些页面逐个写完，用户就要等待大量页面写入。使用 redo 后，可以先把修改记录连续写进日志，数据页稍后写回。同一页被连续修改多次，也有机会合并成一次页面写回。

虽然增加了日志写入，但提交时需要等待的数据页写入减少了。连续追加日志通常也比频繁写入分散页面更有效率，具体能快多少，还要看设备和业务负载。

在可靠的日志同步设置下，只要提交所需的日志已经保存，即使数据文件里还是 xiaohong，重启后也能补回 xiaolin。这帮助保证事务的持久性，也就是已经确认提交的修改，在约定的故障条件下仍能保留。

#### 3.2 WAL 规定日志与数据页的保存顺序

WAL 的全称是 Write-Ahead Logging，中文叫预写日志。它要求：修改后的数据页写入持久存储之前，对应 redo 必须已经可靠保存。这样，数据页写入中途发生故障，数据库仍然有恢复所需的日志。

这里要求的是日志和数据页的持久保存顺序。修改内存页时，InnoDB 会协调生成 redo，但无需每改一次内存页就同步一次磁盘。脏页可以在事务提交前写回，也可以在提交后写回，事务结果仍由提交记录决定。

redo 记录页面和引擎内部操作的变化，不同操作使用的记录格式可能不同。理解它的用途时，重点是它能帮助恢复页面修改，不能假设所有 redo 都是完整 SQL，或者某个字节修改前后的值。

如果一个数据页只写了一部分，还需要 doublewrite，也就是双写等保护机制。双写会先保留可恢复的页面副本，再写最终数据页。恢复时可以先取得完整页面，再配合 redo 处理后续修改。

#### 3.3 日志缓冲、写入文件与同步磁盘

redo 生成后，先进入内存中的 redo log buffer，也就是 redo 日志缓冲。后面还要经过文件写入和持久保存。

常见情况下，写入日志文件会先把数据交给操作系统的文件缓存。如果这时只是 MySQL 进程退出，操作系统仍可能保留它；如果整台主机掉电，缓存里的数据就可能消失。

通过 fsync 等操作同步到持久存储，才是要求操作系统和设备完成可靠保存。后面说“同步”，指的就是等待这一步完成。它的保证也依赖设备正确完成同步请求。

innodb_flush_log_at_trx_commit 这个参数，决定提交时如何处理 redo。

设为 1 时，提交会写入并等待必要 redo 同步完成。这是常用的可靠配置。

设为 2 时，提交会把 redo 写入操作系统缓存，后台再周期性同步。主机或操作系统故障时，近期提交仍可能丢失。

设为 0 时，提交时的 redo 可能还留在 MySQL 进程的日志缓冲里，由后台周期性写入并同步。这时连 MySQL 进程故障也可能丢失近期提交。

后台虽然会按周期处理日志，但线程调度和 I/O 延迟会影响完成时间，不能保证损失严格限于一秒。事务提交、后台周期任务、日志缓冲空间不足，以及刷脏页前需要满足 WAL，都会促使日志写出或同步。具体等待到哪一步，要看触发原因和配置。

#### 3.4 redo 空间怎样循环使用

redo 的总容量有限，旧空间需要重复使用。write position 表示新日志已经写到哪里，checkpoint，也就是检查点，标记故障恢复仍需保留日志的起始位置。随着相关脏页写回，较早的 redo 不再被恢复需要，检查点就能向前推进。这样，原来必须保留的那部分日志空间，就可以交给后续日志覆盖。

如果新日志不断产生，脏页写回却跟不上，可复用空间就会越来越少。接近容量限制时，更新可能需要等待后台刷新和检查点推进。复用空间时可以覆盖旧记录，无需先逐条擦除。

MySQL 8.0.30 起，主要用 innodb_redo_log_capacity 设置 redo 总容量。容量增大，可以承受更长时间的写入高峰；如果更新量长期超过设备能力，仍然需要减少写入或提高设备处理能力。

#### 3.5 undo 与 redo 在恢复中怎样配合

重启恢复时，redo 会帮助补回页面修改，其中可能同时包含已提交和未提交事务的变化，也包括 undo 页的变化。页面恢复以后，数据库还要判断事务结果。已经提交的修改保留，未提交的修改用 undo 撤销。因此，redo 负责恢复页面变化，undo 负责撤销不应保留的事务修改，两者配合才能得到正确的数据状态。

### 4. binlog：把变更提供给复制与历史恢复

binlog 由 MySQL Server 记录，保存 SQL 或行变更等事件。副本可以执行这些事件，得到对应的数据变化；恢复历史数据时，也可以从合适的备份开始，继续应用后面的 binlog。redo 主要服务于 InnoDB 自己的页面恢复。binlog 提供可以用于复制和历史恢复的变更记录，所以两类日志都需要保留各自承担的作用。

#### 4.1 binlog 与 redo 保存不同层面的信息

redo 记录的是 InnoDB 页面和内部操作的修改。binlog 记录的是 MySQL 的变更事件，具体内容由日志格式决定。

使用 STATEMENT 格式时，主要记录语句；使用 ROW 格式时，记录行变更；使用 MIXED 格式时，按规则选择。行事件包含哪些字段，还会受到相关配置影响。

redo 在有限空间里循环复用。binlog 持续追加，达到文件轮换条件后改用新文件，旧文件再按保留策略清理。因此，binlog 可以保留一段时间内连续发生的变更。

比如误删了用户，要恢复到删除前，可以先还原合适的完整备份，再应用备份之后、误删之前的 binlog。完成这种时间点恢复，既需要作为起点的数据备份，也需要中间连续可用的日志。

#### 4.2 binlog 在提交时写入并按配置同步

事务执行期间，变更事件先进入当前会话用于缓存这个事务的 binlog cache。缓存超过内存容量时，可能使用临时文件。提交时再把事务事件写入 binlog，按照 sync_binlog 的设置决定何时同步。

多个并发事务可以集中处理日志，共享一次同步，这叫组提交。一个提交组里可能有多个事务，可以分摊每个事务的同步成本。

sync_binlog 设为 1，表示每个提交组写完后同步。因为一组可以有多个事务，所以每个事务无需单独调用一次 fsync。

设为 0，表示由操作系统决定何时同步，故障时可能丢失近期日志。设为大于 1 的 N，表示累计 N 个提交组后同步。这里数的是提交组，不能直接当成 N 个事务。

binlog 会按完整事务组织事件，但文件写入仍然可能被故障打断，尾部也可能只写了一部分。恢复时必须确认事务的提交记录完整有效，不能看到几条变更事件就认定事务已经提交。

### 5. 把三类日志串进完整的 UPDATE 过程

一次改名会先找到数据，准备 undo，再修改内存页并生成 redo，同时缓存 binlog 事件。之后还要协调 InnoDB 和 binlog，让它们对这个事务给出相同的提交结果。数据已经改到内存里，只能说明更新执行到了那里。事务是否提交、故障后应该保留还是撤销，还要结合提交过程和有效日志判断。

#### 5.1 执行阶段：修改数据并生成日志

继续看把 xiaohong 改成 xiaolin 的过程。Server 组织语句执行，InnoDB 通过主键找到 id=1 这行。数据页不在 Buffer Pool 时，就先读进内存，修改前取得需要的锁。

准备修改时，InnoDB 生成 undo，保留恢复 xiaohong 所需的信息。随后修改内存里的姓名，使页面成为脏页，并生成相应 redo。用户数据页和相关 undo 页的修改都受到 redo 保护。

Server 也会把这次变更记录到事务的 binlog cache 中。到这里，内存中的改名已经执行，但事务还没有完成提交。接下来，数据库需要确认这次修改到底算不算提交，并让 InnoDB 和 binlog 的记录保持一致。

#### 5.2 两阶段提交：协调引擎与 binlog 的提交决定

假如 InnoDB 已经确认提交，binlog 却没有记录这次改名，本机可能保留 xiaolin，副本却收不到更新。反过来，binlog 记录了提交，InnoDB 却撤销修改，也会造成不一致。

MySQL 用内部两阶段提交协调两者。准备阶段表示引擎已经准备好完成事务，最终结果还要等待 binlog 的提交证据；提交阶段表示确认保留修改。这里协调的是本机引擎与 binlog。

下面按 innodb_flush_log_at_trx_commit 和 sync_binlog 都设为 1，并且设备能正确完成同步来理解过程。

首先，InnoDB 进入 prepared，也就是准备状态，并确保必要 redo 和准备状态能够在重启后恢复。这样，即使中途故障，事务内容和它正在等待决定的状态仍然有据可查。

接着，Server 写入并同步完整的 binlog 事务事件和提交记录。这个事务由此有了可以在恢复时确认的提交决定。

最后，InnoDB 完成提交，Server 随后向客户端返回成功。多个事务可以通过组提交共享同步，无需每个事务都为每个动作单独同步一次。

整个提交过程无需等待所有数据页写回。必要 redo 和完整 binlog 已经可靠保存时，即使最后的引擎提交标记还没单独同步，重启后也可以据此完成提交。

#### 5.3 中途故障时怎样决定提交还是回滚

恢复时，要看磁盘上能够读取的有效日志，两边通过事务标识关联同一个事务。

普通内部事务如果还没进入可恢复的 prepared 状态，也没有提交，就撤销它未提交的修改。

事务已经处于 prepared 状态时，继续查找对应的 binlog。如果找不到完整有效的提交记录，就回滚；如果找到了，就完成提交。引擎已经有效记录提交的事务，则保留它的修改。

判断依据是日志内容。即使 fsync 还没返回，数据也可能已经保存，所以不能只根据故障发生在某次函数调用前后猜测结果。降低日志同步要求，也会改变故障时的数据保证。

客户端提交时断线，同样不能证明事务失败。数据库可能已经提交，只是成功响应没有送到客户端。

需要可靠重试时，可以给请求分配唯一编号，把编号、处理结果和业务修改放在同一事务里保存，再通过唯一约束防止重复处理。重新连接后按编号确认结果，比直接猜测这次请求是否成功更可靠。

#### 5.4 两阶段提交的主要成本

提交要协调引擎和 binlog，还要等待必要日志写入与同步。设备同步慢，或者每次只改一点数据却频繁提交，都会增加提交等待。

如果使用半同步复制，主库还需要等待指定数量的副本保存日志并回复确认，这又增加了网络等待。

组提交可以让并发事务共享同步。批量修改时，如果业务允许，也可以把适量操作放在同一个事务里，减少提交次数。事务过大又会带来其他成本：锁占用更久，undo 更多，可能产生临时文件，副本执行和故障回滚也要处理更多工作。因此要结合提交延迟、事务大小和设备能力选择批次。

### 6. 主从复制：副本接收并执行 binlog

主库接收业务写入，副本保存另一份数据。复制过程既要把日志传过去，也要让副本执行日志里的变更。

主库执行事务并记录 binlog，然后把日志事件发送给已连接的副本。副本的接收线程先把它们写入 relay log，也就是中继日志。它保存已经收到、但还没有全部执行的变更。

副本的应用线程再读取 relay log，执行相应变更，让姓名也变成 xiaolin。应用过程可以使用并行工作线程。

因此，副本收到日志和完成修改是两个进度。主库刚返回成功，就马上查询副本，仍有可能读到旧姓名，这就是复制延迟的一种表现。

默认的异步复制中，主库向客户端返回成功前，不会等待副本确认。如果主库故障后切换到一个缺少近期事务的副本，这些修改就可能丢失。

半同步复制正常启用时，主库会等待配置要求数量的副本确认，确认通常表示日志已经收到，并按要求写入和同步到 relay log，不代表副本已经执行完修改。等待超时后，主库可能转为异步复制。

半同步从 MySQL 5.5 起已经提供。它能降低丢失近期事务的风险，但最终保证还取决于是否已经转为异步、故障影响了哪些节点，以及选择哪个副本接替主库。因此它不能保证任何故障下都不丢数据。

同步复制需要结合具体方案理解：等哪些节点，以及等到接收、持久保存还是执行完成，都要看方案规定。如果要求所有目标副本都确认，慢副本就会增加提交等待，必须等待的副本不可用时，还可能阻止提交。

副本数量也需要结合负载选择。更多副本可以分担读取，但主库发送日志的网络和线程开销也会增加，每个副本还需要资源来接收、保存和执行变更。

### 7. 异常重启：恢复页面，再处理未完成事务

正常关闭时，数据库有机会完成相关保存。突然断电时，内存里的修改可能消失，数据文件和日志文件也可能停在不同进度。

重启后，InnoDB 从检查点相关位置开始恢复，用有效 redo 补回必要的页面修改，也包括 undo 页。再根据事务状态和 binlog 的有效提交证据，完成应提交的事务，撤销未提交事务。如果存在页面部分写入，还需要双写等页面保护机制参与恢复。

所以异常启动可能比较慢，错误日志里会出现恢复进度，磁盘读写也可能比较多。大量 redo 或大事务回滚都会增加恢复工作。有些回滚可能在后台继续，即使数据库已经开始接收连接，也可能继续占用资源或让其他事务等待锁。

如果启动后立即退出，就根据错误日志检查空间是否足够、文件路径和权限是否正确，以及版本兼容性或页面损坏等问题。保留日志和数据文件，按错误原因处理。强制恢复模式主要用于故障排查和导出可读数据，不宜用于日常业务运行。

### 8. 磁盘 I/O 高：按产生读写的原因处理

磁盘 I/O 高，说明读写很忙，但还需要结合读写量和请求延迟判断原因。数据库的等待事件可以说明它正在等什么，比如读取数据页或同步日志。执行计划则说明查询准备通过哪些索引和扫描方式取得数据。

如果查询读了大量页面，就检查是不是扫描范围太大、索引不合适，或者常用页面没能留在内存里。可以优化 SQL 和索引，有内存余量时再调整 Buffer Pool。

如果修改本身很快，提交却等很久，就检查日志同步延迟和提交频率。业务允许时采用适量批次，利用并发组提交，并评估设备的同步能力。

如果 redo 可用空间持续减少，更新也开始等待，通常需要检查脏页写回是否跟得上。可以观察新日志位置与检查点之间仍需保留的日志量、脏页数量和写入延迟，再调整 redo 容量与后台刷新能力。

如果 undo 长时间积累，就查找长事务和长时间运行的查询。旧视图还需要历史版本时，相关 undo 就无法清理，缩短不必要的事务持续时间有助于释放这些历史信息。

如果临时文件读写很多，可能是大事务超过了 binlog 缓存容量，也可能是排序、分组需要磁盘空间。可以查看缓存和临时表统计，优化事务大小及查询，再结合内存余量调整配置。

如果 binlog 占用持续增长，要核对保留时间，以及副本和备份恢复是否仍需要旧日志。确认这些需求以后，再通过日志管理方式清理。

innodb_io_capacity 等参数会影响后台刷新能力，应参考设备在当前负载下能够持续提供的 IOPS，也就是每秒 I/O 操作次数。扩大 Buffer Pool 需要给其他内存用途留出空间，新增索引也会增加更新成本。

降低 redo 或 binlog 的同步频率，会改变故障时的数据保证，不能只看延迟。调整后应在相近负载下比较处理量、提交延迟、磁盘等待和复制延迟。更换设备时，也要确认它能正确完成同步请求。
